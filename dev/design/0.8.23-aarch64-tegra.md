# 0.8.23 Slice 80 — AArch64 correctness and Jetson Orin CUDA

> **COMMISSIONED.** This design was reviewed and its plan approved; the § 9
> commissioning edits landed at `89e4b8c2` on `0.8.23-tegra`
> (`dev/plans/plan-0.8.23.md`, `dev/plans/release-state-0.8.23.json`). This
> document now records the approved plan, not a proposal awaiting sign-off.
> An independent design review checked its factual claims against the tree and
> this Jetson Orin host directly; findings are folded in throughout, most
> visibly at § 2.1, § 7 80.1, and § 10 R-3.

## 1. Decision

0.8.23 makes Linux AArch64 a **fixed**, not merely documented, platform, and
adds Jetson Orin (Tegra, `sm_87`) as a first-party CUDA execution target,
reached the same way an end user reaches it on x86_64: through
`fathomdb doctor gpu`, not through picking an artifact flavor themselves.

**Ruled product scope (§ 11 item 7): 0.8.23 supports CUDA on x86_64 and on
Tegra; it explicitly does not support `arm64-sbsa`.** Tegra is declared,
first-party scope, not an experimental add-on — see § 11 "Still open" for the
one question this does not settle (how that declared scope squares with the
standing publication hold).

Four things are true today; three need work:

1. AArch64 **CPU correctness** is already sound. The Fathom-maintained Candle
   pin, the published manylinux wheel, and the C-interop surface are all
   verified good on a real Jetson Orin (§ 2.4).
2. The published **npm native artifact does not load** on any Linux with glibc
   < 2.39 — on either architecture. It is broken in every published release.
3. **Tegra CUDA has no engineering path yet**, though it is now ruled-in scope
   (above). The CUDA contract is x86_64-literal throughout, and its GPU
   witness (as originally specified) is physically unobtainable on Tegra.
4. **The dual CPU/GPU runtime this slice needs already exists for x86_64.**
   Slices 70/71/72 (landed on `origin/release/0.8.23`, `REVIEWED_PENDING_INTEGRATION`)
   built exactly the typed device-policy, classifier, and `doctor gpu`/
   `doctor reranker-gpu` diagnostic surface a Tegra-aware answer needs
   (`dev/adr/ADR-0.8.23-dual-runtime-device-policy.md`, HITL `seq:250`). Slice 80
   **extends** that surface to a second architecture; it does not design a new
   one. § 2.5 details what already transfers unmodified.

The bias of this slice is **fix over document**. Documentation changes are
admitted only where the underlying fact is intentional and correct after the
fix (§ 8), never as a substitute for repairing a broken artifact.

## 2. Evidence base

All findings below were measured on the target host, not inferred. Host:
Jetson Orin AGX, L4T R36.5.2, Ubuntu 22.04.5, **glibc 2.35**, aarch64,
12 cores, 61 GB, CUDA 12.6 / driver 540.5.0.

Baseline test run — `bash scripts/agent-test.sh --tier=fast` on the host:
`registered=73 ran=73 passed=60 failed=13`.

### 2.1 The npm native artifact cannot load (BLOCKER)

```console
$ node -e 'require("./fathomdb.linux-arm64-gnu.node")'
LOAD FAILED: /lib/aarch64-linux-gnu/libc.so.6: version `GLIBC_2.39' not found

$ bash scripts/release/smoke/smoke-npm-package.sh 0.8.22 ; echo $?
1
```

- Unresolved symbols: `pidfd_spawnp`, `pidfd_getpid` @ `GLIBC_2.39`. Their
  `.gnu.version_r` entry is `Flags: none` — **not weak** — so `ld.so` hard-fails
  rather than skipping them.
- Root cause: `.github/workflows/release.yml:463` (`build-napi` job) runs
  `npm run build:native` bare on the runner. `build:native`
  (`src/ts/package.json:22`) is plain `napi build` with no container, so the
  artifact inherits the runner's glibc (`ubuntu-24.04-arm` for the job's only
  current Linux matrix row → 2.39). The Python wheel is built through
  `PyO3/maturin-action` with `manylinux: "2_28"` and measures a **2.28**
  floor, which is why it works.
- **Not AArch64-specific and not a regression.** `fathomdb-linux-x64-gnu@0.8.22`
  carries the same 2.39 floor, and so does `fathomdb-linux-arm64-gnu@0.8.21`.
  Every published npm Linux artifact has shipped this way.
- **x64 Linux npm is a special case, verified directly, not just historical.**
  `build-napi`'s current matrix (`release.yml:421-436`) has exactly one Linux
  row — `linux-arm64-gnu` — no `linux-x64-gnu` row exists. The
  `publish-npm-platform-linux-x64-gnu` job (`:1035`) still downloads an
  artifact named `napi-linux-x64-gnu`, but **no job in the current workflow
  uploads an artifact by that name** — grep confirms it appears exactly once,
  as that download target. That job's real gate, `all-builds-passed`
  (`:744-758`), requires `canonical-cuda-package-route-required` to succeed
  for any non-dry-run release, and that job (`:728-738`) unconditionally
  `exit 1`s — a deliberate hard block, not a bug, pending Slice 20's
  not-yet-built canonical CUDA delivery route (§ 2.5). So x64 Linux npm
  publication cannot run *at all* on this branch today, independent of glibc.
  The 0.8.22 measurement above is real but historical: it reflects whatever
  `release.yml` shape produced that artifact before the Slice 70–72
  CUDA/dual-runtime restructuring introduced this block. § 7 80.1 scopes
  itself to what `build-napi` can currently build — `linux-arm64-gnu` plus
  both Python wheel architectures — rather than a job that doesn't exist yet;
  wiring x64 Linux npm's CUDA build is Slice 20's canonical-route work, out of
  scope here per § 3.
- Platforms silently excluded: Ubuntu 22.04 (2.35 — **every Jetson on L4T R36**),
  Debian 12 (2.36), RHEL 9 and Amazon Linux 2023 (2.34).
- **No gate exists.** Nothing under `scripts/` or `.github/workflows/` asserts a
  maximum required `GLIBC_*` symbol version. `readelf -d` in
  `scripts/release/cuda-preflight.sh:202,204` dumps dynamic deps informationally and
  asserts nothing about the floor.

### 2.2 Two tests encode an x86_64 host assumption

Both pass on x86_64 CI and fail on any ARM64 developer machine.

- `scripts/tests/test_install_shellcheck.sh:91,129` hardcode the cache fixture
  path as `linux.x86_64-$LINUX_X86_64_SHA`, and `:76` feeds the x86_64 SHA to
  the `sha256sum` shim. On aarch64 the installer correctly derives
  `linux.aarch64-12b331c1…` (`scripts/install-shellcheck.sh:68-70`), so the
  fixture never matches, cache-hit arms A and C miss, and the test falls through
  to the stubbed offline download. **The installer itself is correct** — the
  defect is entirely in the test's fixture.
- `scripts/tests/test_idempotent_republish.sh:224` builds a fixture platform
  package declaring `cpu: ["x64"]`. npm correctly skips optional platform
  packages that do not match the host CPU, so on aarch64 the "platform package
  present after install" assertion and the loader arm both fail.

### 2.3 The developer environment is unattainable on the OS Jetson ships

L4T R36 ships Ubuntu 22.04 → Python 3.10, and `scripts/bootstrap.sh:31` creates
the venv with a bare `python3 -m venv`, inheriting it. Seven of the thirteen
failures follow from that and from tooling that was never installed here:

| Failing suite | Cause |
| --- | --- |
| `test-check-license-consistency` (20 arms) | `tomllib` needs Python ≥ 3.11 |
| `test-check-pinned-override-rot` | `tomllib` needs Python ≥ 3.11 |
| `test-pip-skew` | venv-bundled pip 22.0.2 lacks `--dry-run` |
| `test-agent-lint-shellcheck-gate` | shellcheck not installed |
| `test-shell-lint-ci-job` | shellcheck not installed |
| `test-actionlint-go-install-version` | shellcheck not installed |
| `test-ci-verify-observability` | `js-yaml` unavailable (no `npm ci`) |
| `test-ci-rust-workspace-gate` | `js-yaml` unavailable (no `npm ci`) |
| `test-gitleaks-guards` | gitleaks not installed |

The two `tomllib` gates fail **closed** ("refusing to report a pass it did not
verify"). That behavior is correct and must be preserved; the fix is to make the
parser available, not to soften the gate. Note `scripts/check-cuda-release-contract.py:19-21`
already carries a `tomli` fallback — the two failing scripts simply lack it.

Contract inconsistency: `docs/compatibility/index.md:14` lists Python 3.10 as
supported with `requires-python = ">=3.10"`, but the repo's own gates require
3.11+, and that requirement is documented nowhere — not in `AGENTS.md`, not in
`dev/design/0.8.23-planning-foundation.md`.

Two failures in the run are **not** environment or architecture defects and are
out of this slice's scope: `test-check-release-state-views` arm R5 failed on a
network transport error during a shallow-clone probe, and
`test-shell-pipefail-guards` failed only as a cascade of that same arm.

Two tools are already arch-clean and need no installer work — only bootstrap
execution: `scripts/install-gitleaks.sh` builds from source via `go install`
(Go 1.26.1 linux/arm64 is present on the host), and
`scripts/install-shellcheck.sh` already pins the correct `linux.aarch64` slug
and SHA-256.

### 2.4 What is already correct on AArch64 — preserve, do not disturb

- All three AArch64 suites pass on the host: `test-linux-aarch64-release-artifacts`
  (323 ms), `test-aarch64-candle-feature-closure` (345 ms), and
  `test-aarch64-candle-cpu` (63.6 s, a real compile and run).
- The Candle fork pin (`Cargo.toml:63-70`) works as designed: `cargo tree`
  confirms `default-embedder` never resolves `gemm-f16`, whose F16 backend would
  emit `fullfp16` instructions outside the ARMv8-A Tier-1 baseline. The CPU
  regression confirms f32 matmul succeeds and f16 matmul returns
  `UnsupportedDTypeForOp` cleanly.
- The published `fathomdb-0.8.22-cp310-abi3-manylinux_2_28_aarch64.whl` installs
  and passes the canonical open/write/search/close/exit smoke with a clean
  process exit. Measured floor: `GLIBC_2.28`.
- C interop uses `std::os::raw::c_char` throughout — no hardcoded `i8`/`u8`, so
  the AArch64 char-signedness trap is avoided.
- The typed device-resolution surface Slice 70 landed
  (`resolve_embed_device_policy` / `resolve_embed_device_policy_from_env` in
  `src/rust/crates/fathomdb-embedder/src/device_policy.rs`, and
  `resolve_default_embedder_device_from_env` /
  `diagnose_default_embedder_gpu_from_env` in
  `src/rust/crates/fathomdb-embedder/src/candle_bge.rs`) makes no architecture
  assumption — it dispatches on typed CUDA driver/cuBLAS error codes, not on
  `uname`.
- CI already builds and smokes both the wheel and the `.node` on
  `ubuntu-24.04-arm` (`.github/workflows/ci.yml:764,863`).

### 2.5 What Slices 10/20/70–72 already built, and what still doesn't reach Tegra

The release ladder moved substantially between this doc's first draft and
this revision (branch pulled to `0dfe96da`). Two things are true at once:
most of the CUDA release-engineering and device-policy substrate this slice
needs now exists; none of it yet reaches AArch64 or Tegra.

**What now exists (x86_64 only), per `dev/plans/release-state-0.8.23.json`:**

| Slice | Status | What it built |
| --- | --- | --- |
| 10 CUDA-CONTRACT | `PENDING_EXTERNAL` | Reviewed local RED→GREEN: witness/receipt verifiers, one-record provenance policy, protected environment, credentialless candidate jobs. Release-complete only pending a real trusted-runner dispatch (HITL `seq:249`) — the *engineering* is done. |
| 20 CUDA-PACKAGE | `PENDING_EXTERNAL` | Reviewed local RED→GREEN package-rehearsal control plane: sealed candidate wheel/npm/tarball, GPU UUID/PID attestation, substitution rejection. A real rehearsal awaits a valid Slice 10 witness; no canonical tag-bound CUDA delivery route exists yet. |
| 70 DUAL-RUNTIME-TC5 | `REVIEWED_PENDING_INTEGRATION` | **The typed CPU/GPU device policy this slice depends on.** `ADR-0.8.23-dual-runtime-device-policy.md` (HITL `seq:250`): one policy (`auto`/`cpu`/`cuda:N`), `fathomdb doctor gpu [--json]` (exit `0`/`65`/`70`, per `dev/interfaces/cli.md:65`), and a closed, code-based compatibility classifier in `src/rust/crates/fathomdb-embedder/src/candle_bge.rs::classify_cuda_driver_error` / `::classify_candle_cuda_error`. |
| 71 RERANK-DUAL-RUNTIME | `REVIEWED_PENDING_INTEGRATION` | Same policy applied to the cross-encoder reranker; `doctor reranker-gpu`. |
| 72 CONCURRENT-DUAL-RUNTIME | `REVIEWED_PENDING_INTEGRATION` | Real RTX 3090 evidence bar: UUID/PID-bound telemetry, retained receipt hashes, an independently-caught timestamp-epoch bug fixed before acceptance. **This is the evidence bar § 7 80.6 should match for Tegra.** |

**The good news this surfaces: the compatibility classifier is already
architecture-agnostic and already does the right thing for a Tegra-arch
mismatch.** `classify_cuda_driver_error` maps `CUDA_ERROR_NO_BINARY_FOR_GPU`
and `CUDA_ERROR_UNSUPPORTED_PTX_VERSION` to `CudaProbeError::Incompatible` —
not `ProbeFailed` — which `doctor gpu` reports as `cuda_incompatible` with a
typed CPU fallback and exit `0` (ADR, "Consequences"). That is *exactly* the
failure a Tegra-linked (`sm_87`-only) binary hits on the wrong hardware, or
that a generic AArch64/SBSA binary would hit on Tegra. **This is the
mechanism decision 2c's "refuse cleanly, continue on CPU" resolves to** — it
already exists, generically, for the discrete-GPU case; Slice 80 does not
build a new refusal path, it confirms this one holds under a Tegra build and
adds the friendlier detection layer on top (§ 7 80.7).

**What still doesn't reach Tegra:**

- `scripts/release/cuda-artifact-contract.sh` — the single checked source of
  CUDA build inputs — is x86_64-literal throughout:
  `CUDA_MANYLINUX_PLATFORM='linux/amd64'`,
  `CUDA_MANYLINUX_BASE_IMAGE='quay.io/pypa/manylinux_2_28_x86_64@sha256:…'`,
  `CUDA_RUSTUP_TOOLCHAIN='1.95.0-x86_64-unknown-linux-gnu'`,
  `CUDA_MANYLINUX_GCC_LIB='…/x86_64-redhat-linux/13'`,
  `CUDA_RUSTUP_INIT_URL='…/x86_64-unknown-linux-gnu/rustup-init'`.
  `scripts/check-cuda-release-contract.py` asserts those literals, now also
  covering a Slice 71 rerank-cuda tuple (`CUDA_RERANK_NAPI_FEATURES`,
  `CUDA_RERANK_PYTHON_FEATURES`) — still x86_64-only.
- `CUDA_COMPUTE_CAP='75'` is a single hardcoded value (T4, `sm_75`) asserted
  literally at `scripts/check-cuda-release-contract.py:487`. **Orin AGX is
  `sm_87`.** The contract has no compute-capability axis, and — confirmed by
  vendor documentation, not just inference — Tegra has no forward-compatibility
  guarantee across compute capabilities the way discrete GPUs do: an `sm_75`
  build will not run on `sm_87` hardware. `nvcc`'s own `-gencode` reference
  states Tegra SMs (`sm_72` Xavier, `sm_87` Orin) are never implied by a
  discrete-GPU gencode list and must be added as their own explicit target.[^1]
- The GPU witness *as originally specified* is unobtainable on Tegra.
  `scripts/release/cuda-preflight.sh:473` requires the smoke PID to appear in
  `nvidia-smi --query-compute-apps` output. On this Orin:

  ```console
  $ nvidia-smi --id=0 --query-compute-apps=pid --format=csv,noheader
  [N/A]
  ```

  Tegra's `nvidia-smi` never reports compute processes, and reports `Not
  Supported` for memory. A different witness mechanism is required for the
  Tegra build specifically (§ 7 80.5) — the x86_64 witness is unaffected and is
  not being replaced.
- The Rust side (`embed-cuda` / `rerank-cuda` feature chains, the device-policy
  crate, the classifier) is already architecture-agnostic, and the host
  carries `libcuda.so`, `libcublas.so.12`, and nvcc 12.6. The blockers are the
  release contract's literals and the x86_64-only GPU witness mechanism, not
  the runtime code.

[^1]: <https://arnon.dk/matching-sm-architectures-arch-and-gencode-for-various-nvidia-cards/>;
  corroborated independently by llama.cpp's Jetson Orin build, which pins a
  single `-DCMAKE_CUDA_ARCHITECTURES="87"` rather than a fat-binary list for
  exactly this reason
  (<https://github.com/ggml-org/llama.cpp/issues/17747>).

### 2.6 The plan has Slices 70–72 for x86_64 dual-runtime; nothing for AArch64/Tegra

`dev/plans/plan-0.8.23.md` now has Slices 70 and 71 for the x86_64 dual
CPU/GPU runtime (§ 2.5), Slice 72 for its concurrent-GPU characterization, but
**no AArch64 or Tegra slice**. The ladder, per the release-state file, is
`next_slice: 70`, `remaining_ladder: [70, 71, 72, 40]` — Slice 40 (scale
characterization) was explicitly `SET_ASIDE` by ruled HITL decision
`release-ladder-reorder` so that 10/20/70 could be sequenced first. No commit
on the branch touches aarch64, ARM, napi, glibc, or manylinux outside the
pre-existing CI matrix rows and the Slice 0 Candle pin.

AArch64 CPU correctness today therefore rests entirely on the Slice 0 Candle
pin plus pre-existing CI matrix rows; AArch64/Tegra CUDA rests on nothing.
Nothing in the current ladder addresses the glibc floor, the two host-arch
test defects, the developer environment, or Tegra — Slice 80 is additive to
70–72, not a rework of them.

## 3. Scope

**In scope.**

- Repairing the npm native-artifact glibc floor on **both** Linux architectures,
  and gating it so it cannot regress.
- Removing the x86_64 host assumption from the two affected tests.
- Making `scripts/bootstrap.sh` produce a complete, gate-capable developer
  environment on Ubuntu 22.04 / AArch64.
- A first-party Tegra (`sm_87`) CUDA build path, a device-truthful GPU witness
  that works on integrated Tegra GPUs, and a real Jetson Orin evidence run
  matching Slice 72's evidence bar (§ 2.5).
- Extending the **existing** `fathomdb doctor gpu` (Slice 70) with Tegra/SBSA
  detection, so an end user never picks a CUDA flavor themselves — the tool
  detects and either uses it or names the exact next step. No new CLI verb.
- Correcting the public compatibility claims that the fixes make true or false.

**Out of scope.**

- Publishing a Tegra-specific wheel or npm package under the existing package
  names. § 7 80.6 D-1 explains why this is a packaging impossibility rather
  than a choice, and what replaces it.
- Windows and macOS ARM CUDA. Unchanged.
- A postinstall network fetch or auto-build of the Tegra artifact. § 7 80.7
  explains why guided-install (the tool prints the exact command) is preferred
  over silent download/build.
- Shipping an untested `arm64-sbsa` CUDA build. § 7 80.7 covers detection and a
  clean, CPU-continuing refusal instead.
- The x86_64 CUDA/dual-runtime ladder (Slices 10, 20, 70, 71, 72). Slice 80
  **extends the device-policy and contract substrate those slices already
  built** (§ 2.5) but does not implement, reorder, or block them; see § 6 on
  sequencing.
- Musl, 32-bit ARM, and Jetson platforms older than Orin (`sm_87`).
- The `test-check-release-state-views` R5 network-transport failure and its
  `test-shell-pipefail-guards` cascade (§ 2.3).
- Raising the AArch64 Candle F16 baseline. Orin's Cortex-A78AE does implement
  `fullfp16`, so the current pin is conservative for this host — but it is
  correct for the Tier-1 baseline, and relaxing it is a separate, evidence-first
  decision. See § 10 R-4.

## 4. Requirements

- **R80-1** No published native artifact — wheel or `.node`, either Linux
  architecture — may require a glibc symbol version above the declared floor of
  **2.28**.
- **R80-2** The floor is enforced by an automated gate that fails closed when
  its inspection tool is unavailable, and that runs on the artifact actually
  published, not only on a locally built equivalent.
- **R80-3** No suite in `scripts/agent-test.sh` may pass or fail as a function
  of host architecture. A suite that cannot run on a host must SKIP explicitly,
  as the AArch64 suites already do.
- **R80-4** `bash scripts/bootstrap.sh` on a stock Ubuntu 22.04 AArch64 host
  must yield an environment in which the full `--tier=fast` suite runs with no
  failure attributable to a missing or too-old tool.
- **R80-5** The CUDA artifact contract must express architecture and compute
  capability as inputs rather than literals, without weakening any assertion the
  x86_64 lane currently makes.
- **R80-6** The CUDA GPU witness must prove device engagement on a Tegra
  integrated GPU, where `nvidia-smi` reports no compute processes.
- **R80-7** Every public compatibility claim about Linux artifacts must match a
  measured property of the artifact it describes.
- **R80-8** `fathomdb doctor gpu` must detect Tegra vs. generic AArch64/SBSA
  hardware and report which, without requiring the end user to know the
  distinction. Detection must not use `uname`-reported architecture strings as
  the Tegra signal (§ 7 80.7 explains why).
- **R80-9** On detected SBSA hardware, `doctor gpu` must refuse CUDA cleanly,
  continue on the typed CPU path, and name `arm64-sbsa` as unsupported — never
  load a Tegra-linked binary there, and never fail the process. This
  requirement covers tool-failure during detection too: if the Tier 2 probe
  itself fails (`nvidia-smi` missing, times out, exits non-zero), the outcome
  must be a named, typed probe failure — never a false SBSA or false-Tegra
  classification reached by misreading a failed probe as a signal (AC80-14).
- **R80-10** Where a Tegra-capable install exists, `doctor gpu` must name the
  exact install command for it. No release artifact may perform a network
  fetch or source build during install without the user invoking it.
- **R80-11** The CPU-default runtime contract is preserved on every AArch64
  and Tegra artifact: with the device policy unset or `cpu`, no code path may
  touch CUDA (AC80-7). This slice changes nothing about that contract; it only
  extends where CUDA is additionally *available* under `auto`/`cuda:N`.

## 5. Acceptance criteria

- **AC80-1** `objdump -T` over each `.node` and each `_fathomdb.abi3.so`
  `build-napi`/`build-python` currently produce (§ 7 80.1: `linux-arm64-gnu`
  npm plus both Python wheel architectures) reports no required `GLIBC_*`
  version above 2.28. Does not cover x64 Linux npm, which has no current
  build row (§ 2.1) — the gate must still apply automatically once one exists.
- **AC80-2** A fixture native object requiring `GLIBC_2.39` fails the new gate;
  removing `objdump` from `PATH` also fails it, with distinct diagnostics.
- **AC80-3** `bash scripts/release/smoke/smoke-npm-package.sh <version>` exits 0
  on a glibc-2.35 host for the published `linux-arm64-gnu` artifact and for
  the Python wheel of both architectures.
- **AC80-4** `test_install_shellcheck.sh` and `test_idempotent_republish.sh`
  pass on aarch64 **and** on x86_64, and each exercises both architectures'
  fixtures regardless of host.
- **AC80-5** On a stock Ubuntu 22.04 AArch64 host, post-bootstrap
  `--tier=fast` reports zero failures attributable to environment (the two
  out-of-scope network/cascade failures of § 2.3 excepted, and named as such).
- **AC80-6** A Jetson Orin build produces artifacts whose embedder resolves to
  `Device::Cuda(0)` under `FATHOMDB_EMBED_DEVICE=cuda:0`, proven by an
  in-process device assertion **and** a measured nonzero GPU allocation delta.
- **AC80-7** The same artifacts complete open/write/search/close/exit on the
  Jetson with `FATHOMDB_EMBED_DEVICE` unset, on a CPU-only code path, with a
  clean process exit.
- **AC80-8** The x86_64 CUDA contract assertions in
  `scripts/check-cuda-release-contract.py` remain green, byte-for-byte
  equivalent in strength, after the contract is parameterized.
- **AC80-9** `docs/compatibility/index.md` states one measured glibc floor per
  artifact family, and a fixture asserting a false floor fails a doc-truth gate.
- **AC80-10** On a Jetson Orin, `fathomdb doctor gpu --json` reports a
  Tegra-specific field distinguishing it from generic AArch64/SBSA, resolved
  via the two-tier detection in § 7 80.7 (`/proc/device-tree/compatible` or
  `/etc/nv_tegra_release` for Tegra-family; `nvidia-smi` `nvgpu` substring only
  to resolve the Thor case) — not `uname`.
- **AC80-11** A fixture presenting Jetson Thor's signature (Tegra-family true
  by Tier 1, but SBSA-capable) is classified as SBSA, not Tegra — the negative
  test named in § 7 80.7, sourced from a real upstream detection bug.
- **AC80-12** On simulated SBSA hardware, `doctor gpu` exits `0`, reports
  `cuda_incompatible` with an unsupported-`arm64-sbsa` message, and the process
  completes the CPU-path smoke — it never attempts to load a Tegra binary and
  never exits non-zero for this case.
- **AC80-13** On a Tegra host where the Tegra-capable package is not installed,
  `doctor gpu` prints the exact install command/package name for that host; no
  test may show a network call or subprocess build invoked without an explicit
  user command.
- **AC80-14** A fixture where `nvidia-smi` exits non-zero (or is absent) during
  Tier 2 resolution on Tegra-family hardware reports a typed probe failure, not
  a false SBSA or false-Tegra classification — the exact class of bug the
  memex note's own reviewer caught (§ 7 80.7) and named as fixed only after
  checking subprocess exit status before reading stdout.

and can land first; 80.4–80.6 are the Tegra CUDA path.

### 80.4 — parameterize the CUDA artifact contract

- Split `scripts/release/cuda-artifact-contract.sh` into a shared core plus
  per-target files (`…-x86_64.sh`, `…-tegra-sm87.sh`), or introduce an explicit
  target selector. The x86_64 values must remain byte-identical.
- Introduce a compute-capability axis, one variable per target rather than a
  list: `CUDA_COMPUTE_CAP_X86_64='75'`, `CUDA_COMPUTE_CAP_TEGRA_ORIN='87'`.
  This follows the pattern real multi-target CUDA build systems converge on —
  PyTorch's `TORCH_CUDA_ARCH_LIST` and `nvcc -gencode` are list-valued because
  discrete GPUs are forward-compatible and a fat binary is viable; llama.cpp's
  Jetson Orin build instead pins a single `CMAKE_CUDA_ARCHITECTURES="87"`,
  because Tegra is not forward-compatible and a fat binary would either bloat
  the build or silently ship a kernel that fails with "no kernel image is
  available for execution on the device" — the same failure §2.5 shows the
  existing classifier already turns into a clean `cuda_incompatible` diagnostic
  rather than a crash. One axis, list-shaped for x86_64 and single-valued for
  Tegra, not two different mechanisms.
  `scripts/check-cuda-release-contract.py:487` must assert the value **for the
  selected target** rather than the literal `'75'` — without weakening the
  assertion (AC80-8).
- Per-target values that must be established by measurement, not assumption:
  base image and digest, gcc lib path (`aarch64-redhat-linux`), rustup toolchain
  triple, rustup-init URL and SHA-256, and the CUDA toolkit source.

### 80.5 — Tegra-portable GPU witness

The PID-in-`nvidia-smi` witness is unavailable on Tegra (§ 2.5) and must be
replaced by something device-truthful on both discrete and integrated GPUs.
Proposed primary witness, in the process under test:

1. Assert the resolved device is `Device::Cuda(N)` — not a silent CPU fallback.
   `resolve_device()` already warns loudly on fallback; the witness must turn
   that warning into a hard signal.
2. Assert a **nonzero GPU allocation delta** across model load, measured through
   the CUDA API in-process, so the proof does not depend on an external
   reporting tool.

`tegrastats` GR3D utilization sampling is admitted as corroboration only, never
as the sole witness. The existing x86_64 PID witness is **retained** for
discrete GPUs — this sub-slice adds a second mechanism, it does not remove the
first, and the x86_64 lane's evidence strength must not drop.

### 80.6 — Jetson Orin CUDA build and evidence

**D-1 — the packaging constraint that shapes this sub-slice (ruled).** CUDA for
`aarch64` exists in two mutually incompatible flavors: `arm64-sbsa` (server) and
Tegra/L4T (Jetson). Neither PyPI wheel tags nor npm `os`/`cpu` fields can
distinguish them — a Tegra-linked artifact and a generic AArch64 artifact both
tag as `manylinux_2_28_aarch64` / `linux-arm64-gnu`. **Publishing a Tegra CUDA
build under the existing package names would break every generic ARM64 user.**
This is not a preference; NVIDIA's own docs confirm `sbsa-linux` ships no
SASS/PTX slices for Tegra iGPUs, so a fat cross-flavor artifact is not viable
either.

Ruled: Tegra CUDA ships as a **verified source-build path plus a
separately-named, first-party artifact** — supported product scope (§ 11 item
7), just not distributable under the existing generic AArch64 package names
for the technical reason above. § 7 80.7 covers how an end user reaches it
without knowing this naming distinction exists.

- Evidence must match Slice 72's bar (§ 2.5): real hardware, UUID/PID-bound
  telemetry, retained receipt hashes, independent review before acceptance —
  not merely "it compiled."
- Evidence comes from a self-hosted Jetson Orin runner. **This exact host
  already runs one**, for another repository: `actions.runner.coreyt-memex.jetson-memex.service`
  under `~/actions-runner/memex/`, a standard `svc.sh`-installed systemd unit.
  A second, separately-registered runner instance under `~/actions-runner/fathomdb/`
  follows the identical, already-proven pattern — new instance, not a shared
  or repurposed one, so `fathomdb`'s workflow-restricted group discipline
  (`dev/design/0.8.23-gpu-artifacts.md`'s `windchill3-fathomdb-cuda` precedent)
  is not diluted by the `memex` repo's access. Labels are routing hints, not
  access control.
- The artifact is built **on the Jetson host** against JetPack's CUDA 12.6,
  not in a manylinux container, because the Tegra CUDA runtime is host-bound.
  Its glibc floor is consequently 2.35, not 2.28 — a deliberate, documented
  exception scoped to the Tegra artifact, and it must be asserted as such by
  the 80.1 gate rather than exempted from it.
- The CPU-default contract holds unchanged: with the device policy at `auto`
  or `cpu` (§ 2.5), the Tegra artifact must complete the full smoke without
  touching the GPU (AC80-7).

### 80.7 — extend `doctor gpu` for Tegra/SBSA, guided install

This is new UX on an existing diagnostic, not new plumbing: `fathomdb doctor gpu`
already exists (Slice 70, `dev/interfaces/cli.md:65`), already resolves a typed
CPU/GPU decision, and its classifier already treats a wrong-architecture CUDA
binary as `cuda_incompatible` rather than a crash (§ 2.5). This sub-slice adds
the detection layer that tells the *user*, not just the process, what to do.

**Detection (R80-8) — two-tier, per the independently-researched cross-language
design in `~/projects/memex/dev/notes/2026-08-18-tegra-sbsa-platform-detection-design.md`.**
That note reaches the same core signal this document already cited
(`nvidia-smi` GPU-name `nvgpu` substring, same jetson-containers/Thor
source[^2]) but structures it more robustly, with reference implementations in
exactly this repo's three language surfaces (Python, Rust, TypeScript). Adopt
its two-tier structure rather than a single nvidia-smi check:

1. **Tier 1 — Tegra-family, no subprocess required.**
   `/proc/device-tree/compatible` contains `nvidia,tegra`, **or**
   `/etc/nv_tegra_release` exists (`R36 (release), REVISION: 5.2` on this host
   — this file also supplies the L4T revision for the glibc-floor message
   decision 3 requires). Either signal alone is sufficient; both are cheap
   filesystem reads, no `nvidia-smi` dependency, no `uname` involved.
2. **Tier 2 — resolve Thor's ambiguity.**
   - Tier 1 false → check `/sys/firmware/acpi/tables` exists. Present means
     SBSA-capable non-Tegra hardware (Grace, Graviton, Ampere Altra).
   - Tier 1 true → shell out to
     `nvidia-smi --query-gpu=name --format=csv,noheader` and check for the
     `nvgpu` substring. Present (`"Orin (nvgpu)"` on this host) → classic
     Tegra iGPU, non-SBSA. Absent (`"NVIDIA Thor"`) → Tegra-family hardware
     that is nonetheless SBSA-capable.

Do not use `uname`-reported architecture strings as the sole Tegra signal —
this is why Tier 2 exists at all. `jetson-containers` shipped exactly a
`uname`-only check and broke it when Jetson Thor began reporting `tegra` in
`uname -a` despite being SBSA-capable.[^2] AC80-11 encodes the Thor case as a
named negative test specifically so this mistake cannot recur here.

Two things from the memex note's own risk section carry over as implementation
constraints, not just references:

- **A reviewer there caught a real bug worth not repeating**: an early Rust
  sketch didn't check the `nvidia-smi` subprocess's exit status, so a failing
  call with empty stdout was misread as SBSA-affirmative instead of failing
  closed. Our implementation must check exit status before interpreting
  stdout.
- **The `nvgpu` substring is an unofficial, empirically-observed signal** — no
  documented NVIDIA API confirms it, and the memex note explicitly flags it
  could change across driver/JetPack versions without notice. Tier 1 does not
  depend on it (filesystem-only), which is why Tier 1 must be tried first and
  is the harder invariant to rely on; Tier 2's `nvgpu` check should degrade to
  a named `probe_failed`-shaped outcome, not a silent default, if `nvidia-smi`
  is missing, times out, or exits non-zero. Invoke it by an absolute path,
  with a bounded timeout — the memex note flags bare-name PATH lookup and no
  timeout as acceptable only for a design sketch, not production.

Python and TypeScript reference implementations exist in the memex note but
are not currently needed here: `doctor gpu` is Rust-CLI-only (§ 2.5) — neither
SDK exposes an independent GPU-diagnostic surface today (confirmed: no `gpu`
symbol in `src/python/fathomdb/__init__.py`, `types.py`, or `src/ts/src/index.ts`).
Keep the Python/TS snippets as ready reference if a future slice adds
SDK-level device diagnostics rather than routing everything through the CLI.

**SBSA refusal (R80-9, ruled continue-on-CPU).** On detected SBSA hardware,
`doctor gpu` reports `cuda_incompatible` naming `arm64-sbsa` explicitly as
unsupported, exits `0`, and the process continues on the typed CPU path. It
never attempts to load a Tegra-linked binary there and never fails the
process outright — an unsupported *accelerator* is not a reason to make the
*database* unusable.

**Guided install, not silent fetch (R80-10, ruled).** When the Tegra-capable
package exists but is not installed, `doctor gpu` prints the exact install
command for the detected host. It does not fetch or build anything itself.
This was a deliberate rejection of the "fully automatic" alternative
(`node-llama-cpp`'s postinstall pattern: detect incompatibility, silently
download and build from source, which "can take up to an hour" and fails
opaquely without build tools present) — an hour-long silent network build
during `npm install`/`pip install` is the kind of surface this repo's
digest-pinned, fail-closed release discipline exists to avoid. The end user
still never has to know *which* ARM64 CUDA flavor exists; they're told the one
command that gets them the right one.

Structure the artifact/package metadata so this guided step is a stepping
stone, not a dead end: name the Tegra artifact so it can become a PEP 817
wheel variant (still Draft, WheelNext-originated) with a null-variant CPU
fallback once that mechanism ships, at which point the guidance step
disappears on its own rather than requiring a second migration.

## 10. Risks

- **R-1 — the containerized N-API build may not be turnkey.** `napi build`
  inside `manylinux_2_28` needs Node and the pinned Rust toolchain present in
  the image. Mitigation: 80.1 lands the gate and the fixtures first, so the
  defect is *visible and failing* even if the build fix takes a second pass.
- **R-2 — lowering the glibc floor may change artifact size.** The wheel-size
  gate (`.github/workflows/ci.yml:747`) has a 20 MB regression budget; a floor
  change should not approach it, but 80.1 must check rather than assume.
- **R-3 — de-risked by direct inspection of the pinned fork; verify at build
  time, don't assume a rewrite.** The pinned Candle fork checkout
  (`~/.cargo/git/checkouts/candle-fathomdb-07553b5f3bcf1ce0/5719d90`, matching
  `Cargo.toml:63`'s pin exactly) shows `candle-kernels/build.rs` compiles
  every kernel the BGE embedder path touches via `cudaforge::KernelBuilder::build_ptx()`
  — PTX, not native SASS, and PTX JIT-compiles forward to newer compute
  capabilities including `sm_87` by design. Only `moe_*.cu` (Mixture-of-Experts
  kernels — BGE-small doesn't use them; `fathomdb-embedder/Cargo.toml` has no
  `flash-attn` dependency either) is natively compiled, gated by
  `cudaforge::detect_compute_cap() < 80` to disable a bf16 WMMA flag on
  pre-Ampere hardware — not a hard failure. **`CUDA_COMPUTE_CAP` itself is
  currently inert for our build**: it's read only by `candle-flash-attn-v3/build.rs`,
  which nothing in this crate graph depends on; 80.4 parameterizes it because
  the release contract checks its literal value, not because it gates real
  kernel compilation today. 80.6's job is to verify PTX JIT actually succeeds
  end-to-end on real Orin hardware — a measurement, not a rewrite risk.
- **R-4 — the AArch64 F16 pin is conservative for Orin.** Orin's Cortex-A78AE
  implements `fullfp16`, so the Gemm F16 exclusion costs performance on this
  host specifically. Out of scope here (§ 3), but worth a separate
  evidence-first look once CUDA lands, since GPU execution may make it moot.
- **R-5 — a second self-hosted runner on shared hardware needs its own
  isolation, not inherited trust.** This Jetson already hosts
  `actions.runner.coreyt-memex.jetson-memex.service` for the unrelated `memex`
  repository. Registering `~/actions-runner/fathomdb/` as a second, separate
  runner instance is the proven, low-risk shape (identical `svc.sh` pattern),
  but the two runners must not share credentials, work directories, or
  registration, and `fathomdb`'s instance still needs the org-scoped,
  workflow-restricted group discipline of `dev/design/0.8.23-gpu-artifacts.md`
  — `memex` already being present on the box is not a reason to relax that.
