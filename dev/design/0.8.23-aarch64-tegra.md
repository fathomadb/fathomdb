## 1. Decision

0.8.23 makes Linux AArch64 a **fixed**, not merely documented, platform, and
adds Jetson Orin (Tegra, `sm_87`) as a first-party CUDA execution target,
reached the same way an end user reaches it on x86_64: through
`fathomdb doctor gpu`, not through picking an artifact flavor themselves.

**Ruled product scope (§ 11 item 7): 0.8.23 supports CUDA on x86_64 and on
Tegra; it explicitly does not support `arm64-sbsa`.** Tegra is declared,
first-party scope, not an experimental add-on. How that declared scope squares
with the standing publication hold was the one question this document left open;
it is now ruled in **§ 11 item 8** — Slice 80 sits behind the same staged
publication gate as every other slice, with no Slice-80-specific exception.
(This sentence previously pointed at a "§ 11 Still open" subsection that no
longer exists.)

Four things are true today; three need work:

1. AArch64 **CPU correctness** is already sound. The Fathom-maintained Candle
   pin, the published manylinux wheel, and the C-interop surface are all
   verified good on a real Jetson Orin (§ 2.4).
2. The published **npm native artifact does not load** on any Linux with glibc
   < 2.39 — on either architecture. It is broken in every published release.
3. **Tegra CUDA has no engineering path yet**, though it is now ruled-in scope
   (above). The CUDA contract is x86_64-literal throughout, and its GPU
   witness (as originally specified) is physically unobtainable on Tegra.
4. **The dual CPU/GPU runtime this slice needs already exists for x86_64.**
   Slices 70/71/72 (landed on `origin/release/0.8.23`, `REVIEWED_PENDING_INTEGRATION`)
   built exactly the typed device-policy, classifier, and `doctor gpu`/
   `doctor reranker-gpu` diagnostic surface a Tegra-aware answer needs
   (`dev/adr/ADR-0.8.23-dual-runtime-device-policy.md`, HITL `seq:250`). Slice 80
   **extends** that surface to a second architecture; it does not design a new
   one. § 2.5 details what already transfers unmodified.

The bias of this slice is **fix over document**. Documentation changes are
admitted only where the underlying fact is intentional and correct after the
fix (§ 8), never as a substitute for repairing a broken artifact.

## 2. Evidence base

All findings below were measured on the target host, not inferred. Host:
Jetson Orin AGX, L4T R36.5.2, Ubuntu 22.04.5, **glibc 2.35**, aarch64,
12 cores, 61 GB, CUDA 12.6 / driver 540.5.0.

Baseline test run — `bash scripts/agent-test.sh --tier=fast` on the host:
`registered=73 ran=73 passed=60 failed=13`.

### 2.1 The npm native artifact cannot load (BLOCKER)

```console
$ node -e 'require("./fathomdb.linux-arm64-gnu.node")'
LOAD FAILED: /lib/aarch64-linux-gnu/libc.so.6: version `GLIBC_2.39' not found

$ bash scripts/release/smoke/smoke-npm-package.sh 0.8.22 ; echo $?
1
```

- Unresolved symbols: `pidfd_spawnp`, `pidfd_getpid` @ `GLIBC_2.39`. Their
  `.gnu.version_r` entry is `Flags: none` — **not weak** — so `ld.so` hard-fails
  rather than skipping them.
- Root cause: `.github/workflows/release.yml:463` (`build-napi` job) runs
  `npm run build:native` bare on the runner. `build:native`
  (`src/ts/package.json:22`) is plain `napi build` with no container, so the
  artifact inherits the runner's glibc (`ubuntu-24.04-arm` for the job's only
  current Linux matrix row → 2.39). The Python wheel is built through
  `PyO3/maturin-action` with `manylinux: "2_28"` and measures a **2.28**
  floor, which is why it works.
- **Not AArch64-specific and not a regression.** `fathomdb-linux-x64-gnu@0.8.22`
  carries the same 2.39 floor, and so does `fathomdb-linux-arm64-gnu@0.8.21`.
  Every published npm Linux artifact has shipped this way.
- **x64 Linux npm is a special case, verified directly, not just historical.**
  `build-napi`'s current matrix (`release.yml:421-436`) has exactly one Linux
  row — `linux-arm64-gnu` — no `linux-x64-gnu` row exists. The
  `publish-npm-platform-linux-x64-gnu` job (`:1035`) still downloads an
  artifact named `napi-linux-x64-gnu`, but **no job in the current workflow
  uploads an artifact by that name** — grep confirms it appears exactly once,
  as that download target. That job's real gate, `all-builds-passed`
  (`:744-758`), requires `canonical-cuda-package-route-required` to succeed
  for any non-dry-run release, and that job (`:728-738`) unconditionally
  `exit 1`s — a deliberate hard block, not a bug, pending Slice 20's
  not-yet-built canonical CUDA delivery route (§ 2.5). So x64 Linux npm
  publication cannot run *at all* on this branch today, independent of glibc.
  The 0.8.22 measurement above is real but historical: it reflects whatever
  `release.yml` shape produced that artifact before the Slice 70–72
  CUDA/dual-runtime restructuring introduced this block. § 7 80.1 scopes
  itself to what `build-napi` can currently build — `linux-arm64-gnu` plus
  both Python wheel architectures — rather than a job that doesn't exist yet;
  wiring x64 Linux npm's CUDA build is Slice 20's canonical-route work, out of
  scope here per § 3.
- Platforms silently excluded: Ubuntu 22.04 (2.35 — **every Jetson on L4T R36**),
  Debian 12 (2.36), RHEL 9 and Amazon Linux 2023 (2.34).
- **No gate exists.** Nothing under `scripts/` or `.github/workflows/` asserts a
  maximum required `GLIBC_*` symbol version. `readelf -d` in
  `scripts/release/cuda-preflight.sh:202,204` dumps dynamic deps informationally and
  asserts nothing about the floor.

### 2.2 Two tests encode an x86_64 host assumption

Both pass on x86_64 CI and fail on any ARM64 developer machine.

- `scripts/tests/test_install_shellcheck.sh:91,129` hardcode the cache fixture
  path as `linux.x86_64-$LINUX_X86_64_SHA`, and `:76` feeds the x86_64 SHA to
  the `sha256sum` shim. On aarch64 the installer correctly derives
  `linux.aarch64-12b331c1…` (`scripts/install-shellcheck.sh:68-70`), so the
  fixture never matches, cache-hit arms A and C miss, and the test falls through
  to the stubbed offline download. **The installer itself is correct** — the
  defect is entirely in the test's fixture.
- `scripts/tests/test_idempotent_republish.sh:224` builds a fixture platform
  package declaring `cpu: ["x64"]`. npm correctly skips optional platform
  packages that do not match the host CPU, so on aarch64 the "platform package
  present after install" assertion and the loader arm both fail.

### 2.4 What is already correct on AArch64 — preserve, do not disturb

- All three AArch64 suites pass on the host: `test-linux-aarch64-release-artifacts`
  (323 ms), `test-aarch64-candle-feature-closure` (345 ms), and
  `test-aarch64-candle-cpu` (63.6 s, a real compile and run).
- The Candle fork pin (`Cargo.toml:63-70`) works as designed: `cargo tree`
  confirms `default-embedder` never resolves `gemm-f16`, whose F16 backend would
  emit `fullfp16` instructions outside the ARMv8-A Tier-1 baseline. The CPU
  regression confirms f32 matmul succeeds and f16 matmul returns
  `UnsupportedDTypeForOp` cleanly.
- The published `fathomdb-0.8.22-cp310-abi3-manylinux_2_28_aarch64.whl` installs
  and passes the canonical open/write/search/close/exit smoke with a clean
  process exit. Measured floor: `GLIBC_2.28`.
- C interop uses `std::os::raw::c_char` throughout — no hardcoded `i8`/`u8`, so
  the AArch64 char-signedness trap is avoided.
- The typed device-resolution surface Slice 70 landed
  (`resolve_embed_device_policy` / `resolve_embed_device_policy_from_env` in
  `src/rust/crates/fathomdb-embedder/src/device_policy.rs`, and
  `resolve_default_embedder_device_from_env` /
  `diagnose_default_embedder_gpu_from_env` in
  `src/rust/crates/fathomdb-embedder/src/candle_bge.rs`) makes no architecture
  assumption — it dispatches on typed CUDA driver/cuBLAS error codes, not on
  `uname`.
- CI already builds and smokes both the wheel and the `.node` on
  `ubuntu-24.04-arm` (`.github/workflows/ci.yml:764,863`).

### 2.5 What Slices 10/20/70–72 already built, and what still doesn't reach Tegra

The release ladder moved substantially between this doc's first draft and
this revision (branch pulled to `0dfe96da`). Two things are true at once:
most of the CUDA release-engineering and device-policy substrate this slice
needs now exists; none of it yet reaches AArch64 or Tegra.

**What now exists (x86_64 only), per `dev/plans/release-state-0.8.23.json`:**

| Slice | Status | What it built |
| --- | --- | --- |
| 10 CUDA-CONTRACT | `PENDING_EXTERNAL` | Reviewed local RED→GREEN: witness/receipt verifiers, one-record provenance policy, protected environment, credentialless candidate jobs. Release-complete only pending a real trusted-runner dispatch (HITL `seq:249`) — the *engineering* is done. |
| 20 CUDA-PACKAGE | `PENDING_EXTERNAL` | Reviewed local RED→GREEN package-rehearsal control plane: sealed candidate wheel/npm/tarball, GPU UUID/PID attestation, substitution rejection. A real rehearsal awaits a valid Slice 10 witness; no canonical tag-bound CUDA delivery route exists yet. |
| 70 DUAL-RUNTIME-TC5 | `REVIEWED_PENDING_INTEGRATION` | **The typed CPU/GPU device policy this slice depends on.** `ADR-0.8.23-dual-runtime-device-policy.md` (HITL `seq:250`): one policy (`auto`/`cpu`/`cuda:N`), `fathomdb doctor gpu [--json]` (exit `0`/`65`/`70`, per `dev/interfaces/cli.md:65`), and a closed, code-based compatibility classifier in `src/rust/crates/fathomdb-embedder/src/candle_bge.rs::classify_cuda_driver_error` / `::classify_candle_cuda_error`. |
| 71 RERANK-DUAL-RUNTIME | `REVIEWED_PENDING_INTEGRATION` | Same policy applied to the cross-encoder reranker; `doctor reranker-gpu`. |
| 72 CONCURRENT-DUAL-RUNTIME | `REVIEWED_PENDING_INTEGRATION` | Real RTX 3090 evidence bar: UUID/PID-bound telemetry, retained receipt hashes, an independently-caught timestamp-epoch bug fixed before acceptance. **This is the evidence bar § 7 80.6 should match for Tegra.** |

**The good news this surfaces: the compatibility classifier is already
architecture-agnostic and already does the right thing for a Tegra-arch
mismatch.** `classify_cuda_driver_error` maps `CUDA_ERROR_NO_BINARY_FOR_GPU`
and `CUDA_ERROR_UNSUPPORTED_PTX_VERSION` to `CudaProbeError::Incompatible` —
not `ProbeFailed` — which `doctor gpu` reports as `cuda_incompatible` with a
typed CPU fallback and exit `0` (ADR, "Consequences"). That is *exactly* the
failure a Tegra-linked (`sm_87`-only) binary hits on the wrong hardware, or
that a generic AArch64/SBSA binary would hit on Tegra. **This is the
mechanism decision 2c's "refuse cleanly, continue on CPU" resolves to** — it
already exists, generically, for the discrete-GPU case; Slice 80 does not
build a new refusal path, it confirms this one holds under a Tegra build and
adds the friendlier detection layer on top (§ 7 80.7).

**What still doesn't reach Tegra:**

- `scripts/release/cuda-artifact-contract.sh` — the single checked source of
  CUDA build inputs — is x86_64-literal throughout:
  `CUDA_MANYLINUX_PLATFORM='linux/amd64'`,
  `CUDA_MANYLINUX_BASE_IMAGE='quay.io/pypa/manylinux_2_28_x86_64@sha256:…'`,
  `CUDA_RUSTUP_TOOLCHAIN='1.95.0-x86_64-unknown-linux-gnu'`,
  `CUDA_MANYLINUX_GCC_LIB='…/x86_64-redhat-linux/13'`,
  `CUDA_RUSTUP_INIT_URL='…/x86_64-unknown-linux-gnu/rustup-init'`.
  `scripts/check-cuda-release-contract.py` asserts those literals, now also
  covering a Slice 71 rerank-cuda tuple (`CUDA_RERANK_NAPI_FEATURES`,
  `CUDA_RERANK_PYTHON_FEATURES`) — still x86_64-only.
- `CUDA_COMPUTE_CAP='75'` is a single hardcoded value (T4, `sm_75`) asserted
  literally at `scripts/check-cuda-release-contract.py:487`. **Orin AGX is
  `sm_87`.** The contract has no compute-capability axis, and — confirmed by
  vendor documentation, not just inference — Tegra has no forward-compatibility
  guarantee across compute capabilities the way discrete GPUs do: an `sm_75`
  build will not run on `sm_87` hardware. `nvcc`'s own `-gencode` reference
  states Tegra SMs (`sm_72` Xavier, `sm_87` Orin) are never implied by a
  discrete-GPU gencode list and must be added as their own explicit target.[^1]
- The GPU witness *as originally specified* is unobtainable on Tegra.
  `scripts/release/cuda-preflight.sh:473` requires the smoke PID to appear in
  `nvidia-smi --query-compute-apps` output. On this Orin:

  ```console
  $ nvidia-smi --id=0 --query-compute-apps=pid --format=csv,noheader
  [N/A]
  ```

  Tegra's `nvidia-smi` never reports compute processes, and reports `Not
  Supported` for memory. A different witness mechanism is required for the
  Tegra build specifically (§ 7 80.5) — the x86_64 witness is unaffected and is
  not being replaced.
- The Rust side (`embed-cuda` / `rerank-cuda` feature chains, the device-policy
  crate, the classifier) is already architecture-agnostic, and the host
  carries `libcuda.so`, `libcublas.so.12`, and nvcc 12.6. The blockers are the
  release contract's literals and the x86_64-only GPU witness mechanism, not
  the runtime code.

[^1]: <https://arnon.dk/matching-sm-architectures-arch-and-gencode-for-various-nvidia-cards/>;
  corroborated independently by llama.cpp's Jetson Orin build, which pins a
  single `-DCMAKE_CUDA_ARCHITECTURES="87"` rather than a fat-binary list for
  exactly this reason
  (<https://github.com/ggml-org/llama.cpp/issues/17747>).

### 2.7 Measured witness facts on this Orin (added when 80.5 was commissioned)

Everything in this subsection was **measured on this Jetson Orin AGX**, with a
CUDA driver-API probe compiled by this host's `nvcc` 12.6.68 and with a real
`cargo build`, not inferred. It exists because § 7 80.5's original text
proposed a mechanism without establishing that the mechanism works here.

- **`cuMemGetInfo` requires a current CUDA context.** Called after `cuInit(0)`
  but before any context exists it returns `201` = `CUDA_ERROR_INVALID_CONTEXT`;
  after `cuCtxCreate` it succeeds. This is an **ordering invariant**, not an
  implementation detail: a witness that samples "before" too early gets a typed
  error, and a witness that silently treats that error as a zero sample would
  manufacture a false delta. The sample-before must therefore be taken *after*
  the Candle device is constructed and *before* the model is loaded.
- **It works on the integrated GPU, and reports unified system memory.** With a
  context: `total = 65_879_896_064` bytes — the whole 61 GiB of unified system
  memory, consistent with `CU_DEVICE_ATTRIBUTE_INTEGRATED = 1` and
  `CU_DEVICE_ATTRIBUTE_UNIFIED_ADDRESSING = 1`. `total` equals `/proc/meminfo`
  `MemTotal` exactly, and `free` tracks `MemAvailable`.
- **CORRECTED — an allocation does NOT reliably move the counter, and the
  original measurement here did not generalize.** This subsection first recorded
  that a 268_435_456-byte (256 MiB) `cuMemAlloc` moved free memory by
  274_161_664 bytes. That was a single observation on a freshly-booted,
  never-used GPU, and **it does not reproduce**. Re-measured directly, twice, by
  two independent probes: on a host whose GPU has been used at all, the *first*
  256 MiB allocation moves free by only **1_032_192 bytes**, the second by
  512_000, the third and fourth by **0**, and freeing returns **0** to the
  counter. A deliberate 133_466_304-byte allocation — the exact size of the
  pinned model — moved free by **0 bytes**.

  Cause: Tegra's nvgpu/nvmap **page pool** retains freed pages and satisfies
  subsequent allocations from them without touching system free memory. The pool
  is warm on any host that has run a GPU workload since boot, which is every
  realistic host, including CI after its first run.

  **Consequence — this is the load-bearing correction for 80.5.** A witness that
  simply brackets the model load and asserts a floor is not merely fragile, it
  fails closed on every run on a warm host: measured, the model load charged
  **6_189_056 bytes** against a warm pool for a 133 MB model. D-80.5-3's control
  allocation is therefore not corroboration — it is a **precondition**, and it
  must *drain* the pool rather than merely sample it. With the pool drained, the
  same load on the same host charges **141–144 MB across four runs (0.4%
  spread)**, and the floor becomes meaningful again.
- **Idle jitter is not the dominant term.** Five consecutive `cuMemGetInfo`
  samples with no allocation in between differed by **0 bytes**. The counter
  does not free-run; it simply does not observe allocations the pool absorbs,
  which is a different and more dangerous failure than noise — a masked
  allocation looks exactly like no allocation.
- **Tegra's `nvidia-smi` omits the `GPU-` UUID prefix.** This host reports
  `bbbe9f37-7028-556a-930b-54e5f3b67a82` for
  `nvidia-smi --query-gpu=uuid --format=csv,noheader`, whereas Slice 72's
  x86_64 evidence records `GPU-5f9cfc90-2be1-06a7-ce39-5a6d294b209b`. The
  driver-API bytes are identical either way, and this repo's existing
  `cuda_uuid_string` (`candle_bge.rs`) renders them as
  `GPU-bbbe9f37-7028-556a-930b-54e5f3b67a82`. **This breaks a second Tegra
  assumption nobody had found yet:** `verify-cuda-preflight-witness.py:335`
  asserts `nvidia_smi_uuid == device["uuid"]` by string equality, which cannot
  hold on Tegra without normalization. It is not only the compute-apps PID that
  fails to port.
- **Driver-API device name is `Orin`; `nvidia-smi --query-gpu=name` is
  `Orin (nvgpu)`.** Independent corroboration of the `nvgpu` substring § 7 80.7
  relies on, obtained from this host rather than from the upstream issue.
- **R-3 is now measured, not merely de-risked by inspection.**
  `cargo build -p fathomdb-embedder --features embed-cuda` **succeeds on this
  Orin** with CUDA 12.6 and `CUDA_COMPUTE_CAP=87`, in 1m41s. The pinned Candle
  fork's PTX path compiles for `sm_87` with no fork change.
- **The runtime PTX JIT is measured too — R-3 is now fully discharged.** The
  `gpu_speedup` example, which reaches the device through the product's own
  `FATHOMDB_EMBED_DEVICE` seam and the product's own loader, **ran to
  completion on `cuda:0` on this Orin**: 32 documents, model load 14.44 s,
  single-embed 2.1 docs/s, batched 70.0 docs/s (33.53× batching gain), and
  batched-vs-single parity `min_cosine = 0.999999`. The run cannot have silently
  degraded to CPU: `cuda:0` is a **forced** policy, and
  `resolve_embed_device_policy`'s `EmbedDevicePolicy::Cuda(ordinal)` branch never
  returns `cpu_resolution` — it yields either `selected_resolution` or
  `Err(ForcedCudaUnavailable)`, which this example surfaces as a panic. A
  completed run is therefore proof of GPU execution by construction, not by the
  absence of a warning. This is the end-to-end proof § 10 R-3 said only a real
  forward pass could give: the PTX those kernels carry loads and executes on
  `sm_87`, and produces numerically correct embeddings.
- **Two host-native build facts the Tegra lane needs** (§ 7 80.4 deferred these
  to 80.6 as "must be established by measurement" — these are the measurements):
  the CUDA runtime libraries live at
  `/usr/local/cuda-12.6/targets/aarch64-linux/lib` (with `lib64` a symlink to
  it), and the NVIDIA driver library is at
  `/usr/lib/aarch64-linux-gnu/nvidia/libcuda.so.1` — an **L4T-specific
  subdirectory**, not the bare multiarch path. Without `LIBRARY_PATH` naming the
  first, linking fails with `cannot find -lcudart`, measured here before the
  fix.

One prior-art tension this subsection settles. `dev/design/gpu-device-allocation-policy.md`
(SUPERSEDED, § 2.8(b)) records NVIDIA's own position that `cuMemGetInfo` is a
racy, point-in-time estimate that **cannot be used to predict whether a future
allocation will succeed**. That critique is correct and does not apply here:
80.5 uses the call **post hoc, to witness an allocation that has already
happened**, never predictively as an eligibility gate. The two uses have
opposite failure modes, and the earlier document's refusal to build a
free-VRAM admission gate stands unchanged.

## 3. Scope

**In scope.**

- Repairing the npm native-artifact glibc floor on **both** Linux architectures,
  and gating it so it cannot regress.
- Removing the x86_64 host assumption from the two affected tests.
- Making `scripts/bootstrap.sh` produce a complete, gate-capable developer
  environment on Ubuntu 22.04 / AArch64.
- A first-party Tegra (`sm_87`) CUDA build path, a device-truthful GPU witness
  that works on integrated Tegra GPUs, and a real Jetson Orin evidence run
  matching Slice 72's evidence bar (§ 2.5).
- Making the **existing** `fathomdb doctor gpu` consume a Tegra/SBSA platform
  classification for its existing policy mapping, plus the sibling
  `fathomdb doctor platform` diagnostic that reports the classification without
  asking an end user to select a CUDA flavor themselves.
- Correcting the public compatibility claims that the fixes make true or false.

**Out of scope.**

- Publishing a Tegra-specific wheel or npm package under the existing package
  names. § 7 80.6 D-1 explains why this is a packaging impossibility rather
  than a choice, and what replaces it.
- Windows and macOS ARM CUDA. Unchanged.
- A postinstall network fetch or auto-build of the Tegra artifact. § 7 80.7
  explains why user-invoked source-build guidance (`doctor gpu --help` and docs
  print the procedure; the wrapper prints its concrete install command) is
  preferred over silent download/build.
- Shipping an untested `arm64-sbsa` CUDA build. § 7 80.7 covers detection and a
  clean, CPU-continuing refusal instead.
- The x86_64 CUDA/dual-runtime ladder (Slices 10, 20, 70, 71, 72). Slice 80
  **extends the device-policy and contract substrate those slices already
  built** (§ 2.5) but does not implement, reorder, or block them; see § 6 on
  sequencing.
- Musl, 32-bit ARM, and Jetson platforms older than Orin (`sm_87`).
- The `test-check-release-state-views` R5 network-transport failure and its
  `test-shell-pipefail-guards` cascade (§ 2.3).
- Raising the AArch64 Candle F16 baseline. Orin's Cortex-A78AE does implement
  `fullfp16`, so the current pin is conservative for this host — but it is
  correct for the Tier-1 baseline, and relaxing it is a separate, evidence-first
  decision. See § 10 R-4.

## 4. Requirements

- **R80-1** No published native artifact — wheel or `.node`, either Linux
  architecture — may require a glibc symbol version above the declared floor of
  **2.28**.
- **R80-2** The floor is enforced by an automated gate that fails closed when
  its inspection tool is unavailable, and that runs on the artifact actually
  published, not only on a locally built equivalent.
- **R80-3** No suite in `scripts/agent-test.sh` may pass or fail as a function
  of host architecture. A suite that cannot run on a host must SKIP explicitly,
  as the AArch64 suites already do.
- **R80-4** `bash scripts/bootstrap.sh` on a stock Ubuntu 22.04 AArch64 host
  must yield an environment in which the full `--tier=fast` suite runs with no
  failure attributable to a missing or too-old tool.
- **R80-5** The CUDA artifact contract must express architecture and compute
  capability as inputs rather than literals, without weakening any assertion the
  x86_64 lane currently makes.
- **R80-6** The CUDA GPU witness must prove device engagement on a Tegra
  integrated GPU, where `nvidia-smi` reports no compute processes.
- **R80-7** Every public compatibility claim about Linux artifacts must match a
  measured property of the artifact it describes.
- **R80-8** `fathomdb doctor gpu` must consume a detection of Tegra vs. generic
  AArch64/SBSA hardware for its unchanged policy surface, while `fathomdb
  doctor platform` reports the full classification without requiring the end
  user to know the distinction. Detection must not use `uname`-reported
  architecture strings as the Tegra signal (§ 7 80.7 explains why).
- **R80-9** On detected SBSA hardware under `auto` or an unset policy,
  `doctor gpu` must refuse CUDA cleanly, continue on the typed CPU path, and
  name `arm64-sbsa` as unsupported — never load a Tegra-linked binary there.
  Forced `cuda:N` preserves the existing refusal/exit-65 contract; explicit
  `cpu` preserves the existing no-CUDA path unchanged. If the Tier 2 probe
  fails (`nvidia-smi` missing, times out, exits non-zero), `doctor platform`
  reports its named typed probe failure; `doctor gpu` instead proceeds to its
  ordinary CUDA-provider diagnosis, never a false SBSA or false-Tegra refusal
  reached by misreading a failed probe as a signal (AC80-14).
- **R80-10** While no Tegra package index exists, `doctor gpu --help` and public
  docs must name the exact documented source-build procedure; the frozen normal
  and JSON diagnostic output remains unchanged. The build wrapper must print
  the exact `pip install <built-wheel>` command for the wheel it produced. No
  release artifact may perform a network fetch or source build without the user
  invoking it.
- **R80-11** The device-policy contract of ADR-0.8.23-dual-runtime-device-policy
  is preserved unchanged on every AArch64 and Tegra artifact. Concretely, and
  **corrected during 80.5 commissioning** — the earlier wording of this
  requirement grouped `auto` with `cpu` and was false against the landed code:
  - `cpu` **never initializes CUDA**, on any artifact, on either architecture.
    This is the guarantee AC80-7 asserts.
  - a **non-CUDA-compiled** artifact (the generic AArch64 wheel/npm package)
    stays on CPU under `auto` too, reporting `cuda_not_compiled`.
  - on a **CUDA-compiled** artifact, `auto` is the default and **does select
    CUDA** when a device probes successfully
    (`device_policy.rs::resolve_embed_device_policy`, `EmbedDevicePolicy::Auto`;
    ADR § "Proposed decision": "`auto` is default on CUDA-capable artifacts").
    On the Tegra CUDA artifact this is the intended product behavior, not a
    regression: an Orin user who sets nothing gets GPU embeddings, exactly as
    an x86_64 user with the CUDA artifact does (AC80-21).

  Slice 80 changes none of this; it only extends *where* a CUDA-compiled
  artifact exists. Any implementation that made `auto` stay on CPU for Tegra
  specifically would be a runtime behavior change and is forbidden by § 12.
- **R80-12** The Tegra GPU witness fails closed. Any outcome other than a
  proven CUDA device engagement — CPU fallback, a probe or driver error, an
  ordinal or UUID mismatch, a missing sample, or an allocation delta at or
  below the declared floor — is a **named, typed failure**. It is never a pass,
  never a warning, and never a silent skip. A host with no CUDA device is the
  one legitimate non-failure outcome and must SKIP explicitly with a named
  reason (R80-3).
- **R80-13** The witness binds its verdict to device identity obtained
  **in-process from the CUDA driver** — the ordinal Candle actually retained
  plus the driver-reported UUID — never to an external reporting tool, and it
  retains the raw samples (free-before, free-after, total, and the declared
  floor) so a reader can re-derive the verdict rather than trust it. Where a
  witness field is compared against an `nvidia-smi`-sourced value, the
  comparison must normalize the UUID spelling difference measured in § 2.7,
  and must check the subprocess exit status before reading its stdout.
- **R80-14** The default-embedder loader must never record a cache hit for an
  asset it cannot subsequently read. Materializing a pinned asset from an
  external cache yields a readable regular file matching the pin, or a typed
  error — never a link that resolves outside the destination cache. Discovered
  while producing 80.5's evidence and folded into it by HITL direction
  (AC80-23); the defect is architecture-independent, not a Tegra concern.
- **R80-15** Every cache entry the loader publishes is published **atomically**,
  by verifying a privately-named temporary and then renaming it into place —
  never by writing the final path in situ. A concurrent reader therefore always
  observes either the complete previous entry or the complete new one, never a
  partial write and never a transient absence. Cleanup on failure is
  **owner-scoped**: a process removes only the temporary it created, never the
  published entry, which it does not exclusively own. This is the discipline
  `fetch_under_lock` already applies on the download path (`.partial` → verify →
  `fs::rename` → `fsync_parent_dir`, design §5/§6); R80-15 requires it on every
  publishing path, including the HF-hub materialization the probe reaches
  outside the loader lock. Two corollaries, both established by the research
  cited in § 7 80.5 rather than assumed:
  - **The temporary's name must be obtained by exclusive creation, not by
    being improbable.** A PID-derived name is not unique across PID namespaces
    (containers sharing a bind-mounted cache — this repo's own CUDA preflight
    bind-mounts caches into containers), across hosts sharing an NFS/SMB home,
    or across PID reuse. A collision reproduces the very race this requirement
    exists to close, one level down. `link(2)` and `O_CREAT|O_EXCL` are each
    atomic create-exclusive primitives and are sufficient; no new dependency is
    warranted, and adding one would breach the `default-embedder` footprint
    invariant (EMB-3).
  - **Durability is a property of the data path, not of verification.** Reading
    a temporary back to check its digest proves *content* and forces no
    writeback. A path that writes real bytes must `fsync` the temporary before
    the rename; a path that only creates a hard link writes no file data, and
    the post-rename parent-directory `fsync` is then both necessary and
    sufficient.

- **AC80-6** A Jetson Orin build produces artifacts whose embedder resolves to

- **AC80-7** The same artifacts complete open/write/search/close/exit on the
  Jetson with **`FATHOMDB_EMBED_DEVICE=cpu`**, on a CPU-only code path that
  never initializes CUDA, with a clean process exit. **Corrected during 80.5
  commissioning:** this criterion previously said "unset", which is `auto`, and
  `auto` on a CUDA-compiled artifact correctly selects CUDA (R80-11) — so the
  old wording was unsatisfiable on the very artifact 80.6 builds. `cpu` is the
  policy that carries the never-touch-CUDA guarantee; unset/`auto` is covered
  by AC80-21 instead.
- **AC80-8** The x86_64 CUDA contract assertions in
  `scripts/check-cuda-release-contract.py` remain green, byte-for-byte
  equivalent in strength, after the contract is parameterized.
- **AC80-9** `docs/compatibility/index.md` states one measured glibc floor per
  artifact family, and a fixture asserting a false floor fails a doc-truth gate.
- **AC80-10** On a Jetson Orin, the CLI reports a Tegra-specific platform
  classification distinguishing it from generic AArch64/SBSA, resolved via the
  two-tier detection in § 7 80.7 (`/proc/device-tree/compatible` or
  `/etc/nv_tegra_release` for Tegra-family; `nvidia-smi` `nvgpu` substring only
  to resolve the Thor case) — not `uname`.

  **Corrected at 80.7 planning: this is a NEW sibling record, not a field added
  to `doctor gpu` v1.** The criterion originally said "`fathomdb doctor gpu
  --json` reports a Tegra-specific field". That cannot be done without breaking
  a frozen contract: `dev/interfaces/cli.md:75-79` fixes v1's key set **and
  order** (`schema_version`, `policy`, `cuda_compiled`, `status`,
  `effective_device`, `devices`, `reason`, `selected_uuid`), and
  `dev/design/0.8.23-slice-70-dual-runtime-device-policy.md:58` **deliberately
  excludes** build/platform provenance from v1 — a ruling, not an oversight.
  `fathomdb.doctor.gpu.v1` is additionally pinned in
  `src/rust/crates/fathomdb-cli/src/lib.rs`, `tests/operator_cli.rs`, and the
  `test-slice70-embedding-docs-contract` gate.

  Follow **Slice 71's own precedent**, which hit this exact wall and solved it
  by minting `fathomdb.doctor.reranker-gpu.v1` as a separate record explicitly
  "to preserve the Slice 70 doctor v1 schema". 80.7 mints
  **`fathomdb.doctor.platform.v1`** the same way. `doctor gpu` v1 is **not**
  touched — no new key, no reordering, no version bump, and the Slice 70 gate
  stays green with no consumer migration.

  Note this costs nothing for AC80-12: the SBSA message it requires lands in
  v1's **existing `reason` field**, which is already contractually present and
  nullable. Only the *structured platform classification* needs the new record.
- **AC80-11** A fixture presenting Jetson Thor's signature (Tegra-family true
  by Tier 1, but SBSA-capable) is classified as SBSA, not Tegra — the negative
  test named in § 7 80.7, sourced from a real upstream detection bug.
- **AC80-12** On simulated SBSA hardware under **`auto` or unset policy only**,
  `doctor gpu` exits `0`, reports `cuda_incompatible` with
  `reason: "arm64_sbsa_unsupported"`, and the process completes the CPU-path
  smoke — it never attempts to load a Tegra binary and never exits non-zero for
  this case.

  **Explicit `cpu` is NOT in scope and must be left exactly as it is.** A design
  review caught this and it was a real error in the previous scoping, which
  wrote "non-forced policy (`auto`, unset, or `cpu`)". The frozen matrix maps
  **`cpu` (any artifact) → `selected_cpu_no_cuda`, `devices: []`,
  `reason: null`, exit `0`**, with **no CUDA activity at all**. Reporting
  `cuda_incompatible` there would (a) contradict the frozen row and (b) require
  probing CUDA on the one path whose defining property is that CUDA is never
  touched — the same property AC80-7 asserts via `/proc/self/maps`. So `cpu`
  keeps `selected_cpu_no_cuda` and a `null` reason on SBSA exactly as on any
  other host.

  **The `reason` value is `arm64_sbsa_unsupported`** — lowercase snake_case, per
  the established vocabulary (`cuda_probe_failed`, `probe_failed`,
  `cuda_not_compiled`). It is a **new value in an existing, already-nullable
  field**, not a schema change.

  **Three policy arms, three different answers — a fixture must assert all
  three:** `auto`/unset → `cuda_incompatible`, exit `0`; forced `cuda:N` →
  `cuda_incompatible`, `effective_device: null`, exit `65`; explicit `cpu` →
  `selected_cpu_no_cuda`, `reason: null`, exit `0`, unchanged.

  **Scoped at 80.7 planning — SBSA does NOT override a forced policy.** As
  originally written ("exits 0 ... never exits non-zero for this case") this
  contradicted the Slice 70 contract, which a plan review caught. The twelve-row
  matrix at `dev/interfaces/cli.md` maps **forced `cuda:N` + `cuda_incompatible`
  → exit `65`, `effective_device: null`**, under the stated invariant "**Forced
  CUDA never becomes a CPU report.**"

  **Ruled: the forced-policy contract wins; exit `65` stands on SBSA.** R80-9's
  justification is that an unsupported *accelerator* must not make the
  *database* unusable — that protects the **default** path, which is what an
  ordinary user hits and where exit `0` is correct. A user who explicitly typed
  `cuda:N` asked for something this hardware cannot do; telling them so is the
  whole point of a forced policy, and silently downgrading it would break the
  one invariant the Slice 70 matrix states outright. Carving out an SBSA
  exception would make `cuda:N` mean "CUDA, unless the platform is one specific
  unsupported flavor, in which case CPU" — an incoherent contract.

  So the SBSA behavior is a **message and classification** change, not an
  exit-code change. Forced `cuda:N` on SBSA remains exit `65`; the improvement
  is that `reason` now names `arm64-sbsa` explicitly instead of a generic
  incompatibility. A fixture must assert **both** arms: non-forced → `0`,
  forced → `65`.
- **AC80-13** `doctor gpu --help` and public docs emit the exact,
  fixture-tested source-build procedure and do not fetch or build; normal
  `doctor gpu` output remains frozen, and the separately distributed CLI does
  not infer a Python environment's installed-wheel identity. The build wrapper
  fails closed unless it produced a `+tegra` wheel, then prints the exact
  `pip install <built-wheel>` command for that existing path. AC80-27 alone
  ties repair guidance to a detected generic Python build. No test may show a
  network call or subprocess build invoked without an explicit user command.
- **AC80-14** Fixtures for each Tier 2 failure — no executable candidate,
  2000 ms timeout, and non-zero `nvidia-smi` exit — assert the exact paired
  behavior on Tegra-family hardware: `doctor platform` reports the matching
  `unknown` reason and exit 70, never a false SBSA or false-Tegra
  classification; `doctor gpu` proceeds to ordinary CUDA-provider diagnosis
  rather than failing on the ancillary platform probe. This is the exact class
  of bug the memex note's own reviewer caught (§ 7 80.7) and named as fixed
  only after checking subprocess exit status before reading stdout.
- **AC80-15** On this Jetson Orin with `FATHOMDB_EMBED_DEVICE=cuda:0`, the
  witness reports the ordinal Candle actually retained, the driver-API UUID, and
  a free-memory delta **at or above the declared model floor**. The retained
  witness record carries `free_before_bytes`, `free_after_bytes`,
  `total_bytes`, `delta_bytes`, and `delta_floor_bytes`, so the verdict is
  re-derivable from the record alone (R80-13).
- **AC80-16** A witness run that resolves to CPU — `FATHOMDB_EMBED_DEVICE=cpu`,
  a CUDA-less build, or a CUDA request that fell back — exits non-zero with a
  named CPU-fallback outcome and writes **no** success witness (R80-12).
- **AC80-17** Sampling GPU memory before a CUDA context exists yields a named
  typed error, not a zero sample. Encoded as a test against the measured
  `CUDA_ERROR_INVALID_CONTEXT` behavior of § 2.7, so a future refactor that
  reorders the samples fails loudly rather than reporting a false delta.
- **AC80-18** The witness verifier rejects, with distinct diagnostics, a witness
  record whose delta is zero, negative, or below the floor; whose ordinal or
  UUID does not correlate; or which is missing any required field. Fixture-
  driven, so these arms run on hosts with no GPU.
- **AC80-19** The x86_64 lane's evidence strength does not drop. In 80.5 that
  means **strictly unchanged**: `seal_gpu_observation` in
  `scripts/release/cuda-preflight.sh` is not edited, its
  `nvidia-smi --query-compute-apps` PID correlation and the 11-key
  `fathomdb.cuda-device-observation/v1` record are untouched, and
  `test-cuda-preflight-witness` stays green with its committed fixtures
  unmodified. **Corrected during 80.5 commissioning:** an earlier draft of this
  criterion required x86_64 to gain the allocation evidence *within 80.5*,
  which is not achievable — the x86_64 witness is produced inside the installed
  wheel/npm process by `gpu-python-smoke.py` / `gpu-napi-smoke.mjs`, which can
  only call the public SDK, and D-80.5-4 rules that 80.5 adds no SDK surface.
  Sourcing it from a sibling process instead would be exactly the
  not-the-artifact weakness this slice forbids for Tegra. The x86_64
  strengthening therefore lands in **80.6.5**, on the x86_64 CUDA runner, after
  80.6 lands the `OpenReport` plumbing that makes it reachable from the artifact
  itself; it is asserted there (AC80-22).
- **AC80-20** On a host with no visible CUDA device, the witness suite SKIPs
  explicitly, naming the reason, and reports neither a pass nor a failure
  (R80-3, R80-12).
- **AC80-21** On the real Jetson Orin, the CUDA-compiled Tegra artifact with
  `FATHOMDB_EMBED_DEVICE` **unset** resolves to `cuda:0` — `auto`'s documented
  default-on-CUDA-capable-artifacts behavior (R80-11) — and completes
  open/write/search/close/exit cleanly. This is the criterion AC80-7 used to
  contradict; it is stated as its own positive assertion so an implementer
  cannot satisfy AC80-7 by regressing `auto` to CPU on Tegra. Together
  AC80-6/AC80-7/AC80-21 pin all three policies: forced `cuda:0`, forced `cpu`,
  and default `auto`.
- **AC80-22** (**80.6.5**, on the x86_64 CUDA runner) Once the allocation
  witness is reachable from the installed artifact's own process (80.6), the
  merged verifier requires the allocation evidence **in addition to**, never
  instead of, the PID/UUID evidence the x86_64 lane already requires — so its
  evidence strength strictly increases. Proven by a real
  `scripts/release/cuda-preflight.sh` run on that runner, not by fixtures alone:
  the Jetson can make these fixtures pass without ever exercising the lane, so a
  fixture-only result is explicitly not acceptance here. This is the half of
  AC80-19 that 80.5 cannot reach; it is asserted where it becomes achievable,
  on the hardware that can actually demonstrate it.
- **AC80-23** The default-embedder loader never leaves an unusable cache entry
  behind. On a host where the Hugging Face hub cache and the FathomDB cache
  share a filesystem, materializing a pinned asset from the hub yields a
  **readable regular file** whose SHA-256 matches the pin — never a dangling
  symlink — and a fixture reproducing the hub's relative-symlink layout fails
  before the fix and passes after (§ 7 80.5, "Folded in"). A cache already
  poisoned by the shipped loader self-heals on the next load rather than
  failing forever.
- **AC80-24** The hub-materialization path publishes atomically (R80-15). Two
  arms, both fixture-driven so they run on any host:
  1. **No in-place write of the published name.** The final path is only ever
     created by `fs::rename` from a temporary the same process created; a test
     observing the destination directory across a materialization sees the
     final name appear complete or not at all, never truncated.
  2. **Owner-scoped cleanup.** A materialization that fails verification removes
     **only its own temporary**. A pre-existing valid entry at the final path
     survives a concurrent failing materialization — the specific regression
     this criterion exists to prevent, where one process's failed verify
     deleted a good entry another process had just published.

  The concurrency hazard is real but narrow: the hub probe is reachable only on
  a cold or stale cache (once warm, the fast path short-circuits before it), so
  the exposure is concurrent cold starts — a fresh container fleet, a CI matrix,
  a cleared cache, a multi-process server booting. It is nonetheless a
  correctness bug, and the module already owns the fix pattern one function
  below.
- **AC80-25** (80.6) The Tegra artifact and the generic AArch64 artifact are
  proven **not co-installable into one environment**. Both ship the same
  top-level `fathomdb/` import package under different distribution names
  (`src/python/pyproject.toml`: `module-name = "fathomdb._fathomdb"`,
  `python-source = "."`), so installing both leaves whichever landed last
  silently shadowing the other. **Enforcement is a runtime check, not
  metadata** — corrected at commissioning after a design review established
  that no PyPI/pip mechanism can deliver it: PEP 621's `[project]` table, which
  maturin builds from here, has no conflicts field, and pip does not act on
  `Provides-Dist`/`Obsoletes-Dist` even where a backend can emit them. The
  criterion is therefore: `fathomdb/__init__.py` inspects installed
  distributions at import time and **raises** when two of them claim the
  `fathomdb` top-level package; a test proves the collision is detected rather
  than silently resolved; any metadata declaration is advisory documentation
  only; and no install guidance § 7 80.7 emits can leave a user holding both.

  **Measured at implementation — `importlib.metadata` is the wrong tool here,
  on both axes.** Importing it costs **48 ms of a 91 ms `import fathomdb`** (it
  drags in `email` and `zipfile`), and `packages_distributions()` returns
  `None` for `fathomdb` under an editable maturin install — this repo's own
  `.venv` — because the RECORD holds only `fathomdb.pth`. So the "general"
  approach is both 50–600× slower *and blind to one side of the collision it is
  meant to detect*. The landed guard is an `os`/`sys`-only `sys.path`
  `.dist-info` name scan: **0.42 ms** at 18 distributions, **0.87 ms** at 318,
  a net **+0.7–1.0 ms** (~1%) on import. Any future revision must keep both
  properties — cheap, and able to see editable installs.

  **Re-scoped after D-80.6-3 was revised.** This criterion was written when the
  Tegra build was to carry a distinct distribution name. It no longer does — the
  name stays `fathomdb`, distinguished by a `+tegra` local version when a
  first-party index is authorized — so pip will never install two `fathomdb`
  distributions and **this guard should never fire in the shipped
  configuration**. It is retained
  as landed, because it is ~1% of import cost and because D-1's source-build path
  lets a user hand-build a locally-named sibling distribution, which is exactly
  the case it catches. Its status is a tripwire for a configuration this design
  no longer produces. Two consequences for future readers: do not delete it on
  the grounds that it is unreachable, and **do not cite it as the reason the
  naming decision is safe** — that role now belongs to AC80-27.
- **AC80-26** (80.6) The glibc floor is asserted per artifact family: **2.35 for
  Tegra, 2.28 for every existing family**, with the Tegra floor *declared* in
  `scripts/release/glibc-floor-contract.sh` rather than exempted from the gate.
  A fixture asserting the wrong floor for **either** family fails.
  `docs/compatibility/index.md` states both measured floors, since AC80-9 now
  covers two families rather than one.

  **The doc-truth gate must be restructured, not merely re-pointed.**
  `scripts/check-glibc-floor-doc-truth.sh:38` reads
  `grep -m1 -oE 'Measured glibc floor: [0-9]+\.[0-9]+'` — **first match only** —
  and compares it against a single `$GLIBC_FLOOR`. The moment the doc carries
  two claims, a wrong Tegra floor passes silently, which is exactly the drift
  AC80-9 exists to prevent. The claims must be per-family *markered* and each
  checked, and a fixture must prove a wrong **second** claim fails, not only a
  wrong first one.
- **AC80-27** (**80.7**, **relocated to the Python package** — see D-80.7-5) the
  **displaced-build** case is detected: a confirmed classic Tegra iGPU (Tier 1
  true and Tier 2 `nvgpu` present) running a `fathomdb` distribution that is
  **not** the Tegra build.
  A named, typed outcome distinct from both `cuda_incompatible` (wrong
  architecture) and the healthy Tegra case, naming the repair path. This is the
  acceptance obligation D-80.6-3 incurred when it chose one distribution name
  over two: the residual failure mode it accepted is acceptable **only because
  it is detected**, so shipping the naming decision without this check would
  leave the design's own justification unmet.

  **Corrected at 80.7 planning.** This criterion originally assigned the check
  to `doctor gpu` and told it to read "the installed distribution's build
  identity". A plan review established that is mis-layered on two counts, both
  verified: (a) `doctor gpu` ships in a **separately distributed Cargo binary**
  that has no reliable way to know *which* Python environment the user means —
  a box may have many venvs, and the CLI belongs to none of them; (b) the Tegra
  build **does not stamp `+tegra` at all** today (`build-python-cuda-tegra.sh`
  sets no local version; the measured artifact is
  `fathomdb-0.8.22-cp310-abi3-linux_aarch64.whl`), so there is currently no
  identity to read. The check therefore moves to the Python package, next to the
  AC80-25 guard in `src/python/fathomdb/_coinstall.py`, which already scans
  `.dist-info` at import and knows its own environment **by construction**.
  D-80.7-4 covers the missing version stamp, which is a prerequisite.

  Criteria: the check reads the **`+tegra` local version segment**, **not** the
  presence of CUDA symbols — a generic build on a Tegra host may expose those
  and still be wrong. A fixture proves the Tegra-host/generic-build combination
  is reported rather than passed. A fixture proves a non-Tegra host with a
  generic build is **not** flagged. Any repair guidance obeys D-80.7-6 (no
  fabricated index URL). Distinct from AC80-25 — one detects a corrupted
  environment that should no longer be producible, the other a wrong-but-intact
  environment that is expected in normal use; neither implementation may be
  claimed as covering the other, even though they now live in the same module.

  **It must use the FULL two-tier probe, not Tier 1 alone (design review, and
  this is a correctness bug not a nicety).** Tier 1 is true on **Jetson Thor**,
  which is Tegra-family *and* SBSA-capable. A Thor user running the generic
  build is running the **correct** build; flagging them would be a false
  positive that tells a correctly-configured user to install something
  unloadable. Only a **confirmed classic Tegra iGPU** — Tier 1 true **and**
  Tier 2's `nvgpu` present — may raise this. Tier 2 indeterminate
  (`nvidia-smi` missing, timeout, non-zero exit) must **not** flag: fail closed
  toward silence, since a false accusation here is worse than a missed one.
  AC80-11's Thor fixture applies to this check too.

  **The Python-visible outcome is a named, default-visible warning — not an
  import failure.** A displaced build is **functional**; it just is not
  GPU-accelerated. Raising `ImportError` (what AC80-25 correctly does for a
  *corrupted* environment) would turn a working install into a dead one over a
  performance problem. So: `warnings.warn` with a dedicated
  `FathomDbPlatformWarning` subclass of **`UserWarning`**.

  **`UserWarning` is load-bearing, not arbitrary.** `DeprecationWarning` and
  `ImportWarning` are **filtered out by default** outside `__main__`. A warning
  nobody sees would not satisfy D-80.6-3's condition that the displacement is
  *detected* — the entire basis on which the naming decision was accepted. A
  test must assert the warning is emitted **under default filters**, not merely
  that it can be emitted under `catch_warnings(always)`.

  Note `scripts/check-glibc-floor.sh` already accepts an arbitrary
  `--floor X.Y` and needs no change; only `glibc-floor-contract.sh` and the call
  sites choosing which floor to pass gain new logic.

### 80.5 — Tegra-portable GPU witness

The PID-in-`nvidia-smi` witness is unavailable on Tegra (§ 2.5) and must be
replaced by something device-truthful on both discrete and integrated GPUs.
Proposed primary witness, in the process under test:

1. Assert the resolved device is `Device::Cuda(N)` — not a silent CPU fallback.
   (**Corrected at 80.5 commissioning:** this sentence originally said
   "`resolve_device()` already warns loudly on fallback; the witness must turn
   that warning into a hard signal." That is stale pre-Slice-70 language — no
   such warning call site exists any more. Slice 70 replaced the loud-stderr
   fallback with typed resolution: CPU fallback is a `DeviceResolutionReason`
   value on `DeviceResolution`, and forced `cuda:N` cannot fall back at all
   (`EmbedDevicePolicy::Cuda` yields `selected_resolution` or
   `Err(ForcedCudaUnavailable)`). The witness therefore inspects the typed
   resolution, not a log line.)
2. Assert a **nonzero GPU allocation delta** across model load, measured through
   the CUDA API in-process, so the proof does not depend on an external
   reporting tool.

`tegrastats` GR3D utilization sampling is admitted as corroboration only, never
as the sole witness. The existing x86_64 PID witness is **retained** for
discrete GPUs — this sub-slice adds a second mechanism, it does not remove the
first, and the x86_64 lane's evidence strength must not drop.

#### Commissioning detail (added before implementation)

The four paragraphs above state the *intent* correctly but are not
implementable as written: they name no measurement primitive, no failure
semantics, no place for the code to live, and no consumer. § 2.7 measured what
was missing on real hardware. This subsection is the resulting build order; it
narrows the section above, and does not reopen it.

**D-80.5-1 — the primitive, and its ordering invariant.** The measurement is
`candle_core::cuda::cudarc::driver::result::mem_get_info() -> (free, total)`
(the pinned Candle fork re-exports `cudarc` 0.19.7; `candle_bge.rs` already
reaches the driver API by this exact path for UUID and compute-capability
queries, so this adds no dependency). Because § 2.7 measured that the call is
`CUDA_ERROR_INVALID_CONTEXT` with no current context, the witness's sample
order is a contract, not a convention:

1. construct the Candle CUDA device (this creates the context),
2. assert the ordinal Candle **actually retained** matches the requested one —
   reusing the `device.location()` check `new_from_local_asset_on_device_attested`
   already performs, rather than writing a second one,
3. sample free/total — the **before**,
4. load the model,
5. sample free/total — the **after**,
6. run one real forward pass and record its vector dimension.

Step 6 exists because steps 3–5 alone prove only that *bytes were claimed*.
The claim this slice must support is that the **model computed on the device**,
so the witness embeds and records the result's dimension; a witness that
allocated but never computed is not a witness.

**D-80.5-2 — a floor, not "nonzero".** The section above says "nonzero
allocation delta". On an integrated GPU that is too weak to be safe:
`cuMemGetInfo` on Tegra reports **system-wide unified memory** (§ 2.7,
`total = 65_879_896_064`), so an unrelated process allocating one page during
the load window would satisfy "nonzero" without the embedder having touched the
GPU at all. The witness therefore asserts `delta_bytes >= delta_floor_bytes`,
where the floor is a declared constant derived from the real device-resident
size of the pinned BGE-small weights, chosen far above the measured idle jitter
(0 bytes over five samples) and comfortably below the true model footprint.
Concretely, the pinned `model.safetensors` is **133_466_304 bytes** (measured
from the warmed cache on this host), and a real `cuda:0` load of it took 14.44 s
here, so a floor on the order of 64 MiB sits an order of magnitude above the
noise and roughly half the true footprint — the implementer picks and justifies
the exact constant, but not by reasoning from an estimate of the model size. The
floor is recorded in the witness record so the verdict is re-derivable
(R80-13), and both the floor and the raw samples are retained.

**D-80.5-3 — the control allocation is a PRECONDITION, not corroboration
(revised after measurement).** This decision originally called for "one control
allocation of a known size" to confirm the counter is live — treating it as
corroboration alongside the delta. § 2.7's corrected measurement shows that is
too weak to work at all: Tegra's nvgpu/nvmap page pool absorbs allocations, so
on any host that has run a GPU workload since boot the model load charges
single-digit megabytes and the floor assertion fails closed on every run.

The control step is therefore **load-bearing and must precede the load**: it
allocates and **holds** large blocks until one of them is charged to the counter
*in full* — proving both that the counter is live and that the pool is drained —
and only then is the model loaded, so the load must draw fresh pages. Measured
on this host, that turns a masked 6_189_056-byte reading into 141–144 MB across
four runs with 0.4% spread.

Two properties this must preserve, and one risk it introduces:

- The design's original assertion is *not* weakened: the counter must still move
  by at least the requested size for the decisive control block.
- The blocks must be held, not allocated-and-freed. Allocating and freeing
  *warms* the pool and makes the subsequent masking worse — the exact inversion
  that made this hard to see.
- **Risk:** this depends on nvmap page-pool behavior that is undocumented and
  could change across JetPack/L4T versions. It is pinned by measurement on
  L4T R36.5.2, and a future JetPack that changes pool policy would show up as
  the witness failing closed — never as a false pass, which is the correct
  direction to fail (R80-12).

The counter is still system-wide on an iGPU, and the earlier `mem_get_info`
critique (§ 2.7's closing paragraph) is still on the record. Confounders are not
hidden: the raw samples and the control-block numbers are retained, and the
status record names the shared-counter caveat explicitly, exactly as Slice 72
retained its unrelated-compute-PID confounder rather than filtering it out.

The floor plus the control allocation narrow the window but do not close it, so
the precondition is stated rather than assumed: **the witness run must be the
sole GPU consumer on the device.** A concurrent unrelated allocation could push
the delta over the floor with the embedder still on CPU (false pass), or claim
memory that masks the model's own delta (false fail). Both directions are real
and neither is detectable from the delta alone. Operationally that means a
single-tenant run, which is what the Jetson evidence run and the self-hosted
runner already are. If a future multi-tenant scenario arises, the outcome is a
**named failure**, not a softened threshold: a delta that does not match the
control allocation's own movement is unattributable, and R80-12 makes
unattributable a failure. The status record states the precondition alongside
the numbers so a later reader can judge the evidence rather than inherit a
silent assumption.

**Folded in at HITL request — the HF-hub materialization defect (AC80-23).**
Found while producing 80.5's real-hardware evidence, and load-bearing for it:
`loader.rs::materialize_from_hf_hub` does `fs::hard_link(src, dst)`, and Linux
`link()` does not dereference symlinks. The Hugging Face hub stores
`snapshots/<rev>/<file>` as a **relative** symlink `../../blobs/<hash>`, valid
only inside the hub tree. Hard-linking it into
`~/.cache/fathomdb/embedders/<id>/` copies the *link*, whose `../../blobs/` now
resolves to a `blobs/` directory that does not exist under the FathomDB cache —
so the loader poisons its own cache with a dangling symlink and then fails
`CacheIoError … NotFound`. The bad link is created once; every later run then
fails afresh, because `file_matches_sha`'s `is_file()` correctly reports `false`
for it, the hub probe runs again, `fs::hard_link` now hits `EEXIST`, and the
`fs::copy` fallback fails `ENOENT` opening the dangling target. The precise
defect is that **success is declared on link creation, not on read-verified
content**: `load_with_config_internal` records a `DefaultEmbedderCacheHit` and
moves on without ever confirming the destination is readable.

Measured on this host: link count `2` on the symlink inode, proving the symlink
itself was linked rather than its target. **It fires only when the two caches
share a filesystem** — true on essentially every developer and end-user machine,
and false in the containerized CUDA preflight, where the read-only bind mount
makes `fs::hard_link` fail cross-device and the `fs::copy` fallback dereferences
correctly. That asymmetry is why CI has never seen it.

Fix: materialize through the symlink's target, not the link — resolve `src`
before linking (or fall back to `fs::copy`, which already dereferences), and
verify the destination is a readable regular file matching the pinned SHA
before recording a cache hit. RED first, with a fixture that reproduces the
hub's relative-symlink layout on one filesystem (AC80-23).

**Second defect on the same path, folded in after the first fix was reviewed
(R80-15 / AC80-24).** The hub probe runs at step 2 of
`load_with_config_internal`'s per-file loop, **outside** the `<cache_dir>/.lock`
that `fetch_under_lock` takes at step 3 — so unlike the download path, it
publishes straight to the final cache path with no atomicity. Two concurrent
cold starts therefore race: the first hard-links the entry into place; the
second gets `EEXIST`, falls back to `fs::copy`, which opens the destination
`O_TRUNC` and rewrites it; and the first, meanwhile, hashes a **torn** file,
fails verification, and deletes an entry it does not own — failing both
processes on data that was never wrong. Adding read-verification (above) is what
turned a previously harmless torn read into a destructive delete, so the two
fixes must land together.

The remedy is the module's own established pattern, not a new mechanism:
materialize into a privately-named temporary, verify it, then `fs::rename` it
into place and `fsync` the parent directory — exactly what `fetch_under_lock`
already does with `.partial` (design §5/§6). `rename(2)` within a filesystem is
atomic, so a concurrent reader sees the complete old entry or the complete new
one and never a partial write; failure cleanup becomes owner-scoped, removing
only the temporary; and because the content is pin-addressed, a last-writer-wins
rename replaces a byte-identical file, which is why this path needs no lock once
it publishes by rename. Hard-linking into the temporary first preserves the
inode-sharing that keeps the 133 MB entry free of extra disk cost.

**Independently researched against normative sources before acceptance.** Three
claims this design rests on were verified against The Open Group POSIX text,
`man7` Linux man pages, Rust `std` documentation and Microsoft Learn, rather
than taken on the implementation's word:

- **`rename()` replaces a destination that is a symlink — including a dangling
  one — removing the link itself rather than following it.** POSIX: "If the
  *new* argument points to a pathname of a symbolic link, the symbolic link
  shall be removed"; and "if either the *old* or *new* argument names a symbolic
  link, `rename()` shall operate on the symbolic link itself, and shall not
  resolve the last component." The AC80-23 poisoned-cache self-heal is therefore
  guaranteed by the standard, and the explicit unlink that an earlier draft
  carried is **correctly removed**: for every destination type where `rename`
  succeeds the unlink is redundant, and for every type where `rename` fails
  (`EISDIR`, `EPERM`, `EBUSY`) `remove_file` fails identically or is unsafe.
- **A same-inode rename is a documented no-op**, which is the *common* case
  here because every racer hard-links the same hub blob. POSIX: "If the *old*
  argument and the *new* argument resolve to either the same existing directory
  entry or different directory entries for the same existing file, `rename()`
  shall return successfully and perform no other action." So a successful
  publish does not necessarily consume the temporary, and temp cleanup must run
  unconditionally rather than only on the failure path. Removing the temporary
  afterwards cannot harm the published entry: `unlink(2)` drops a directory
  entry, and the file survives while any link remains.
- **This is the industry-consensus pattern, not a local invention.** Git's
  `finalize_object_file_flags`, ccache, the Go module cache, and the Nix store
  all publish into content-addressed caches by temp-then-rename; Git in
  particular, on `EEXIST`, unlinks only its own temporary and never the
  destination. `huggingface_hub` — the very cache this path reads from —
  independently arrived at the identical design, writing to a process-unique
  `.incomplete` temporary and renaming it into place, with its own lock
  documented as best-effort precisely because correctness rests on the atomic
  rename rather than on mutual exclusion.

The one materially adverse finding from that research is recorded as R80-15's
first corollary: the temporary's name must be obtained by *exclusive creation*,
because a PID-derived name collides in exactly the container-shared-cache
topology this repository's own CUDA preflight creates.

**D-80.5-6 — test shape.** Verifier and typed-failure arms are fixture-driven
and run on every host including CI with no GPU. The real-hardware arm is
separate and SKIPs explicitly, naming the reason, when no CUDA device is
visible (AC80-20) — never a silent pass. `tegrastats` corroboration, if
collected at all, is recorded and never gates.

**Deliberately not in 80.5.** Plumbing the delta through `OpenReport` into the
Python/N-API/TypeScript surfaces so the *installed wheel's own process* carries
it. That is a four-binding public-surface change; it belongs with 80.6's
artifact evidence run, where the artifact that would carry it actually exists,
and it is recorded there rather than being smuggled in here.

As with 80.5, the section above states intent correctly but is not
implementable: it names no build script, no contract values, no artifact name,
and no mechanism for the glibc exception it requires. The decisions below close

authorizes a `twine upload` or `npm publish`.

primary SDK surface and the one `cuda-preflight.sh` already proves most

**D-80.6-3 — the name (REVISED at 80.6 implementation, after ecosystem
research).** The distribution name stays **`fathomdb`**, unchanged. When the
staged publication gate authorizes a Tegra artifact, it is distinguished by a
**PEP 440 local version segment** — `0.8.23+tegra` — on a **first-party PEP 503

*Superseded ruling.* This decision previously read "the distribution is named
distinctly (e.g. a `-tegra`-suffixed distribution) while keeping the `fathomdb`
import package." Research into how the ecosystem actually solves this reversed
it, on three findings:

1. **The sibling-distribution shape is worse than this document credited.** It
   said two distributions sharing an import package are "not co-installable —
   installing both leaves whichever landed last shadowing the other, silently."
   That understates it. pip does not detect, warn, or error (pypa/pip#4625, open
   since 2017; the only proposed fix, pip#14249, warns *after* the overwrite).
   Both distributions remain listed as installed, and because the
   recording-installed-packages spec has **no concept of file ownership
   arbitration between distributions**, each `RECORD` claims the same paths — so
   a later `pip uninstall` of *either* one deletes files the survivor still
   needs, leaving it installed-but-gutted (pypa/pip#8509, the ansible/ansible-base
   split). The failure is not "the user gets the wrong build"; it is "pip's own
   bookkeeping is corrupted." That is a strictly worse outcome than the one this
   design was trying to avoid, and unlike the wrong-build failure it is not
   detectable at import time — the damage precedes the import.
2. **The rename is not free anyway.** Per D-1 above, our bare `linux_aarch64`
   artifact cannot be uploaded to PyPI under *any* name. So the rename buys no
   distribution channel it doesn't already have, while the separate index needs
   no `auditwheel` work at all.
3. **It is what NVIDIA and PyTorch actually do, for this exact reason.**
   NVIDIA's Jetson PyTorch ships as distribution **`torch`** — the plain PyPI
   name — versioned `2.5.0a0+…nv24.08`, tagged bare `linux_aarch64`, hosted at
   `developer.download.nvidia.com/compute/redist/jp/`. PyTorch's own docs now
   direct Jetson users at `--index-url https://pypi.jetson-ai-lab.io/jp6/cu126`,
   whose `torch`, `onnxruntime-gpu`, `vllm`, `xformers` etc. all carry canonical
   PyPI names, with JetPack and CUDA encoded in the **index path** rather than in
   the name or the tag. The `-gpu`/`-cuNN` suffix convention
   (`cupy-cuda12x`, `onnxruntime-gpu`, `paddlepaddle-gpu`) is real and common,
   but it is precisely the pattern PEP 817's Motivation section singles out as
   broken, and `tensorflow-gpu`'s retirement — which required the TF team to
   republish the name as a poison-pill stub that raises on install — shows a
   variant name is a name you own forever and must eventually kill.

**What this design accepts in exchange once publication is authorized.** Index
selection is not automatic, and the residual failure mode is real: a later
`pip install -U fathomdb` from PyPI can silently replace the Tegra build with
the generic one. This is observed in the wild on Jetson
(facebookresearch/xformers#1193, where NVIDIA's
`torch 2.5.0a0+…nv24.08` was displaced by PyPI's `2.5.1`, silently losing
memory-efficient attention). It is a **wrong-build** failure, which is
detectable and reportable, rather than a **corrupted-install** failure, which is
not — and detecting it is assigned to § 7 80.7 (D-80.7-1) rather than left
implicit.

If a future first-party index is authorized, `--extra-index-url` is *unsafe*
when printed naked: pip documents **no priority** between indexes, and a bare
`linux_aarch64` wheel is tag-compatible on Graviton too, so a non-Tegra aarch64
user who pasted the flag would receive the Tegra build. The future guidance is
therefore behind one declared index constant, emitted only after Tier-1/Tier-2
Tegra confirmation, and pins `==<version>+tegra` rather than floating. It must
not name an endpoint until one exists. Documenting the future uv form alongside
pip is preferred where possible, since `[[tool.uv.index]] explicit = true` plus
a `[tool.uv.sources]` pin restricts the index to `fathomdb` alone and
structurally prevents PyPI fallback. `--index-url` (full replacement) is
correct only if the index also mirrors the dependency closure, which PyTorch
does and this project does not; absent that, the future form is
`--extra-index-url` + detection-gating + an exact pin.

**Consequence for AC80-25.** The co-installation guard is *retained*, but it is
no longer the primary defense — under a single distribution name pip will never
install two `fathomdb` distributions, so in the shipped configuration the guard
should never fire. It stays because it is cheap (measured 0.42–0.87 ms, `os`/
`sys` only) and because the source-build path of D-1 lets a user hand-build a
locally-named sibling distribution, which is exactly the case it catches. Its
status changes from "the mechanism that makes the naming decision safe" to
"a tripwire for a configuration this design no longer produces." Do not delete
it on the grounds that it is unreachable; do not cite it as the reason the
naming decision is safe.

**Alternative kept on file, not adopted: the JAX plugin shape.** If PyPI
distribution ever becomes mandatory, the correct form is *not* a `-tegra`
sibling sharing `fathomdb/`, but a thin `fathomdb` facade over separately-named
distributions with **separately-named import packages** — the shape JAX ships as
`jax` + `jax-cuda12-plugin` + `jax-cuda12-pjrt`, which has no import-name
overlap anywhere in the chain and is therefore genuinely co-installable rather
than merely guarded. It is not adopted now because it is an architectural
refactor of the maturin layout (today `module-name = "fathomdb._fathomdb"` puts
the native module *inside* the import package), it adds an import indirection on
every call path, and it still carries the `auditwheel` prerequisite — all for a
publication step D-80.6-1 explicitly rules out of 0.8.23.

**Forward compatibility.** This is the shape PEP 817/825 wheel variants
eventually replace (§ 7 80.7). Keeping the name `fathomdb` is what makes that
transition free: a variant-labelled wheel is
`{dist}-{version}-…-{platform}-{variant label}.whl`, so **the distribution name
never changes** and the guided-install step simply disappears. Renaming now
would buy a second migration later. See D-80.7-2 for why that adoption cannot be
scheduled.

**D-80.6-4 — Tegra toolchain contract values, measured on this host.** 80.4

**D-80.6-6 — `OpenReport` plumbing: the full surface, named.** Inherited from
D-80.5-4/6 and the reason AC80-6's "in-process" clause is honest here. The
change set is one optional field carried from the Rust core to the SDK

optional field**; this is a witness, not a telemetry API, and § 12's non-goals
still bind.

**The witness is opt-in, and this narrowing is deliberate.** Implementation
surfaced that D-80.6-6 named no *trigger*, and the obvious reading — populate
whenever a CUDA embedder opens — is unacceptable: the 80.5 sequence performs a
**second model load** and holds **up to 16 × 1 GiB of control blocks** to drain
the Tegra page pool (D-80.5-3). Doing that on every CUDA open would change the
runtime contract § 12 forbids, and would make ordinary GPU use dramatically
worse to serve a release-evidence need. Population is therefore gated on an
explicit `FATHOMDB_GPU_ALLOCATION_WITNESS` opt-in; once opted in, `None` stops
being a legal outcome and the open fails with the witness's own typed reason,
preserving R80-12's fail-closed rule.

unset the field is `None` and the run proves nothing about GPU allocation — a
silent no-op that would look like a passing smoke. Whoever executes the evidence
run states the variable in the retained record.

### 80.6.5 — merge the witness schema, strengthen the x86_64 lane

**Split out of 80.6 by HITL ruling, on a hardware boundary.** 80.5 deliberately
introduced a standalone `fathomdb.tegra-gpu-allocation-witness/v1` record rather
than bumping the shared `fathomdb.cuda-device-observation/v1` (D-80.5-5), and
deferred the x86_64 strengthening (AC80-19 → AC80-22). 80.6 then lands the
`OpenReport` binding plumbing that makes an artifact's own process able to carry
the allocation witness. This sub-slice is what those two defer *to*: folding the
allocation evidence into the shared record so the **x86_64** lane requires it in
addition to — never instead of — the PID/UUID evidence it already requires.

**Why this is not part of 80.6.** 80.6 is a Jetson story end to end: the
artifact, the GPU, the witness, and the evidence are all on one aarch64 box.
This sub-slice cannot be verified there at all. `scripts/release/cuda-preflight.sh`
requires `docker run --gpus`, an `nvidia-smi` that reports compute-apps, and
`CUDA_MANYLINUX_PLATFORM='linux/amd64'` with the digest-pinned
`manylinux_2_28_x86_64` image; the three CUDA jobs in `release.yml` are all
`runs-on: [self-hosted, Linux, X64, gpu, cuda-12]`. The Jetson is `aarch64` with
an `arm64` Docker daemon and cannot run any of it.

The fixtures *could* be edited on the Jetson and would go green there, which is
exactly the trap this split exists to avoid: a fixture-only pass would look like
evidence while never having exercised the lane it claims to strengthen. **The
honest gate is a real `cuda-preflight.sh` run on the x86_64 CUDA runner**, and
this sub-slice is scheduled to be worked there directly (HITL: over SSH/tmux to
that box), not simulated from here.

**Scope — the four consumers must change together.** All were left untouched by
80.5 (AC80-19) precisely so this step could change them in one coherent edit:

- `scripts/release/verify-cuda-preflight-witness.py` — the `require_exact_keys`
  set (`:96`) and the UUID/PID correlation (`:335`, `:337-344`). Note the
  UUID comparison must adopt 80.5's normalization: § 2.7 measured that Tegra's
  `nvidia-smi` omits the `GPU-` prefix x86_64's carries, and a merged record
  must be correct on both.
- `scripts/tests/cuda_preflight_v2_fixture.py:112` and the two committed
  canonical fixtures under `scripts/tests/fixtures/cuda-preflight-v2/valid/`.
- `dev/design/0.8.23-slice-10-cuda-contract.md:206-213`'s 11-key statement.
  **Its PID sentence is mutation-tested** by
  `scripts/tests/test_slice70_cli_artifact_design.sh:74,134`, which rejects any
  edit weakening ``process_id` equals `nvidia_smi_compute_process_id``. That
  literal substring must survive verbatim; the Tegra branch is expressed
  alongside it, never by softening it.
- `scripts/check-cuda-release-contract.py:685`'s pinned failure-message
  fragment `"GPU {consumer} observation lacks PID correlation"`, which a
  conditional PID branch will reword.

**Shape of the merged record.** PID correlation becomes **required on discrete
GPUs and absent on Tegra**, with the allocation witness required in both cases.
That asymmetry is the whole point: x86_64 must satisfy PID correlation **and**
the allocation floor, so its evidence strictly increases (AC80-22), while Tegra
— which physically cannot produce a compute-apps PID (§ 2.5) — satisfies the
allocation floor and the in-process identity binding instead.

**A prerequisite found while building this sub-slice's transfer tooling.**
`scripts/release/cuda-preflight.sh` **cannot run without git**: it calls
`git -C "$REPO_ROOT" rev-parse HEAD` at `:104` (`repository_commit`) and `:544`
(`CANDIDATE_SHA`), and `CANDIDATE_SHA` feeds `build-input.json`, the witness
payload, and `verify-cuda-preflight-witness.py --candidate-sha` at `:737`. The
HITL-ruled workflow sends **no `.git`** to the remote — deliberately, so the
no-git rule is structural rather than a matter of discipline — so the script
dies at its first call there.

The fix belongs in the git-backed source, not in a shim that fabricates git
state on the remote: accept the SHA from an environment variable and fall back
to `git rev-parse`. An independent review confirmed this survives the contract
gate untouched — `scripts/check-cuda-release-contract.py:772` pins the literal
fragment `'--candidate-sha "$CANDIDATE_SHA"'` but **not** the assignment
statement — and that it is an enabler for AC80-22 rather than scope creep, since
AC80-22 requires a *real* preflight run on a machine that will not have the
repository's git history.

**Status: APPLIED.** Landed as `scripts/lib/cuda-candidate-sha.sh`
(`resolve_cuda_candidate_sha`), sourced by `cuda-preflight.sh` and called once,
early — before any Docker or model-cache work — so an invalid override aborts
before side effects. `cuda-preflight.sh` now contains **no `git` invocation at
all**: both former call sites read the single resolved value, which also
guarantees `repository_commit=` and the witness's `candidate_sha` can never
disagree. `REPO_ROOT` was already path-derived, not git-derived.

Both sites needed the treatment, not just `:544` — the `repository_commit=`
call ran unconditionally *before* it, so a `:544`-only fix would still have died
on a no-git remote. `FATHOMDB_CANDIDATE_SHA` is validated as 40-character
lowercase hex and **fails closed**: set-but-invalid is an error, never a silent
fall-through to `git`, because the value is stamped into a witness as a
provenance claim. Unset falls back to `git rev-parse` with behavior unchanged.

**Acceptance.** AC80-22, proven by a real preflight run on the x86_64 CUDA
runner producing a witness that carries both evidence classes and is accepted by
the merged verifier, plus fixture arms showing a witness missing *either* class
is rejected with a distinct diagnostic. `test-cuda-preflight-witness` and
`test-cuda-release-contract` stay green.

**Transfer tooling.** The send/run/return/review/clean scripts for this
sub-slice are drafted and independently reviewed (PASS_WITH_NOTES), but they
live in the orchestrator's scratchpad and are **not tracked in this repository
yet** — promoting them under `scripts/release/` is 80.6.5 work, and until that
happens nothing below is verifiable from the repo alone. The measurements are
recorded here so the promotion does not have to re-derive them. They prune
the 8.9 GiB worktree to 2,758 files / 67.7 MiB, never send `.git`, resolve the
target GPU by UUID and fail closed unless it is NVML index 0 — measured: the
intended RTX 3090 `GPU-5f9cfc90-…` is index 0 and the Quadro K620 display card
is index 2, so the current selectors are correct and the assertion is a
reordering tripwire, not a live fix. Note `CUDA_VISIBLE_DEVICES` alone is
**insufficient** for this lane: it pins host-native CUDA processes but does not
redirect `docker run --gpus '"device=0"'` (resolved by the NVIDIA container
runtime through host NVML) nor host-side `nvidia-smi --id=0`, which are the two
selectors `cuda-preflight.sh` actually uses. If the intended GPU ever stops
being index 0, the correct fix is to make the preflight select by UUID — in
scope for a sub-slice about correct-device evidence.

### 80.7 — extend `doctor gpu` for Tegra/SBSA, guided install

This is new UX on an existing diagnostic, not new plumbing: `fathomdb doctor gpu`
already exists (Slice 70, `dev/interfaces/cli.md:65`), already resolves a typed
CPU/GPU decision, and its classifier already treats a wrong-architecture CUDA
binary as `cuda_incompatible` rather than a crash (§ 2.5). This sub-slice adds
the detection layer that tells the *user*, not just the process, what to do.

**Detection (R80-8) — two-tier, per the independently-researched cross-language
design in `~/projects/memex/dev/notes/2026-08-18-tegra-sbsa-platform-detection-design.md`.**
That note reaches the same core signal this document already cited
(`nvidia-smi` GPU-name `nvgpu` substring, same jetson-containers/Thor
source[^2]) but structures it more robustly, with reference implementations in
exactly this repo's three language surfaces (Python, Rust, TypeScript). Adopt
its two-tier structure rather than a single nvidia-smi check:

1. **Tier 1 — Tegra-family, no subprocess required.**
   `/proc/device-tree/compatible` contains `nvidia,tegra`, **or**
   `/etc/nv_tegra_release` exists (`R36 (release), REVISION: 5.2` on this host
   — this file also supplies the L4T revision for the glibc-floor message
   decision 3 requires). Either signal alone is sufficient; both are cheap
   filesystem reads, no `nvidia-smi` dependency, no `uname` involved.
2. **Tier 2 — resolve Thor's ambiguity.**
   - Tier 1 false → check `/sys/firmware/acpi/tables` exists. Present means
     SBSA-capable non-Tegra hardware (Grace, Graviton, Ampere Altra).
   - Tier 1 true → shell out to
     `nvidia-smi --query-gpu=name --format=csv,noheader` and check for the
     `nvgpu` substring. Present (`"Orin (nvgpu)"` on this host) → classic
     Tegra iGPU, non-SBSA. Absent (`"NVIDIA Thor"`) → Tegra-family hardware
     that is nonetheless SBSA-capable.

Do not use `uname`-reported architecture strings as the sole Tegra signal —
this is why Tier 2 exists at all. `jetson-containers` shipped exactly a
`uname`-only check and broke it when Jetson Thor began reporting `tegra` in
`uname -a` despite being SBSA-capable.[^2] AC80-11 encodes the Thor case as a
named negative test specifically so this mistake cannot recur here.

Two things from the memex note's own risk section carry over as implementation
constraints, not just references:

- **A reviewer there caught a real bug worth not repeating**: an early Rust
  sketch didn't check the `nvidia-smi` subprocess's exit status, so a failing
  call with empty stdout was misread as SBSA-affirmative instead of failing
  closed. Our implementation must check exit status before interpreting
  stdout.
- **The `nvgpu` substring is an unofficial, empirically-observed signal** — no
  documented NVIDIA API confirms it, and the memex note explicitly flags it
  could change across driver/JetPack versions without notice. Tier 1 does not
  depend on it (filesystem-only), which is why Tier 1 must be tried first and
  is the harder invariant to rely on. For a missing, timed-out, or non-zero
  `nvidia-smi`, `doctor platform` degrades to its named `probe_failed`-shaped
  outcome, while `doctor gpu` proceeds to its normal CUDA classification rather
  than treating an ancillary probe as provider failure. Invoke it by an absolute
  path, with a bounded timeout — the memex note flags bare-name PATH lookup and
  no timeout as acceptable only for a design sketch, not production.

The Rust implementation owns the CLI diagnostics. Python has no independent
diagnostic surface, but AC80-27 requires its private import guard to repeat the
same full two-tier probe when it must decide whether to warn about the build in
its own environment: the ordered absolute candidates, 2000 ms timeout, and
successful-exit-before-stdout rule all apply. TypeScript has no such work in
this slice.

*Corrected at 80.6 implementation.* This previously read "confirmed: no `gpu`
symbol in `src/python/fathomdb/__init__.py`, `types.py`, or
`src/ts/src/index.ts`", which 80.6 part B made false: it added
`GpuAllocationWitness` / `embedderGpuAllocationWitness` to the Python and
TypeScript surfaces. The *substantive* claim is unchanged — that is a **witness
record hanging off `OpenReport`**, reporting what one engine open observed and
only when `FATHOMDB_GPU_ALLOCATION_WITNESS` is set, not a diagnostic entry
point. 80.7 must not mistake it for an SDK-side `doctor gpu`, and must not route
detection through it.

**SBSA refusal (R80-9, ruled continue-on-CPU).** On detected SBSA hardware
under `auto` or an unset policy, `doctor gpu` reports `cuda_incompatible` with
`reason: "arm64_sbsa_unsupported"`, exits `0`, and continues on the typed CPU
path. A forced `cuda:N` request remains a refusal with exit `65`; explicit
`cpu` remains `selected_cpu_no_cuda` with a null reason and no CUDA activity.
It never attempts to load a Tegra-linked binary on any of these arms.

**Guided install, not silent fetch (R80-10, ruled).** `doctor gpu --help` names
the documented source-build and install procedure while frozen normal and JSON
diagnostics remain unchanged. It does not fetch or build anything itself.
This was a deliberate rejection of the "fully automatic" alternative
(`node-llama-cpp`'s postinstall pattern: detect incompatibility, silently
download and build from source, which "can take up to an hour" and fails
opaquely without build tools present) — an hour-long silent network build
during `npm install`/`pip install` is the kind of surface this repo's
digest-pinned, fail-closed release discipline exists to avoid. The end user
still never has to know *which* ARM64 CUDA flavor exists; they're told the one
command that gets them the right one.

Structure the artifact/package metadata so this guided step is a stepping
stone, not a dead end: keep the distribution name `fathomdb` (D-80.6-3) so the
Tegra artifact can become a PEP 817/825 wheel variant with a null-variant CPU
fallback once that mechanism ships, at which point the guidance step disappears
on its own rather than requiring a second migration.

**No first-party index exists in 0.8.23.** The CLI and public docs therefore
name the source-build procedure and the build wrapper that prints the exact
`pip install <built-wheel>` command it can truthfully know. The future
index-qualified form remains behind one declared constant, uses
`--extra-index-url` and an exact `==<version>+tegra` pin, and is emitted only
after Tier-1/Tier-2 confirmation. A bare `linux_aarch64` Tegra wheel is
tag-compatible on Graviton and other generic aarch64 hosts, so detection-gating
is what makes future index guidance safe to print at all.

**D-80.7-1 — detect the displaced-build case (new; consequence of D-80.6-3).**
Because the Tegra build and the generic build share the distribution name
`fathomdb`, a later `pip install -U fathomdb` resolving against PyPI silently
replaces the Tegra build with the generic one. D-80.6-3 accepts this as the
residual cost of the naming decision **on the explicit condition that it is
detected rather than silent** — which makes detection this sub-slice's
responsibility, not an optional extra. The Python package compares its own
installed distribution identity against a confirmed classic-Tegra host and
emits a named `FathomDbPlatformWarning(UserWarning)` when the build is generic.
The local version segment (`+tegra`) is the natural carrier for that identity;
the check must not infer it from the presence of CUDA symbols, since a generic
build on a Tegra host may still expose them. Thor and Tier-2-indeterminate
results do not warn.
Precedent for the failure being real rather than theoretical:
facebookresearch/xformers#1193. Note this is a *different* check from AC80-25's
co-installation guard, which under the revised naming decision should never fire
(D-80.6-3); do not implement one and claim it covers the other.

**D-80.7-2 — PEP 817 is a watch item, not a mechanism (ruled).** No part of
this design may schedule work against wheel variants. Verified status: PEP 817
is **Draft** and has been *split*, with PEP 825 (also Draft, PEP-Delegate Paul
Moore) covering only the wheel file format; the half this design would actually
need — **how a system's capabilities are detected, i.e. the provider-plugin
mechanism** — is explicitly deferred to future PEPs that are not yet written.
pip has **zero support in any released version** through 26.2.1; the only
working client is an experimental uv side-build distributed outside PyPI. Most
decisively for us, **there is no Tegra-aware provider**: WheelNext's
`nvidia-variant-provider` exposes only `cuda_version_lower_bound`,
`cuda_version_upper_bound`, and `sm_arch`, with no ARM/Jetson/Tegra/SBSA
handling, and it is not published to PyPI. `sm_arch` alone would not
disambiguate our case cleanly either — it describes compute capability, not
which CUDA runtime flavor the binary was linked against. Treat PEP 817/825 as a
reason to keep the name stable (so adoption is free later) and as nothing else.

**D-80.7-3 — npm is permanently out of scope for Tegra (ruled; strengthens
D-80.6-2).** D-80.6-2 scoped npm out of 80.6 as a slice-scope decision. Research
makes it a permanent one: **npm cannot express the distinction at all.** Its
complete matching key is `(process.platform, process.arch, libc)`, and
`process.arch` has no sub-architecture, SoC, or GPU axis — a Jetson Orin and an
AWS Graviton both resolve as `linux`/`arm64`/`glibc`, so an
`optionalDependencies` fan-out selects identically on both. napi-rs inherits
this directly: `aarch64-unknown-linux-gnu` is a single triple covering both, and
Rust itself has no Tegra target to derive one from. The ecosystem's own answer
is to *not distinguish* — the one arm64+CUDA npm package found
(`@sweet-search/native-linux-arm64-gnu-cuda`) explicitly buckets "Jetson Orin,
Grace Hopper, and arm64 server GPUs" together, and the sole Jetson-specific npm
precedent (`@roboflow/tfjs-jetson`) has been unmaintained since 2021. The `libc`
field is the cautionary scale marker: one glibc/musl axis took three years to
propagate from Yarn to documented npm support and still carries an open
lockfile-correctness bug. If a future slice is forced to ship Tegra on npm, the
only safe shape is a distinctly-named package that the main package **does not**
list in `optionalDependencies` — so npm can never auto-select it — with
`doctor gpu` printing the install command post-detection and the loader
`dlopen`ing it if present. Explicitly rejected: `node-llama-cpp`'s
install-both-and-probe pattern, which is sound on x64 (where both binaries are
loadable) but not here, since a Tegra-linked binary on Graviton cannot load at
all.

#### Commissioning detail (added at 80.7 planning)

An implementation plan review found 80.7 not yet internally consistent and
stopped rather than guessing. It was right to stop; four of its findings were
genuine and are ruled below, plus the two under-specified points it named. See
also the corrections folded into AC80-10, AC80-12, and AC80-27.

**D-80.7-4 — the Tegra build must stamp `+tegra`; it does not today (ruled).**
Verified: `scripts/release/build-python-cuda-tegra.sh` sets no local version,
and the measured artifact is `fathomdb-0.8.22-cp310-abi3-linux_aarch64.whl`.
This is a **gap in the landed 80.6 work that only surfaced when 80.7 tried to
consume it**, not a new requirement. Without the stamp, D-80.6-3's naming
decision is not actually realized — the Tegra build is byte-distinct from the
generic one but carries **no identity distinguishing them** — and AC80-27 has
nothing to read.

Ruled: the Tegra build stamps the PEP 440 local version segment `+tegra`, and a
build-level assertion fails closed if the produced wheel lacks it. This is
small, is a prerequisite for AC80-27, and is **80.7's to land** since 80.6 is
closed — recorded here rather than reopening 80.6, so the provenance stays
honest. Note the local segment is legal precisely *because* we never upload to
PyPI (D-1, D-80.6-1); PyPI would reject it outright, which is consistent with
— not in tension with — the naming ruling.

**Stamping mechanism (normative).** The generic build keeps the checked-in
`[project].version` in `src/python/pyproject.toml` unchanged. The Tegra wrapper
reads that one validated PEP 440 base version, appends `+tegra`, and builds from
a temporary staging copy of `src/python`: its staged `pyproject.toml` has only
that version substituted and an absolute manifest path back to the checked-out
Rust crate. It must never rewrite the tracked `pyproject.toml`, Cargo manifest,
or Python package source. The staging directory is removed on success and
failure. This avoids relying on `maturin --config`, which is Cargo
configuration and cannot override PEP 621 metadata. After the build, the
wrapper must require exactly one wheel whose filename carries the derived local
version and inspect its `.dist-info/METADATA` to require the same
`Version: <base>+tegra`; either mismatch fails before the install command is
printed. Fixtures cover the derived filename and embedded metadata, the
fail-closed mismatch, and a generic build path that still emits only the base
version.

**D-80.7-5 — the displaced-build check belongs to the Python package, not the
CLI (ruled).** `doctor gpu` ships in a separately distributed Cargo binary. It
cannot reliably know *which* Python environment a user means: a host may carry
many venvs, and the CLI belongs to none of them. Any answer it gave would be a
guess dressed as a diagnostic. The Python package, by contrast, knows its own
environment **by construction**, and `src/python/fathomdb/_coinstall.py` already
scans `.dist-info` at import for AC80-25 at a measured ~1% of import cost.

Ruled: AC80-27 lands there; `doctor gpu` keeps only what a CLI can truthfully
answer — **host platform detection** (AC80-10/11/12/14). The two checks share a
module but stay separately named and separately tested (AC80-27's closing
clause).

**D-80.7-6 — no index URL may be fabricated (ruled).** There is no FathomDB
PEP 503 endpoint. None exists in the repo, and **none can exist in 0.8.23**,
because D-80.6-1 and § 11 item 8 hold publication behind a staged gate. An
"exact install command" naming an invented hostname would be a false statement
printed by a diagnostic — strictly worse than printing nothing, because users
would copy it.

Ruled: while no index is published, the guided step names **the source-build
path** — which D-1 already establishes as the supported route — and says
plainly that a published Tegra artifact does not yet exist. The index-qualified
form (`--extra-index-url <index>` + `==<version>+tegra`, detection-gated per
D-80.6-3) is implemented behind **a single declared constant**, so authorizing
publication becomes a one-line change plus a test-fixture flip, not a redesign.
R80-10 is satisfied either way: the command is guided, exact, and never a silent
fetch. **Do not invent a hostname to make a test pass.**

**D-80.7-7 — `nvidia-smi` resolution and timeout (ruled).** Never a bare `PATH`
lookup. But a **single hardcoded absolute path is also wrong**, and this is
measured, not theoretical: on this reference Jetson `nvidia-smi` resolves to
**`/usr/sbin/nvidia-smi`**, and `/usr/bin/nvidia-smi` **does not exist** — the
obvious hardcoding would fail on the very host the acceptance runs on.

Ruled: probe an ordered list of absolute candidates —
`/usr/bin/nvidia-smi`, `/usr/sbin/nvidia-smi`, `/usr/local/bin/nvidia-smi` —
taking the first that is executable; if none is, `doctor platform` returns the
typed `probe_failed`-shaped outcome of AC80-14, not an SBSA inference, while
`doctor gpu` proceeds to normal provider diagnosis. Timeout **2000 ms**:
measured cost on this host is ~130 ms, so this is ~15× headroom while still
bounding a hung driver. Check exit status **before** reading stdout (AC80-14).
Tier 2 runs only when Tier 1 is true, so a healthy generic aarch64 box never
pays for this at all.

**D-80.7-8 — Tier-1-false and ACPI-absent is a named class, not a default
(ruled).** The two-tier tree left a hole: Tier 1 false (no `nvidia,tegra`, no
`/etc/nv_tegra_release`) **and** `/sys/firmware/acpi/tables` absent. That is
neither Tegra nor confirmed-SBSA — a generic AArch64 host with no ACPI, which is
an ordinary configuration, not an error.

Ruled: it classifies as the named **`generic_aarch64`** platform class.
Consequences, all explicit: it is treated as **non-Tegra**, so no Tegra install
guidance is emitted (D-80.6-3's detection-gating requires affirmative Tegra
detection, and a bare `linux_aarch64` Tegra wheel would be unloadable here); it
is **not** reported as SBSA, since SBSA was never affirmed and AC80-12's refusal
message must not be shown on a guess; and `doctor gpu` behavior is otherwise
**unchanged from today**. It must be a named outcome that a fixture asserts —
never a silent fallthrough, which is the failure shape AC80-14 exists to
prevent.

#### Second review pass (BLOCK resolved)

A follow-up design review returned BLOCK on six further contract gaps. All six
were genuine — one of them a real error in D-80.7's own first pass — and are
ruled here. See also the corrections folded into AC80-12 and AC80-27.

**D-80.7-9 — `fathomdb.doctor.platform.v1` needs a transport: `doctor platform`
(ruled).** AC80-10 minted a record without saying how it reaches a user, and it
**cannot** be appended to `doctor gpu` v1 (that is the whole point of minting
it). Ruled: a new sibling subcommand **`fathomdb doctor platform [--json]`**,
emitting **only** the platform record — matching how Slice 71 gave
`fathomdb.doctor.reranker-gpu.v1` its own `doctor reranker-gpu` command rather
than widening an existing one.

Contract, in the house style (`dev/interfaces/cli.md` § `doctor-gpu`):

- **JSON keys in exact order:** `schema_version`, `platform_class`,
  `tegra_family`, `sbsa_capable`, `l4t_release`, `reason`. `schema_version` is
  `"fathomdb.doctor.platform.v1"`. `sbsa_capable`, `l4t_release`, and `reason`
  are always present and JSON `null` when indeterminate or absent. Exactly one
  trailing newline, canonical compact form.
- **`platform_class`** is exactly one of `tegra`, `arm64_sbsa`,
  `generic_aarch64`, `non_aarch64`, `unknown`. `generic_aarch64` is
  D-80.7-8's Tier-1-false/ACPI-absent result. `unknown` is only a typed
  Tier-2 probe failure, never a silent default.
- **Text output** mirrors the `doctor gpu` shape: a `doctor platform` header
  line followed by `key=value` lines in the same field order.
- **Exit semantics:** `0` for successful `tegra`, `arm64_sbsa`,
  `generic_aarch64`, and `non_aarch64` classifications. `unknown` is reserved
  for a typed Tier-2 probe failure and exits `70`. It never exits `65`: this
  command expresses no device *policy*, so it has nothing to refuse. Unlike an
  actual CUDA-provider probe failure, this ancillary platform-probe failure does
  not make `doctor gpu` fail.
- Like `doctor gpu`, it **must not** open a database, load or download a model,
  write configuration, or initialize an engine. Tier 1 is filesystem-only; Tier 2
  runs only when Tier 1 is true (D-80.7-7).

  **Normative platform-v1 mapping.** `tegra_family` is a JSON boolean.
  `sbsa_capable` is a boolean when classification establishes it, otherwise

  `reason` is either `null` or one of
  `nvidia_smi_missing`, `nvidia_smi_timeout`, or `nvidia_smi_nonzero`. The
  following fixture-backed table defines every branch:

  | --- | --- | --- | --- | --- | --- | --- |
  | Host architecture is not AArch64 | `non_aarch64` | `false` | `false` | `null` | `null` | 0 |
  | Tier 1 false; ACPI tables present | `arm64_sbsa` | `false` | `true` | `null` | `null` | 0 |
  | Tier 1 false; ACPI tables absent | `generic_aarch64` | `false` | `false` | `null` | `null` | 0 |
  | Tier 1 true; `nvgpu` present | `tegra` | `true` | `false` | parsed or `null` | `null` | 0 |
  | Tier 1 true; successful query without `nvgpu` | `arm64_sbsa` | `true` | `true` | parsed or `null` | `null` | 0 |
  | Tier 1 true; no executable candidate | `unknown` | `true` | `null` | parsed or `null` | `nvidia_smi_missing` | 70 |
  | Tier 1 true; query exceeds 2000 ms | `unknown` | `true` | `null` | parsed or `null` | `nvidia_smi_timeout` | 70 |
  | Tier 1 true; query exits non-zero | `unknown` | `true` | `null` | parsed or `null` | `nvidia_smi_nonzero` | 70 |

**D-80.7-11 — "source-build guidance" must be an exact, testable sequence
(ruled).** "Point at the source-build path" is not implementable as written.
Ruled, splitting it by what each surface can truthfully know:

- **`scripts/release/build-python-cuda-tegra.sh` prints the exact

  It is the only component that knows the concrete artifact path, and the

## 10. Risks

- **R-1 — the containerized N-API build may not be turnkey.** `napi build`
  inside `manylinux_2_28` needs Node and the pinned Rust toolchain present in
  the image. Mitigation: 80.1 lands the gate and the fixtures first, so the
  defect is *visible and failing* even if the build fix takes a second pass.
- **R-2 — lowering the glibc floor may change artifact size.** The wheel-size
  gate (`.github/workflows/ci.yml:747`) has a 20 MB regression budget; a floor
  change should not approach it, but 80.1 must check rather than assume.
- **R-3 — de-risked by direct inspection of the pinned fork; verify at build
  time, don't assume a rewrite.** The pinned Candle fork checkout
  (`~/.cargo/git/checkouts/candle-fathomdb-07553b5f3bcf1ce0/5719d90`, matching
  `Cargo.toml:63`'s pin exactly) shows `candle-kernels/build.rs` compiles
  every kernel the BGE embedder path touches via `cudaforge::KernelBuilder::build_ptx()`
  — PTX, not native SASS, and PTX JIT-compiles forward to newer compute
  capabilities including `sm_87` by design. Only `moe_*.cu` (Mixture-of-Experts
  kernels — BGE-small doesn't use them; `fathomdb-embedder/Cargo.toml` has no
  `flash-attn` dependency either) is natively compiled, gated by
  `cudaforge::detect_compute_cap() < 80` to disable a bf16 WMMA flag on
  pre-Ampere hardware — not a hard failure. **`CUDA_COMPUTE_CAP` itself is
  currently inert for our build**: it's read only by `candle-flash-attn-v3/build.rs`,
  which nothing in this crate graph depends on; 80.4 parameterizes it because
  the release contract checks its literal value, not because it gates real
  kernel compilation today. 80.6's job is to verify PTX JIT actually succeeds
  end-to-end on real Orin hardware — a measurement, not a rewrite risk.
  **Update (80.5 commissioning): the compile half is now measured, not
  inferred** — `cargo build -p fathomdb-embedder --features embed-cuda`
  succeeds on this Orin under CUDA 12.6 with `CUDA_COMPUTE_CAP=87`, in 1m41s,
  with no change to the pinned fork (§ 2.7). What remains for 80.6 is the
  *runtime* JIT proof: that the PTX those kernels carry actually loads and
  executes on `sm_87`, which only a real forward pass can show.
- **R-4 — the AArch64 F16 pin is conservative for Orin.** Orin's Cortex-A78AE
  implements `fullfp16`, so the Gemm F16 exclusion costs performance on this
  host specifically. Out of scope here (§ 3), but worth a separate
  evidence-first look once CUDA lands, since GPU execution may make it moot.
- **R-5 — a second self-hosted runner on shared hardware needs its own
  isolation, not inherited trust.** This Jetson already hosts
  `actions.runner.coreyt-memex.jetson-memex.service` for the unrelated `memex`
  repository. Registering `~/actions-runner/fathomdb/` as a second, separate
  runner instance is the proven, low-risk shape (identical `svc.sh` pattern),
  but the two runners must not share credentials, work directories, or
  registration, and `fathomdb`'s instance still needs the org-scoped,
  workflow-restricted group discipline of `dev/design/0.8.23-gpu-artifacts.md`
  — `memex` already being present on the box is not a reason to relax that.

Every decision this slice needed is now ruled; nothing is open. Recorded here
for provenance, in the order each was resolved across this document's
revisions.

1. **Sequencing — RULED.** Slice 80 does not need to precede or displace the
   existing ladder. `release-ladder-reorder` already established the
   precedent (Slice 40 set aside for 10/20/70): 80.1–80.3 (glibc floor, the two
   host-arch test fixes, the AArch64 developer environment) depend on nothing
   in 40/70/71/72 and can be commissioned now; 80.4–80.7 build on the Slice
   70/71 device-policy substrate (§ 2.5) and are naturally sequenced after it,
   not before. § 9 records this as a single Slice 80 with an internal
   sub-ladder rather than two separately numbered slices — revisit only if the
   HITL prefers splitting them for independent commissioning.
2. **D-1 packaging — RULED, and REVISED at 80.6 implementation.** Tegra CUDA
   currently ships as a source-build path; a first-party artifact remains behind
   the staged publication gate (§ 7 80.6), reached through `doctor gpu` guidance
   (§ 7 80.7) rather than a channel the user must
   already know. The *separation* is a technical necessity — PyPI/npm cannot
   tag-distinguish Tegra from `arm64-sbsa` — but this item previously said the
   separation is carried by a **separate distribution name**, and that is no
   longer the ruling. D-80.6-3 now keeps the name `fathomdb` and separates by
   **PEP 440 local version on a first-party index**, matching how NVIDIA and
   PyTorch ship Jetson wheels, because a sibling distribution sharing the
   `fathomdb/` import package corrupts pip's own uninstall bookkeeping (a worse
   failure than the one it would prevent) and because PyPI rejects our bare
   `linux_aarch64` tag under any name regardless. Neither form signals that the
   artifact is experimental or second-class — see item 7 below.
3. **The 2.35 Tegra glibc exception — RULED.** Confirmed: L4T R36 *is*
   Ubuntu 22.04/glibc 2.35, so every Jetson capable of running this artifact
   already meets that floor; it excludes nobody in the target audience.
4. **SBSA refusal semantics — RULED.** Refuse-and-continue-on-CPU, not
   refuse-and-fail (R80-9). The mechanism already exists generically in the
   Slice 70 classifier (§ 2.5); 80.7 confirms it holds for the Tegra/SBSA case
   specifically and is the one that fires, not a new one.
5. **Runner — RULED.** Reuse this Jetson Orin AGX: it already runs a
   self-hosted GitHub Actions runner for the `memex` repository
   (`~/actions-runner/memex/`, `actions.runner.coreyt-memex.jetson-memex.service`).
   A second instance at `~/actions-runner/fathomdb/` follows the identical
   proven pattern (§ 7 80.6, § 10 R-5) rather than requiring new hardware.
6. **Backport — RULED: no backport.** 0.8.21 and 0.8.22 keep shipping with the
   broken npm artifact (§ 2.1) unremarked; no `npm deprecate`, advisory, or
   other outward action targets them. The fix is forward-only in 0.8.23.
   `dev/design/0.8.23-aarch64-tegra.md` §§ 2.1/80.1 stand as written — this
   ruling only forecloses the deprecation-note question, not the underlying
   fix.
7. **CUDA support scope — RULED.** 0.8.23's stated CUDA support explicitly
   includes x86_64 **and Tegra** (Orin `sm_87`); it explicitly **excludes**
   `arm64-sbsa`. This is declared product scope, not a placeholder — § 7
   80.7's SBSA refuse-and-continue-on-CPU behavior (item 4 above) is therefore
   the final, correct behavior for that hardware class in 0.8.23, not a
   temporary gap pending future SBSA support.

8. **The publication hold is a staged gate, not an open question — RULED.**
   0.8.23 is intended to publish, including CUDA+Tegra (item 7). The standing
   `publication` decision holds registry publication until, in order: all
   work runs clean in local environments, local CI-equivalent checks pass,
   then hosted GitHub Actions CI passes. Only after that sequence completes

   10/20's `PENDING_EXTERNAL` (real trusted-runner dispatch not yet run) and
