# 0.8.23 Gitleaks guardrails design

## Decision

0.8.23 adds Gitleaks at two boundaries: a redacted scan of the staged index in
the tracked pre-commit hook, and an always-on, redacted full-history scan in
GitHub Actions. Neither scan substitutes for review or permits credentials to
be printed into logs.

Implementation is recorded by Slice 50 at `ae7cef0e`: the scanner's Go module
and version are pinned in `scripts/lib/gitleaks-version.sh`; bootstrap and CI
use the same installer; and regression coverage uses only a temporary,
synthetic credential-shaped value.

## Requirements

- Pin the scanner version and make bootstrap install it reproducibly.
- The pre-commit hook scans the staged index, not unstaged working-tree data.
- CI scans reachable history independently of path filters, so a docs-only
  change cannot bypass it.
- Fail closed when the scanner is unavailable or finds a secret; redact output.
- Regression tests prove the hook and CI wiring, including a synthetic staged
  credential that fails without exposing its value.

## Current-tree follow-on

The history scan must not be treated as a current-tree scan: the default
directory source respects ignore files and therefore does not cover tracked
transcripts. Before any historical baseline is considered, CI copies the
tracked working tree into an isolated scan root, scans it with the pinned
default-rule extension, and scans tracked `.log` files explicitly. Its report
template emits only `rule|path|line`; inline `gitleaks:allow` comments are
ignored.

The current-tree policy has four reviewed, rule-scoped `generic-api-key`
exceptions. Each is an AND of one exact path and one exact match/secret
expression:

- the two CUDA tokenizer SHA-256 integrity metadata locations;
- the two code-marker experiment artifacts, limited to their two reviewed
  marker identifiers.

The only tracked `sourcegraph-access-token` match was a full Git-object hash
inside a transcript. It is shortened to a resolvable 12-character Git prefix,
not allowlisted. The policy validator rejects every other configuration shape;
fixture mutations prove that a synthetic credential in an otherwise allowed
path still fails.

This follow-on intentionally adds no historical baseline, `.gitleaksignore`,
or report JSON. Historical findings remain a separate security-triage and
manifest-design step.

### Proposed tracked manifest

The implementation adds `scripts/security/gitleaks-history-manifest.json`. It
is a project-owned,
redacted multiset manifest, **not** a Gitleaks baseline JSON and never an
input to `--baseline-path`. It contains no scanner `Secret`, `Match`, `Line`,
description, commit message, or source text.

The manifest schema is exact:

```json
{
  "schema": 1,
  "scanner_version": "8.30.1",
  "tuple_encoding": "fathomdb-gitleaks-history-v1 NUL commit NUL rule NUL path NUL start_line",
  "expected_records": 100,
  "expected_unique_fingerprints": 51,
  "entries": [{"fingerprint": "sha256-halves", "count": 1}]
}
```

`fingerprint` means the SHA-256 of that exact UTF-8 tuple encoding, rendered
as two 32-hex-character halves separated by one period. Splitting the digest
keeps this redacted data from itself resembling an unscoped secret pattern.
The production manifest has exactly 51 entries: 41 with `count: 1`, two with
`count: 4`, seven with `count: 7`, and one with `count: 2` for the line-5367
tuple. Its counts total 100. Every entry is generated only from the safe
scanner fields and its resulting redacted values are reviewed before tracking.

No path-only, rule-only, global, commit-only, or Gitleaks-native ignore entry
is permitted. A manifest entry matches only its complete tuple and its exact
multiplicity.

### Proposed classifier and CI integration

`gitleaks-history.sh` is a fail-closed classifier rather than an `exec` of raw
scanner output. It first runs `gitleaks-current.sh` and
require its policy-zero result. CI retains an explicit current-tree step
before the history step as an independently visible ordering guard; the
history script repeats the prerequisite for identical local behavior.

The classifier then runs the pinned scanner over `--all` with a fixed template
containing only commit, rule identifier, repository-relative file, and start
line. It validates every field before hashing: a full object ID, one of the
two reviewed rule identifiers (`generic-api-key` or
`sourcegraph-access-token`), a clean relative path with no traversal, and a
positive decimal line number. Its temporary report contains only those safe
fields and is removed on exit. It never writes a native Gitleaks JSON report.

Only scanner exits 0 and 1 are interpretable. Exit 1 means a safe report must
be parsed and compared; exit 0 still fails because the approved manifest is
nonempty. Any other scanner exit, missing report, malformed record, duplicate
encoding error, invalid manifest schema/version, unknown tuple, missing tuple,
or count difference fails the job. Failure output reports only aggregate
counts (expected/observed/unknown/missing/count-mismatch), never a tuple or
scanner match.

The comparison is a `Counter` equality check, not a set comparison. This is
what makes removal, addition, or a second occurrence of the line-5367 tuple
fail. It also means a newly introduced historical-looking value remains a
hard failure until a separately reviewed manifest update explicitly classifies
its complete redacted tuple.

The implementation must retain `--ignore-gitleaks-allow` at both scan
boundaries. For the historical scan, it must create an isolated bare mirror,
scan that mirror rather than the checkout, and pass
`--gitleaks-ignore-path` only to a scan-root-owned empty file. The mirror
prevents a checkout-local native ignore file from becoming a scanner source;
the explicit empty path makes the requested ignore input a no-op. The
classifier checks immediately that its owned input is empty. It may not use
any path-, rule-, global-, commit-, or native-ignore exception to match
history, nor accept a scanner config or global-allowlist input unless a
separate reviewed design proves it safe. It must forbid `--baseline-path`,
global allowlists, and `--exit-code 0`. The unconditional full-history CI job,
pinned installer, `fetch-depth: 0`, and current-before-history order remain
required.

### Implemented RED/GREEN verification

The RED tests begin from the safe fixed-template stream only; no fixture
contains a real or copied secret. They demonstrate failure for a new
tuple, one missing expected tuple, an extra occurrence of the count-two tuple,
a malformed safe record, a missing/changed manifest field, and a failed
current-tree prerequisite. A dynamic fixture proves that an inline scanner
allow and a checkout-root default ignore can each suppress a reachable
historical finding, while the bare-mirror plus controlled-empty-path boundary
retains that finding. Static mutations must also show that deleting the
current prerequisite, inline-allow protection, controlled empty path, or
isolated-source boundary; making the owned input nonempty or deleting its
size check; replacing the multiset comparison with set comparison; or adding
a baseline, scanner-config, global-allowlist, or zero-exit option fails the
contract suite.

GREEN evidence includes the exact safe-stream fixture for 100 records and 51
fingerprints, a successful policy-zero current scan, and an explicit
count-two assertion for line 5367. CUDA integrity tests and the Phase A/B
current-tree mutation tests remain mandatory. A clean classifier result says
only that the observed history equals this reviewed redacted multiset; it is
not a credential-remediation or release-completion claim.

## Non-goals

- This slice does not rewrite history, rotate credentials, or change release
  publication authority.
- It does not introduce a third-party collector or alter the release workflow's
  finalization semantics.
