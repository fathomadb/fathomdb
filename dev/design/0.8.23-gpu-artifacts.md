# 0.8.23 CUDA-capable Linux artifact design

## Decision

0.8.23 ships CUDA capability in the normal Linux x86_64 Python wheel and Node
native package. The compiled capability is opt-in at runtime: CPU remains the
default and an application selects CUDA with `FATHOMDB_EMBED_DEVICE=cuda:N`.

The scope is deliberately Linux x86_64 only. Windows and macOS are not called
CUDA-capable until each can pass an equivalent platform-native build and hardware
smoke. The existing CPU artifacts on those platforms remain unchanged.

## Artifact boundary

The existing `embed-cuda` feature chain reaches the embedder from the Python
binding, but the N-API crate currently stops at `default-embedder`. Slice 5 adds
the equivalent N-API forwarding feature and selects it only for the Linux x86_64
release build. The normal package names remain unchanged: hardware selection is
not delegated to npm optional-dependency resolution.

Before that wiring lands, Slice 0 measures the release-equivalent binary's
dynamic dependencies and runs it in a genuinely driverless Linux container or
host. This establishes whether a CUDA-built process can load when the caller
leaves the device at CPU. The measured result determines the CPU compatibility
contract and any explicit runtime prerequisite documentation; it must not be
guessed from feature names or a smoke on the GPU host.

## Runner and trust boundary

The host runner is named `windchill3-fathomdb-cuda` and uses labels
`self-hosted`, `Linux`, `X64`, `gpu`, and `cuda-12`. Its local installation is
`/home/coreyt/.local/actions-runner/fathomdb-gpu` and its enabled user service
is `fathomdb-gpu-runner.service`.

It is registered at organization scope in `fathomadb`'s selected-repository,
workflow-restricted `fathomdb-gpu-release` group. The group contains the
persistent `windchill3-fathomdb-cuda` runner and the one-concurrent
GitHub-hosted `fathomdb-gpu-t4` NVIDIA T4 pool. Labels and workflow prose are
routing hints, not access control: a repository-scoped runner is unsafe for
this public repository because a hostile workflow can select its labels. The
group is a release gate, not general-purpose CI capacity.

Workflow restriction must admit the workflow ref that actually publishes. Since
normal publication evaluates `release.yml` from an immutable `v*` tag, Slice 0
must prove one of two PR-safe paths before tag creation: a deliberately
main-pinned dispatch release path, or a pre-tag update that permits the exact
immutable tag workflow ref and is removed after completion. A main-only
allow-list that rejects the tag cannot be accepted as a release gate.

Slice 0 records `nvidia-smi`, `nvcc --version`, the CUDA toolkit path, and the
exact maturin/manylinux build strategy used by the runner. It must demonstrate
that this build context can compile the release artifact before Slice 5 makes it
a publishing dependency.

## Evidence model

Each release candidate produces three distinct witnesses:

1. Build/link witness: exact Cargo/maturin/N-API feature arguments and dynamic
   dependency inspection of the generated artifacts.
2. CPU compatibility witness: release-equivalent artifacts complete an
   open/write/search/close/exit smoke in a genuinely driverless environment
   without requesting CUDA.
3. GPU witness: installed artifacts run the same smoke with
   `FATHOMDB_EMBED_DEVICE=cuda:0`; the job records successful behavior and the
   spawned smoke PID appears in `nvidia-smi` compute-process output on the
   selected device.

The GPU witness proves acceleration was attempted and engaged. It does not alter
the existing CPU-based vector-equivalence and recall-fidelity gates.

## Failure behavior

- Missing CUDA feature wiring, a bad runner-group restriction, a driverless
  CPU-load failure, or an absent smoke-PID GPU witness fails the release gate.
- A CUDA initialization failure under an explicit CUDA request remains the
  existing loud CPU fallback behavior until a future safety-policy release
  changes that contract.
- No release workflow is allowed to replace the hardware witness with a compile
  success from a GitHub-hosted CPU runner. Pre-publish artifacts must pass their
  CPU and GPU smokes; post-publish registry-installed smoke gates promotion and
  release completion, since a registry upload is immutable.

## Design review checklist

- Verify feature forwarding from Python and N-API to the engine/embedder.
- Review `readelf`/`ldd` results for both generated Linux artifacts.
- Review CPU smoke on the agreed genuinely driverless environment.
- Review GPU witness PID attribution and whether it distinguishes GPU 0/1 from
  the display-only GPU.
- Review workflow permissions, triggers, labels, and release-job dependencies.
- Review the organization runner-group and selected-workflow restriction.
- Review CUDA toolkit/driver evidence and the manylinux/maturin build context.
- Review package metadata and public docs for platform-specific claims.
