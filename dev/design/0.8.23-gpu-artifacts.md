# 0.8.23 CUDA-capable Linux artifact design

## Decision

0.8.23 ships CUDA capability in the normal Linux x86_64 Python wheel and Node
native package. The compiled capability is opt-in at runtime: CPU remains the
default and an application selects CUDA with `FATHOMDB_EMBED_DEVICE=cuda:N`.

The scope is deliberately Linux x86_64 only. Windows and macOS are not called
CUDA-capable until each can pass an equivalent platform-native build and hardware
smoke. The existing CPU artifacts on those platforms remain unchanged.

## Artifact boundary

The existing `embed-cuda` feature chain reaches the embedder from the Python
binding, but the N-API crate currently stops at `default-embedder`. Slice 5 adds
the equivalent N-API forwarding feature and selects it only for the Linux x86_64
release build. The normal package names remain unchanged: hardware selection is
not delegated to npm optional-dependency resolution.

Before that wiring lands, Slice 0 measures the release-equivalent binary's
dynamic dependencies. This establishes whether a CUDA-built process can load on
a host with no NVIDIA driver when the caller leaves the device at CPU. The
measured result determines the clean CPU smoke environment and any explicit
runtime prerequisite documentation; it must not be guessed from feature names.

## Runner and trust boundary

The repository-scoped runner is `windchill3-fathomdb-cuda`, installed at
`/home/coreyt/.local/actions-runner/fathomdb-gpu` and supervised by the enabled
user service `fathomdb-gpu-runner.service`. Its labels are `self-hosted`,
`Linux`, `X64`, `gpu`, and `cuda-12`.

Only protected-branch/tag release jobs and explicit trusted dispatches may use
those labels. Pull-request jobs, especially fork-originated jobs, must never
select them. The runner is a release gate, not general-purpose CI capacity.

## Evidence model

Each release candidate produces three distinct witnesses:

1. Build/link witness: exact Cargo/maturin/N-API feature arguments and dynamic
   dependency inspection of the generated artifacts.
2. CPU compatibility witness: release-equivalent artifacts complete an
   open/write/search/close/exit smoke without requesting CUDA.
3. GPU witness: installed artifacts run the same smoke with
   `FATHOMDB_EMBED_DEVICE=cuda:0`; the job records successful behavior and a
   CUDA process-memory/activity observation from the selected device.

The GPU witness proves acceleration was attempted and engaged. It does not alter
the existing CPU-based vector-equivalence and recall-fidelity gates.

## Failure behavior

- Missing CUDA feature wiring, a bad workflow label, a driverless CPU-load
  failure, or an absent GPU-engagement witness fails the release gate.
- A CUDA initialization failure under an explicit CUDA request remains the
  existing loud CPU fallback behavior until a future safety-policy release
  changes that contract.
- No release workflow is allowed to replace the hardware witness with a compile
  success from a GitHub-hosted CPU runner.

## Design review checklist

- Verify feature forwarding from Python and N-API to the engine/embedder.
- Review `readelf`/`ldd` results for both generated Linux artifacts.
- Review CPU smoke on the agreed driverless environment.
- Review GPU witness robustness and whether it distinguishes GPU 0/1 from the
  display-only GPU.
- Review workflow permissions, triggers, labels, and release-job dependencies.
- Review package metadata and public docs for platform-specific claims.
