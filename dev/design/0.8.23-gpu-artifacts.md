# 0.8.23 CUDA-capable Linux artifact design

> **Supersession note (0.8.25):** the prior driverless evidence was incomplete:
> an N-API path mounted `libcudart.so.12`. The corrective architecture is
> [0.8.25 driverless CUDA-capable artifact design](0.8.25-driverless-cuda-runtime.md)
> and ADR-0.8.25-driverless-cuda-runtime-linkage. It requires no dynamic
> CUDA/NVIDIA dependency in every packaged ELF member and no CUDA mount in CPU
> or forced-driverless evidence.
>
> **Slice 70 owns runtime device policy; this document retains only the Slice 10/20 artifact-evidence plan.** The current embedding contract is `auto`,
> `cpu`, or forced `cuda:N` through `FATHOMDB_EMBED_DEVICE`, with no end-user
> rebuild on a supported CUDA-capable artifact. In particular, `auto` may
> select typed CPU when CUDA is unavailable, while forced `cuda:N` fails typed
> and never falls back to CPU. See
> [`0.8.23-slice-70-dual-runtime-device-policy.md`](0.8.23-slice-70-dual-runtime-device-policy.md).
>
## Current slice ownership

This initial design uses historical Slice 0 and Slice 5 labels. For the active
0.8.23 ladder, [Slice 10's CUDA trusted-runner and artifact contract](0.8.23-slice-10-cuda-contract.md)
owns the protected-runner, source-contract, and candidate-preflight boundary;
Slice 20 owns final release-package bytes, rehearsal provenance, and
installed-artifact evidence. Where this document's historical slice labels
conflict, the Slice 10 design controls current ownership. Neither document
authorizes publication.

## Planned artifact outcome (Slice 20)

After Slice 10's trusted contract and Slice 20's package rehearsal pass,
0.8.23 may ship CUDA capability in the normal Linux x86_64 Python wheel and
Node native package. The compiled capability would be opt-in at runtime: CPU
is an explicit `FATHOMDB_EMBED_DEVICE=cpu` selection, `auto` is the unset
policy on the CUDA-capable artifact, and an application can force CUDA with
`FATHOMDB_EMBED_DEVICE=cuda:N`. The package contains both CPU and CUDA paths,
so application users do not recompile to make that selection. No final
release-package claim has been made.

The scope is deliberately Linux x86_64 only. Windows and macOS are not called
CUDA-capable until each can pass an equivalent platform-native build and hardware
smoke. The existing CPU artifacts on those platforms remain unchanged.

## Artifact boundary

The existing `embed-cuda` feature chain reaches the embedder from both Python
and N-API. Its static forwarding is candidate-preflight evidence only. Slice 20
will decide whether the equivalent feature tuple reaches final Linux x86_64
release bytes; the normal package names remain unchanged and hardware selection
is not delegated to npm optional-dependency resolution.

Slice 10 must measure candidate-preflight artifact dynamic dependencies and run
them in a genuinely driverless Linux environment with device-selection variables
absent. The measured result establishes the unset/`auto` typed-CPU compatibility
contract; it must not be guessed from feature names, explicitly-CPU-configured
smokes, or a smoke on the GPU host.

## Evidence model

The future Slice 10/20 evidence model requires three distinct witnesses:

1. Build/link witness: exact Cargo/maturin/N-API feature arguments and dynamic
   dependency inspection of the generated artifacts.
2. CPU compatibility witness: release-equivalent artifacts complete an
   open/write/search/close/exit smoke in a genuinely driverless environment
   with the device setting absent (`auto` resolves to typed CPU).
3. GPU witness: installed artifacts run the same smoke with
   `FATHOMDB_EMBED_DEVICE=auto` on a compatible GPU; the job records successful
   CUDA selection and the spawned smoke PID appears in `nvidia-smi`
   compute-process output on the selected device. A separate forced
   `FATHOMDB_EMBED_DEVICE=cuda:0` incompatible/unavailable smoke proves the
   typed fail-closed outcome.

The GPU witness proves acceleration was attempted and engaged. It does not alter
the existing CPU-based vector-equivalence and recall-fidelity gates.

## Failure behavior

- Missing CUDA feature wiring, a bad runner-group restriction, a driverless
  CPU-load failure, or an absent smoke-PID GPU witness fails the release gate.
- A CUDA initialization failure under an explicit CUDA request is a typed,
  fail-closed error; it never becomes CPU execution.
- No release workflow is allowed to replace the hardware witness with a compile
  success from a GitHub-hosted CPU runner. Pre-publish artifacts must pass their
  CPU and GPU smokes; post-publish registry-installed smoke gates promotion and
  release completion, since a registry upload is immutable.

## Design review checklist

- Verify feature forwarding from Python and N-API to the engine/embedder.
- Review `readelf`/`ldd` results for both generated Linux artifacts.
- Review CPU smoke on the agreed genuinely driverless environment.
- Review GPU witness PID attribution and whether it distinguishes GPU 0/1 from
  the display-only GPU.
- Review workflow permissions, triggers, labels, and release-job dependencies.
- Review the organization runner-group and selected-workflow restriction.
- Review CUDA toolkit/driver evidence and the manylinux/maturin build context.
- Review package metadata and public docs for platform-specific claims.
