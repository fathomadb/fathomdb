# 0.8.23 scale artifact aggregator contract

This is the executable-contract companion to
`0.8.23-scale-characterization-protocol.md`. It authorizes neither a matrix
run nor a scale conclusion. An aggregator reads retained matrix evidence; it
does not infer, repair, regenerate, or substitute it.

## Canonical artifact and validator boundary

`0.8.23-scale-artifact.schema.json` is the canonical machine-readable schema
for the emitted JSON artifact. It is a structural schema, not a substitute for
evidence verification. The aggregator is the only writer of `status`; a status
string supplied in an input, a manifest, or a partially assembled artifact is
never trusted. The validator must first validate the schema, then perform the
semantic checks in this document, and only then derive the output status by the
following ordered rule:

1. no retained timing attempt and no raw root means `DEFERRED`;
2. an absent required capture or required raw input means
   `MISSING_PREREQUISITE`;
3. any present invalid input means `ENVIRONMENT_INVALID`;
4. otherwise incomplete valid cells mean `INSUFFICIENT_SAMPLES`; and
5. only a complete valid 3 × 2 × 5 matrix means `CHARACTERIZED`.

`CHARACTERIZED` is therefore a validator result, never a user assertion. The
validator must emit every missing or invalid field as a stable, fully-qualified
reason; it must not replace a missing field with `null`, `0`, `[]`, `unknown`,
or a default. `summary` is `null` for every result except
`CHARACTERIZED`. The output filename is exactly
`dev/plans/runs/0.8.23-scale-<candidate-head-sha>-output.json`, where
`candidate-head-sha` is the lower-case 40-hex Git object ID captured in the
artifact.

### Fixed retained-input root

For a candidate with `candidate.head_sha = H`, the only admissible raw root is
the repository-relative, non-symlink directory
`dev/plans/runs/0.8.23-scale-H-raw/`. The validator rejects absolute paths,
`..`, a different SHA spelling, a symlink, nested directories, and a root
outside the candidate checkout. It has exactly these 62 regular files and no
others:

- `matrix-manifest.json` and `provenance.json`;
- for each `N` in `10000`, `100000`, `1000000`, each treatment in
  `process_cold`, `warm`, and each repetition `R` in `1` through `5`, exactly
  `ac013-N-T-repR.log` and `ac013-N-T-repR.log.sha256`.

The manifest entries use that same lexicographic filename order: rows ascending,
then `process_cold` before `warm`, then repetition ascending. A manifest that
omits, repeats, reorders, or adds an entry is invalid; a filesystem entry not
in this fixed inventory is an extra and invalid. The runner must write the
sidecar in this exact one-line UTF-8 form (where `F` is the adjacent basename):

~~~text
<64 lower-case SHA-256 hex characters><two ASCII spaces>F<LF>
~~~

Thus a sidecar cannot contain a path, a `*` binary marker, a second line, or a
different filename. The validator computes SHA-256 over the raw log bytes and
requires equality with both the sidecar and its manifest digest; it also runs
the equivalent of `sha256sum -c` from the raw root. A missing sidecar is a
missing prerequisite; a malformed, unreadable, or mismatching sidecar is an
environment invalidity.

### Canonical input documents

`matrix-manifest.json` is UTF-8 JSON with no duplicate object keys and exactly
these top-level keys: `schema_version` (integer `1`), `protocol`
(`"0.8.23-scale-characterization-v1"`), `candidate_head_sha` (lower-case
40-hex), and `entries` (the exact 30-entry array above). Every entry has only
`rows` (one of `10000`, `100000`, `1000000`), `treatment`
(`process_cold|warm`), `repetition` (integer `1..5`), `log` (the fixed basename),
`sidecar` (that basename plus `.sha256`), and `sha256` (lower-case 64-hex).
There are no optional keys and no aliases.

`provenance.json` is UTF-8 JSON with no duplicate object keys and exactly these
top-level keys: `schema_version` (integer `1`), `protocol`
(`"0.8.23-scale-characterization-v1"`), `candidate`, `slice5_provenance`,
`lock_build`, `fixture`, and `environment`. Its values are copied verbatim into
the output's top-level `candidate` and `provenance` objects after the semantic
validation below. A capture that could not be made is represented only in the output's
`integrity.missing_prerequisites` with the fully-qualified required field; it
cannot be represented by a placeholder in `provenance.json`.

### Exact 0.8.22 Slice 5 provenance

`slice5_provenance` has only these keys:

| Key | Exact value / validation |
| --- | --- |
| `release` | string `"0.8.22"` |
| `authoritative_release_state` | object with only `path`, `git_blob`, `sha256`, `slice`, `status`, `landed_sha`, and `evidence_sha256` |
| `measured_lock_stack` | object with only `cargo_lock_sha256`, `rusqlite`, `sqlite_vec`, and `libsqlite3_sys` |

The release-state object pins `path` to
`dev/plans/release-state-0.8.22.json`; `git_blob` and `landed_sha` are
lower-case 40-hex IDs, `sha256` and `evidence_sha256` are lower-case 64-hex,
`slice` is integer `5`, and `status` is `LANDED`. `sha256` is the SHA-256 of
the exact authoritative release-state bytes at `git_blob`. The validator parses
that JSON, selects its unique `ladder` object with `slice: 5`, verifies its
`status` and `sha`, verifies `landed_sha == ladder[5].sha`, and requires
`evidence_sha256` to equal the SHA-256 of the UTF-8 bytes of that object's
`evidence` string. A release-state object without exactly one such Slice 5
entry, or one whose SHA/evidence does not agree, is invalid.

Each measured-lock package object (`rusqlite`, `sqlite_vec`, and
`libsqlite3_sys`) has only `name`, `version`, `source`, and `checksum`; every
value is a nonempty string except that `checksum` is lower-case 64-hex. Its
`name` is respectively `rusqlite`, `sqlite-vec`, and `libsqlite3-sys`. The
validator parses the candidate's captured `Cargo.lock`, verifies its digest is
`cargo_lock_sha256`, and requires one exact package match for each object
(name, version, source, and checksum). It then compares the stack against the
0.8.22 Slice 5 candidate named by `landed_sha`. An absent authoritative
release-state/evidence/lock capture is `MISSING_PREREQUISITE`; a parse failure,
non-LANDED Slice 5, changed SHA/evidence, or a stack mismatch is
`ENVIRONMENT_INVALID`.

### Treatment-record grammar

For every log, the validator finds exactly one complete line whose first token
is `AC013_TREATMENT_RECORD`. It rejects zero records, multiple records,
continuations, malformed UTF-8, duplicate keys, unknown keys, an empty value,
or any non-record text that masquerades as a record. The record is one
space-delimited line with exactly these ten keys, each once and in this order:

| Key | Type and required value |
| --- | --- |
| `treatment` | exact filename treatment: `process_cold` or `warm` |
| `n` | decimal integer, exactly the filename row count |
| `seed_write_ms` | decimal integer (non-negative) |
| `embedding_ms` | decimal integer (non-negative) or exact `not_separately_observable` |
| `projection_drain_ms` | decimal integer (non-negative) |
| `accepted_writes` | decimal integer, exactly `n` |
| `vector_rows_after_drain` | decimal integer, exactly `accepted_writes` |
| `drain_outcome` | exact `ok` |
| `samples_us` | comma-separated non-negative decimal integers |
| `result_counts` | comma-separated non-negative decimal integers |

`process_cold` requires exactly one `samples_us` value and exactly one
`result_counts` value. `warm` requires exactly 1,000 values in each of those
two fields, position-for-position. A marker such as
`not_retained_per_query` is not a captured result count and therefore cannot
validate a warm record. The rows/treatment/repetition are taken from the
filename and manifest; a record has no authority to relabel them. Any failure
of this grammar or these cardinalities is malformed retained evidence and is
`ENVIRONMENT_INVALID`, not insufficient samples.

## Input inventory and validation matrix

Every field below is mandatory for `CHARACTERIZED`. Missing planned input is
`MISSING_PREREQUISITE`; present but malformed, contradictory, dirty, corrupt,
or mismatched input is `ENVIRONMENT_INVALID`.

| Group | Required fields/evidence | Validation |
| --- | --- | --- |
| Candidate | full SHA, branch/ref, commit timestamp, clean `git status --porcelain` assertion | SHA resolves; status is empty; any dirty or unavailable fact is invalid. |
| Matching dependency | complete 0.8.22 release-state candidate SHA; Slice 5 SHA/status/evidence; its locked rusqlite, sqlite-vec, and libsqlite3-sys stack | Slice 5 must be LANDED and dependency versions must equal the measured Cargo.lock. Missing closure is prerequisite; a different stack is invalid. |
| Lock/build | Cargo.lock blob and SHA-256; cargo metadata locked digest; schema version/source blob; rustc -Vv; cargo -V; target; release profile; features; complete command; built-process SQLite version | Every digest/blob/version must be nonempty and mutually match the candidate. A shell/tool version is not a substitute for built-process SQLite. |
| Fixture | fixture ID, both seeds, source identity, 384 dimension, 1,000 queries, all three rows, perf_gates blob, canonical descriptor SHA-256 | Exact literal match to the protocol; any difference is invalid, never a new implicit fixture. |
| Host | collect-host-spec JSON, total/available RAM, database filesystem/free bytes, CPU governor/frequency policy, GPU query or explicit unavailable | Required fields must be captured. Explicit unavailable is allowed only where protocol permits; invented zero/unknown is invalid. |
| Isolation | timestamp, load/process evidence, affinity/governor/power/container/VM evidence, explicit no-concurrent-benchmark assertion | Every item must be captured and the assertion affirmative; absence is prerequisite, contamination is invalid. |
| Raw files | exactly 30 named logs and 30 sidecars: rows × treatment × repetitions 1..5 | No extras, duplicate names, missing files, or unreadable files. Each sidecar must verify the raw bytes. |
| Records | exactly one `AC013_TREATMENT_RECORD` per log | Record treatment/rows/repetition must match filename; required metric keys must occur exactly once; unknown record lines/extra records are invalid. |

## Per-repetition schema

Each retained repetition contains: `rows`, `treatment`, `repetition`, raw-log
path/SHA-256, command/exit status, seed/write duration, embedding duration or
the explicitly documented non-observable marker, projection-drain duration,
accepted writes, actual vector rows after drain, drain outcome, result counts,
all query samples, and query errors/timeouts/skips/invariant failures.

`accepted_writes == rows`, actual vector rows equal accepted writes, drain is
successful, exit status is zero, and all error/failure counters are zero are
integrity checks, not defaults. A missing or nonzero value invalidates the
matrix. The aggregator may preserve an incomplete repetition, but may not use
it to satisfy a cell.

`process_cold` has exactly one retained sample and one result count. `warm`
has exactly 1,000 retained samples and 1,000 result counts (or a declared
lossless reproducible histogram plus cardinality). Any other cardinality is
invalid. The treatments are never pooled.

## Outputs and statistics

The artifact preserves every valid/partial repetition under its own cell:
`(10k|100k|1M) × (process_cold|warm)`. For each complete repetition it computes
min, max, mean, p50, p95, and p99 only where defined; cold explicitly omits
undefined within-repetition percentiles rather than inventing them. For each
complete five-repetition cell it reports the repetition-level percentile values
and their median/minimum/maximum. It never pools 5,000 warm samples or five
cold values into a cell percentile.

## Status taxonomy

- `DEFERRED`: no timing was attempted; matrix is empty and summary is null.
- `MISSING_PREREQUISITE`: a required closure, capture facility, host fact, or
  raw input is absent. Preserve partial raw evidence; summary is null.
- `ENVIRONMENT_INVALID`: any dirty/mismatched candidate, malformed record,
  digest failure, extra file/record, failed drain/vector invariant, command
  failure, timeout, contamination, or contradictory provenance. Summary is
  null.
- `INSUFFICIENT_SAMPLES`: all required provenance and retained evidence are
  valid, but one or more cells have fewer than five complete repetitions (or
  wrong treatment sample sufficiency). Summary is null.
- `CHARACTERIZED`: all eight input groups validate, exactly six cells exist,
  each has exactly five complete repetitions, cold has five first-query
  observations, warm has 5×1,000 retained observations, raw digests remain
  verifiable, and only non-pooled summaries are emitted.

Partial, malformed, dirty, corrupt, or mismatched evidence is never
`CHARACTERIZED`, never a threshold pass, and never a supported-scale claim.
