# Slice 10 — CUDA trusted-runner and artifact contract

## Scope decision

Slice 10 owns the trustworthy, non-publishing execution contract for the Linux
x86_64 CUDA embedder route. Slice 20 subsequently owns the release-package
bytes, rehearsal manifest, and installed-artifact smokes. This slice does not
publish a registry artifact, create a tag, promote a dist-tag, or claim a
hardware witness that has not been retained and independently reviewed.

CUDA capability in this release is **embedding-only**. Candidate-preflight
artifacts for the Linux x86_64 Python and N-API routes use the existing
`embed-cuda` feature chain. Slice 20, not Slice 10, decides whether and how the
final release-package bytes use that route.
It does not claim CUDA CE reranking, CUDA retrieval, CUDA support for other
platforms, or a change to normal CPU-only artifact behavior.

On a CUDA-capable artifact the unset policy is `auto`, and CPU is an explicit selection.

## Code-grounded current state

The existing feature forwarding is present: Python and N-API forward
`embed-cuda` through the engine to the embedder, and the N-API CUDA build
command exists. The existing CUDA contract, preflight, provisioning, dynamic
link inspection, driverless smokes, and GPU-PID observation have static
regression coverage. Those checks establish source shape only.

The ordinary release Python and N-API artifact jobs still build
`default-embedder`, not `embed-cuda`; their bytes are therefore Slice 20 work.
The current `cuda-contract-preflight` job is an isolated dry-run job and is not
a required predecessor of the normal aggregate or publish graph. The reviewed
exact-SHA provenance route may supersede its default-main-ancestry guard only
after separately reviewed, main-owned manifest, receipt, and environment
controls accept one exact candidate. The current release branch is not
main-reachable, the local control plane is intentionally non-authorizing, and
no retained trusted-runner, driverless, or GPU-PID witness is present. These
facts prohibit a Slice 10 completion claim today.

## Need and requirements

**N10-CUDA-TRUSTED-CONTRACT.** A release candidate needs an auditable,
non-publishing CUDA embedding contract that can execute only through a trusted
runner route and produces evidence strong enough to gate later package work.

**R10-1 — bounded CUDA surface.** Only Linux x86_64 Python and N-API
candidate-preflight embedding artifacts may use the complete `embed-cuda`
feature tuple. On a CUDA-capable artifact the unset policy is `auto`, and CPU is an explicit selection.
The contract excludes CUDA CE reranking, retrieval, non-Linux-x64 platform
claims, and any claim that a candidate-preflight artifact is a final release
package.

**R10-2 — privileged-route integrity.** A public-repository candidate may not
cause arbitrary code or a candidate-controlled workflow to run on the
trusted self-hosted runner. The privileged workflow must be owned by the
default branch and may check out only an immutable commit already reachable
from the protected default branch. A separate GitHub-hosted
`verify-cuda-trusted-route` job must enforce this before the self-hosted job is
eligible. Its inline, default-branch-owned logic pins
`github.workflow_ref` by exact quoted comparison to
`fathomadb/fathomdb/.github/workflows/release.yml@refs/heads/main`. It resolves
the requested full candidate SHA, requires `HEAD == candidate_sha`, then uses
`merge-base --is-ancestor candidate_sha refs/remotes/origin/main`; sufficient
history and the remote ref are mandatory. It must not execute a checked-out
candidate script to make either decision. The verifier has job-level
`permissions: { contents: read }`, uses pinned action SHAs, and its checkout
has `persist-credentials: false`; no candidate action, package-manager hook, or
script may run. All trust decisions are literal inline shell owned by the
default-branch workflow. The
`cuda-contract-preflight` job needs that verifier in addition to ordinary
release verification. A release-branch candidate is not eligible until an
explicit, separately reviewed trust mechanism proves equivalent protection;
the precise authorized alternative is
`dev/design/0.8.23-unmerged-candidate-provenance.md`.
Do not weaken this rule to admit a branch name, label, or candidate-controlled
script. The required external configuration attestation names the runner-group
ID, selected repository, selected workflow identity, default-branch/ref
behavior, and principals allowed to dispatch it. Repository tests may verify
the workflow/ref invariant, but labels and comments alone are not evidence of
that external configuration.

**R10-3 — reproducible build contract.** The privileged route fixes and records
the image, CUDA toolchain, Rust compiler, build strategy, model/cache inputs,
feature tuple, and dynamic-link inspection. The CUDA build must not require a
driver library for driverless CPU startup.

**R10-4 — retained preflight witness.** A successful trusted execution retains
the immutable candidate SHA, environment/image provenance, build/link output,
driverless installed Python and npm smoke results with all device-selection
variables absent (`auto` resolves to typed CPU), and selected-GPU PID/device
evidence. Existing explicitly-CPU-configured smokes are insufficient until
replaced by this behavior. Missing, mismatched, or incomplete evidence is
failure, not a substitute success.

Driverless smokes leave device-selection variables absent (`auto` resolves to typed CPU).
The same candidate witness also retains a forced `cuda:N` unavailable/incompatible smoke:
a forced request must produce its classified typed error, never a CPU
success report. This is preflight policy evidence, not the later Slice 20
installed CLI archive smoke.

**R10-5 — witness verifier hand-off.** Slice 10 supplies a versioned,
immutable-candidate-SHA-bound preflight-witness schema and fail-closed verifier.
Slice 20 owns the actual `all-builds-passed`/package-rehearsal edge that
requires verification of that witness for the same candidate SHA before any
future non-dry-run promotion. Slice 10 does not claim that the existing
dry-run-only sibling preflight is already a release-graph gate.

### P1 — v2 preflight witness and model-cache binding

The current `fathomdb.cuda-preflight-witness/v1` implementation is an interim
three-artifact record. Slice 10 implementation must replace it, rather than
loosening it, with `fathomdb.cuda-preflight-witness/v2`. Its canonical root
object has exactly `schema_version`, `candidate_sha`, `outcome`,
`build_input_sha256`, `model_cache_manifest_sha256`, and `evidence_sha256`.
`outcome` is only `passed`; every digest is lowercase SHA-256; and the v2
verifier rejects v1, unknown keys, a noncanonical JSON byte stream, a symlink,
or a candidate mismatch.

The root's `evidence_sha256` has exact-name equality for
`environment.txt`, `manylinux-build.txt`, `dynamic-dependencies.txt`,
`python-auditwheel.txt`, `driverless-python-cpu-smoke.txt`,
`driverless-napi-cpu-smoke.txt`, `gpu-python-cuda-witness.txt`,
`gpu-node-cuda-witness.txt`, `gpu-node-cuda-smoke.txt`, `build-input.json`,
`model-cache-manifest.json`, `forced-cuda-unavailable-python.json`,
`forced-cuda-unavailable-napi.json`, `forced-cuda-incompatible-python.json`,
`forced-cuda-incompatible-napi.json`,
`forced-cuda-unavailable-python-stdout.txt`,
`forced-cuda-unavailable-python-stderr.txt`,
`forced-cuda-unavailable-napi-stdout.txt`,
`forced-cuda-unavailable-napi-stderr.txt`,
`forced-cuda-incompatible-python-stdout.txt`,
`forced-cuda-incompatible-python-stderr.txt`,
`forced-cuda-incompatible-napi-stdout.txt`, and
`forced-cuda-incompatible-napi-stderr.txt`. Every named item is a regular,
nonempty, non-symlink file. `build-input.json` is canonical
`fathomdb.cuda-preflight-build-input/v2` JSON with exactly `schema_version`,
`candidate_sha`, `target`, `python_features`, `napi_features`,
`rerank_cuda`, and `model_cache_manifest_sha256`; its target is
`x86_64-unknown-linux-gnu`, its feature arrays are respectively
`["embed-cuda", "pyo3/extension-module"]` and
`["default-embedder", "embed-cuda"]`, and `rerank_cuda` is false. Its digest
equals the root `build_input_sha256`, and its cache-manifest digest equals the
root `model_cache_manifest_sha256`. Each forced record is canonical
`fathomdb.cuda-forced-device-failure/v1` JSON with exactly `schema_version`,
`consumer`, `requested_policy`, `cuda_compiled`, `visible_devices`, `status`,
`effective_device`, `reason`, `command`, `exit_code`, `stdout_filename`,
`stdout_sha256`, `stderr_filename`, and `stderr_sha256`. `requested_policy` is `cuda:0`; `consumer` is `python` or
`napi`; `cuda_compiled` is true; and `effective_device` is null. The unavailable
record has `visible_devices: []`, status `cuda_unavailable`, and reason
`no_visible_cuda_device`; the incompatible record has exactly one nonempty
visible-device identity object, status `cuda_incompatible`, and reason
`cuda_incompatible`. Both commands must fail typed and nonzero, never select
CPU, and retain hashes of the exact captured stdout and stderr bytes.

`command` is the fixed command identity `installed_python_engine_open` for
Python and `installed_napi_engine_open` for N-API: each opens a fresh temporary
database with its installed candidate artifact and `use_default_embedder` true,
then exits before any write. The harness records the actual argv in the paired
stdout/stderr capture, whose byte hashes are in the record; neither identity
permits `cargo run`, a source import, a host binary, a cache downloader, or a
success exit. `exit_code` is exactly `1`. This preserves a fixed schema despite
platform-specific interpreter paths while making the installed-artifact
operation auditable.

Each forced record binds to exactly its two retained captures: for example,
`forced-cuda-unavailable-python.json` names
`forced-cuda-unavailable-python-stdout.txt` and
`forced-cuda-unavailable-python-stderr.txt`; the other three outcome/consumer
pairs use the corresponding exact names above. Its `stdout_sha256` and
`stderr_sha256` are SHA-256 of those exact byte files, and the root
`evidence_sha256` map binds each named capture with the same digest. The
verifier rejects a missing, symlinked, empty, renamed, substituted, or
cross-record capture, even if its record digest is otherwise well formed.

`model-cache-manifest.json` is canonical `fathomdb.cuda-model-cache/v1` JSON
with exactly `schema_version`, `repository`, `revision`, `snapshot_relpath`,
and `files`. Its fixed repository/revision are the
`CUDA_DEFAULT_EMBEDDER_HF_REPO` and `CUDA_DEFAULT_EMBEDDER_HF_REVISION` values
from `cuda-artifact-contract.sh`; `snapshot_relpath` is
`hub/models--BAAI--bge-small-en-v1.5/snapshots/<revision>`; and `files` has
exactly `config.json`, `tokenizer.json`, and `model.safetensors`, mapped to the
three fixed SHA-256 contract values. The preflight creates the canonical file,
hashes it into both root fields, and records it before every smoke.

Every build and smoke that loads the default embedder receives that exact cache
seed through a read-only `HF_HOME=/fathomdb-hf` bind mount and a separate fresh
writable `XDG_CACHE_HOME=/fathomdb-product-cache`. Network is disabled, the
product cache is a controlled empty writable mount for that smoke, and `/tmp`
is distinct from both roots. `HOME` points at an unavailable directory; no
other cache root is mounted or supplied (`HUGGINGFACE_HUB_CACHE`,
`TRANSFORMERS_CACHE`, and loader test overrides are absent). This matches the
loader: it reads a valid pinned file from the read-only HF-hub seed, then
hard-links or copies it into its FathomDB product cache below
`$XDG_CACHE_HOME/fathomdb/embedders/...`; a cross-mount hard-link may fail and
the verified copy fallback is expected. Read-only mounting proves the HF seed
cannot be repaired or modified in place, while the fresh product cache proves
the normal production cache materialization path rather than an accidental
read-only-cache shortcut. The verifier checks the manifest against the fixed
contract values and retained preflight manifest, while the preflight fails
before sealing unless `sha256sum --check` has verified the mounted seed bytes;
neither check accepts a self-reported cache digest alone.

The migration starts with deterministic, committed fixtures for one complete
v2 witness and each unavailable, visible-incompatible, digest mismatch,
noncanonical, v1, and CPU-effective forced-CUDA mutation. Tests run the new
verifier over those fixtures; they do not run a trusted runner or treat fixture
success as a hardware witness.

## Acceptance criteria

**AC10-1.** RED→GREEN mutation tests prove that removing a forwarding edge,
moving `embed-cuda` to an unsupported artifact, or adding CUDA reranking to the
scope fails the contract checker.

**AC10-2.** RED→GREEN repository workflow tests prove that the privileged route
rejects a candidate not reachable from the protected default branch and rejects
a candidate-controlled workflow/ref or gate script. They prove the
self-hosted job needs the dedicated hosted verifier, while the ordinary
prerelease package/rehearsal policy remains unchanged. Before a real dispatch,
independently reviewed external configuration attestation proves the runner-
group ID, selected-repository/workflow restriction, default-branch/ref
behavior, and authorized dispatch principals.

**AC10-3.** Tests prove the pinned build/provisioning inputs, dynamic driver
loading boundary, and driverless unset/`auto` smoke contract are fail-closed.
They fail if either driverless smoke injects an embedder, reranker, CUDA,
device-visibility, or device-policy selection variable.

**AC10-4.** A real non-publishing trusted-runner run produces a retained,
schema-valid witness binding the exact candidate SHA to link inspection,
driverless Python/npm smokes with device-selection variables absent (`auto`
resolves to typed CPU), selected-GPU PID/device observations, and the forced
`cuda:N` unavailable/incompatible smoke's typed fail-closed outcome. Independent
evidence review verifies the downloaded witness. Static tests alone do not meet
this criterion.

**AC10-5.** RED→GREEN verifier/schema tests reject a missing, malformed,
different-candidate-SHA, or incomplete preflight witness. Slice 20's later
workflow-graph mutation test proves the actual aggregate/package-rehearsal edge
cannot omit that verifier. No Slice 10 test invokes publication, creates a tag,
or uses registry credentials.

## Secure-route decision required

The current release branch cannot satisfy R10-2: it is not reachable from
`origin/main`. The safe default-branch-owned design permits a preflight only
after the exact source commit is protected-default-branch reachable. That
conflicts with using the unmerged release branch as the preflight candidate.

An explicit HITL/security decision is therefore required before implementation
that changes runner access or the privileged route, and before a real runner
dispatch or acceptance of a hardware witness. The safe choices are:

1. Integrate the exact candidate into the protected default branch before its
   privileged preflight, then use its immutable default-branch SHA; or
2. Approve a new, independently reviewed attestation/provenance mechanism that
   gives an immutable release-branch commit protection equivalent to the
default branch before any privileged checkout.

HITL has authorized such an alternative only under the exact-SHA controls in
`dev/design/0.8.23-unmerged-candidate-provenance.md`; that document supersedes
the main-ancestry-only condition for the single approved route. It does not
authorize a branch-name, label, or candidate-owned workflow exception.

The decision record must include the external runner-policy attestation named
by R10-2. Allowing an arbitrary `release/*` ref, a label, or candidate-owned
scripts on the self-hosted runner is rejected.

## TDD and implementation sequence

   unset/`auto` environment absence, and witness-verifier failure cases.
2. Green the static checker, schema, and verifier work without changing runner
   access, dispatching a job, or accepting a hardware witness.
3. Commit a new RED workflow test that mutates a candidate gate script and the
   hosted-verifier dependency, then Green a default-branch-owned hosted route
   verifier. It must not change the ordinary prerelease package/rehearsal
   policy.
4. After the explicit HITL/security decision and external configuration
   attestation, implement only the approved secure route.
5. Obtain independent design/code review, then execute one authorized
   non-publishing trusted preflight and independently inspect its witness.
6. Write the Slice 10 status record and advance only when every acceptance
   criterion has direct evidence.
