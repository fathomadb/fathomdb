# Slice 70 — supported dual CPU/GPU runtime policy

## Decision and scope

HITL `seq:250` requires a released FathomDB executable to support CPU and GPU
without an end-user rebuild, a configurable GPU on/off policy, and a GPU
availability diagnostic. This design owns the product device-policy, doctor,
and artifact contract that must land before TC-5 can rely on the private,
cache-only benchmark factory.

The supported CUDA-capable artifact is Linux x86_64. It contains both CPU and
CUDA embedding support and dynamically loads an NVIDIA driver only when CUDA is
selected. Other current platform artifacts remain CPU-only and must report that
fact rather than advertise unavailable CUDA. This adds no registry publication.

## Requirements

**R70-D1 — one artifact, explicit policy.** A supported Linux x86_64
CUDA-capable CLI/Python/N-API artifact is built once with `embed-cuda` and can
run on CPU without an NVIDIA driver. Its single cross-surface preference is
`auto`, `cpu`, or `cuda:N`:

- `auto` is the default on a CUDA-capable artifact. It probes a visible provider
  and selects a compatible CUDA device; absent/unusable CUDA selects CPU with a
  typed compatibility report.
- `cpu` is explicit off. It never initializes or loads CUDA.
- `cuda:N` is explicit on. It must initialize and probe that ordinal or fail
  with a typed error; it never silently falls back to CPU.

CPU-only artifacts treat `auto` as CPU and report `cuda_not_compiled`; forced
`cuda:N` fails typed. `FATHOMDB_EMBED_DEVICE` is the sole configuration
transport for all Rust, Python, and TypeScript opens: unset means `auto`, and
the accepted values are exactly `auto`, `cpu`, and `cuda:N` (base-10 ordinal).
It supersedes the legacy `cpu`/`cuda` ambient spellings; malformed or legacy
values are typed configuration errors. `FATHOMDB_RERANK_DEVICE` does not select
the embedder and is rejected as an embedder-policy override. No SDK-specific or
hidden device setting is introduced.

**R70-D2 — typed provider evidence.** The embedder exposes an injectable,
typed provider probe and resolution report: requested policy, compiled CUDA
capability, visibility, selected/effective device, compatibility reason, and
safe CUDA identity metadata where available. `Engine::open` consumes that
resolved report exactly once. It preserves vector-equivalence enforcement and
cannot silently re-use a compatibility result across a CPU/CUDA backend change.

CUDA compatibility requires actual provider initialization and a minimal CUDA
allocation/provider probe. It never performs a model load, download, or
inference, and does not guess a driver version. Runtime reports retain only
facts the provider observes reliably: process-visible ordinal, UUID where the
provider exposes one, name, and compute capability.
Build target, CUDA toolkit, and driver-version provenance remain Slice 10/20 artifact-witness facts; they
are not fields in `fathomdb.doctor.gpu.v1` and are not fabricated as runtime
observations.

### Current-state gap and production provider extension

The production contract extends the injected boundary with
`CudaProvider::enumerate_visible_cuda_devices`, returning an ordered
`CudaVisibleDevice` inventory before a device is selected. The Candle provider
uses the loaded CUDA driver API to initialize the driver, obtain the process
visible count and handles (`cuDeviceGetCount`, `cuDeviceGet`), and read each
visible device's UUID (`cuDeviceGetUuid`), name, and compute capability. The
inventory records the process-visible ordinal and UUID; it does not infer host
index from a physical-device ordering hidden by `CUDA_VISIBLE_DEVICES`.

Resolution maps a requested `cuda:N` to the inventory member with visible
ordinal `N`, and `auto` selects the lowest visible ordinal. A successful empty
enumeration is `no_visible_cuda_device`/`cuda_unavailable`. A successful probe
returns the same UUID and visible ordinal that the report publishes. The public
`DeviceResolution`/doctor JSON consequently gains the ordered inventory and
selected UUID, while a forced failure carries the observed inventory but no
effective CPU device.

The production Candle classifier is deliberately closed and code-based rather
than message-matched. Absent dynamic driver library, `CUDA_ERROR_NO_DEVICE`,
and `CUDA_ERROR_STUB_LIBRARY` are unavailable evidence. Exactly
`CUDA_ERROR_SYSTEM_DRIVER_MISMATCH`,
`CUDA_ERROR_COMPAT_NOT_SUPPORTED_ON_DEVICE`, `CUDA_ERROR_NO_BINARY_FOR_GPU`,
`CUDA_ERROR_UNSUPPORTED_PTX_VERSION`, `CUBLAS_STATUS_ARCH_MISMATCH`, and
`CUBLAS_STATUS_NOT_SUPPORTED` are compatibility/architecture evidence. Unknown
driver/Candle errors, `CUDA_ERROR_OUT_OF_MEMORY`, and
`CUBLAS_STATUS_ALLOC_FAILED` are probe-failed evidence. A mapped-device
`NoVisibleDevice` remains unavailable rather than being promoted to
`probe_failed`. No other error is promoted because its rendered text resembles
one of these classes.

ONNX uses its dedicated strict provider resolver because ONNX Runtime exposes
CUDA-provider availability and session construction but not the Candle driver
inventory/UUID seam. Explicit CPU performs no CUDA query. `auto` probes ordinal
zero and may build CPU only when CUDA is unavailable or CUDA session
construction fails; forced `cuda:N` attempts that CUDA provider/session only
and never builds CPU. `Ok(false)` availability is unavailable, while an
availability API error is `probe_failed`. Its honest open report has an empty
visible inventory and no UUID; the UUID-bearing `doctor gpu` remains the Candle
provider diagnostic.

Hardware-independent tests use deterministic `FixtureCudaProvider`
inventory/probe fixtures: empty inventory, one UUID that fails its probe, and
one UUID that probes successfully. Trusted-runner contract fixtures use the
same deterministic fixture input for the unavailable and visible-incompatible
records; they prove serializer/verifier classification and UUID/ordinal binding,
not a claim that a particular host can manufacture an incompatible GPU. The
real trusted-runner selected-GPU smoke instead uses the production provider and
retains its actual UUID/visible-ordinal mapping.

Current state enumerates visible CUDA devices through
`CudaProvider::enumerate_visible_cuda_devices`; UUIDs come from
`cuDeviceGetUuid` rather than names or host ordinals.

**R70-D3 — public diagnostic.** `fathomdb doctor gpu [--json]` is a
configuration *reader* and isolated CUDA diagnostic, not an Engine or model
initializer: it does not open or mutate a database, load or download a model,
write configuration, create `init`, or initialize an engine. It is the CLI's
provider enumeration/allocation-probe seam only; `doctor warm-cache` remains
separate. There is no SDK doctor method or SDK device setter: Rust, Python, and
TypeScript continue to use only `FATHOMDB_EMBED_DEVICE` at open time.

This diagnostic does not create `init`, and it introduces no SDK device setter
or alternate configuration transport.

Its JSON has `schema_version: "fathomdb.doctor.gpu.v1"`. Its canonical compact
JSON object has keys in this exact order:
`schema_version`, `policy`, `cuda_compiled`, `status`, `effective_device`,
`devices`, `reason`, and `selected_uuid`. `schema_version` is
`"fathomdb.doctor.gpu.v1"`; `reason` and `selected_uuid` are always present and
are JSON `null` when absent. Each device object has exactly
`visible_ordinal`, `uuid`, `name`, and `compute_capability` in that order;
`compute_capability` is present as `null` when unavailable. The compact object
is followed by exactly one newline.
`devices` is an ordered process-visible CUDA inventory. Each member contains
`visible_ordinal`, a driver UUID, name, and compute capability; the ordinal is
the `CUDA_VISIBLE_DEVICES`-relative ordinal and no host/physical ordinal is
reported or inferred. `selected_uuid`, when present, is the UUID of the
effective CUDA device and must match exactly one `devices` member. If driver
initialization prevents enumeration, `devices` is an empty inventory rather
than a fabricated device observation. `status` is exactly `selected_cuda`,
`selected_cpu_no_cuda`, `cuda_not_compiled`, `cuda_unavailable`,
`cuda_incompatible`, `invalid_policy`, or `probe_failed`.

### Doctor exit matrix

Normal open resolution and the diagnostic have deliberately different result
types. Open uses `DeviceResolution`, for which automatic CPU fallback can carry
`DeviceResolutionReason::CudaProbeFailed`. `doctor gpu` instead produces a
`DoctorGpuDiagnosticResult`, distinct from `DeviceResolution`, from the raw
driver, inventory, and allocation/provider-probe evidence. It must not
serialize a normal open resolution as its diagnostic result. In particular,
`CudaProbeError::ProbeFailed` maps to `probe_failed` and exit `70`, rather than
becoming a policy-satisfied automatic fallback merely because CPU is usable.

The command emits one report on every classified outcome. `effective_device` is
the literal typed CPU device (`"cpu"`) for an automatic CPU result, a selected
`cuda:N` for `selected_cuda`, and `null` for invalid or forced-policy failure.
`devices` is `[]` if enumeration did not succeed; otherwise it is the observed
ordered inventory. `selected_uuid` is `null` unless CUDA was selected. The exit
code is part of the schema contract:

The semantic matrix has exactly twelve rows. Pre-inventory failures retain
`devices: []`; the corresponding mapped-device phase retains the observed
inventory. Those phase shapes are separate AC70-D3 process cases even when
they share one semantic row.

| Requested policy / observation | CUDA activity | Status | Effective device | Devices | Selected UUID | Exit |
| --- | --- | --- | --- | --- | --- | --- |
| `cpu` (any artifact) | none | `selected_cpu_no_cuda` | `cpu` | `[]` | `null` | `0` |
| `auto`, CPU-only artifact | none | `cuda_not_compiled` | `cpu` | `[]` | `null` | `0` |
| `auto`, unavailable evidence | driver-presence, enumeration, or ordinal mapping | `cuda_unavailable` | `cpu` | `[]` before inventory; otherwise observed inventory | `null` | `0` |
| `auto`, listed compatibility/architecture evidence | enumeration or mapped-device probe | `cuda_incompatible` | `cpu` | `[]` before inventory; otherwise observed inventory | `null` | `0` |
| `auto`, unknown, OOM, or allocation/provider failure | enumeration or mapped-device probe | `probe_failed` | `cpu` | `[]` before inventory; otherwise observed inventory | `null` | `70` |
| `auto`, selected device allocation/provider probe succeeds | enumeration + mapped-device probe | `selected_cuda` | selected `cuda:N` | observed inventory | matching UUID | `0` |
| forced `cuda:N`, CUDA not compiled | none | `cuda_not_compiled` | `null` | `[]` | `null` | `65` |
| forced `cuda:N`, unavailable evidence | driver-presence, enumeration, or ordinal mapping | `cuda_unavailable` | `null` | `[]` before inventory; otherwise observed inventory | `null` | `65` |
| forced `cuda:N`, listed compatibility/architecture evidence | enumeration or mapped-device probe | `cuda_incompatible` | `null` | `[]` before inventory; otherwise observed inventory | `null` | `65` |
| forced `cuda:N`, unknown, OOM, or allocation/provider failure | enumeration or mapped-device probe | `probe_failed` | `null` | `[]` before inventory; otherwise observed inventory | `null` | `70` |
| forced `cuda:N`, selected device allocation/provider probe succeeds | enumeration + mapped-device probe | `selected_cuda` | selected `cuda:N` | observed inventory | matching UUID | `0` |
| malformed, legacy, or otherwise invalid policy | none | `invalid_policy` | `null` | `[]` | `null` | `70` |

Thus every policy-satisfied automatic CPU fallback exits `0`; an automatic true
driver or allocation/provider diagnostic failure is deliberately visible as
`probe_failed` with a typed CPU `effective_device` and exit `70`, never
reclassified as a normal CPU fallback. Thus forced `cuda:N` reports no
`effective_device` for not-compiled/unavailable/incompatible outcomes and exits
`65`; it never silently falls back to CPU. Invalid policy invokes no CUDA
provider code.

**R70-D4 — artifact truth.** Slice 20’s installed-artifact contract proves
driverless CPU with the policy unset/`auto`, compatible GPU engagement under
`auto`, and forced-CUDA fail-closed behavior. Linux x86_64 Python, N-API, and
CLI use the same CUDA feature tuple. Slice 20 adds the versioned Linux x86_64
`fathomdb` CLI archive coordinate to its rehearsal bundle, installing and
smoking it with driverless `auto`, compatible-GPU `auto`, and forced-CUDA
failure before a future canonical publisher can consume its exact digest.
Its strict v2 manifest/verifier accepts the exact four-artifact inventory and
all four CLI evidence modes; it rejects a legacy three-artifact bundle or a
substituted archive. Canonical publication remains hard-blocked until its
separately commissioned route exists.

**R70-D5 — TC-5 isolation.** TC-5 accepts no ambient product policy. Its
private cache-only factory takes an explicit preflight-selected device and
pinned local asset directory; `measurement_complete` never derives from
product `auto` resolution.

### P1 — CLI feature forwarding and deterministic archive

The future Linux CLI candidate is a real CUDA-capable product artifact, not a
wrapper around a source checkout.  `fathomdb-cli` must add exactly this feature
edge:

```toml
embed-cuda = ["default-embedder", "fathomdb/embed-cuda", "fathomdb-embedder/embed-cuda"]
```

The `fathomdb` facade must in turn expose
`default-embedder = ["fathomdb-engine/default-embedder"]` and
`embed-cuda = ["default-embedder", "fathomdb-engine/embed-cuda"]`. The direct
CLI embedder edge is required because `doctor warm-cache` uses that crate; the
facade edge is required because an `Engine::open` invoked from the CLI must get
the same CUDA implementation. No CLI CUDA artifact enables `rerank-cuda`.

For release version `${version}` and target `x86_64-unknown-linux-gnu`, the
canonical candidate file name is
`fathomdb-${version}-x86_64-unknown-linux-gnu.tar.gz`. The build command is
exactly
`cargo build --locked --release -p fathomdb-cli --features embed-cuda --target x86_64-unknown-linux-gnu`.
It takes the resulting `target/x86_64-unknown-linux-gnu/release/fathomdb` into
a fresh staging tree whose only root is
`fathomdb-${version}-x86_64-unknown-linux-gnu/` and whose only leaf is
`fathomdb-${version}-x86_64-unknown-linux-gnu/fathomdb`. The directory and
binary mode are `0755`; there are no symlinks, hard links, device nodes, extra
files, owners other than numeric `0:0`, or variable timestamps. With `umask
022`, the sealer must use
`tar --format=posix --sort=name --mtime=@0 --owner=0 --group=0 --numeric-owner --pax-option=delete=atime,delete=ctime`
over that staging root and pipe the result through `gzip -n`. The archive
SHA-256 is over those final gzip bytes, not the extracted executable.

Extraction is fail-closed: before it can run a CLI smoke, the consumer checks
the retained archive digest; rejects a symlinked archive; and rejects an
archive that does not have exactly that one POSIX root directory and one regular
`fathomdb` leaf at mode `0755`. It extracts into a new directory and invokes
only that extracted leaf by absolute path. A source checkout, a host `PATH`
binary, `cargo run`, or a binary copied after archive sealing is not CLI
evidence.

### P1 — CLI v2 evidence records

The Slice 20 manifest changes from `fathomdb.cuda-package-rehearsal/v1` to
`fathomdb.cuda-package-rehearsal/v2`. Its `packages` map has exactly the Python
wheel, thin npm tarball, Linux N-API tarball, and the canonical CLI archive;
the CLI key is its canonical filename and value is the archive SHA-256 above.
The v2 `build_input` includes the exact `cli_features` array
`["embed-cuda"]`, target `x86_64-unknown-linux-gnu`, and the archive coordinate;
it cannot claim the CLI CUDA feature through a transitive or ambient feature.

The v2 smoke map has two exact CLI evidence classes in addition to the existing
Python and N-API evidence: metadata records `cpu-cli.json` and
`forced-cuda-unavailable-cli.json`, plus their raw canonical doctor-output
files. Every metadata record uses schema
`fathomdb.cuda-package-cli-smoke/v2` and binds archive identity, requested
policy and ordinal, exact environment, diagnostic-only isolation, exit/status,
and raw-output filename/SHA-256. `consumer` is `cli`; `target` is
`x86_64-unknown-linux-gnu`; `argv` is exactly
`["/fathomdb-cli/fathomdb-${version}-x86_64-unknown-linux-gnu/fathomdb", "doctor", "gpu", "--json"]`.
The sealed archive is extracted into the fresh fixed `/fathomdb-cli` directory,
and the harness executes only that absolute leaf; it must not record a logical
`fathomdb` replacement or resolve a `PATH` command.
`doctor_output_sha256` is SHA-256 of its one stdout JSON object including its
trailing newline. The raw output files are exactly `cpu-cli-stdout.json` and
`forced-cuda-unavailable-cli-stdout.json`. Compatible-GPU CLI evidence stays
`PENDING_EXTERNAL`; visible-incompatible classification stays in deterministic
provider fixtures rather than being mislabeled installed-candidate evidence.

CLI evidence is diagnostic-only: every CLI policy-probe command is `doctor gpu --json` on the extracted binary and deliberately neither opens a database nor
loads/downloads a model. Python and N-API installed-artifact smokes are the
only model-operation proof: they retain the cache-backed
open/embed/write/search/close exercise. The CLI records prove only runtime
selection or forced fail-closed diagnostics, not SDK or model behavior.

`cpu-cli.json` has exit `0`, status `cuda_unavailable`,
`effective_device: "cpu"`, and reason `no_visible_cuda_device`.
`forced-cuda-unavailable-cli.json` invokes the same command with
`FATHOMDB_EMBED_DEVICE=cuda:0`, has exit `65`, `effective_device: null`, and
status/reason `cuda_unavailable`/`no_visible_cuda_device`. It must never record
a CPU effective device or zero exit. The short-lived doctor command makes no
GPU PID claim. This command proves selection and fail-closed policy without
opening a database or downloading a model.

### P1 — OpenReport binding representation

Every binding mirrors a present `OpenReport.embedder_device_resolution` as a
strict `DeviceResolution`: requested policy (`auto`, `cpu`, or `cuda:N`),
artifact CUDA capability, effective CPU/CUDA selection, optional safe CUDA
provider facts, and optional automatic-fallback reason. Python uses frozen
snake_case dataclasses; TypeScript exposes readonly camelCase read shapes; the
native binding objects carry the same fields. The report is `None`/`null` only
when open received no resolution. A forced-CUDA failure remains a typed open
error and must never be represented as CPU.

A report-bearing `OrtBgeEmbedder` caller passes its constructed embedder and
the captured resolution through `EmbedderChoice::CallerWithDeviceResolution`,
because ONNX Runtime only knows its final CPU/CUDA outcome after session
construction. The older `Caller` variant remains resolution-less; no runtime
re-probe is permitted merely to fill the report.

## Acceptance criteria

**AC70-D1.** RED→GREEN parser/probe tests cover `cpu`, `auto`, `cuda:N`,
invalid input, CPU-only artifact, no visible GPU, incompatible GPU, compatible
GPU, and forced-CUDA failure. Tests prove `cpu` makes no provider call and
forced CUDA never yields CPU.

**AC70-D2.** Engine and binding tests prove the `FATHOMDB_EMBED_DEVICE`
policy/report reaches
default-embedder construction once, reports requested/effective selection, and
does not hide backend changes from vector-equivalence handling.

**AC70-D3.** CLI tests prove every doctor exit-matrix row, including automatic
CPU fallback success (`0`), automatic driver/probe failure (`probe_failed`,
typed CPU, `70`), forced not-compiled/unavailable/incompatible (`null`, `65`),
and invalid policy (`70` without a provider call). They prove text/JSON shapes,
the UUID-visible-ordinal inventory/selection binding, and absence of database,
engine, loader/download, and configuration-write activity. Interface
documentation lists the command and policy.

AC70-D3 runs eighteen deterministic process cases: the twelve semantic rows,
with unavailable, incompatible, and probe-failed split into pre-inventory and
post-inventory cases for both `auto` and forced CUDA. Each case pins one exact
exit, text and JSON output, reason, inventory, selected UUID/ordinal binding,
and empty stderr. Fresh working, home, XDG, and model-cache roots plus explicit
side-effect canaries prove no database, engine, loader/download, model-cache,
or configuration-write activity.

The normative text output is exactly this newline-terminated sequence, with
one `device=<canonical compact device JSON>` line per ordered inventory member:

```text
doctor gpu
policy=<JSON string>
cuda_compiled=<true|false>
status=<status>
effective_device=<cpu|cuda:N|null>
reason=<reason|null>
devices=<decimal count>
device={"visible_ordinal":N,"uuid":"...","name":"...","compute_capability":"..."|null}
selected_uuid=<UUID|null>
```

Process coverage uses a non-shipping subprocess fixture dispatcher inside the
`fathomdb-cli` library test executable. The parent parses the real
`doctor gpu [--json]` argv into `Cli`, selects one of the eighteen typed fixture
providers in test code, and spawns the same test executable once for text and
once for JSON. The private dispatcher calls the same command-routing and output
functions as the product entry point; only provider construction differs.
No product binary argument or environment variable selects a fixture. The test
selector is read exclusively by `cfg(test)` code in the non-shipping test
executable.

For each child, the parent supplies fresh working, `HOME`, XDG, Hugging Face,
model-cache, and database-canary roots and snapshots them before and after.
`strace -f` records file and network syscalls: the assertion permits runtime
library/config reads outside those roots, rejects every network syscall, rejects
write/create/remove/rename operations, and rejects every access beneath the
database, XDG, Hugging Face, and model-cache canary roots. If sandbox ptrace is
denied, the unchanged strict gate runs unconfined as required by `AGENTS.md`;
the test is not weakened or skipped. Together with the private injected
provider boundary, this proves the command cannot reach Engine, database,
model-loader/download, cache, or configuration-write activity.

**AC70-D4.** Release-contract mutation tests reject losing CLI CUDA forwarding,
driverless unset/`auto` policy absence, a CUDA artifact without GPU probe
evidence, the versioned CLI archive/digest or any required CLI smoke, a
forced-CUDA fallback, or a non-Linux CUDA claim.

**AC70-D5.** TC-5 tests prove all `FATHOMDB_*` product settings remain rejected
and its explicit cache-only device factory is the only benchmark selection path.

## Documentation reconciliation audit

The current-document audit is `scripts/tests/test_slice70_embedding_docs_contract.sh`.
It pins the public embedder guide, Python API, TypeScript API, locked Rust/Python/
TypeScript interfaces, package/source help, eval CLI help, and the Slice 10/20
artifact-evidence design to the one runtime policy. It also rejects the prior
default-CPU and forced-CUDA-to-CPU fallback claims from the artifact design.
It requires forced-`cuda:N` evidence in both the Slice 10 and Slice 20 designs.
Slice 10 preflight must retain the unavailable/incompatible typed outcome, and
Slice 20 must retain the installed CLI archive's unavailable and incompatible
typed outcomes. This audit is design/static evidence only; it does not run a
trusted runner, build an archive, or authorize publication.

The deliberately historical exclusions are the original 0.8.1 GPU/portability
proposal, the 0.8.16 ONNX design and ADR, and the internal GPU allocation/eval
policies. Each must carry an explicit Slice 70 current-policy pointer; their
retained architecture, measurement, or internal-allocation history is not a
live runtime contract.
