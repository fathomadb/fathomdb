# Slice 70 — supported dual CPU/GPU runtime policy

## Decision and scope

HITL `seq:250` requires a released FathomDB executable to support CPU and GPU
without an end-user rebuild, a configurable GPU on/off policy, and a GPU
availability diagnostic. This design owns the product device-policy, doctor,
and artifact contract that must land before TC-5 can rely on the private,
cache-only benchmark factory.

The supported CUDA-capable artifact is Linux x86_64. It contains both CPU and
CUDA embedding support and dynamically loads an NVIDIA driver only when CUDA is
selected. Other current platform artifacts remain CPU-only and must report that
fact rather than advertise unavailable CUDA. This adds no registry publication.

## Requirements

**R70-D1 — one artifact, explicit policy.** A supported Linux x86_64
CUDA-capable CLI/Python/N-API artifact is built once with `embed-cuda` and can
run on CPU without an NVIDIA driver. Its single cross-surface preference is
`auto`, `cpu`, or `cuda:N`:

- `auto` is the default on a CUDA-capable artifact. It probes a visible provider
  and selects a compatible CUDA device; absent/unusable CUDA selects CPU with a
  typed compatibility report.
- `cpu` is explicit off. It never initializes or loads CUDA.
- `cuda:N` is explicit on. It must initialize and probe that ordinal or fail
  with a typed error; it never silently falls back to CPU.

CPU-only artifacts treat `auto` as CPU and report `cuda_not_compiled`; forced
`cuda:N` fails typed. `FATHOMDB_EMBED_DEVICE` is the sole configuration
transport for all Rust, Python, and TypeScript opens: unset means `auto`, and
the accepted values are exactly `auto`, `cpu`, and `cuda:N` (base-10 ordinal).
It supersedes the legacy `cpu`/`cuda` ambient spellings; malformed or legacy
values are typed configuration errors. `FATHOMDB_RERANK_DEVICE` does not select
the embedder and is rejected as an embedder-policy override. No SDK-specific or
hidden device setting is introduced.

**R70-D2 — typed provider evidence.** The embedder exposes an injectable,
typed provider probe and resolution report: requested policy, compiled CUDA
capability, visibility, selected/effective device, compatibility reason, and
safe CUDA identity metadata where available. `Engine::open` consumes that
resolved report exactly once. It preserves vector-equivalence enforcement and
cannot silently re-use a compatibility result across a CPU/CUDA backend change.

CUDA compatibility is decided by actual provider initialization and a minimal
embed probe, not a guessed driver version. The report retains the artifact CUDA
toolkit/build target and driver/compute metadata as supplemental facts.

**R70-D3 — public diagnostic.** `fathomdb doctor gpu [--json]` is read-only:
it neither opens/mutates a database nor downloads a model. It reports the
policy, compiled capability, visible devices, provider-init/probe verdict,
effective selection, and classified incompatibility. Its JSON is
`fathomdb.doctor.gpu.v1` with `policy`, `cuda_compiled`, `status`,
`effective_device`, `devices`, and optional `reason`; `status` is exactly
`selected_cuda`, `selected_cpu_no_cuda`, `cuda_not_compiled`,
`cuda_unavailable`, `cuda_incompatible`, `invalid_policy`, or `probe_failed`.
It exits 0 when policy is
satisfied, 65 for unavailable forced CUDA, and 70 for malformed policy or
diagnostic runtime failure. `doctor warm-cache` remains separate.

**R70-D4 — artifact truth.** Slice 20’s installed-artifact contract proves
driverless CPU with the policy unset/`auto`, compatible GPU engagement under
`auto`, and forced-CUDA fail-closed behavior. Linux x86_64 Python, N-API, and
CLI use the same CUDA feature tuple. Slice 20 adds the versioned Linux x86_64
`fathomdb` CLI archive coordinate to its rehearsal bundle, installing and
smoking it with driverless `auto`, compatible-GPU `auto`, and forced-CUDA
failure before a future canonical publisher can consume its exact digest.
Canonical publication remains hard-blocked
until its separately commissioned route exists.

**R70-D5 — TC-5 isolation.** TC-5 accepts no ambient product policy. Its
private cache-only factory takes an explicit preflight-selected device and
pinned local asset directory; `measurement_complete` never derives from
product `auto` resolution.

### P1 — OpenReport binding representation

Every binding mirrors a present `OpenReport.embedder_device_resolution` as a
strict `DeviceResolution`: requested policy (`auto`, `cpu`, or `cuda:N`),
artifact CUDA capability, effective CPU/CUDA selection, optional safe CUDA
provider facts, and optional automatic-fallback reason. Python uses frozen
snake_case dataclasses; TypeScript exposes readonly camelCase read shapes; the
native binding objects carry the same fields. The report is `None`/`null` only
when open received no resolution. A forced-CUDA failure remains a typed open
error and must never be represented as CPU.

A report-bearing `OrtBgeEmbedder` caller passes its constructed embedder and
the captured resolution through `EmbedderChoice::CallerWithDeviceResolution`,
because ONNX Runtime only knows its final CPU/CUDA outcome after session
construction. The older `Caller` variant remains resolution-less; no runtime
re-probe is permitted merely to fill the report.

## Acceptance criteria

**AC70-D1.** RED→GREEN parser/probe tests cover `cpu`, `auto`, `cuda:N`,
invalid input, CPU-only artifact, no visible GPU, incompatible GPU, compatible
GPU, and forced-CUDA failure. Tests prove `cpu` makes no provider call and
forced CUDA never yields CPU.

**AC70-D2.** Engine and binding tests prove the `FATHOMDB_EMBED_DEVICE`
policy/report reaches
default-embedder construction once, reports requested/effective selection, and
does not hide backend changes from vector-equivalence handling.

**AC70-D3.** CLI tests prove `doctor gpu` text/JSON shapes, exit codes, and
absence of database, loader, and download activity. Interface documentation
lists the command and policy.

**AC70-D4.** Release-contract mutation tests reject losing CLI CUDA forwarding,
CPU driverless policy absence, a CUDA artifact without GPU probe evidence, a
forced-CUDA fallback, or a non-Linux CUDA claim.

**AC70-D5.** TC-5 tests prove all `FATHOMDB_*` product settings remain rejected
and its explicit cache-only device factory is the only benchmark selection path.

## Documentation reconciliation audit

The current-document audit is `scripts/tests/test_slice70_embedding_docs_contract.sh`.
It pins the public embedder guide, Python API, TypeScript API, locked Rust/Python/
TypeScript interfaces, package/source help, eval CLI help, and the Slice 10/20
artifact-evidence design to the one runtime policy. It also rejects the prior
CPU-default and forced-CUDA-to-CPU fallback claims from the artifact design.

The deliberately historical exclusions are the original 0.8.1 GPU/portability
proposal, the 0.8.16 ONNX design and ADR, and the internal GPU allocation/eval
policies. Each must carry an explicit Slice 70 current-policy pointer; their
retained architecture, measurement, or internal-allocation history is not a
live runtime contract.
