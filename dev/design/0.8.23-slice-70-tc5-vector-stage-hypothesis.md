# Slice 70 — TC-5 vector-stage controls

> **Product-runtime prerequisite.** Per HITL `seq:250`, the supported
> dual-runtime device policy, diagnostic, and artifact contract in
> `0.8.23-slice-70-dual-runtime-device-policy.md` must be reviewed and locally
> complete before this private benchmark seam resumes. TC-5 continues to reject
> ambient product configuration.

## Hypothesis

A dedicated benchmark executable with a narrow, typed internal interface can
measure pre-fusion 1-bit candidate retrieval, exact-f32 rerank, and exact-f32
top-k without calling any hybrid search path or widening public language APIs.
The experiment runner supplies allowed values such as `candidate_k`; the
runtime validates, applies, and attests the resolved values rather than
hard-coding them. It selects and attests a usable GPU when one is visible and
usable, permits CPU only when no CUDA GPU is visible, and fails closed on device-selection drift,
missing identity or timing evidence, an incomplete result, or a prohibited
route.

## Need and requirements

**N70-TC5-VECTOR-STAGE.** TC-5 experiment tooling needs a supported,
benchmark-only way to measure the exact pre-fusion vector pipeline with its
selected settings and identities.

## Current state and net-new surface

The existing `set_vector_stage_only_for_test` and search-limit controls are
process-global test seams. They still enter ordinary hybrid search and must not
be wrapped or promoted. Ordinary hybrid search retains its hard-coded
`TOP_K_BIT_CANDIDATES = 192` behavior unchanged.

Slice 70 is net-new: private `VectorStageRequest` and `VectorStageResult`
values, a dedicated reader-worker request variant, a `fathomdb-tc5-benchmark`
executable, and a strict benchmark spec/result ABI. It adds no Python,
TypeScript, CLI, or ordinary Rust SDK benchmark control.

**R70-1 — typed control plane.** The runner supplies one versioned,
allowlisted experiment specification to the `fathomdb-tc5-benchmark`
executable. Its exact CLI is `--spec <path> --result <path>` and it accepts no
other arguments. Its benchmark-control environment allowlist is empty:
`FATHOMDB_TC5_*`, `FATHOMDB_EMBED_DEVICE`, and other FathomDB device/config
overrides are rejected rather than interpreted. The executable rejects an
existing or symlink result destination, network/download behavior, and any
output that contains corpus content, paths, raw IDs, or predictions. It uses a
create-new temporary file plus Linux non-replacing final installation (or a
demonstrably equivalent primitive), so an adversary cannot win a race and have
an existing result overwritten.

The closed result status set is `measurement_complete`, `asset_unavailable`,
and `device_unavailable`. Malformed CLI/specification/manifest/pin inputs,
fixture/index identity failures, database-open failures, and execution failures
emit no result file. A missing cache-only asset must emit
`asset_unavailable`; visible-but-unusable, ambiguous, or unattestable CUDA must
emit `device_unavailable`. A non-measurement result contains only its version,
status, typed error code, and safe resolved-settings digest; it contains no
timings, identities, cardinalities, routes, or result evidence. Only
`measurement_complete` carries all required identities, cardinalities, route
attestations, and timings.
Its envelope identifies `workload = vector_stage_v1`; other workload modules
such as FTS, graph, CE, and fusion are intentionally absent and rejected until
separately commissioned. Its only vector-stage tunable fields are
`candidate_k`, `top_k`, and bounded warmup/repetition/single-process controls.
The strict schema fixes
`algorithm = bit_knn_f32_rerank_v1` and `rerank = exact_f32`; it references a
qualified manifest whose model asset, fixture, index, indexed-vector population,
query, and seed identities are immutable pins. It derives an immutable
`VectorStageScope` from the manifest's allowed kind/selection and carries it to
the dedicated handler; it is not a runner-supplied filter. The handler applies
that same scope to candidate SQL, f32 rerank hydration, and full-corpus ground
truth, then rejects observed selection or row-count drift. It begins one
deferred SQLite read transaction before candidate lookup, makes the query vector
once, and carries immutable scope, expected count, and selection digest through
all three routes. Every order is deterministic: distance followed by a stable
internal row key for candidate, rerank, and full-corpus truth results. The manifest
specifies the allowed candidate/top-k set or range and `expected_vector_rows`; a
pin mismatch fails closed and the executor enforces
`1 <= top_k <= candidate_k <= expected_vector_rows`. TC-5 sets
`candidate_k = 192` and `top_k = 10` in its manifest; neither value is an engine
constant. It cache-loads only the manifest-pinned local model asset, never
falls back to loader download, and emits a typed asset-unavailable result before
database open when that asset is absent. Unknown fields, invalid ranges, and
prohibited combinations also fail before database open.

**R70-2 — exact execution seam.** An immutable, request-scoped vector-stage
request carries the query input, `candidate_k`, and `top_k` through a dedicated
reader-worker `VectorStage` path. It runs 1-bit candidate retrieval followed by
exact-f32 rerank. Candidate retrieval, rerank, and full-corpus exact-f32
top-k ground truth use that one deferred read snapshot and query vector. The path
must not invoke `Engine::search`, compile or query FTS, fuse results,
graph-expand, or CE-rerank; a process-global test toggle is not a supported
execution seam. Its handler cannot receive compiled text, runner-supplied
filters, CE, graph, recency, importance, or fusion parameters. A request-scoped
test observer proves `VectorStage`, never `Search`, dispatch. The implementation
uses a documented, narrowly `pub` benchmark module gated behind a dedicated
`tc5-benchmark` Cargo feature in `fathomdb-engine`. The crate declares
`fathomdb-tc5-benchmark` with `required-features = ["tc5-benchmark"]`; the
`fathomdb` facade does not re-export the module. A governed-surface/compile-fail
test proves ordinary builds cannot name it. Any enabled `pub` surface is
recorded in `dev/interfaces/rust.md`.

**R70-3 — runtime enforcement.** The benchmark runtime, not `Embedder`, owns
device selection and attestation. Before database open, it performs an explicit
CUDA/NVIDIA visibility and usable-device preflight. Ambiguous visibility is
failure; no visible CUDA GPU permits CPU. A visible GPU is usable only after
provider initialization/probe succeeds and its returned identity matches the
benchmark-owned logical `cuda:0` mapping; then GPU selection is mandatory. The
Linux x86_64 CUDA-only runtime derives this mapping from exactly one manifest-
pinned physical CUDA GPU UUID and records its UUID, PCI ID, name, driver, and
logical ordinal. Multiple visible CUDA devices without that unique mapping,
masked/ambiguous CUDA visibility, or a non-CUDA accelerator are typed failure,
not CPU permission. The effective `CandleBgeEmbedder::device_label()` must be
`cuda:0`. An attempted GPU whose initialization, probe, effective-device label,
or attestation fails is an explicit fail-closed outcome, never a
reclassification to CPU.

The `tc5-benchmark` feature supplies a benchmark-only cache-only embedder
factory. It accepts the preflight-selected concrete device and manifest-pinned
local asset path; it performs no ambient device parse and has no downloader
fallback. Its typed asset-unavailable result occurs before database open. The
selected provider applies to query embedding only: SQLite bit-KNN and exact-f32
rerank remain CPU stages, separately attested. Missing model/fixture/index/
runtime or build identity, incomplete candidate or top-k result sets, and
missing stage timing also fail closed with no successful measurement result.

**R70-4 — attestable result.** The result schema has a version and declares its
canonical length-prefixed UTF-8 field order and SHA-256 digest algorithm. It
retains a resolved-settings digest; fixture, query, model asset, index digest,
indexed-vector population/selection, index-construction-device witness, runtime,
and build identities; candidate, rerank, and ground-truth result cardinalities
and ordered result-ID digests,
and separately bounded candidate and rerank timings. Candidate timing covers
only bit-KNN with `candidate_execution = cpu/sqlite-vec`; rerank timing covers
only exact-f32 rerank with `rerank_execution = cpu/sqlite-vec`. Embedding is
separately named or excluded, and ground-truth has a distinct timing or an
explicit exclusion field. The attestation includes
no corpus content, paths, raw result IDs, or predictions. Non-measurement
results omit every measurement-only field named here.

## Acceptance criteria

**AC70-1.** Committed RED→GREEN tests prove that the runner-selected
`candidate_k`, top-k, and permitted execution settings reach the request-scoped
vector-stage executor and appear exactly in the canonical resolved-settings
attestation. They prove TC-5 can set `candidate_k = 192` and `top_k = 10`
without an engine-side hard-coded `K`.

**AC70-2.** Tests use traps or instrumentation to prove public search, FTS,
fusion, graph, and CE paths were not called. They prove unknown settings,
disallowed CLI or FathomDB control environment variables, algorithm/rerank
deviations, malformed or mismatched specification digests,
qualified-manifest pin/index-population mismatch, a fake device-provider result, failed
CUDA/NVIDIA visibility preflight, a visible GPU whose provider initialization,
probe, effective-device label, or attestation fails, an available GPU that is not selected,
device-attestation mismatch, missing identities/timings, insufficient vector
rows, and incomplete top-k results are rejected before a successful benchmark
result or measurement artifact is emitted. A deterministic fixture covers the
GPU-selected, no-visible-GPU CPU, and failed-visible-GPU cases. It also proves
the embedding provider is the only device-selected component and candidate/
rerank timing reports CPU execution. It rejects missing cache-only model assets
before database open and proves no network/download fallback occurs. It rejects
ambiguous/multiple CUDA devices without the pinned mapping, non-CUDA
accelerators, ambient device selection, and ordinary builds that name the
benchmark module. They prove malformed input creates no output, typed
non-measurement device/asset results cannot contain timings/results, and a
racing pre-existing output destination cannot be overwritten.

**AC70-3.** A real deterministic-fixture test proves that the pre-fusion
candidate, exact-f32 rerank, and same-snapshot full-corpus exact-f32
ground-truth routes are distinct and deterministically tie-broken. Its fixture makes candidate-stage and
full-corpus exact ordering differ, proving both routes ran, while producing a
provenance-safe attestation. A selection-drift fixture proves the immutable
`VectorStageScope` is identically applied to all three routes and fails on an
unexpected row count.

**AC70-4.** Documentation identifies the dedicated executable and its narrow
internal Rust interface as the supported benchmark surface. Python, TypeScript,
CLI, and ordinary Rust SDK surfaces expose no general benchmark knobs. Any
introduced `pub` Rust item is documented and accompanied by the applicable Rust
interface-document update. The feature-gated benchmark module is unavailable
from ordinary builds and admits only the benchmark executable's typed ABI.

## Design, tests, implementation, and documentation

- Design: add a dedicated benchmark executable/crate and narrow internal typed
  request/result interface. It uses immutable per-request state; it is not an
  `Engine::search()` wrapper, compatibility shim, global test switch, or
  language-binding API.
- Tests: commit RED tests for each rejected route and state before Green. Use
  a request-scoped route observer to prove `VectorStage`, not `Search`, and no
  public search, FTS, fusion, graph, or CE invocation;
  then use real vector data to prove the direct path and attestation.
- Implementation: preflight device availability, fail if a visible GPU cannot
  initialize, probe, and attest, otherwise select it (CPU only when none is),
  attest the embedding-provider result and CPU candidate/rerank execution before
  measurement, take one deferred reader snapshot, create the query vector once,
  and retain only canonical identities/digests/cardinalities plus correctly
  bounded stage durations and a non-replacing result finalization.
- Documentation: define the narrow supported benchmark boundary, attestation
  schema, timing semantics, and device-selection verification. Bind execution to a
  qualified fixture/index manifest identity. The external TC-5 execution
  contract currently freezes CPU execution; it needs a later amendment before
  any GPU-backed TC-5 run. Slice 70 does not modify that other worktree.

## Runner-supplied settings hypothesis

Use one versioned, typed experiment specification rather than scattered
environment variables or public search options. The runner validates a
canonical configuration containing fixture/index identity, `candidate_k`,
`top_k`, fixed algorithm/rerank identifiers, query/seed pins, and bounded
execution controls such as warmups, repetitions, and single-process mode. The
fixture, index, model, query, and seed values are qualified-manifest pins, not
runner-selectable knobs; only `candidate_k`, `top_k`, and the bounded execution
controls may vary within the allowlist.

The benchmark executor accepts only that validated specification through its
two exact CLI paths, and no benchmark-control environment variables. It rejects
unknown fields, invalid ranges, prohibited combinations, ambient FathomDB
control variables, and any implicit fallback before opening the database. It preflights device availability, fails
when a visible GPU cannot initialize, probe, and attest, constructs a selected
GPU provider otherwise (or a CPU provider only when no GPU is visible), and
verifies the returned embedding-device identity before emitting the canonical
resolved configuration and digest with the required identities, result-ID
digests and cardinalities, embedding-device plus explicit CPU SQLite-stage
attestations, and bounded stage timings. The result validator recomputes the length-prefixed SHA-256
digest and rejects missing, mismatched, or unrecognized settings. Environment
variables never transport a specification path, output destination, device
assertion, algorithm setting, or device selection.

## Design-review disposition

Independent reviews found the existing test-only seam unsuitable because it is
global and executes ordinary hybrid search before its vector result. They also
found a hard-wired candidate count, no supported executable ABI, and no current
Embedder device authority. This revision incorporates the code-grounded audit
requirements and requires a confirming design review before implementation.
Slice 70 is sequenced after Slice 20 because its installed-binary GPU smoke
depends on the Linux x86_64 CUDA platform/readiness evidence Slice 20 owns.
Slice 70 separately builds, feature-enables, and tests the new benchmark binary
and its attestation; Slice 20 does not establish that binary's behavior. These
are Slice 70 design requirements, not authorization to repair adjacent SCALE
work.
