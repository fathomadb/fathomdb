# Slice 71 — cross-encoder dual runtime

## Audited scope

The existing TinyBERT cross-encoder used a separate `FATHOMDB_RERANK_DEVICE`
parser that accepted `cuda`, `metal`, whitespace, and arbitrary values before
printing a warning and executing on CPU. Its CUDA feature was available only
through `fathomdb-embedder` and `fathomdb-engine`; the facade, CLI, and N-API
artifact routes did not forward it. The model is lazily loaded, so an embedding
resolution is neither an inference engagement nor a valid reranker report.

This slice replaces that legacy parser. It does not alter Slice 70's embedding
resolver, SQLite candidate retrieval, FTS, graph work, indexing, or storage.

## Contract

`FATHOMDB_RERANK_DEVICE` is the sole shared configuration transport. Its exact
grammar is `auto`, `cpu`, or `cuda:N`, where `N` is a process-visible decimal
ordinal. Unset is `auto`. Legacy bare `cuda`, `metal`, whitespace, case variants,
and malformed values are typed configuration errors.

- `cpu` does not enumerate, initialize, or probe CUDA.
- `auto` probes the CUDA reranker provider. It selects the first compatible
  visible CUDA device, otherwise selects CPU with exactly one classified reason:
  `cuda_not_compiled`, `no_visible_cuda_device`, `cuda_incompatible`, or
  `cuda_probe_failed`.
- `cuda:N` is fail-closed: absent, incompatible, probe/session, or inference
  initialization failure is typed; it must not retry or score on CPU.
- The resolution records requested policy, artifact capability, effective
  device, visible inventory, selected UUID, and fallback reason independently
  from embedding-device state. A selected CUDA result means the CUDA provider
  initialized that ordinal and accepted a minimal allocation; it does not claim
  that SQLite retrieval ran on GPU.

The CUDA-capable reranker artifact contains its CPU path as well. `rerank-cuda`
therefore forwards `default-reranker` through the facade, CLI, N-API, Python,
and engine feature routes; no end-user rebuild switches execution device.

## Test and evidence boundary

The resolver is provider-injected. Behavioral tests cover exact grammar,
CPU-no-probe, CPU-only artifacts, unavailable/incompatible/probe failure,
selected CUDA with UUID binding, and forced no-fallback. CUDA compilation is
checked locally with the configured CUDARC target variables. Real model
inference on compatible hardware, installed-package engagement, and
driverless/forced failure receipts remain `PENDING_EXTERNAL`; no synthetic GPU
evidence is accepted.

The existing Slice 20 v2 rehearsal schema remains the completed embedding-only
artifact contract. The parallel v3 candidate route validates exact
`rerank-cuda` tuples for Python (`embed-cuda`, `rerank-cuda`,
`pyo3/extension-module`), N-API (`default-embedder`, `embed-cuda`,
`rerank-cuda`), and CLI (`embed-cuda`, `rerank-cuda`) without mutating v2.
Its two genuine-GPU receipt keys are
`compatible_gpu_reranker_cli` and
`incompatible_reranker_classifier_observation`; they remain
`PENDING_EXTERNAL` until installed-artifact model inference and forced-CUDA
refusal are observed on hardware. Local verification proves the candidate
schema/build inputs and rejects a missing feature; it never substitutes for
those receipts.

## Explicit exclusions

There is no configuration-writing `init` command, no model download in
diagnostics, and no merging of embedding and reranker device reports. A CLI
diagnostic that reports both subsystems must retain two independently named
records and may not imply GPU database retrieval.
