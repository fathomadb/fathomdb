# Slice 72 — concurrent BGE and CE GPU characterization

## Decision

One CUDA-capable FathomDB process may select the same process-visible CUDA
ordinal for its BGE embedder and its optional TinyBERT cross-encoder reranker.
The two independently resolved model instances do not claim, reserve, or
partition that GPU. Candle has no FathomDB memory quota or allocator fraction;
CUDA allocation remains on demand. Slice 72 adds a **test-only** way to
characterize that coexistence on an authorized NVIDIA runner. It does not add a
product scheduler, a public telemetry API, or a performance promise.

`CUDA_VISIBLE_DEVICES` must be fixed before the test process begins. Within the
process, both `FATHOMDB_EMBED_DEVICE` and `FATHOMDB_RERANK_DEVICE` are set to
`cuda:0`. That is a process-visible ordinal, not a host ordinal. The harness
binds each successful model resolution and each telemetry sample to the one
visible CUDA UUID before it can claim shared-device evidence.

The scope is BGE execution and CE execution only. Bit-KNN, exact-f32 database
rerank, FTS, fusion, graph, and storage remain CPU stages. A CE score proves CE
inference happened; it says nothing about retrieval acceleration.

## Existing seams and resulting test shape

`CandleBgeEmbedder::new` resolves the embedder policy and loads the real pinned
BGE model. `CandleTinyBertReranker::try_load` independently resolves the
reranker policy and loads the real pinned TinyBERT model. Both resolvers expose
a process-visible CUDA inventory and selected UUID through the Slice 70/71
device-resolution reports. Neither resolver has a shared-device lock.

The engine deliberately serializes calls into its projection embedder with
`Shared::embed_serialize`; this protects arbitrary caller-supplied embedders
and remains unchanged. The CE singleton is separate from that lock. Therefore
the concurrency assertion is not "two engine embedding workers run in
parallel." It is a production-engine projection BGE forward and a CE rerank
forward that overlap in one process.

The integration target will contain an `Embedder` forwarding wrapper only in
test code. It wraps the real `CandleBgeEmbedder`, signals immediately before
the real `embed()` call, and waits at a bounded rendezvous until the CE worker
is ready. It changes neither the BGE model nor the engine path. A projection
write through `Engine::open_with_choice(...Caller(real_bge_wrapper))` supplies
the BGE operation; `try_rerank_fused` over the canonical Berlin fixture supplies
the CE operation. The test must prove a non-identity CE result (`ce_score` is
present and the relevant passage wins) and a finite, unit-norm BGE vector.

The CE side uses a bounded **test-only** hook at the actual
`CandleCrossEncoder::score_batch` forward boundary, immediately before
`inner.score_batch(...)` and immediately after it returns. The hook is compiled
only by a private `slice72-test-hooks` engine feature and exposed only through
a `#[doc(hidden)]`, feature-gated test harness module. It receives a
single-use `ForwardRendezvous`: both sides record monotonic start/end markers,
set their active flag, meet at a two-party barrier, invoke their real model
forward, then clear the flag. The test fails unless both forward intervals
overlap (`bge_start < ce_end && ce_start < bge_end`), instead of inferring
concurrency from thread creation or cache warm-up. The hook has a 15-second
barrier timeout; timeout, duplicate installation, or leaked hook is a test
failure. Its RAII installation guard unregisters the hook before restoring the
environment. This instrumentation is absent from normal builds and introduces
no production callback, polling, or API.

## Activation and cache-only preflight

The implementation adds one integration target,
`slice72_concurrent_gpu`, to `fathomdb-engine`. Its private
`slice72-gpu-tests` feature requires `embed-cuda`, `rerank-cuda`, and the
private `slice72-test-hooks` feature; those CUDA features transitively require
the real BGE and reranker implementations. The target requires that aggregate
feature and is not selected by normal test commands. Its documented invocation
is deliberately narrow:

```text
CUDA_VISIBLE_DEVICES=<one authorized GPU> \
FATHOMDB_SLICE72_RUNNER=approved-nvidia \
FATHOMDB_SLICE72_ASSET_ROOT=<immutable staged asset root> \
FATHOMDB_SLICE72_RECEIPT_DIR=<empty retained-output directory> \
cargo test -p fathomdb-engine --features slice72-gpu-tests \
  --test slice72_concurrent_gpu -- --nocapture --test-threads=1
```

The basic and low/moderate tests first require the runner sentinel, Linux,
exactly one process-visible CUDA device, `nvidia-smi`, a writable receipt
directory, and an asset root. Otherwise they print one `PENDING_EXTERNAL`
prerequisite message and return without claiming execution. The stress test is
also `#[ignore]` and requires `FATHOMDB_SLICE72_STRESS=1`; `AGENT_LONG` alone
never activates it. Every test acquires one process-global `Mutex` before it
changes policy/cache/XDG/CUDA environment, installs the forward rendezvous, or
reads telemetry, and releases it only after the receipt attempt and complete
environment restoration. The explicit test-thread setting makes the
command-level serialization visible; the mutex makes the invariant hold even
when a developer accidentally omits that argument.

Before `Engine::open` or model construction, the harness copies the named
immutable BGE and TinyBERT cache trees from the asset root into a fresh,
test-owned cache root. It validates every pinned required file against the
source constants' SHA-256 values, then makes the staged files and model
directories read-only. It sets `XDG_CACHE_HOME` to that root for BGE and sets
`FATHOMDB_RERANKER_CACHE` to the parent cache root expected by TinyBERT. Thus a
cache miss or hash mismatch fails before a loader may fetch; a valid cache is
the only permitted input. The harness preserves and restores
`CUDA_VISIBLE_DEVICES`, both FathomDB device settings, `XDG_CACHE_HOME`, and
`FATHOMDB_RERANKER_CACHE` under one process-global environment mutex. Tests in
this target run serially (`--test-threads=1`).

The cache preflight is a test harness guard, not a new product cache policy.
It does not treat `FATHOMDB_SKIP_NETWORK_TESTS` as a network block.

## Test tiers

### Basic shared-device function check

`basic_shared_cuda_device_runs_real_bge_and_ce` opens a real engine path with
the wrapped BGE model and warms the CE path. It obtains the embedder and
reranker resolution reports, requires `cuda:0` in both, requires one equal
non-empty UUID, and verifies the BGE wrapper's actual Candle device label is
`cuda:0`. It then performs one projection embedding and one CE rerank through
the production engine seams. The test fails on CPU fallback, different/missing
UUID, unavailable model, invalid vector, absent CE scores, or a fixture that
did not reorder.

It writes a receipt even for a failed post-preflight run. The no-run external
prerequisite case writes no successful receipt and is visibly labelled
`PENDING_EXTERNAL`.

### Low/moderate bounded co-residency

`bounded_overlap_characterizes_shared_cuda_residency` first warms BGE and CE,
then runs a fixed small workload: four projection writes and four canonical
three-passage CE reranks, with maximum fixture text below the models' normal
token limits. One bounded barrier establishes that the projection worker has
entered the real BGE call before the CE worker begins its real rerank; both
workers must finish within 90 seconds. The test gathers samples before warm-up,
after both models are warm, and while the barrier-released operations execute.

Functional completion, valid vectors, and non-identity CE results are the only
portable pass conditions. It records observations but imposes no utilization,
throughput, or free-VRAM threshold. OOM, timeout, device failure, a wrong UUID,
missing sensor, missing test PID correlation, malformed telemetry, or a failed
operation fails the characterization. It must not retry the work on CPU.

### Explicit stress characterization

`stress_shared_cuda_device_is_bounded_and_records_outcome` repeats the same
real engine operations for a fixed 60-second window with two CE workers and
one engine projection feed. It records the requested duration, fixed
concurrency, counts, cache identities, host identity, summary, and typed
failure. It is `#[ignore]`, requires `FATHOMDB_SLICE72_STRESS=1`, and has a
120-second termination ceiling. It asserts bounded termination and correctness,
not a machine-independent speed SLO. A failed or partial run remains failure
evidence; it cannot change runtime fallback policy.

## Test-only telemetry and receipt contract

`tests/support/slice72_gpu_telemetry.rs` is a private integration-test helper;
it is not compiled into the library. It invokes `nvidia-smi` only from the test
coordinator, never from BGE, CE, an engine worker, or a hot operation. It takes
at most one sample at each phase boundary plus one bounded overlap sample.
Two commands provide the raw observations:

- GPU sample: `uuid`, `utilization.gpu`, `utilization.memory`, and
  `memory.total`, `memory.used`, `memory.free`.
- Compute-app sample: GPU UUID, PID, process name, and used GPU memory.

The helper obtains the driver version once as provenance. It parses
comma-separated, `nounits` output with captured fixtures and rejects malformed
rows, duplicate selected UUIDs, wrong selected UUIDs, missing test PID, and
non-monotonic sample timestamps. `nvidia-smi` utilization values are
device-wide driver-window averages, not per-process or per-request metrics.
Other compute PIDs are retained as confounders. RSS and process CPU time come
from the test process (`/proc/self/stat` and `/proc/self/status`) and are never
represented as GPU metrics.

The test writes exactly one create-new JSON receipt per attempted real run to
the required receipt directory. Its schema name is
`fathomdb.slice72.concurrent_gpu.v1`; the stable top-level fields are:

```text
schema_version, test_name, outcome, started_monotonic_ns,
finished_monotonic_ns, host, pid, build_features, driver_version,
cuda_visible_devices, selected_visible_ordinal, selected_uuid,
cache_identities, phases, summary, failure
```

`phases` is ordered `before_warm`, `warmed`, then `overlap` (and `stress` when
applicable). Each phase includes monotonic timestamp, process CPU nanoseconds,
RSS bytes, selected-UUID GPU compute and memory utilization, total/used/free
VRAM bytes, the test process's compute-app observation, other compute-apps,
and explicit `null`/unavailable fields where a value cannot be read. A receipt
cannot say `success` unless all required telemetry exists and binds to the
selected UUID and test PID. The fixture/parser unit tests cover normalizing
units, UUID/PID binding, phase order, rejected sensor output, and receipt
shape. They are deterministic and make no hardware claim.

For every adjacent phase interval, `summary.cpu_utilization_percent` is exactly
`100 × Δprocess_cpu_time_ns / Δmonotonic_wall_time_ns`; it can exceed 100% when
the process uses more than one CPU core. The receipt retains its numerator and
denominator beside the derived percentage, and uses `null` rather than divide
by zero. `summary.rss_peak_bytes` is the maximum observed process RSS across
the phase samples. `summary.vram_used_peak_bytes` is the maximum selected-UUID
device-wide used VRAM across those samples; it is explicitly not a per-process
allocation. The same peak rules apply to the stress summary. No derived CPU,
RSS, or VRAM value is a threshold, reservation, or admission guarantee.

## TC-5 disposition

**No TC-5 GPU execution path is added.** TC-5's external execution contract
remains CPU-only. Its private vector-stage workload measures query embedding,
1-bit candidate retrieval, and exact-f32 reranking before fusion; it excludes
CE. Slice 72 instead measures the coexistence of a product BGE model and the
CE model. The `tc5-benchmark-cuda` feature is an implementation capability,
not authorization to characterize or label a TC-5 execution as GPU-backed.

If a future question needs GPU query-embedding TC-5 evidence, it must first
amend TC-5's execution contract with GPU UUID, cache/build identity, CPU and
GPU controls, and cross-device result-comparability rules. It must not relabel
SQLite bit-KNN or exact-f32 database rerank as GPU work.

## Documentation and review scope

The implementation corrects the public statements that still describe CE as
CPU-only or its old permissive device grammar: `README.md`, `docs/embedder.md`,
and Python/TypeScript reference GPU sections. It documents independent
`FATHOMDB_EMBED_DEVICE` and `FATHOMDB_RERANK_DEVICE` selection, the supported
`auto|cpu|cuda:N` grammar, shared-GPU coexistence, CPU-only retrieval stages,
and the absence of a scheduler or hard memory cap. It calls telemetry sampled,
device-wide characterization, not a resource guarantee.

Developer documentation updates this design, the corresponding implementation
comments, Slice 70/71/72 records, interfaces where the runtime contract is
described, and `dev/DOC-INDEX.md`. An independent reviewer must compare every
changed public, project, and developer document with the final code, focused
test output, and any retained receipt before closure. Markdown, docs, MkDocs,
links, and release-state checks remain mechanical gates; none substitutes for
that semantic review.

## Non-goals and stop conditions

- No GPU scheduler, reservation, device auto-placement, hard Candle memory
  cap, continuous NVML polling, public telemetry, or SDK benchmark knob.
- No database mock, no synthetic residency/utilization evidence, and no CPU
  fallback after a forced CUDA characterization has started.
- No actual GPU claim, release tag, publication, or TC-5 GPU result without an
  authorized external runner and the separate TC-5 contract amendment.
