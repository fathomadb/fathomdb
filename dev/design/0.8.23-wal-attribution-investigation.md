# Windows WAL checkpoint attribution investigation

## Design-review disposition

Slice 65 is an explicitly commissioned follow-on to Slice 60. It reviewed the
0.8.23 plan and its post-plan work; the completed Slice 30 no-embedder and
erasure repair; the completed Slice 60 Windows witness and retained artifact;
the Slice 3 draft allocation; the downstream Memex evidence note; the engine
checkpoint, erasure, reader-pool, projection-runtime, and Python-binding seams;
and the Python SDK's materialized result shapes.

- **Adjusted and approved:** the completed `N23-WINDOWS-WAL`,
  `R23-WINDOWS-WAL-DIAGNOSIS`, and `AC23-WINDOWS-WAL-DIAGNOSIS` establish the
  fail-closed cross-process witness only. Slice 65 adds the temporary planning
  labels `N23-WAL-ATTRIBUTION`, `R23-WAL-ATTRIBUTION`, and
  `AC23-WAL-ATTRIBUTION` for owner attribution and discriminating controls.
  They are not CRUD changes to the locked needs, requirements, or acceptance
  records.
- **Approved:** private, opt-in attribution instrumentation and the narrow
  real-SQLite Windows experiments below. The record must explain whether a
  known FathomDB reader snapshot, a Python-SDK concurrent request, a serial
  lifecycle, an external reader, or an unclassified checkpoint collision was
  present at the failure.
- **Rejected pending evidence:** changing the five-attempt retry policy,
  exposing a retry parameter, changing binding finalization or adding a
  context-manager API, reader-pool restructuring, public diagnostics, public
  error fields, or an OS/antivirus root-cause assertion.

The existing erasure contract remains unchanged: `purge`, `erase_source`, and
operator `excise_source` freeze projection work, delete/redact durably, then
call `complete_erasure_at_rest`; a failed truncating checkpoint remains typed
`ErasureIncomplete { stage: "wal_checkpoint", .. }`. Freezing projection work
does **not** presently quiesce reader-worker requests. Nor does the present
erasure boundary prove every projection dispatcher/worker connection is idle at
each checkpoint; both are hypotheses to measure rather than established defects.

## Why this is an attribution study

SQLite's WAL documentation says a reader fixes its end mark for the lifetime
of its transaction, and a checkpoint must stop before WAL pages used by a
reader. Long-lived or overlapping readers can therefore starve checkpoint
completion. It also says that `RESTART` and `TRUNCATE` may block readers.
([SQLite WAL](https://www.sqlite.org/wal.html)) The checkpoint result has a
separate busy/result contract; a busy outcome alone does not identify a reader
or exclude a concurrent checkpoint attempt.
([SQLite checkpoint pragma](https://www.sqlite.org/pragma.html#pragma_wal_checkpoint))

This explains the Slice 60 witness, but not the Memex failures. Slice 60
deliberately held an external child reader and observed the correct refusal. It
did not determine whether a normal FathomDB reader worker, a Python call,
another client connection, or an overlapping checkpoint caused a downstream
run. No conclusion about Windows itself, external scanners, or another OS is
licensed by this design.

### Incident-shaped downstream comparison

Memex's verified Windows run `31988695978`, job `95268355659`, used the
released FathomDB 0.8.22 wheel. Its document-first recovery/erasure nodes
exhausted all eight fresh-process attempts with fail-closed WAL-checkpoint
`ErasureIncompleteError`; process isolation and the downstream retry did not
make this incident disappear. The affected shape is not a generic serial
`read` then `purge`: it closes an old store, opens a fresh store that performs
startup recovery reads, then drives nested relation/source erasure or purge.

Slice 65 therefore adds an incident-shaped, real-SQLite control and requires a
two-version Windows comparison for every applicable control: the released
0.8.22 wheel and the current Slice 65 source/wheel. Each run must retain only
the private redacted attribution output and report the exact version/control
pair. A version difference is evidence to investigate, not proof of a remedy;
the comparison must not silently substitute a direct Rust call for the
installed Python binding path.

## Code-grounded baseline and hypotheses

`Engine` opens one writer connection and `READER_POOL_SIZE = 8` thread-affine
reader-worker connections. Each read request dispatches to one worker and its
`read_*_in_tx` routine opens a deferred SQLite transaction. `Engine::close`
joins those reader workers before dropping the writer connection. The current
checkpoint helper runs `PRAGMA wal_checkpoint(TRUNCATE)` on the writer under
the connection mutex, suppresses the SQLite busy timeout for erasure, and the
outer erasure loop retries five times with a 25 ms backoff.

The projection runtime also owns SQLite connections: `projection_dispatcher_loop`
opens one runtime connection and each `projection_worker_loop` opens its own.
The dispatcher scans durable projection work; workers perform projection
transactions and commits. `freeze_projection_for_erasure` freezes new scans and
waits for worker idleness, but that control is not ownership evidence at a
checkpoint attempt. Slice 65 must include these runtime roles before it may
classify an attempt as having no FathomDB-owned activity.

The Python binding clones the engine `Arc` and runs each engine call through
`py.detach`; Python threads can therefore issue a read and erasure concurrently.
The Python wrapper converts native search/read results into Python dataclasses
and lists before returning. A returned result has no SQLite cursor or live
reader transaction to finalize. Consequently, retaining a completed Python
result in a serial lifecycle is expected to be a negative control, not a
binding-lifetime explanation. It remains worth testing because the downstream
failure is process-sensitive.

The candidate explanations are deliberately distinguishable:

1. A FathomDB reader worker holds a snapshot while erasure checkpoints.
2. A concurrent Python request reaches such a worker; `py.detach` makes that
   possible even when a consumer believes its lifecycle is simple.
3. A projection dispatcher or worker has a transaction/snapshot that overlaps
   the checkpoint despite the erasure freeze boundary.
4. A completed Python result or serial Memex-shaped lifecycle holds no
   snapshot; an observed failure then has another owner.
5. A distinct external process holds the snapshot, as Slice 60 proves.
6. No owned connection is active, but a locally visible checkpoint overlap or
   an unattributed SQLite holder produces `BUSY`.

## Private opt-in instrumentation

The implementation must add a private diagnostic collector, disabled by
default and enabled only by test/controlled CI configuration. It is neither a
public SDK surface nor an `EngineError` shape change. It may retain only:

- a generated run/correlation token, monotonic elapsed times, attempt ordinal,
  `busy`, WAL log/checkpointed-frame counts, and outcome class;
- owned connection role (`writer`, `reader_worker`, `projection_dispatcher`, or
  `projection_worker`) and a stable role-local index;
- state and transaction/snapshot transitions for every owned role: opened,
  idle, request/scan/job admitted, transaction opened, snapshot acquired where
  applicable, commit/rollback, result materialized/responded, and completed;
  and
- local checkpoint-attempt ownership/overlap classification.

It must never emit a database path, SQL, query/body text, result contents,
source/logical identifiers, Python object addresses, or a new public error
field. At every checkpoint attempt it must list active owned roles before
classifying one of `owned_reader_snapshot`, `owned_runtime_transaction`,
`local_checkpoint_overlap`, `no_owned_snapshot`, or
`unclassified_external`. That internal diagnostic label means **unattributed**:
it does not establish an external process or a Windows cause. `no_owned_snapshot` is valid only after reader
workers **and** projection dispatcher/worker connections report no active
transaction or snapshot, and there is no local checkpoint overlap. A busy
attempt in that state may then be `unclassified_external`; its outcome is an
honest unattributed holder, not a guess. A test hook may pause a chosen reader only after
its snapshot-acquired transition, so it proves a real SQLite snapshot rather
than queue latency.

### Implementation review — Fix-N

The implementation must not infer a transaction from a queued reader request
or from an entire projection/embed work phase. An attributed reader records
`transaction_opened` only after `BEGIN DEFERRED` succeeds and
`snapshot_acquired` only after a collector-only canonical-table read succeeds;
`SELECT 1` is not sufficient because it need not touch the database/WAL.
Dispatcher
activity begins only when its actual query statement has started a read
snapshot; worker activity begins only after its `BEGIN IMMEDIATE` succeeds.
The managed-reader witness consumes a private retained-record buffer and
asserts the exact role/index for every busy attempt plus a no-owned post-release
success. The ordinary Rust control keeps its pause hook in-crate. The installed
binding control receives an opaque rendezvous only from a disposable
`test-hooks` wheel; that feature is non-default and absent from shipped wheels
and the production Rust surface. The Windows command selects the in-crate test
by its fully qualified path and inspects the retained output for `running 1
test`; a zero-test invocation is a hard CI failure rather than evidence.

## Conditional remedy rules

No remedy is approved merely because the witness is timing-sensitive.

- **Retry tuning:** propose a bounded, parameterized policy only if repeated
  controlled Windows evidence attributes busy attempts to a known transient
  owner, measures its release distribution relative to the current budget, and
  shows that an expanded bounded wait completes after release without turning a
  still-pinned reader into success. The parameter's public/private placement,
  defaults, cancellation, and cross-platform behavior need a separate design.
- **Binding lifecycle work:** consider it only if the completed-result or
  serial control shows a live native request/snapshot after the Python call has
  returned, or a Python-owned engine/close path demonstrably retains one. The
  current materialized-result design is contrary evidence; GC/finalizer theory
  alone is insufficient.
- **Reader-pool/quiescence work:** consider a narrow erasure/read admission
  barrier before restructuring the pool, and only if attribution shows an
  owned worker snapshot survives beyond its request boundary or accepted
  concurrent SDK calls reproducibly conflict. Pool-size or architecture changes
  require a new design and concurrency/throughput regression evidence.
- **No owned role / checkpoint collision:** only after reader workers **and**
  projection runtime roles are demonstrably idle may the collector report no
  owned snapshot. If it then finds a local checkpoint overlap or an
  unclassified external holder, retain the typed refusal, report the
  classification, and investigate the coordinating caller or checkpoint
  ownership. Do not blame Windows or loosen erasure.

At least three independently fresh repetitions of the relevant positive and
negative control, with the same attribution class, are required before a
remedy proposal. Any ambiguous record is `UNATTRIBUTED`, not evidence for a
preferred fix.

## Acceptance and non-goals

`AC23-WAL-ATTRIBUTION` is satisfied only when a retained first-party Windows
x64 artifact demonstrates every matrix case, its safe correlation records,
the current typed fail-closed response under a still-held snapshot, and the
decision classification for each case. The Slice 65 status must say either
`ATTRIBUTED` with its evidence-supported next action, or `UNATTRIBUTED` and
retain all remedies as rejected pending data.

Non-goals: retry/pool/finalizer changes, a public diagnostics API, changing
the erasure error or success criteria, a general Memex test-suite import,
Windows-only blame, CUDA/artifact work, publication, or integration of this
release branch into `main`. Slices 30 and 60 remain completed on
`origin/release/0.8.23`; `origin/main` integration remains pending.
