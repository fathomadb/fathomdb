# Windows x64 WAL-checkpoint reader-conflict diagnosis

## Design-review disposition

Slice 60 reviewed `plan-0.8.23.md`, the Slice 3 allocation
(`N23-WINDOWS-WAL`, `R23-WINDOWS-WAL-DIAGNOSIS`, and
`AC23-WINDOWS-WAL-DIAGNOSIS`), the Slice 5 adequacy gap, the Slice 6 workplan,
the local-Windows environment record, current CI, and the engine/test seam at
`f887690d`.

- **Approved:** a bounded first-party Windows x64 diagnostic. It must hold a
  real SQLite WAL reader in a separate process, distinguish the existing
  typed `ErasureIncomplete { stage: "wal_checkpoint", .. }` refusal from
  false success, and retain the lock/timing outcome in CI.
- **Approved:** the draft need, requirement, and acceptance labels as the
  evidence framing for this slice. They remain planning labels; this slice
  does not mint entries in the locked authoritative needs, requirements, or
  acceptance records.
- **Rejected as ungrounded:** retry-budget tuning, binding finalizers/GC
  theory, reader-pool restructuring, and new public `EngineError` fields.
  The engine already retries five times with 25 ms backoff, then fails closed;
  this diagnostic neither changes that behavior nor claims its cause.

## Code-grounded baseline

`Engine::complete_erasure_at_rest` performs
`wal_checkpoint(TRUNCATE)` after durable pending-redaction discharge. Its five
attempts and 25 ms backoff deliberately culminate in the typed
`EngineError::ErasureIncomplete` error when a reader leaves frames pinned.
The existing `erasure_busy_yields_incomplete_not_success` test proves that
contract using another connection in the same process. It does not exercise a
Windows cross-process reader, nor does it retain elapsed checkpoint time.

This is a diagnosis of the already fail-closed path, not proof that Windows
has a retry-budget defect. A successful cross-process reproduction proves only
that the current refusal remains observable and informative under its intended
contention; it does not authorize a reliability change.

## Final implementation design

The source test lives in
`fathomdb-engine/tests/erasure_completeness.rs` and is compiled only on
Windows.

1. The parent opens a real temporary SQLite database, writes/drains a source
   to erase, and invokes the current integration-test executable with an
   ignored child test name.
2. The child opens its own `rusqlite::Connection`, begins a read transaction,
   queries `canonical_nodes` to acquire a WAL snapshot, then writes a ready
   sentinel. The parent never begins the erase until that sentinel exists.
3. The parent calls `excise_source`, records elapsed milliseconds and the
   returned typed error, signals a release sentinel, and reaps the child with a
   finite timeout before asserting the result.
4. The assertion requires `stage == "wal_checkpoint"` and the current
   bounded-attempt/frame diagnostic text. `--nocapture` exposes the elapsed
   time, stage, and diagnostic text without expanding the public error shape.

The first-party CI job `windows-wal-checkpoint-diagnosis` runs only for
non-markdown changes on GitHub-hosted `windows-latest`. It executes that one
source test with `--nocapture`, copies the complete output to
`slice60-windows-wal-diagnostic.log`, and uploads it even when the test fails.
This job is deliberately separate from native-artifact validation: an artifact
smoke cannot establish this engine-source lock witness.

## Acceptance evidence

`AC23-WINDOWS-WAL-DIAGNOSIS` is satisfied by one retained first-party job
output showing all of the following:

- distinct parent and child processes reached the ready/release protocol;
- a real WAL reader produced the typed `wal_checkpoint` incomplete outcome,
  never `Ok`/false success;
- elapsed checkpoint time and the bounded-attempt/remaining-frame diagnostic
  are available in the uploaded log; and
- the child was released and reaped before the test completed.

The local Linux development host can lint the workflow and run the
same-process fail-closed regression, but cannot substitute for this evidence.

## TDD record and evidence boundary

The RED test was constructed and staged before the ignored child implementation:
the parent waited for a ready sentinel that no process yet wrote, so on Windows
it times out rather than accidentally exercising an unpinned reader. The
child implementation turns that into the GREEN protocol without changing
production code. The required `x86_64-pc-windows-msvc` target is not installed
on this Linux host, so neither the RED nor the Windows GREEN execution is
claimed locally. The GitHub-hosted job is the authoritative execution witness
once the release branch is pushed.

## Non-goals

- No retry-budget, error-shape, schema, binding, finalizer, or reader-pool
  change.
- No claim about a local Windows guest or a downstream consumer's root cause.
- No Windows ARM64/32-bit, CUDA, artifact, or publication scope.
- No replacement of the existing same-process regression.
