# Windows x64 WAL-checkpoint reader-conflict — report and diagnosis design

## Reported issue

Memex's CI (a downstream FathomDB consumer) reported that its "run portable
test subset" step is much slower on `windows-x64` than on `ubuntu-latest`, and
that the difference is not just constant per-process overhead. On Windows,
Memex's runner:

- starts separate pytest processes for FathomDB/WAL-sensitive modules — and
  sometimes individual tests — specifically to release native readers cleanly;
- retries transient WAL-reader conflicts up to 8 times;
- absorbs repeated Windows process-startup and `uv` invocation overhead as a
  result.

Memex's own read, which this doc adopts as the working premise, is that the
conflicts occur in FathomDB-backed tests on Windows "when an old reader still
holds a snapshot while the next test needs a WAL-truncating checkpoint after
an erase/purge," and that this is a **teardown-timing/file-handle-scheduling**
issue, not an application-logic defect. This doc exists to move that premise
from a plausible read of symptoms to a code-grounded hypothesis, and to
propose how FathomDB gets enough evidence to confirm, refine, or reject it.
A local Windows development environment is available for controlled
reproduction; it is not yet an automated first-party CI or release-evidence
path.

## Hypothesis

**A race between FathomDB's fixed, short retry budget for the erase/purge WAL
TRUNCATE checkpoint, and Windows' OS-level mandatory file locking, which turns
GC-timed binding cleanup latency — harmless on POSIX — into an observable
lock conflict on Windows.**

Mechanism, grounded in the current engine:

1. Erase/purge (`complete_erasure_at_rest`, `fathomdb-engine/src/lib.rs:9108-9136`)
   calls `wal_checkpoint_truncate_once` (`lib.rs:9048-9086`), which runs
   `PRAGMA wal_checkpoint(TRUNCATE)` under the writer's exclusive lock. If a
   reader still holds an open WAL snapshot, the checkpoint returns busy. The
   engine retries `ERASURE_WAL_TRUNCATE_ATTEMPTS = 5` times with
   `ERASURE_WAL_TRUNCATE_BACKOFF_MS = 25` sleeps between attempts
   (`lib.rs:219,222`) — a **~100ms total budget** — then deliberately raises
   `EngineError::ErasureIncomplete { stage: "wal_checkpoint", .. }`
   (`lib.rs:9127-9135`) rather than report a false success. This exact
   scenario is a tested, intentional contract:
   `fathomdb-engine/tests/erasure_completeness.rs::erasure_busy_yields_incomplete_not_success`
   pins a reader snapshot and asserts `ErasureIncomplete`, not a wrong answer.
   **The engine is behaving as designed.**

2. `PyEngine` (`fathomdb-py/src/lib.rs:1230-1233`) and the napi `Engine`
   (`fathomdb-napi/src/lib.rs:1343-1347`) both wrap `Arc<RustEngine>` with no
   custom `Drop`/`__del__`/finalizer. `close()` is exposed but optional;
   absent an explicit call, cleanup happens only when the `Arc` refcount hits
   zero — a point driven by Python/Node GC scheduling, not deterministic
   scope exit.

3. On POSIX, advisory locking means a slightly-late-to-release reader handle
   does not block another process's exclusive-lock acquisition, so this
   latency window is normally invisible. On **Windows**, SQLite's TRUNCATE
   checkpoint needs a real OS-level exclusive lock, and Windows enforces
   locking as **mandatory**: any handle still technically open — because its
   Python/Node reference hasn't been collected yet, or because Defender/AV
   real-time scanning or slower CI-runner disk I/O is holding it an extra
   beat, or because FathomDB's 8-worker reader pool (`ReaderWorkerPool`,
   `lib.rs:652`) has more threads to drain before `Engine::close()`
   (`lib.rs:7174-7196`) lets the writer's checkpoint proceed — can be enough
   to exhaust the ~100ms retry budget and surface as `SQLITE_BUSY` /
   `ErasureIncomplete`.

4. Memex's CI response (process isolation + up to 8 retries) is absorbing, at
   the process level, exactly the timing variance FathomDB's fixed ~100ms
   engine-level budget was not necessarily sized for on Windows.

**This is a latency/scheduling hypothesis, not a correctness hypothesis.**
Nothing found in the code or in the existing test contradicts the erasure
path's correctness; `ErasureIncomplete` is the intended fail-closed outcome
under a pinned reader on every platform.

### External corroboration

This is a well-documented, recurring class of problem, independent of
FathomDB:

- SQLite's own docs: `TRUNCATE`/`RESTART`/`FULL` checkpoints require an
  exclusive lock; a concurrent reader/checkpointer gets `SQLITE_BUSY` with no
  busy-handler invoked.
  ([wal_checkpoint_v2](https://sqlite.org/c3ref/wal_checkpoint_v2.html),
  [WAL doc](https://www.sqlite.org/wal.html))
- Windows' **mandatory** file locking vs. POSIX **advisory** locking is the
  specifically named platform divergence — Windows blocks operations on
  files still briefly held open; POSIX does not.
  ([oven-sh/bun#25964](https://github.com/oven-sh/bun/issues/25964),
  [sqlite/doc/wal-lock.md](https://github.com/sqlite/sqlite/blob/master/doc/wal-lock.md))
- Short-lived read-only WAL connections getting spuriously locked is a
  documented *general* WAL connection-lifecycle overhead issue (open/close
  can briefly need exclusive locks even with no data change).
  ([hynek.me TIL](https://hynek.me/til/sqlite-read-only-wal-locked/))
- Unclosed Python cursors/connections relying on GC are a repeatedly reported
  cause of `WinError 32` file-in-use errors that do not occur on Linux/macOS.
  ([cpython#135117](https://github.com/python/cpython/issues/135117),
  [sqlite-utils#503](https://github.com/simonw/sqlite-utils/issues/503))
- Process-per-test isolation is a known workaround for this class of Windows
  SQLite flakiness in pytest suites, though fork-based isolation plugins do
  not work on Windows — consistent with Memex needing a bespoke isolation
  approach.
  ([pytest-isolate](https://github.com/gilfree/pytest-isolate),
  [pytest#2384](https://github.com/pytest-dev/pytest/issues/2384))

## Why this belongs in 0.8.23, and what it depends on

The available local Windows development environment allows controlled,
first-party reproduction before a CI path exists. It does not establish a
durable Windows CI or release-evidence capability. Slice 60 must use the local
environment to characterize the issue, while Slice 6 determines whether and
how to establish the automated Windows evidence path needed for a broader

## Proposed steps

Ordered so each step produces evidence the next step needs; no step assumes
the hypothesis is already confirmed.

1. **Get first-party Windows test signal.** Ride Slice 5's VM runner
   `source` mode (or, if that lands late, the smaller interim step of adding
   `windows-latest` to the existing `cargo test --workspace` CI job) so
   `erasure_completeness.rs` and other WAL/lock-timing tests execute on a
   real Windows host inside FathomDB's own pipeline, not just Memex's.

2. **Add a cross-process Windows-faithful repro test.** The existing
   `erasure_busy_yields_incomplete_not_success` pins a reader with a second
   `Connection` in the *same process*, which validates the Rust retry/backoff
   logic but does not exercise the suspected mechanism (a binding-layer
   handle lingering past GC, under Windows' mandatory-lock enforcement across
   process boundaries). Add a Windows-only integration test that holds the
   reader open from a **separate OS process** (a small helper binary or
   script that opens a read transaction and sleeps) and asserts the
   checkpoint retry behavior under real cross-process Windows locking.

3. **Instrument before tuning anything.** `ErasureIncomplete` currently
   carries no attempts-used or elapsed-time data. Add that (plus a trace span
   around `wal_checkpoint_truncate_once`) so a Windows CI failure reports,
   e.g., "failed on attempt 5/5, reader held snapshot for Nms past checkpoint
   start" instead of a bare pass/fail. This turns confirmation/refutation of
   the hypothesis into a data question, not a debate.

4. **Only then, consider a platform-tuned retry budget.** If step 3's data
   from a real Windows host shows the ~100ms budget is systematically, not
   marginally, insufficient, make `ERASURE_WAL_TRUNCATE_ATTEMPTS` /
   `ERASURE_WAL_TRUNCATE_BACKOFF_MS` platform-aware (a `cfg(windows)`
   override, or an overridable platform-tuned default) — scoped to exactly
   those two constants. This does not change retry *logic* or the fail-closed
   contract; it only gives a genuinely slower platform more time before
   giving up.

5. **Reduce reliance on GC-timed binding cleanup.** Independent of platform,
   add a best-effort finalizer (`__del__` on `PyEngine`, equivalent on the
   napi `Engine`) that calls `close()` if a caller never did, with a warning
   log — since finalizer timing is itself non-deterministic, this narrows but
   does not eliminate the window, and should not be sold as a fix on its own.
   This helps every platform; it is listed here because Windows' mandatory
   locking makes the same latency far more visible there.

## Constraints and non-goals

- **Do not weaken the fail-closed erasure contract.** `ErasureIncomplete`
  must remain the outcome under a genuinely pinned reader, on every platform.
  No proposed change may convert a busy checkpoint into a false success.
- **No broad `cfg(windows)` branching.** The only constants proposed for a
  platform-specific value are the two erasure retry-budget constants
  (step 4), gated on real evidence from step 3. Reader-pool drain order,
  connection-open pragmas, and `close()` sequencing are not to be
  restructured per-OS absent a shown correctness (not just timing) divergence:
  reach for the cheap instrumented signal (step 3) before a structural change.
- **No regression to `erasure_completeness.rs`.** The same-process test stays
  as unit-level coverage of the retry/backoff logic; the new cross-process
  test (step 2) is additive, Windows-only, and does not replace it.
- **Stays inside the 0.8.23 Windows scope.** x86_64-pc-windows-msvc only,
  consistent with `plan-0.8.23.md` §1 and the VM-runner design's exclusion of
  Windows ARM64/32-bit and any GPU/CUDA Windows promise. This diagnosis work
  adds no new platform target.
- **Does not block or gate Slices 5/10.** This is complementary evidence-
  gathering that consumes the VM runner once it exists; it must not be read
  as a precondition for, or a scope increase to, the runner's own acceptance
  criteria in `0.8.23-windows-x64-local-vm-runner.md`.
- **No public API or on-disk format change.** Steps 3–5 are internal
  diagnostics/robustness; none alters `EngineError`'s public shape beyond
  additive fields, none changes SCHEMA, and none requires an ADR on its own
  reading. If step 3's field additions to `ErasureIncomplete` are judged
  public-surface-sensitive, that determination is Slice 0's kind of gate, not
  assumed here.
- **Evidence before tuning.** Step 4 is explicitly contingent on step 3's
  data; this doc does not authorize changing the retry budget speculatively.
