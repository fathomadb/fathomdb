# 0.8.25 driverless CUDA-capable artifact design

## Goal and non-goals

This corrective design makes the existing Linux x86_64 dual-runtime artifact
honest: a user who selects CPU, or leaves the policy at `auto` on a CUDA-free
host, can load and use the installed package. It corrects the 0.8.24 npm smoke
failure caused by a dynamic `libcudart.so.12` dependency.

It does not create a new package identity, change the public device-policy
grammar, add Windows CUDA, or loosen any post-publish smoke. It is a new
release because published package versions are immutable.

## Requirements and acceptance criteria

**R25-CUDA-LOAD-1 — CPU loadability.** Every ELF member in the supported Linux
x86_64 Python wheel and npm platform package has no `DT_NEEDED` CUDA or NVIDIA
user-mode library, and neither archive carries a CUDA/NVIDIA shared-library
payload (including renamed/bundled forms). The complete `candle-kernels` crate
resolves to the reviewed FathomDB fork revision alongside Candle core, nn, and
transformers; a core/nn/transformer-only pin is insufficient. A statically
linked CUDA runtime is permitted only when it preserves the runtime behavior
below.

**R25-CUDA-LOAD-2 — policy isolation.** With CUDA libraries, `/dev/nvidia*`,
and CUDA device-selection variables absent, `auto` resolves to CPU and explicit
`cpu` does not initialize or load the CUDA driver. Forced `cuda:N` fails typed
and never runs CPU work. This applies to both embedding and reranker CUDA
features because the published artifact enables both and they share the link
boundary.

**AC25-CUDA-LOAD-1.** The release-equivalent wheel and npm platform tarball
are inventoried. `readelf -d` output for every ELF member contains no `NEEDED`
CUDA/NVIDIA user-mode library, and neither archive carries a CUDA/NVIDIA shared
library. The verifier rejects missing, substituted, uninspected, or
nonconforming evidence, binding the archive, each inspected member, and each
inspection output to SHA-256 digests.

**AC25-CUDA-LOAD-2.** In network-isolated, genuinely driverless Linux
containers, fresh-installed Python and npm packages complete import,
open/write/search/close/exit under both unset (`auto`) and explicit `cpu`
policy. The containers neither mount CUDA runtime libraries nor expose NVIDIA
device nodes. The smoke must fail if either mount or a CUDA library search path
is added. Driverless forced `cuda:0` cases use the same no-CUDA environment and
must reach the typed fail-closed result, not an ELF loader failure.

**AC25-CUDA-LOAD-3.** On the trusted CUDA runner, fresh-installed artifacts
with explicit `cuda:N` complete the same lifecycle and produce a selected-GPU
allocation witness. A driverless forced-CUDA smoke remains typed and
fail-closed.

**AC25-CUDA-LOAD-4.** On the trusted CUDA runner, fresh-installed Python and
npm artifacts under explicit `cpu` complete the lifecycle without driver
initialization, CUDA library access, a selected GPU, or a smoke PID in GPU
compute processes. A bounded loader/system-call witness and the absent GPU PID
are retained for both bindings.

## Architecture and linkage boundary

The binding module remains one normal-name artifact containing CPU and CUDA
code paths. The module loader must be able to map it without a CUDA runtime.
The existing `cudarc` dynamic-driver path is the only driver-discovery boundary;
the runtime policy is evaluated after module load and before a CUDA provider is
used.

The FathomDB-maintained Candle fork owns kernel linkage. Its kernel build must
avoid all ELF dynamic CUDA/NVIDIA dependencies. The `candle-kernels` package is
part of that fork boundary and must be explicitly patched/resolved with the
same reviewed revision as core, nn, and transformers. If it uses CUDA's static
runtime, that static code may be present but must be dormant until the CUDA path
is selected. FathomDB owns the pin to the reviewed fork revision, the complete
archive/member inspection, and the installed-package evidence.

```text
module import / Engine.open(cpu|auto, CUDA-free)
  -> OS loader: no CUDA-runtime or driver dependency
  -> device resolver: select CPU
  -> CPU embedder lifecycle

Engine.open(cuda:N)
  -> module already loaded
  -> dynamic driver discovery + CUDA runtime use
  -> CUDA allocation witness, or typed fail-closed error
```

## Implementation and verification plan

1. Add failing FathomDB release-contract tests that reject a driverless or
   forced-driverless smoke which mounts CUDA runtime files/search paths, reject
   a partial Candle pin, and reject a CUDA/NVIDIA dependency or payload in any
   packaged ELF member.
2. Change the Candle fork's `candle-kernels` linkage and pin all four Candle
   packages to the reviewed immutable fork commit.
3. Build the actual x86_64 CUDA Python and N-API artifacts on Windchill and
   record `readelf -d` output. The actual binary result, not source inspection,
   determines green.
4. Remove all CUDA runtime mounts and `LD_LIBRARY_PATH` injections from CPU and
   forced-driverless Python/npm/CLI rehearsal paths; add full-lifecycle
   explicit-CPU alongside unset/`auto` evidence.
5. On the trusted GPU runner, retain explicit-CUDA PID/UUID allocation evidence
   and add explicit-CPU no-driver/no-GPU-PID evidence. Perform the CUDA
   redistribution/license/SBOM review before release.
6. Run independent design review, then code review with at most three
   correction/re-review cycles. Do not tag, publish, or promote a release as
   part of this implementation.

## Evidence and completion

The release witness must retain archive/member inventory and digests, every
binary inspection output, no-CUDA-mount CPU and forced-unavailable records,
explicit-CPU non-use records, and selected-GPU records. A successfully
published registry version is not completion: the installed npm smoke and all
required lifecycle proofs must pass before a corrective release is considered
ready.
