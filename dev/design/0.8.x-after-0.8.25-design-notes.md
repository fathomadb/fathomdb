# FathomDB design notes after 0.8.25

## Purpose

This record preserves design work removed from the executable 0.8.25 slice
designs. It is an inventory and design input, not requirements, READY design,
or implementation authority. Each target release must revalidate the consumer
need, write acceptance criteria, reconcile the shipped substrate, and complete
its own design review before implementation.

The reviewed maximum-envelope designs remain in Git history and their review
records remain historical evidence. This file states the useful decisions
without requiring a future planner to reconstruct them from obsolete active
contracts.

## 0.8.26 — richer dependencies and actuation

Re-entry requires an immediate consumer path that cannot use the shipped
single-source core without shadow state or multiple non-atomic calls.

### Multi-source and derived dependency sets

- Add immutable dependency-set revisions with bounded members.
- Admit canonical-source and derived-artifact members only after defining a
  cycle-safe prospective-graph validator.
- Retain both logical-current and pinned-revision reference modes only if a
  demonstrated consumer needs retargeting; pinned revisions remain the safer
  default.
- Define the small Engine-known liveness grammar `all_required` and
  `any_surviving`. FathomDB enforces a caller-selected rule but never chooses
  its semantic meaning.
- Recompute finite validity-loss boundaries and fail closed while a due closure
  cannot be admitted.
- Extend provenance from the 0.8.25 one-source bound to a bounded source set
  without changing the existing wire representation where possible.

### Broader atomic semantic actuation

- Extend the core batch with facts/edges, dependency-set replace/retire, and
  explicit caller-decided coexist/supersede/invalidate/merge operations only
  where the existing record plus lifecycle primitives are insufficient.
- Extend compact receipts with complete state, dependency, projection, and
  lifecycle consequences when consumers need them for recovery or audit.
- Preserve whole-batch atomicity, prospective-reference validation, request
  digest idempotency, and non-content terminal records.
- Reconcile multi-source erasure: a caller-derived artifact that may contain
  erased source material is removed unless a declared Engine-owned projection
  can prove source-separable removal.

The former 1,000-operation omnibus batch, arbitrary dependency DAG/liveness
language, public crash-journal administration, and exhaustive reference index
remain Parked. SQLite transaction atomicity plus compact operation receipts are
the 0.8.25 baseline; a durable prepared-request journal needs a concrete crash
recovery requirement before reconsideration.

## 0.8.27 — full cross-operation replay

Re-entry requires proof that the compact 0.8.25 contracts cannot provide the
needed consistency or continuation behavior.

### Frozen snapshot leases

- Persist authenticated, expiring snapshot leases bound to database identity,
  canonical boundary, validity instant, eligibility digest, and projection
  generations.
- Define exact-context matching, retention, pruning, restart behavior, and
  typed unavailable, mismatch, drift, and expiry outcomes.
- Do not impose lease persistence or a held SQLite transaction on ordinary
  reads.

### Fully bound cursors and generalized pagination

- Bind opaque cursors to request, snapshot lease, projection generation,
  ordering version, exclusive key, and expiry.
- Add graph/list continuation only where a stable complete ordering and
  no-duplicate/no-omission contract can be proved.
- Extend governed `operational_state` continuation beyond the minimal 0.8.25
  keyset pages only from a measured consumer need.

### Persisted evidence and trace replay

- Persist privacy-minimal evidence receipts only if a caller must resolve a
  handle across process restart or beyond the originating call context.
- Bind replay to the original lease and eligibility authority, recheck current
  access/lifecycle/erasure fences, and never store query text or source bytes
  merely to make a handle replayable.
- Persist trace frontiers/pages only if bounded one-call tracing is inadequate;
  duplicate continuation requests must replay identical bytes.

## 0.8.28 — manually selected advanced reads

Re-entry requires a reviewed use case plus bounded quality, lifecycle, and
performance evidence. These remain caller-selected; no automatic routing or
default change is included.

- A versioned named-profile/configuration/qualification contract.
- Specialized time-scoped and changed-fact temporal retrieval.
- Rich constrained-graph continuation and replayable path evidence.
- Expanded deterministic exclusion and not-selected explanation.

## Odd-micro experimental review schedule

Experimental work generates evidence and cannot become product scope without
the target release's normal requirements, design, TDD, and verification gates.

| Review | Candidate design work | Promotion boundary |
| --- | --- | --- |
| 0.8.29 | Entity/alias expansion; complementary-evidence and coverage-aware selection; new MMR/diversity treatments. | Held-out gain without correctness, groundedness, attribution, lifecycle, or accepted-default regression. |
| 0.8.31 | Associative PPR/graph diffusion; automatic profile routing. | A deterministic treatment first passes the retrieval/answer boundary; routing additionally needs at least two accepted manual profiles and inspectable fallback. |
| 0.8.33 | Full integrity-job orchestration, sophisticated repair planning, and exhaustive scale-by-feature-by-CUDA matrices. | Representative checks must demonstrably miss a material operational risk or release decision. |

## Parked architecture

The following is deliberately not on a release path:

- database-owned query decomposition, synthesis, consolidation judgment,
  answer verification, or abstention;
- arbitrary dependency or liveness languages;
- mandatory frozen snapshots and unbounded browse/trace APIs;
- a public projection-work scheduler or repair planner without a concrete
  operational requirement; and
- exhaustive release matrices where representative regression cells suffice.

These either cross FathomDB's data-plane boundary or add machinery without an
accepted consumer-value case. Reconsideration requires an explicit architecture
decision, not an opportunistic slice expansion.

## Preserved implementation details from the maximum envelope

If the corresponding work re-enters scope, the following reviewed ideas are
useful inputs rather than accepted contracts:

- immutable projection generation IDs, applicability manifests, contiguous
  ready-through calculation, and verified old-to-new binding maps;
- fail-closed source-erasure barriers that precede candidate truncation;
- authenticated cursor/reference formats that carry no source content;
- complete path ordering only after bounded graph discovery, with bound
  exhaustion reported as failure rather than a misleading partial page;
- frozen integrity boundaries, generation-scoped reverse-index rebuilds,
  dual-write cutover, and stale-repair-plan refusal; and
- sealed workload manifests, raw per-cell receipts, cold/steady separation,
  and explicit missing-prerequisite outcomes.

These ideas must be simplified against the shipped release before reuse.
