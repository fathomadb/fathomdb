# MCP agent loop on LoCoMo conversation 0

This is a paid, answer-level evaluation of FathomDB reached through the
`fathomdb-mcp` server. Each arm answers 150 LoCoMo questions. An LLM judge
grades every answer with the same prompt, the same judge model and the same
scoring code as the FathomDB-vs-Mem0 LoCoMo comparison
(`experiments/runs/fathomdb-vs-mem0-locomo-comparison-20260824T2140Z-01e702be`).

**Result:** three of the four planned arms ran. The fourth, B-5mini, is
blocked: the existing route cannot serve `gpt-5-mini` (see
[Blocker](#blocker-b-5mini)).

| Arm | What answers | Accuracy | 95% CI |
| --- | --- | --- | --- |
| A1 | one text search (top 10), official answer prompt, gpt-4o-mini | 0.827 | [0.767, 0.887] |
| A2 | one hybrid search (top 10), official answer prompt, gpt-4o-mini | **0.853** | [0.793, 0.907] |
| B-4o | gpt-4o-mini agent calling the MCP tools itself | 0.787 | [0.720, 0.847] |
| B-5mini | gpt-5-mini agent | not run | blocked |

Paired, hybrid is 2.7 points above text, and the gpt-4o-mini agent is 6.7
points below the single hybrid search. Both intervals include zero. The agent
lost ground because it asked for fewer results, sometimes did not search at
all, and then said it did not know. It did not lose because the tools failed.

Receipt:
`experiments/runs/mcp-agent-loop-locomo-conv0-20261017T2008Z-fed1c6f2/record.json`
(content-free; generated by `python -m experiments.mcp_agent_loop receipt`).

**Run 2** ([below](#run-2-usage-guide-instructions-and-gpt-54-mini)) gave the
agent the server's instructions, rewritten as a usage guide, plus a client
starter prompt. With that guidance the gpt-4o-mini agent scored 0.960 and a
gpt-5.4-mini agent 0.953. Both are about 10 points above the single hybrid
search (A2, 0.853), and the paired intervals exclude zero.

## Setup

- **Questions:** conversation 0 of `data/corpus-data/raw/locomo10.json`
  (sha256 `79fa87e9…`, the same file as the Mem0 comparison). The set is
  categories 1–4, keeping items with at least one evidence id that maps to a
  turn. That gives 150 questions: 32 multi-hop (1), 37 temporal (2), 11
  open-domain (3) and 70 single-hop (4). The question ids and gold turns match
  `dev/experiments/mcp-hybrid-vs-keyword/results/per_query.jsonl` exactly
  (checked before the run).
- **Store:** `conv0.sqlite` from the MR-021 run
  ([`../mcp-hybrid-vs-keyword/README.md`](../mcp-hybrid-vs-keyword/README.md)).
  It holds one `note` per turn, `[<session date>] <speaker>: <text>` plus
  `[shared image: <caption>]` where present, embedded with
  `bge-small-en-v1.5`. The server is read-only and the store has no edges.
- **Server:** `fathomdb-mcp` 0.8.27 built with `embed-cuda` (binary sha256
  `dea36c50…`), spoken to over stdio, with this config:

  ```json
  {"roots": [{"path": "<stores dir>", "suffix": ".sqlite"}], "default_store": "conv0",
   "use_default_embedder": true, "idle_timeout_secs": 0, "call_deadline_ms": 120000,
   "search_mode": "text | hybrid"}
  ```

  `snippet_bytes` (300) and `default_max_tokens` (4000) are left at their
  defaults. `search_mode` is `text` for A1 and `hybrid` for the other arms. The
  root lists all ten conversation stores, so `list_stores` shows ten names and
  the agent could have switched store. It never did.
- **GPU:** `CUDA_VISIBLE_DEVICES=0 FATHOMDB_EMBED_DEVICE=cuda:0`.
  `nvidia-smi` was sampled once a second for the whole run. In all 2,031
  samples that listed `fathomdb-mcp`, it was on RTX 3090 #0, using up to
  436 MiB. That GPU peaked at 70% utilization; the second 3090 stayed at 0%.
- **Model route:** the local Airlock proxy with the `dev/.env.eval`
  credentials. The `gpt-4o-mini` alias was served by `openai/gpt-4o-mini` at
  api.openai.com on every call (the `x-litellm-model-name` header). The Mem0
  run recorded its route as `openrouter_exact_models`. The model is the same,
  but the upstream path is not.
- **Scoring:** the official `mem0ai/memory-benchmarks` LOCOMO module,
  `benchmarks/locomo/prompts.py` at `4b61c5d`. It was imported from its
  external checkout and pinned by sha256 `8ebac1ef…`; the MEMORY-01
  resilience patch does not touch it. The parts used:
  - `ANSWER_GENERATION_PROMPT` with the last session's date as the reference
    date;
  - the evidence-aware judge prompt, `JUDGE_SYSTEM_PROMPT` and
    `preprocess_answer`;
  - the evidence lookup, answer extraction (`ANSWER:` split) and label parsing
    (`CORRECT` ⇒ 1). These mirror the official `run.py` and `llm_client.py`
    and are unit-tested.

  The answerer and the judge both run gpt-4o-mini at temperature 0 with
  `max_tokens` 4096; the judge also uses `response_format: json_object`. 149
  of 150 questions had evidence the judge could see. One evidence id is a
  multi-id string that the official lookup cannot resolve, so that question
  got the plain judge prompt, as it would in the official harness.

## Arms

- **A1 / A2 (single search):** one MCP `search` with
  `{"query": <question>, "mode": "text" | "hybrid", "limit": 10}`, then
  `fetch` of the ten refs. The fetched bodies, in rank order and without
  `created_at`, fill the official answer prompt. This is how the official
  harness formats the FathomDB arm of the Mem0 run, which also carried no
  dates. Each line therefore reads `(unknown date) [<session date>] …`.
- **B-4o (agent loop):** gpt-4o-mini with function calling, temperature 0.
  - The tools are the server's own `tools/list`: name, description, and
    `inputSchema` as the function parameters. `outputSchema` is not sent.
  - Every tool result is passed back as the MCP text content block, or as the
    error text when `isError` is set.
  - Budget: at most four executed tool calls per question, and at most three
    of them `search`. `search` stops being offered once three have run. Calls
    past a budget get a "not executed" tool message. After the fourth call,
    one final turn runs with `tool_choice: "none"`. There is also a cap of
    eight model turns, which was never reached.
  - The session's default store is reset to `conv0` before each question.
  - The agent's final message is the answer; the judge is the same.
- **B-5mini:** the same loop on gpt-5-mini at reasoning effort `low`. Not run.

### Agent system prompt

The prompt is `AGENT_SYSTEM_PROMPT` in `experiments/mcp_agent_loop.py`
(sha256 recorded in the receipt). It carries no gold hints:

> The tools give you access to the memory of a conversation between two
> people. Use them to answer the user's question. Answer concisely. If the
> memory does not contain the answer, say that you do not know.

The user message is the question, verbatim.

## Observations

- **Hybrid helps a little at answer level.** The retrieval gain MR-021
  measured carries through to answers: gold seen 0.700 against 0.647, and
  accuracy +2.7 points. The interval includes zero at n = 150. Most of the
  gain is on temporal questions (+10.8 points); multi-hop is 3.1 points
  lower.
- **The gpt-4o-mini agent under-retrieves.** It almost always made exactly one
  search and rewrote the question into keywords. In 141 of its 152 searches it
  set `limit` to 5 or 1, below the A arms' 10, and gold seen fell to 0.553.
  It searched again only 13 times and never used `fetch` to read past a cut
  snippet.
- **It gives up rather than digging.** On 12 questions it answered with no
  tool call, and every one of those answers was a "do not know" variant. About
  25% of its answers contain an abstention phrase (a declared regex heuristic
  in the harness), against 4–5% for the A arms. Of the 23 questions A2 got
  right and B-4o got wrong, 17 were abstentions, 9 had no search, and B-4o
  saw a gold turn on only 1.
- **The judge is lenient towards abstentions.** 13 of B-4o's 38
  abstention-like answers were judged CORRECT. The evidence-aware rules
  accept partial matches, and this flatters "do not know" answers that name
  part of the topic. The same leniency applies to every arm.
- **Unused tools.** The agent never called `orient`, `list_stores`,
  `use_store`, `expand` or `feedback`. It therefore never found that `expand`
  returns no targets on these edge-free stores. `mode` was overridden on only
  4 searches.
- **No tool-level failures.** There were no tool errors and no degradation:
  every A2 search was `limit_reached` with an empty degradation list. A1 had
  148 `limit_reached` and 2 `complete`.
- **The budget never bound.** No question reached the four-call budget, so
  this run does not test whether a larger budget would help. The agent's
  habits, not the budget, limited it.

## Blocker: B-5mini

The Airlock route cannot serve `gpt-5-mini`. The aliases `gpt-5-mini` and
`openai/gpt-5-mini`, and dated names such as `gpt-5-mini-2025-08-07`, all
come back with `x-litellm-model-name: openai/gpt-5.4-mini`. The Airlock
`config.yaml` maps `model_name: gpt-5-mini` to `model: openai/gpt-5.4-mini`.
The billed cost matched gpt-5.4-mini pricing ($0.75 input, $4.50 output per
million tokens), not the gpt-5-mini prices in the task.

Under the task's rule, the arm was not run and no provider was switched. The
harness enforces this: its client refuses any response whose served model
does not start with `openai/gpt-5-mini`.

Running B-5mini needs an owner decision. One option is to accept gpt-5.4-mini
at its higher price, relabelled honestly. The other is to add a true
gpt-5-mini route. The arm then runs as:

```bash
python -m experiments.mcp_agent_loop run --arm B-5mini --resume --out <run dir> …
```

The receipt would then need regenerating.

## Reproduce

The harness is `experiments/mcp_agent_loop.py`, with unit tests in
`tests/experiments/test_mcp_agent_loop.py`. The arms were produced at
`8fad834fb`; later commits add only aggregation and the receipt writer. Use a
scratch venv with `openai` installed, and keep `<run dir>` outside the
repository:

```bash
python -m experiments.mcp_agent_loop run --arm A1 --limit 10 --out <run dir> \
  --dataset <main>/data/corpus-data/raw/locomo10.json \
  --harness <external memory-benchmarks checkout> \
  --stores <stores dir> --binary <fathomdb-mcp-cuda> --env-file <main>/dev/.env.eval
python -m experiments.mcp_agent_loop estimate --out <run dir>
python -m experiments.mcp_agent_loop run --arm A1 --resume …    # then A2, B-4o
python -m experiments.mcp_agent_loop summarize --out <run dir>
python -m experiments.mcp_agent_loop receipt --out <run dir> --binary <fathomdb-mcp-cuda> …
```

`<run dir>` holds the per-question checkpoints, transcripts, spend ledger,
server stderr, `tools/list` and GPU samples. It contains dataset text and
model output, so it is never committed.

## Caveats

- **One conversation, 150 questions.** The intervals are wide (±6 points
  overall, far wider per category), and open-domain has only 11 questions.
  The paired differences do not exclude zero.
- **An LLM judge.** gpt-4o-mini grades gpt-4o-mini answers under lenient,
  evidence-aware rules. Those rules accept partial matches and some
  abstentions. That suits comparing arms, which all share the bias, but the
  absolute accuracy is inflated.
- **Not the Mem0 run's FathomDB arm.** These stores prefix each turn with the
  session date and render image captions differently. Retrieval goes through
  MCP text and hybrid search, not the SDK FTS facade. The upstream route
  differs too (direct OpenAI, not OpenRouter). The A arms reuse the official
  prompt and scorer, so they are comparable in method, not in inputs.
- **The agent prompt is deliberately minimal.** It tells the agent to say it
  does not know when the memory lacks the answer. With gpt-4o-mini, that
  instruction plus a small `limit` produced most of the losses. A prompt that
  asks the agent to search thoroughly would likely change B-4o, and so would
  a stronger model; B-5mini was meant to test the latter.
- **The store was reused.** The task fixed the store, so this run used the
  already-loaded and embedded MR-021 store read-only. It did not create a
  fresh database through `experiments.fathomdb_test_setup`, which the
  experiments directory's standing rule requires for a new measurement cell.
- **The abstention rate is a regex heuristic** (`ABSTENTION_PHRASE` in the
  harness), reported only as a rough indicator.

## Run 2: usage-guide instructions and gpt-5.4-mini

Run 1 left two causes for the agent's losses. First, the harness never passed
the server's initialize `instructions` to the model, which real MCP clients
such as Claude Code put in the system prompt. Second, those instructions said
what each tool returns, not how to use the tools to answer a question. Nothing
said that a snippet is the start of a record, not the matched passage, so the
agent had no reason to fetch.

Receipt:
`experiments/runs/mcp-agent-loop-locomo-conv0-20261017T2203Z-153693da/record.json`.
It covers all six arms: A1, A2 and B-4o from the run-1 checkpoints, and the
three new arms from run 2.

### What changed

- **Server instructions (binary change: instructions text only).**
  `INSTRUCTIONS` in `fathomdb-mcp/src/edge.rs` is now a 1,140-byte usage
  guide (sha256 `ec160a83…`). It names all seven tools and says when to use
  each:
  - choose a store with `list_stores` / `use_store`, skipped when a default
    is set;
  - `orient` optionally, once;
  - always `search` first, keep the default limit of 10, and rephrase on a
    miss;
  - `fetch` references whose snippet looks relevant or is cut off, because
    snippets are the first N characters of a record;
  - `expand` may return nothing on an edge-free store;
  - `feedback` optionally, after a hybrid search.

  The read-only, `l:` reference, bytes/4 budget, continuation and
  data-not-instructions facts stay. Tool descriptions and schemas are
  unchanged. `tests/protocol.rs` pins the tool names, the guidance and the
  1,200-byte cap. The run-2 binary (`embed-cuda`) has sha256 `92d9c832…`;
  run 1 used `dea36c50…`.
- **Prompt variants.** `neutral` is the run-1 prompt (sha256 `b2cea7bf…`)
  without the instructions; B-4o and B-5.4mini use it. `guided` is the live
  initialize `instructions`, a blank line, then `GUIDED_CLIENT_PROMPT`
  (sha256 `8b6a4bf9…`). The composed guided prompt has sha256 `76df778d…`.
  The client prompt tells the agent to:
  - always search;
  - query with the question's key names, objects and events;
  - keep limit 10;
  - fetch when a snippet is cut off or does not show the answer;
  - rephrase when the first search misses;
  - resolve relative times from the record timestamps;
  - say it does not know only after two searches found nothing.
- **Model gpt-5.4-mini.** The arm requests `openai/gpt-5.4-mini` on the same
  Airlock route at `reasoning_effort: low`. The served-model guard requires
  `openai/gpt-5.4-mini*`, and every call was served by that model. Prices:
  $0.75 input, $0.075 cached input and $4.50 output per million tokens. This
  is **not** gpt-5-mini, which the route still cannot serve; B-5mini stays
  not run.
- **Everything else as run 1:** the same 150 questions, `conv0.sqlite` and
  server config, a budget of 4 calls / 3 searches with a forced final turn,
  and the same gpt-4o-mini evidence-aware judge.

### Observations

- **Guidance is the big lever.** With the same model, the guided prompt
  moved gpt-4o-mini from 0.787 to 0.960 (+17.3 points, 27 questions gained,
  1 lost). It moved gpt-5.4-mini from 0.880 to 0.953. Both guided agents
  beat the single hybrid search by about 10 points, with intervals that
  exclude zero.
- **The fixes act on the run-1 failure modes.** With guidance, gpt-4o-mini:
  - searched on every question, always with `limit` 10;
  - fetched on 98% of questions;
  - almost stopped abstaining (0.7% against 25%).

  Gold seen rose from 0.553 to 0.713, just above A2's 0.700.
- **A stronger model helps without guidance too, but less.** Neutral
  gpt-5.4-mini searched on every question and never abstained. It still
  asked for `limit` 5 on 74% of searches, and it chose `mode: text` on 79%
  of them. Its +9.3 points over B-4o have a lower bound of only +1.3. Against
  A2 the difference includes zero.
- **The guided gpt-5.4-mini wasted calls on `list_stores`.** It called
  `list_stores` on 92 of 150 questions, although a default store was set.
  The instructions say to skip it "when a default store is already set", but
  the agent cannot tell that without a call. Those calls used up budget: 18%
  of its questions hit the 4-call limit, against 4.7% for guided gpt-4o-mini.
  It also passed an unsupported `limit` to `fetch` five times. Saying in the
  instructions that calls without `store` use the default, and that
  `list_stores` is only needed to switch, would likely recover some of
  those calls. That is untested.
- **Accuracy when no gold turn was seen is high for the guided arms** (0.86
  and 0.79). The likely causes, not checked here, are LoCoMo facts that
  recur in turns other than the annotated evidence, and an evidence-aware
  judge that accepts partial matches. Treat the gold-seen rate as a lower bound on useful retrieval.
- **Cost.** The guided gpt-4o-mini arm cost $0.167, about 1.7× a single
  search ($0.098), because fetched bodies and the longer prompt raise input
  tokens. Guided gpt-5.4-mini cost $0.650 for slightly lower accuracy.

### Caveats (run 2)

- **Two changes are confounded.** The guided arms get both the new server
  instructions and the client starter prompt. This run does not separate
  their effects. A neutral-plus-instructions arm would.
- **The guidance was written after seeing run 1.** The client prompt targets
  the failure modes observed on these same 150 questions. Its "resolve
  relative times from timestamps" line fits LoCoMo's dated turns. Gains on
  other conversations or corpora are not established.
- **gpt-5.4-mini is not gpt-5-mini.** The B-5mini arm in the original plan
  is still not run.
- **The binary changed** between runs: instructions text only. The neutral
  arms do not send the instructions. B-4o (run 1) and B-5.4mini (run 2) saw
  the same prompt and a byte-identical `tools/list`.
- The run-1 caveats (one conversation, LLM judge, reused store) still apply.
