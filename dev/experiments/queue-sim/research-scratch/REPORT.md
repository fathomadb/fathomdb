# Grounded inputs for the FathomDB admission-queue simulator

Access date for all sources: 2026-10-17. Every number was read from the cited page/PDF unless marked UNVERIFIED. Full source log (cited + visited-uncited): SOURCES.md. Raw PDF text extractions (tracelab.txt, humanless.txt, tail.txt, mitz.txt, bronson.txt, huang.txt) were used during the research and are not committed.

## (a) Simulator inputs

Agent think time (gap between an agent's tool calls, no human). TraceLab (UW SyFI; ~8k Claude Code + Codex sessions, 665k LLM steps, 744k tool calls): per-step LLM generation p50 4.9 s, p90 20.2 s, p99 1.3 min (individual spans p50 5.7 s, p90 22.2 s); tool execution per step p50 0.1 s, p90 10.0 s, p99 3.2 min; Claude tool latency p50 115 ms, p90 10.1 s; human waits p50 1.4 min, p90 20.6 min (https://tracelab.cs.washington.edu/ ; https://arxiv.org/pdf/2606.30560 Tables 2, 7). Within a request the loop is closed: 86% of steps are tool-initiated. "inter-arrival time is bounded by tool execution latency, not human think time"; Mooncake ToolAgent traces: "median IAT near zero for closed-loop agent" vs 2-5 s human (https://arxiv.org/pdf/2606.20577). Recommendation: log-normal think time, median ~5 s, p90 ~20 s, p99 ~80 s. Decode: TraceLab median 46.8 tok/s (Claude), Codex est. TTFT 3.1 s; Artificial Analysis Sonnet 4.6 ~44 tok/s, TTFT ~1.4 s (https://artificialanalysis.ai/models/claude-sonnet-4-6/providers).

Parallel tool calls per turn. TraceLab: tool calls per step avg 1.2, p50 1, p90 2, p99 4; "most steps issue only one". Anthropic: "By default, Claude may call multiple tools in a single response"; no numeric cap documented; recommended prompt says "Err on the side of maximizing parallel tool calls" (https://platform.claude.com/docs/en/agents-and-tools/tool-use/parallel-tool-use). OpenAI: multiple calls per turn, no cap (https://developers.openai.com/api/docs/guides/function-calling). Anthropic research system: "subagents use 3+ tools in parallel", "3-5 subagents in parallel", "1 agent with 3-10 tool calls" (https://www.anthropic.com/engineering/multi-agent-research-system). Observed 5-6-call bursts exceed the population p99 but match prompted-parallel agents; heavy-case mixture: 70% single, 20% 2-4, 10% 5-8. UNVERIFIED: that no cap on tool_use blocks per turn exists (none documented).

Concurrent agents. Claude Code default 20 concurrent subagents per session (CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS); limit error "tells Claude not to retry"; nesting depth default 3 (https://code.claude.com/docs/en/sub-agents). Typical 1-5; heavy 10-20.

Client timeout. Claude Code MCP_TOOL_TIMEOUT default "about 28 hours"; stdio idle timeout 30 min; auto-background after 2 min; MCP_TIMEOUT is startup only (https://code.claude.com/docs/en/mcp). MCP TS SDK DEFAULT_REQUEST_TIMEOUT_MSEC = 60_000 (https://github.com/modelcontextprotocol/typescript-sdk/blob/main/packages/core-internal/src/shared/protocol.ts); Python SDK read_timeout_seconds=None (https://github.com/modelcontextprotocol/python-sdk/blob/main/src/mcp/client/session.py). Spec: SHOULD time out and cancel; MAY reset on progress but SHOULD enforce a maximum (https://modelcontextprotocol.io/specification/2025-06-18/basic/lifecycle). Server 10 s deadline is binding; model generic clients at 60 s.

Retries. Claude Code does not auto-retry stdio tool calls (remote reconnect 5x backoff from 1 s; one retry on 401) (https://code.claude.com/docs/en/mcp). Model level: on is_error Claude "will reissue the call on the next turn"; invalid input "retry 2-3 times" (https://platform.claude.com/docs/en/agents-and-tools/tool-use/parallel-tool-use ; https://platform.claude.com/docs/en/agents-and-tools/tool-use/handle-tool-calls). Model: re-issue after one LLM turn (~5 s), up to 2-3 times, unless retry_after_ms is honoured.

Slow-read probability/magnitude. WAL readers never block on writers, but the COMMIT crossing 1000 WAL pages runs the checkpoint ("occasional COMMIT" slow); checkpoint "must stop when it reaches a page in the WAL that is past the end mark of any current reader", so overlapping readers starve it and the WAL "will grow without bound"; readers get SQLITE_BUSY only in exclusive mode, last-connection close, or crash recovery (https://sqlite.org/wal.html). Measured: WAL reads with 1,000 w/s writer p99 4.4 ms, worst 17 ms; writer flat out p99 5.2 ms, worst 30 ms (M1, warm, 343 MB) (https://www.dbpro.app/blog/sqlite-is-all-you-need, secondary). sqlite-vec 10k p50 2.1 ms / p99 4.3 ms; 100k p99 28 ms (https://dev.to/hypernexus/sqlite-vector-search-the-dependency-free-ai-memory-stack-that-outperforms-pinecone-5d27, weak). Brute-force vector scan bimodal ~21 s cold vs ~1-2 s warm, non-SQLite (https://arxiv.org/pdf/2608.05441). No published SQLite cold-cache or checkpoint-stall p999 found. Recommendation: p99 = 3-5x median, worst = 10-30x median; rare (1e-3 to 1e-2) cold/checkpoint mode at 100-1000x median is a design assumption, not measured.

## (b) Cutoff percentile and estimator window

- AWS: choose a false-timeout rate "such as 0.1%" and use that percentile (p99.9); pad when p99.9 is near p50; too-low timeouts raise retry traffic and "can cascade" (https://builder.aws.com/content/3EumjoZascWd1oZiEgL8ORlv3qE/timeouts-retries-and-backoff-with-jitter).
- Google SRE: deadlines "several orders of magnitude longer than the mean" are bad; propagate one absolute deadline; queue "50% or less" of thread pool (https://sre.google/sre-book/addressing-cascading-failures/). Retry budget 10%, <=3 attempts, retry at one layer; adaptive throttling K=2 (https://sre.google/sre-book/handling-overload/).
- Tail at Scale: hedge after the 95th-percentile expected latency (~5% extra load); 10 ms hedge cut p99.9 1,800 ms to 74 ms at +2% requests (https://www.barroso.org/publications/TheTailAtScale.pdf).
- CoDel: minimum sojourn over INTERVAL (100 ms ~ RTT), TARGET 5 ms ~ 5% of interval; averages "would indicate a persistent queue where there is none" (https://www.rfc-editor.org/rfc/rfc8289.html). Facebook variant: short timeout M when queue has not drained within N, else N; adaptive LIFO; "A short timeout ensures that the server always accepts just a little bit more work than it can actually handle" (https://blog.acolyer.org/2015/11/19/fail-at-scale-controlling-queue-delay/, secondary for https://queue.acm.org/detail.cfm?id=2839461, 403).
- Adaptive-limit failure modes: Netflix Gradient2 Javadoc: "using minimum can result in an bias towards an impractically low base RTT resulting in excessive load shedding"; EWMA baseline "lags the current measurement, which keeps the gradient < 1.0 and limit low"; after load the long-term RTT "could potentially be several multiples higher than the current RTT" (https://github.com/Netflix/concurrency-limits/blob/master/concurrency-limits-core/src/main/java/com/netflix/concurrency/limits/limit/Gradient2Limit.java ; https://github.com/Netflix/concurrency-limits). Envoy: periodic minRTT re-measurement at min_concurrency with jitter and buffer %, 100 ms sample window, p90 aggregate in example, headroom sqrt(limit) (https://www.envoyproxy.io/docs/envoy/latest/configuration/http/http_filters/adaptive_concurrency_filter).
- Low vs high percentile: no source argues for an optimistic p5 cutoff. Admission estimators use the minimum (CoDel, Vegas) to detect a standing queue; timeouts use p99-p99.9 to detect lost calls. Netflix documents over-shedding/censoring from low percentiles; AWS documents fragility of tight high percentiles. For "remaining < estimated service", p90-p99 of recent completions is the conservative choice; min/p5 only as a queue-presence signal. Windows seen: 100 ms (CoDel, Envoy); 1 s + EWMA 0.2 (Gradient2); 60 s / 50 requests (Envoy minRTT).

## (c) Stacked-queue failure modes

1. Metastable failure: trigger + sustaining effect; 1 s retry doubles DB load to 560 QPS and it "will remain there until the load is significantly reduced or the retry policy is changed" (https://sigops.org/s/conferences/hotos/2021/papers/hotos21-s11-bronson.pdf). Retries sustain >50% of 22 public incidents; recovery "often requires reducing load" (https://www.usenix.org/system/files/osdi22-huang-lexiang.pdf).
2. Retry amplification: 3 retries x 5 layers = 243x (AWS); 4x4x4 = 64 (SRE).
3. Graveyard queues: bound size and age, shed before client deadlines, spillover/fast-fail, LIFO if protocol allows (https://builder.aws.com/content/3Eun1EEyX6p2e3VYNyRLSJzLuMV/using-load-shedding-to-avoid-overload).
4. Round-robin per-worker queues under heavy tails: head-of-line blocking; "once a request is actually scheduled ... variability goes down"; two-choice enqueue "exponentially improves load-balancing" (Tail at Scale; https://www.eecs.harvard.edu/~michaelm/postscripts/tpds2001.pdf). Size-unaware static policies lose by orders of magnitude under heavy tails (https://www.cs.cmu.edu/~harchol/Papers/abstract-tags.html). sync_channel(4) per worker + round-robin is the d=1 case; a shared queue or JSQ is work-conserving.
5. Lock convoy / fair handoff: strict handoff "extends the lock hold time by the communication and context switch latency"; "If you remove the strict fairness policy, however, the system scales" (https://joeduffyblog.com/2006/12/14/anticonvoy-locks-in-windows-server-2003-sp1-and-windows-vista/ ; https://learn.microsoft.com/en-us/archive/blogs/sloh/lock-convoys-and-how-to-recognize-them).
6. Bimodal latency + long deadline pins a fixed concurrency pool (SRE cascading) - C=4 slots held by 10 s waits.

## (d) Primitive facts

- std::sync::Mutex: futex-based on Linux since 1.62 (https://blog.rust-lang.org/2022/06/30/Rust-1.62.0/); unlock swaps to UNLOCKED then wakes one waiter, no handoff, barging possible; docs give no fairness guarantee (https://github.com/rust-lang/rust/blob/master/library/std/src/sys/sync/mutex/futex.rs ; https://doc.rust-lang.org/std/sync/struct.Mutex.html).
- parking_lot::Mutex: eventual fairness, fair unlock on average every 0.5 ms; >1 ms sections always fair-unlock (https://docs.rs/parking_lot/latest/parking_lot/type.Mutex.html).
- tokio::sync::Semaphore: fair FIFO; large acquire_many at head blocks later smaller acquires (https://docs.rs/tokio/latest/tokio/sync/struct.Semaphore.html). tokio::sync::Mutex: "guaranteed FIFO" (https://docs.rs/tokio/latest/tokio/sync/struct.Mutex.html).
- std::sync::mpsc: crossbeam-channel since 1.67 (https://blog.rust-lang.org/2023/01/26/Rust-1.67.0/); sync_channel(n) blocks when full, sync_channel(0) rendezvous (https://doc.rust-lang.org/std/sync/mpsc/fn.sync_channel.html).
- spawn_blocking: max_blocking_threads default 512, keep-alive 10 s, tasks queue past the limit (https://docs.rs/tokio/latest/tokio/runtime/struct.Builder.html ; https://docs.rs/tokio/latest/tokio/task/fn.spawn_blocking.html).
- rmcp client: timeout, max_total_timeout, reset_timeout_on_progress (https://github.com/modelcontextprotocol/rust-sdk/blob/main/crates/rmcp/src/service.rs).
- SQLite: THREADSAFE 0/1/2 = single/serialized/multi-thread, default serialized; NOMUTEX/FULLMUTEX per connection (https://sqlite.org/threadsafe.html ; https://sqlite.org/c3ref/c_config_covering_index_scan.html); memstatus on by default and "must be serialized with a mutex", SQLITE_CONFIG_MEMSTATUS 0 removes it (https://sqlite.org/malloc.html ; https://sqlite.org/compile.html); wal_autocheckpoint 1000 pages (https://sqlite.org/wal.html); busy_timeout sleeps until >= ms accumulated then SQLITE_BUSY, bypassed on deadlock detection (https://sqlite.org/c3ref/busy_timeout.html ; https://sqlite.org/c3ref/busy_handler.html); rusqlite default busy timeout 5000 ms (https://docs.rs/rusqlite/latest/rusqlite/struct.Connection.html).
