# Memex Windows x64 WAL evidence handoff — 2026-08-16

## Purpose and scope

This note preserves downstream observations from Memex's local Windows x64
test gate for the FathomDB 0.8.23 Windows WAL-checkpoint investigation. It is
supporting evidence, not an accepted root-cause finding or a request to weaken
the erasure contract. The proposed diagnosis and first-party investigation
sequence remain in
[`dev/design/0.8.23-windows-wal-checkpoint-reader-conflict.md`](../design/0.8.23-windows-wal-checkpoint-reader-conflict.md).

The observed platform is Windows x64 in Memex's local VM test environment.
The runs are downstream evidence, not FathomDB first-party CI evidence.

## Executive finding

FathomDB-backed Memex erase/purge tests can surface
`ErasureIncompleteError` on Windows x64 after Memex has added deterministic
test-resource teardown and process isolation. A fresh pytest process followed
by a bounded retry can pass the same target. This establishes
process-boundary-sensitive timing as an observed characteristic of the test
path; it does **not** establish the particular surviving reader, its owner, or
the cause of its release latency.

Memex retains the failure as a failure unless a later complete attempt passes.
It does not turn `ErasureIncomplete` into success or suppress the diagnostic.

### 2026-08-17 downstream recovery/erasure signal

Memex GitHub run `31988695978`, job `95268355659`, used the released FathomDB
0.8.22 Windows wheel. Its two document-first nodes exhausted all eight
fresh-process attempts with fail-closed WAL-checkpoint `ErasureIncompleteError`:
the exact shared-candidate/source purge and recovery-after-visibility-block
crash paths. This is stronger evidence against cross-module contamination as a
complete explanation, but it does not identify a FathomDB-owned reader, Python
binding lifetime, external holder, or Windows cause.

The node shape matters for the FathomDB follow-on: it closes an old store,
opens a fresh store which performs startup recovery reads, then executes
nested relation/source erasure or deleted-first purge. Slice 65 must compare a
small real-SQLite control for that sequence on the released 0.8.22 wheel and
the current FathomDB source/wheel, alongside the installed-binding concurrency,
retained-result/idle-engine, and projection-runtime controls. The comparison
retains redacted FathomDB attribution artifacts; it does not import the Memex
suite or authorize retry, pool, finalizer, or OS-specific changes.

## Controls already applied downstream

Memex has deliberately reduced confounders before retaining the CI workaround:

- Its test fixtures now explicitly close `FathomStore` and related workflow,
  API, engine, and read-result owners in reverse teardown order; they do not
  rely on Python garbage collection.
- A shared-process audit distinguished ordinary tests from a small,
  evidence-backed FathomDB-sensitive cohort. The current gate gives selected
  modules or exact nodes a fresh pytest process, rather than starting every
  test in a separate process.
- Only observed `ErasureIncomplete`, `SQLITE_BUSY`, or WAL-reader failures
  receive a retry, with at most eight attempts. Any other pytest failure is
  returned immediately.
- Each failed attempt records target, attempt number, elapsed time, exit code,
  normalized error, and a captured log. The final host-side status propagates
  back to the Linux launcher.

These controls lowered the local Windows gate from roughly two hours to a
roughly 13–15 minute gate while preserving complete test coverage. They are a
downstream containment measure, not evidence that an upstream retry-budget
increase is necessarily the right remedy.

## What this evidence does and does not support

### Supported

- The observed failures are Windows-x64 test-path timing/lifetime sensitive.
- A process boundary can remove the condition in some cases.
- Some exact tests can still require more than one fresh-process attempt,
  which rules out *cross-module contamination alone* as a full explanation.
- FathomDB's fail-closed `ErasureIncomplete` behavior remains the correct
  contract when a checkpoint cannot complete.

### Not yet established

- That the surviving reader is binding GC/finalizer timing rather than a
  reader-worker, external scanner, SQLite scheduling, or another holder.
- That FathomDB's current approximately 100ms checkpoint retry budget is the
  primary cause in these runs, or that widening it would reliably cure them.
- That the issue is an engine correctness defect, or that the Windows behavior
  applies to macOS/Linux or to every Windows workload.

## Requested FathomDB follow-up

Treat this note as new input to the existing proposed design, not as authority
to tune retry constants. The lowest-risk evidence sequence is:

1. Run FathomDB's erasure-completeness coverage on a first-party Windows x64
   host and preserve failures as first-party CI artifacts.
2. Add the proposed cross-process reader-holder reproduction, so Windows file
   locking is exercised without relying on Memex's broader test suite.
3. Instrument `wal_checkpoint_truncate_once` / `ErasureIncomplete` with
   attempts used and elapsed time before changing its retry budget. If safe to
   obtain, reader-pool/connection lifetime diagnostics would distinguish the
   leading hypotheses.
4. Use those data to decide whether a narrowly scoped Windows-tuned retry
   budget, binding-lifetime improvement, or another lifecycle change is
   justified. Preserve the existing fail-closed result under a genuinely
   pinned reader.

## Reproducibility and interpretation discipline

For a Memex reproduction, run its local Windows gate with
`scripts/ci/run-windows-vm.sh`; the launcher stages the current worktree into
the VM and returns the remote terminal status. To diagnose only this class of
failure, preserve the per-attempt artifacts under
`test-results/windows-wal/` and report the exact target plus normalized error.

Do not generalize a passing retry into proof that an erasure completed during
the failed attempt. The only safe conclusion from the current downstream data
is that the later, independently executed attempt completed successfully.
