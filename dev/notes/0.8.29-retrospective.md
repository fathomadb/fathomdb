# FathomDB 0.8.29 retrospective

0.8.29 shipped substantial correctness, interface and CUDA work, with actual
registry-installed consumers. It also spent too much effort on the machinery
around that work: measurement-controller repairs, repeated qualification joins,
large static checks, release recovery and duplicated status prose. The lesson
is to keep the evidence that distinguishes correct behavior from apparent
success, while reducing repeated execution and administrative work.

This retrospective supports the owner's next-release focus on correctness,
performance, low latency and robustness. The companion
[0.8.30 recommendations](../plans/0.8.30/quality-performance-robustness-recommendations.md)
turns these findings into proposed technical work. Neither document changes
accepted contracts, grants a new run budget or activates a release ladder.

**Subsequent owner clarification, November 17 Chicago (seq-398):** version-matched
0.8.29 Tegra CUDA/Pages delivery is required. It was subsequently completed in
**0.8.29**, by [run 44246092920](https://github.com/fathomadb/fathomdb/actions/runs/44246092920):
all seven build/platform/publication/public-consumer jobs passed on the existing
`10.83.10.13` host, and the exact wheel/addon were added to retained distribution.
The temporary FathomDB runner was stopped. The first attempt exposed a staged
Cargo-configuration defect, fixed with a genuine regression and independent
review. Confirm each release's expected deliverable platforms early; generic
ARM CPU support and an older Tegra release did not meet this .29 requirement.

## What worked

**Reconciliation prevented unnecessary implementation.** The initial branch
and contract audit found integrated queue/MCP/Block1 work and already-built
parts of Block2. It also identified the real identity change: fusion by body
text was not fusion by stored record. Checking callers exposed consequences
for provenance, explanations, graph exclusion, snippets and feedback. The
[identity census](../plans/0.8.29/features/slice-50/census.md) and
[feedback decision](../plans/0.8.29/features/slice-50/feedback-decision.md) are
better examples of useful design work than a second implementation of an
already-satisfied feature.

**Behavioral tests found consequential defects.** Slice 20 reproduced hook theft
and alias-related fault masking. Slice 60 found a structured-output seam emitting
compact text and a real273.8 μs hints-overhead result above the unchanged 200 μs
bound; caching budget-independent serialized size and avoiding deep clones fixed
the measured problem. Slice 90's installed malformed-null case exposed a native
decoder error-path defect. Typed open-admission tests required correct error
kind/stage/hint/anchor, repeated refusal without a leaked lock and successful
reopen after profile restoration. These tested user-visible contracts and
cleanup, rather than only the presence of source text.

Sources: [20 execution](../plans/0.8.29/features/slice-20/execution.md),
[60 execution](../plans/0.8.29/features/slice-60/execution.md),
[90 status](../plans/0.8.29/features/slice-90/status.md),
[installed admission proof](../plans/0.8.29/features/slice-160/status.md#typed-open-admission-fix-and-current-artifacts).

**The final recovery proof distinguished operator success from product success.**
Earlier debugger/MI failures did not establish that a fault had been delivered.
The final selected Slice 100 case witnessed the active checkpoint, confirmed the
SIGKILL, preserved main/WAL/SHM and passed separate observation, retry and reopen.
Healthy completion, a fake debugger transport and an outer timeout could not
substitute for that proof. See [100 execution](../plans/0.8.29/features/slice-100/execution.md).

**Reuse and precise source scope avoided some expensive repeats.** Frozen native
measurements, existing fork qualification, installed artifacts and unchanged
controls were inherited where their inputs and consumed behavior still matched.
The paid comparison ran once: 72 episodes, 144 grades, reported model/judge cost
$0.13444673. That amount is not total engineering, agent or infrastructure cost.
Its wide paired intervals did not establish universal answer-quality equivalence
or noninferiority. See [agent comparison](../experiments/agent-remeasure/README.md).

**The release finished through actual consumer proof.** The published CUDA wheel
matched the GPU-qualified wheel bytes. The published npm native member matched;
the enclosing tarball differed only in README. All eight installed-registry jobs
passed, and Pages verified retained public Tegra downloads. This earned delivery
credit without repeating scientific or paid campaigns.

The first Linux npm smoke established a successful install command followed by
no optional native binary. Its exact resolver cause was not captured. Observed
registry propagation and the passing failed-only retry support that hypothesis,
not proof of it. Likewise, the OIDC log proves successful promotion and failed
immediate verification, but does not show the failed read's value. These unknowns
must remain unknown rather than becoming confident “flake” diagnoses.

### S50 remains a specific correctness question

Sample860/query360/op9971 in the natural-write SDK-hybrid diagnostic differed in
two scores: eager relative to winner was+1.240362% and+0.850694%. Ordered document
IDs and text matched; both calls used the reference route. Exact fusion math
reconstructs different vector ranks, but the actual candidate IDs, distances and
ranks were not captured. Async projection is plausible and unproved. This is not
an established CPU/GPU floating-point rounding difference or a proved deferred-
hydration defect. Owner seq-393 permits the release to proceed; it does not add
a general score tolerance or pass the failed exact comparison retrospectively.

The [0.8.30 receiving allocation](../plans/0.8.30/release-followups.md) and
`/mnt/data/fathomdb/0.8.29-S50-data/` retain the observation, reports, source pins
and final databases. Fixed-state exactness remains a separate contract.

### Process overhead deserves a candid correction

The owner repeatedly asked for inherited verification credit, less paperwork,
fewer approval stops, earlier high-risk tests and a useful GPU completion
forecast. We still proposed three additional CUDA rehearsals that the owner
rejected as ceremony. One real shipping CUDA build was necessary and eventually
passed in about 12 minutes; it was not a substitute claim that those omitted
rehearsals had passed. Actual new host access and the protected-main exception
needed explicit authorization; routine continuation under settled limits did not.

Repeated helper reviews, status-copy reconciliation and tooling-only corrections
reduced progress. An idle helper was also sent follow-up messages without being
reactivated; the parent eventually performed the reviewed cleanup directly.
The interval from CUDA job completion03:29:18Z to cleanup confirmation03:33:08Z
includes necessary cleanup and cannot all be attributed to that messaging error.
The lesson is to verify agent state and finish a coherent work batch, not add a
new review or approval boundary for every helper.

Some historical instructions remained actively misleading: the old
`release-publish-gotchas.md` memory advised force-moving published tags and always
rehearsing, whereas current permissions forbid force-push and the owner explicitly
omitted the extra rehearsals. Main was actually verified unprotected; seq-397 was
an exact-tag exception to a protected-main runner trust contract, not a change
to branch protection. Keep operational settings, owner preferences and trust
requirements distinct. Historical phase prose still saying “held” or “pending”
should be labeled or replaced, rather than followed with another status appendix.

## Scale of the work and limits of the accounting

At the shipping tag, `git log v0.8.28..v0.8.29` contains 1767 reachable commits
and 656 first-parent commits. The net tag-to-tag diff touches 231 `src/` files
(+46446/−2076 lines), 100 script/workflow files (+5779/−412), and 720 `dev/`
files (+98144/−203). Within `dev/`, 329 Markdown files add 46037 lines and 297
Python files add 36745 lines. These include inherited branches, tests, experiment
code and design material. They are not person-hours, new-feature counts or a
measurement of wasted effort. The volume does show why a smaller executable
plan and less duplicated narrative would improve orientation and maintenance.

The final cleanup reclaimed65.12 GiB of inactive compiler output while preserving
native/raw evidence under `/mnt/data/fathomdb/cleanup-2026-11-17/`. This was useful
capacity recovery, not permission to remove live scratch, source, shared models
or the S50 archive. Disk use belongs in execution planning, not a late surprise.

## Practices to keep and practices to change

Keep genuine behavior-specific RED→GREEN, independent review of coherent changes,
real databases, exact source/artifact applicability, independent result oracles,
actual fault delivery, owned cleanup and installed-registry consumers. Keep
conditional non-adoption and honest uncertainty as valid outcomes.

Change the default from “another proving run” to “what changed that invalidates
which claim?” Spend testing effort on state transitions, concurrency, malformed
boundaries and measured hot paths. Make a failed suite understandable immediately;
make normal publication finish without a recovery tour. Use one current release
state, one concise final result and links to raw history, instead of maintaining
several active versions of the same progress narrative.
