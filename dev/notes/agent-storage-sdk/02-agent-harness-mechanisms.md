# UI SDK’s agent and harness mechanisms

Research date: 19 November 2026; UI SDK revision `3647512865fe0242b749dd8981c51c75ad5f486b`. This reflection distinguishes shipped SDK behavior, application responsibility, and harness policy. It builds on the [SDK review](01-vercel-ui-sdk-review.md) and covers source inspection, not executed conformance tests.

## The model receives an application-owned protocol

`createAgent` produces a browser-side bridge with `snapshot`, `query`, `act`, and `subscribe`. Framework agent entries re-export the core implementation. The bridge installs observation hooks and shares the primitive registry with observation tooling. It also discovers existing components through `watchEarlier`, so startup initialization is optional; it may be created when an assistant opens. [Startup contract](https://ui-sdk.dev/docs/agents/connect-an-agent). It therefore reads component semantics that the application already owns, rather than learning a separate interpretation from screenshots. It still reads DOM information for accessible names, nearby row text, visibility, buttons, and rendered options: this is not a wholly DOM-independent protocol. [Core bridge](https://github.com/vercel-labs/ui/blob/3647512865fe0242b749dd8981c51c75ad5f486b/packages/core/src/page/agent/agent.ts), [registry](https://github.com/vercel-labs/ui/blob/3647512865fe0242b749dd8981c51c75ad5f486b/packages/core/src/page/observe/registry.ts), [React re-export](https://github.com/vercel-labs/ui/blob/3647512865fe0242b749dd8981c51c75ad5f486b/packages/react/src/agent.ts).

`snapshot` describes components, current exposed state, available actions, and relevant status. `query` narrows discovery by text, kind, or one list’s ref/label through `within`; it does not open controls. A snapshot caps long pages at 100 entries and queries cap choice lists at 50, reporting omitted counts. This gives the harness a way to retrieve more selectively. Off-page entries are remembered observations, explicitly marked, rather than live state. [Runtime reference](https://ui-sdk.dev/docs/agents/connect-an-agent/reference).

Inference: the model can reason at approximately the user’s task level—set Visibility, choose Email, remove a named member—while the application resolves that intent into its actual controls. A tiny set of tools serves many components without sending hundreds of per-control tool definitions. However, coverage follows participating primitives; this is not universal control of arbitrary websites.

## Identity, discovery, and stale observations

Mounted refs survive rerenders; labels and row text aid lookup. Matching normalizes case and accents and refuses ambiguous component names. Importantly, an exact label does not automatically defeat another row containing those same words, since another user might supply the row text. This reduces accidental target selection but does not eliminate prompt injection. [Lookup and ambiguity tests](https://github.com/vercel-labs/ui/blob/3647512865fe0242b749dd8981c51c75ad5f486b/packages/core/test/agent.test.ts).

The registry uses weak instance references, internal IDs, remembered refs, and capped off-page state. It remembers the identities of the last 500 departed components, but identical returning controls may exchange remembered refs. A harness must refresh after renaming/reordering and distinguish off-page memory from the present. Neither a friendly label nor a `c1` ref is a durable database key or authorization credential. [Registry implementation](https://github.com/vercel-labs/ui/blob/3647512865fe0242b749dd8981c51c75ad5f486b/packages/core/src/page/observe/registry.ts), [server-integration guide](https://ui-sdk.dev/docs/agents/connect-an-agent/run-on-your-server).

Failure example: after sorting a member list, blindly reusing a remembered ref for “the second Remove menu” risks acting on a different member. Query the current row, refuse ambiguity, and inspect the returned acted-on ref. The SDK improves the available evidence; the harness still has to use it.

## Schemas are useful but incomplete

`agentTools` ships names, descriptions, and JSON Schemas for the three tools. These describe the envelope, not a complete per-action typed RPC system: `args` is an array of arbitrary values. Primitive metadata can explicitly list permitted API methods, item data, whether choices are closed, visibility, and secrecy. Without an explicit action list, verb conventions discover mutating methods. This keeps custom primitives inexpensive to expose but makes deliberate declarations preferable when the public action surface matters. [The Agent Key](https://ui-sdk.dev/docs/agents/connect-an-agent/your-components).

Runtime tests show limited option-based argument checking: boolean and number setters reject incompatible values, numeric text can be parsed, and closed lists reject nonexistent or disabled options. A custom action without a corresponding schema option receives arguments unchecked. Therefore “typed actions” should mean typed envelope plus some runtime constraints, not comprehensive validation. Custom APIs must validate all inputs and remain usable without a synthetic DOM event. [Validation tests](https://github.com/vercel-labs/ui/blob/3647512865fe0242b749dd8981c51c75ad5f486b/packages/core/test/agent.test.ts), [primitive type contract](https://github.com/vercel-labs/ui/blob/3647512865fe0242b749dd8981c51c75ad5f486b/packages/core/src/foundation/kernel/primitive-types.ts).

## Policy boundaries and shared mutation paths

There is no separate deny-list or element-scope option on `createAgent`; its options are `allow` and confirmation timeout. App code expresses action policy in `allow`, visibility/secrecy/confirmation with element marks, and value policy in component callbacks. Query’s `within` narrows one lookup; it is not a session capability boundary. Actions are accepted by default when supported, except marked confirmations that require a person. `allow` does not hide readable state. Target discovery during `act` can open a section or popup before checking the requested action; a shared open-change callback is needed to reject that opening too. [Permissions guide](https://ui-sdk.dev/docs/agents/connect-an-agent/permissions).

`data-agent-hidden` excludes components, `data-agent-secret` redacts filled values while allowing entry, and `data-agent-confirm` describes a consequence that policy must approve. Password and similar sensitive fields receive special handling. These marks propagate through relevant regions and shadow hosts. The marks’ implementation and tests matter more than a vague claim of safe agents. Browser tests separately exercise CSS-hidden controls and modal-inert backgrounds. [Mark logic](https://github.com/vercel-labs/ui/blob/3647512865fe0242b749dd8981c51c75ad5f486b/packages/core/src/page/observe/marks.ts), [mark tests](https://github.com/vercel-labs/ui/blob/3647512865fe0242b749dd8981c51c75ad5f486b/packages/core/test/agent-marks.test.ts), [browser security tests](https://github.com/vercel-labs/ui/blob/3647512865fe0242b749dd8981c51c75ad5f486b/tests/specs/agent.security.spec.ts).

Changes use component APIs and callbacks with `details.source === "agent"`; callbacks can reject values. Keyboard/pointer-only validation will be bypassed by direct API setters, so rules belong at the shared mutation path. Source is useful provenance, not an authenticated principal. It is dynamically scoped; work after an `await` needs explicit `withSource` to preserve attribution. [Change-details implementation](https://github.com/vercel-labs/ui/blob/3647512865fe0242b749dd8981c51c75ad5f486b/packages/core/src/foundation/kernel/details.ts).

Approvals can be asynchronous, with an abort signal and a default five-minute timeout. Calls queue on one bridge so a later agent call cannot answer its own pending confirmation. The implementation rechecks changed marks and disabled status after waits; tests cover a browser cancelling a pending approval and freeing the queue. This does not establish cancellation of a network effect already started. An `allow` returning unconditional true also approves confirmation-marked actions: policy code must actually examine the consequence. [Approval tests](https://github.com/vercel-labs/ui/blob/3647512865fe0242b749dd8981c51c75ad5f486b/packages/core/test/agent-marks.test.ts).

## Results, partial execution, and asynchronous work

`act` runs steps in order, stops on the first bridge error, and returns completed steps, an indexed error, changes, disappeared/appeared components, and exposed field values. Earlier effects remain applied. A cancelled callback can leave `ok: true` without the requested value changing. Both facts defeat any claim that a batch is atomic or that tool success proves task success. Check resulting values before saving; avoid blind retries of non-idempotent steps. [Result contract](https://ui-sdk.dev/docs/agents/connect-an-agent/reference#act-steps).

The bridge waits for rendering and for a component’s reported pending work, with a 15-second bound. An arbitrary Promise-returning custom action can still report pending; early rejection fails the step, while later rejection belongs to the application. A pending result is not durable completion. A failure after renaming a project but before removing a member calls for reconciliation from returned/current state, not replay of the entire batch. [Async implementation](https://github.com/vercel-labs/ui/blob/3647512865fe0242b749dd8981c51c75ad5f486b/packages/core/src/page/agent/agent.ts#L1206), [custom-action tests](https://github.com/vercel-labs/ui/blob/3647512865fe0242b749dd8981c51c75ad5f486b/packages/core/test/agent.test.ts).

`subscribe` supplies settled changes from humans and agents, allowing a host to refresh model context. Experimental `createHistory` and `stageChanges` can restore component values through current permissions. They do not undo network requests, resurrect removed components, or reverse saving. Staging changes real controls; reverting can overwrite later human edits. This is useful UI coordination, not durable replay, event sourcing, or transaction rollback. [Observation guide](https://ui-sdk.dev/docs/agents/connect-an-agent/observe-changes), [history source guide](https://github.com/vercel-labs/ui/blob/3647512865fe0242b749dd8981c51c75ad5f486b/apps/docs/content/docs/agents/connect-an-agent/history-and-undo.mdx).

## Where the harness begins

The core does not select a model, manage credentials, establish a remote connection, or run a reasoning loop. The documented server example supplies tool definitions to AI SDK, forwards browser-executed calls, and returns JSON results to the model. The benchmark instead uses a localhost HTTP wrapper with a bearer token and Playwright evaluation. Those are integration examples, not a bundled production transport or MCP server. [Server example source](https://github.com/vercel-labs/ui/blob/3647512865fe0242b749dd8981c51c75ad5f486b/apps/docs/content/docs/agents/connect-an-agent/run-on-your-server.mdx), [benchmark wrapper](https://github.com/vercel-labs/ui/blob/3647512865fe0242b749dd8981c51c75ad5f486b/benchmarks/agent/harness/browser.mjs).

`registerTools` is a shipped WebMCP bridge: it feature-detects `document.modelContext.registerTool`, requires a second `allow`, registers three tools, and returns cleanup via an abort controller. It marks reads as read-only, all page-derived output as untrusted, and action calls as consequential. These annotations assist the consumer; they are not authorization enforcement. Unsupported browsers get no registration. [UI SDK WebMCP guide](https://ui-sdk.dev/docs/agents/connect-an-agent/webmcp).

WebMCP remains an evolving Draft Community Group Report, explicitly not a W3C Standard or Standards Track document. Browser and agent support must be checked for the target deployment; registration alone does not imply every harness will discover it. The upstream status page lists Chrome 149 and Edge 150 origin trials; Firefox and Safari entries link to standards-position or tracking discussions rather than announcing support. This is an upstream status snapshot, not a browser test. WebMCP page registration is distinct from backend MCP transports. [Implementation status](https://github.com/webmachinelearning/webmcp/blob/main/implementation-status.md). [Current specification](https://webmachinelearning.github.io/webmcp/), [Chrome documentation](https://developer.chrome.com/docs/ai/webmcp).

## Transferable principles and limits

The transferable design is a narrow semantic protocol over real application state, progressively discoverable contracts, shared validation, explicit uncertainty, and inspectable results. Testing helpers and security tests make those claims challengeable. The inspected code offers in-memory observations and benchmark call logs; I found no core promise of durable audit, exactly-once delivery, replay safety, cross-client isolation, or storage authorization.

For persistent data, those omissions become central requirements: stable identity, authorization outside model-controlled input, concurrency preconditions, transaction boundaries, durable completion, and retry semantics. FathomDB should copy the reduction in translation and uncertainty, while specifying these stronger storage guarantees independently. This is an architectural lesson, not evidence that UI action batching supplies them.
