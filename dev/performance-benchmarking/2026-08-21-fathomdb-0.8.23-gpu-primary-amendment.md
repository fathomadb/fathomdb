# FathomDB 0.8.23 GPU-primary performance amendment

**Date:** 2026-08-21  
**Authority:** direct HITL instruction.  
**Status:** planning amendment only; it authorizes no corpus, model, GPU, or
external execution.

## Decision

Use released FathomDB 0.8.23 as the next performance baseline. GPU is the
primary runtime for new embedding- or cross-encoder-accelerable experiment
cells. TC-5 becomes GPU-primary once its private 0.8.23 benchmark executable
and v2 controls are independently reviewed and integrated.

CPU is not a more faithful backend. It is only a controlled historical bridge.
The prior CPU/CUDA calibration establishes tolerance-based, not byte-identical,
equivalence; GPU and CPU must therefore remain separate measured cells and must
not be pooled.

## Preconditions

1. Integrate the performance branch with the 0.8.23 mainline in a dedicated
   worktree. The existing branch is still 0.8.22 and its editable environment
   cannot provide the private benchmark executable. Reconcile append-only
   ledgers through their prescribed tools; do not hand-resolve ledger merge
   conflicts.
2. Pin the exact published Python wheel or the exact `v0.8.23` source/binary
   digest, respectively. The wheel supports Python LOCOMO/PARENT execution;
   the unpublished `fathomdb-tc5-benchmark` executable must be built from
   source with `tc5-benchmark-cuda`.
3. Before every GPU action, reserve exactly one RTX 3090 through
   `CUDA_VISIBLE_DEVICES`, pin its UUID in the manifest, and record the
   resolved process-visible ordinal, UUID, device policy, and allocation
   evidence. The K620 is excluded. A CUDA environment variable alone is not
   evidence of GPU engagement.
4. Retain the existing external corpus, model-cache, no-payload, safe-receipt,
   coordinator-release, and independent-review boundaries.

## LOCOMO and PARENT use of 0.8.23

The completed directional 26-cell GPU evidence is retained; it is not
retroactively relabelled as a 0.8.23 result and does not require a duplicate
CPU grid. Any later LOCOMO/PARENT or ANSWER-01 action using the released wheel
must pin `FATHOMDB_EMBED_DEVICE=cuda:0` and, when cross-encoder scoring is in
scope, `FATHOMDB_RERANK_DEVICE=cuda:0`. Its receipt records the independent
embedding and reranker resolutions and selected UUIDs. SQLite retrieval,
bit-KNN, exact-f32 rerank, fusion, graph work, and storage remain CPU stages;
the receipt must not call them GPU work.

## SCALE-01 TC-5 v2 design

The current CPU-only `tc5-*-v1` configuration, driver, and executor remain
historical controls. They may not issue a new release after the v2 contract is
accepted. V2 must add red-first tests before implementation for all of the
following:

1. a GPU-primary bridge-plus-primary action admits only the 7,667- and
   17,272-document real-only arms, `K=192`, 100 queries, 1,000 bootstrap
   resamples, and exact-f32 same-model top-10 ground truth;
2. the GPU binary is `fathomdb-tc5-benchmark` built with
   `tc5-benchmark-cuda`, receives one process-visible GPU, and fails closed on
   a missing, ambiguous, unpinned, or UUID-mismatched device;
3. the cache-only private executable receives no `FATHOMDB_*` controls and
   attests its direct vector-stage route, selected UUID, model asset identity,
   and result digests without exposing payloads or paths; and
4. a CPU bridge action cannot admit the 17,272-document primary arm, a GPU, or
   more than twelve effective CPU workers.

The normal v2 order is a GPU smoke over the 7,667 bridge then the 17,272
primary, review, and a separately released long GPU characterization over the
same two arms. Its claim remains vector-stage fidelity and uncertainty only;
it creates no latency, SCALE-02, or product claim.

### Optional CPU bridge

Do not run a full CPU TC-5 primary arm. If a release-version equivalence bridge
is needed, run only the existing 7,667-document bridge with an explicit
`cpu_worker_count=12` control. The implementation must define the actual
thread/worker mechanism and record the observed effective count; an unrelated
engine scheduler setting is not evidence that the private benchmark used twelve
cores. The CPU bridge is a separate coordinator release and receipt.

Before that bridge is released, freeze tolerance and decision rules for maximum
embedding difference/cosine, sign-bit flips, candidate and top-10 overlap,
exact-ground-truth overlap, and paired recall delta with confidence interval.
ULP-level CPU/GPU differences are expected; byte identity is not an acceptance
criterion.

## Required record updates

The Track Runner and SCALE-01 charter must name the private 0.8.23 selector as
available-but-not-yet-integrated, replace the stale NVIDIA-driver blocker with a
fresh per-run preflight requirement, and point to this amendment. Historical
v1 plans and receipts remain immutable evidence.
