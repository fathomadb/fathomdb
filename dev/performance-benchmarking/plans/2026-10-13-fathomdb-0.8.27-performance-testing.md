# FathomDB 0.8.27 performance testing plan

**Status:** Proposed revision, 2026-10-13. This defines implementation and
experiments; it contains no benchmark result. Before execution, register
`COMP-01` (FTS), `COMP-02` (readiness and filtering), and `COMP-03` (answers)
in [PROGRAM](../PROGRAM.md), create their track briefs, and use the
[Track Runner](../TRACK-RUNNER.md). Keep cross-SDK overhead in its existing
separate suite. The independent [critical review](2026-10-13-fathomdb-0.8.27-performance-testing-critical-review.md)
records findings and recommendations that informed this revision.

## Outcome and limits

Produce three local scoreboards: **latency/capacity**, **retrieval**, and
**answer**. FathomDB 0.8.27 is the fixed baseline. Run LanceDB locally for
FTS, then use the relevant methodology and, where feasible, a pinned version
of [SurrealDB crud-bench](https://github.com/surrealdb/crud-bench) for a local
SurrealDB comparison. Follow the top-5 isolated-memory structure of
[LanceDB's Hermes experiment](https://github.com/lancedb/hermes-agent-memory)
with local answer and judge models. Vendor-published numbers are context, not
paired results. The [source survey](../../../experiments/research/2026-10-13-embedded-competitor-benchmark-survey.md)
and [competitive requirements](../competitive-testing-requirements.md) give
the rationale and broader contract.

### Select one cell or a batch

The campaign file expands to a deterministic ordered roster of cells, where
one cell is one case, product arm, and fresh-database repetition. The proposed
coordinator accepts a selection such as `--cell <id>` or `--max-cells <n>`:
`1` takes one pending cell; `n` takes the next `n` pending cells; an omitted
limit takes the remaining roster. A resume operation uses the same immutable
campaign hash and manifest, skips already recorded cells, and never appends a
second receipt for one attempt. Record selected, pending, complete, blocked,
and unsupported cells in the manifest. The fixed `AB/BA/BA/AB` order is
preserved across batches; partial batches are not interpreted as complete
comparisons.

Selection count is distinct from simultaneous execution and from a cell's
query concurrency. Run selected latency cells serially on the shared host
(`jobs=1`); otherwise concurrent cells would contend for CPU, cache, and I/O.
A future `jobs>1` mode needs declared isolated hosts or an explicit throughput
experiment. One cell may yield several metrics from the same timed query calls.

The coordinator captures hashes, versions, resolved settings, hardware,
schedule, timestamps, statuses, and receipts. Each product adapter must
capture its actual ordered hits, timing samples, readiness, and resource
observations during execution. The coordinator validates those artifacts and
scores them against pinned gold. It cannot reconstruct IDs after an adapter
has discarded them; the current FTS adapter therefore needs an output change.

The current FTS adapter calls `Engine.search` with no embedder and returns only
hit counts; its one database is reused across its configured repetitions. It
cannot produce the requested ranked-ID quality comparison unchanged. The
current product v2 runner is one arm and one scoreboard per invocation; the
thin campaign coordinator must own repetition and pairing without replacing
the single-arm runner. One measured attempt
must write one result and receipt, with latency and retrieval aggregates
computed from its saved ordered hits and timings. Rendering two scoreboards
must not rerun queries. The SDK answer fixture uses a first-sentence rule
and cannot serve as a real answerer.

Each executable case file captures treatment and effective options, corpus/
query/gold hashes, search/result unit, top-K, filter and validity semantics,
hardware, cache state, process state, concurrency, warmup, timer boundaries,
query order, seeds, timeouts, expected metrics, and adapter/build digests.
The external campaign manifest binds the resolved files and per-attempt raw
artifacts to safe `experiments.record.v1` receipts and append-only index rows.
Store raw text, predictions, logs, DB files, and private paths externally.
For FathomDB, call `prepare_test_database` for every independent attempt.

Use concurrency one and the same host. For paired performance cells, use arm
order `AB/BA/BA/AB` (A is FathomDB). Do one dry preflight and a small untimed
smoke before each measured phase. Then use four independent fresh-database
repetitions per performance arm. COMP-03 states its answer-run exception.
Report each repetition,
median across repetitions, and the paired per-repetition difference; do not
pool 323 queries across repetitions as if they were independent databases.
Keep cold/first-query and steady-state results separate. Query-time boundaries
start at the public API call and end after ordered IDs and needed fields are
materialized. Quality uses the same frozen IDs and gold, not a second query
with different settings. Record errors and attempted/completed denominators.

## COMP-01 — NFCorpus FTS and local LanceDB

**Prepare.** The local [BEIR NFCorpus](../../../data/corpus-data/raw/beir/nfcorpus/)
has 3,633 documents and 323 distinct test IDs in `qrels/test.tsv`. Select
exactly those 323 IDs from `queries.jsonl`; the file also contains other
splits. Freeze raw and converted file hashes, all 323 IDs, `title`/`text` to
indexed-body mapping, and qrel grade interpretation. Use one original document
ID as one primary scored retrieval unit. Freeze a duplicate-body map:
FathomDB's `search_text_only` deduplicates matching bodies before top-10,
while the official qrels score IDs independently. Pin each FTS analyzer,
query-term translation, and index option. Native query translation is a
product treatment, including FathomDB's short-token/stopword removal and OR
term composition.

**Run design.** Implement and smoke FathomDB first, then LanceDB. In measured
attempts both index the identical converted documents and query the same
shuffled 323 test IDs with `top_k=10` and the balanced arm schedule above.
Use FathomDB's public `search_text_only` to guarantee the FTS-only path; the
current adapter's `Engine.search` is not an explicit FTS-only contract. Use
LanceDB's local indexed FTS path. Verify index readiness before timing, and
record build-to-ready separately. A warm query pass is explicit; time one
steady pass per fresh database. Four arm-order-balanced repetitions supply
the comparison. Record ordered document IDs, hit count, query latency, and
errors for every query. Score nDCG@10 with graded qrels, Recall@10 using
qrel grade `>0`, and MRR@10 as reciprocal rank of the first grade `>0` hit.
Report per-arm query p50/p95, index/build time, and disk/RSS separately.
Score the unchanged official IDs/qrels as primary; report queries affected
by duplicate bodies separately. An optional duplicate-equivalence score is
secondary and needs a frozen group-gold rule. Do not alter indexed text to
defeat native deduplication.

**Acceptance.** Each arm returns a valid top-10 document-ID list for all 323
queries in every repetition; IDs are unique within a result and belong to
the same 3,633-document corpus. A scored report includes aggregate and
per-query retrieval metrics, timing distributions, four attempt receipts
per arm, and the campaign manifest. Analyzer differences are named treatment
differences. Prior IR-C and vendor results are context only.

## COMP-02a — ingest-to-queryable time and bounded scale

**Feasibility task.** Pin and inspect crud-bench's *implemented* source and
configs before writing an adapter. Its README lists some search/index items
as future work. Produce a one-page capability map: implemented ingest,
readiness, filtered search, embedded SurrealDB mode, external corpus/query
import, ordered ranked-ID export, result artifacts, and extension points.
Its template value generator alone cannot establish a same-corpus comparison.
Use its runner for an eligible leg. If the needed timing
hooks are absent, add a minimal versioned bridge/extension with tests and
identify it as **our extension to crud-bench**. If the extension grows beyond
the two scoped workloads, use our product runner with the crud-bench protocol
and label that clearly. Never call a planned README
item an upstream benchmark result.

**Run design.** Use the existing qualified SCALE-02 10,000 and 17,272-document
input prefixes, with their real versus derived fixture labels. Begin at 10k;
only proceed to 17,272 when both arms load the identical 10k IDs and pass the
readiness probe. For each of four fresh-database attempts per tier/arm,
record monotonic timestamps for first write, last acknowledged write,
index-build call return (if an explicit build exists), first successful
index-backed query containing a preselected late-inserted sentinel, close/
reopen, first post-reopen successful query, and a steady query pass. A single
sentinel is insufficient to prove corpus completion: also check indexed
visible count and deterministic probes spanning early/middle/late IDs.
Bound readiness polling and retain the failed probes and timeout status.
Report ingest acknowledgement time, build-return time, true query-ready
time, reopen/first-query time, p50/p95 steady latency, disk bytes, peak RSS,
and inserted versus visible counts. Exclude corpus conversion, downloads,
and embedding generation from database timers; include them separately in
the record. Fix batch size, durability/sync policy, and concurrency in the
case file. No extrapolation to a million records.

**Acceptance.** Both tiers have complete FathomDB attempts or typed stops.
SurrealDB is paired only for a shared embedded deployment, corpus, operation,
durability rule, and timing boundary. Missing build-call support is recorded
as `not_applicable`, while query-ready time remains measurable. The largest
successful tier is a measured envelope, not a product capacity limit.

## COMP-02b — filtered retrieval at measured selectivity

**Prepare.** Use one fixed 10k corpus from COMP-02a. Add a deterministic
categorical `bench_cohort` property with disjoint groups targeting 1%, 10%,
and 33% of documents. Freeze the assignment and queries, count the matching
records in both databases, and report observed selectivity `matches/visible`.
For FathomDB, test an actual `FILTERABLE` projection plus
`SearchFilter(attributes=(("bench_cohort", value),))` through public
`search_projected_text` on a declared searchable-text projection. Avoid
`status`, whose 0.8.27 search column has no population source, and `kind`,
which would change the indexed partition. Prove by a small preflight that the
filter is applied before the result cap and every returned ID satisfies it.
This is a supported projected-FTS route; the direct `search_text_only` method
has no filter parameter. The benchmark must name which route it measures.

**Run design.** Qualify shared filtered FTS in both products before timing:
freeze native query translation and verify that both arms use an indexed
text predicate plus the same categorical eligibility rule. Native lexical
analyzer/term differences remain treatment differences. Then compare
**filtered FTS** as a shared operation, using
the same 100 frozen text queries at top-10, concurrency one, four fresh
attempts per arm/selectivity, and steady p50/p95 latency. Validate membership
of every result and count queries with fewer than ten matches; do not call
engine-specific BM25 scores an exact-neighbor oracle. If the pinned
crud-bench supports a compatible filtered-vector operation, define a
**separate** KNN case with one precomputed vector set, metric, dimension,
query vectors, and an independent brute-force top-10 oracle over *only* the
predicate-matching rows. Score predicate-correct Recall@10 and latency at
each observed selectivity. FathomDB 0.8.27 has no declared common public
vector-only SDK query; verify a true equivalent public method before adding
its KNN arm. Hybrid search cannot substitute for vector-only KNN.

**Acceptance.** FTS produces six attempted selectivity/arm cells, each with
measured counts or a typed refusal, timings and predicate-correct ordered IDs
for completed cells, and receipts. Pair only the shared eligible operations. Vector
cells appear only after the capability check and exact oracle pass. An
unsupported 0.8.27 vector case is a recorded capability result with no
fabricated recall or time. A post-filtered `top_k` implementation is not
paired with a prefiltered one unless the same final retrieval semantics and
oracle are verified.

## COMP-03 — Hermes-style answer comparison without network time

**Prepare.** Local LongMemEval-S contains 500 questions in six types (the
smallest type has 30). Select ten per type with a fixed seed, sorted within
type, and commit only the 60 selected IDs, selection code/seed, counts, and
hashes. Keep full question/history/gold payloads external. Each question is
its own isolated memory store. Convert history to the same document unit and
IDs for FathomDB and LanceDB. Freeze the gold-answer/abstention rule and
supporting-evidence mapping before reading results. The history converter
whitelists only role, content, session identity/date, and other declared
non-gold chronology needed for temporal questions. It excludes nested
`has_answer`, reference answers, support IDs, and all gold labels from indexed
records, retrieval snippets, and answerer prompts. Changing gold labels must
leave those three outputs byte-identical in a test. Only the isolated judge
and scoring stage may consume reference answers and declared grading gold;
its prompts may change when the gold changes. Preserve the question date in
the query contract, not in indexed answer metadata.

**Run design.** Compare the two local FTS arms first. For each question, build
both stores from identical history; retrieve top five; pass the same ordered
evidence fields through the same truncation code and fixed token budget to
one pinned **local** answerer. Use one pinned local judge, rubric, decoding
seed/temperature, and prompt for both arms. Models and tokenizer must be
present before the run; disable network calls for retrieval, generation,
and judging. Record model hashes and device policy. Reuse FathomDB and
LanceDB evidence only after binding ordered IDs, snippets, and retrieval
result digests to the answer attempt. Record retrieval R@5/MRR@5 where
supporting-evidence gold is adequate, answer correctness, abstention, and
per-type counts; keep retrieval, answer, and judge time separate. Blind the
judge to product identity and manually audit a small fixed answer sample for
rubric mistakes. Run three seeded attempts only if answerer/judge stochastic
variation matters; otherwise one deterministic pass on all 60 is descriptive,
with a paired question-level interval for the answer difference.

**Acceptance.** Exactly 60 questions, ten per class, have complete matched
evidence budgets and answer/judge outputs, or explicit per-question failures.
The report states the paired denominator, per-type rates and uncertainty,
and links every answer to its retrieved evidence. The current SDK
`first_sentence_v1` fixture is not used as an answerer. Published Hermes
scores and its network-inclusive latency remain context only.

## Closeout and decisions

Execute COMP-01, then COMP-02a and COMP-02b, then COMP-03. Release the
answer cases only after retrieval evidence is valid. Render separate local
latency/capacity, retrieval, and answer views with `paired_eligible`,
`local_descriptive`, and `unsupported` labels. Publish a concise result note
with exact configs, denominators, distributions, uncertainties, failures,
resource costs, and links/digests for raw artifacts. For a FathomDB deficit,
first test measurement mismatch and configuration, then identify the real
mechanism and adjustment cost for a user decision.

The [quality testing roadmap](../../notes/fathomdb-quality-testing-roadmap.md)
supports real-database workloads and independent oracles here. Broad fault
injection and new release gates are outside this measurement plan; confirmed
failures can become targeted regression tests.
