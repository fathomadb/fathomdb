# FathomDB 0.8.27 performance testing plan

**Status:** Proposed, 2026-10-13. This is a successor campaign plan, not a
completed measurement or an active PROGRAM track. Register its execution
tracks in [PROGRAM](../PROGRAM.md) and follow the
[Track Runner](../TRACK-RUNNER.md) before implementation or measurement.

## Decision and scope

Build three comparable, repeatable scoreboards for the 0.8.27 product:
retrieval quality and query latency on a real lexical dataset; ingest,
query-readiness, bounded scale, and filtered retrieval; and downstream answer
quality. The first local product comparison is LanceDB FTS. The second adopts
the relevant protocol from [SurrealDB crud-bench](https://github.com/surrealdb/crud-bench)
and tests a local SurrealDB arm where a pinned implementation supports the
same operation. The answer experiment follows the design of
[LanceDB's Hermes memory experiment](https://github.com/lancedb/hermes-agent-memory),
with local execution and no network operation in a measured stage. These are
local product comparisons; cross-SDK overhead has its own suite.

Use the [competitive testing requirements](../competitive-testing-requirements.md),
[experiment record](../../../experiments/README.md), and
[competitor survey](../../../experiments/research/2026-10-13-embedded-competitor-benchmark-survey.md)
as the shared contracts. Published vendor results are context only. This plan
does not turn an unmatched published number into a speed ratio.

## Common setup and outputs

1. Pin the FathomDB 0.8.27 commit, package/native build, LanceDB version, and
   the SurrealDB and crud-bench commits before running. Record deployment
   mode, host CPU/RAM/storage/OS, process count, memory and device policy,
   effective engine/index settings, and adapter hashes. The primary local
   comparisons run on the same host, at concurrency one. Identify each arm's
   treatment, including its analyzer or embedding/index method.
2. Define each case in a versioned experiment file. Reuse the path-free
   `competitive.experiment.v2` runner and standard `experiments.record.v1`
   receipt/index envelope. Add reusable adapters and a successor case schema
   only for fields the current product runner cannot express; do not put
   workload constants in one-off command lines. Preflight must reject unknown
   fields, missing assets, hash drift, unsupported methods, and incompatible
   top-K/filter semantics before measurement.
3. Keep databases, corpora, queries, qrels, ordered hits, per-query times,
   prompts, answers, judge traces, and logs in a fresh external artifact root.
   Each cell attempt, including a failed or unsupported one, gets a typed safe
   receipt and index row. The external manifest binds config, inputs, code,
   settings, raw output digests, cell statuses, and result digests. Prepare a
   fresh FathomDB database with `experiments.fathomdb_test_setup` for each
   independent cell/repetition.
4. Predeclare warmup, cold versus steady process/cache state, query order,
   repetitions, timer start/end, materialization boundary, exclusions,
   percentile estimator, and uncertainty method in the file. Report per-arm
   distributions and quality even when pairing is ineligible. Never score an
   unsupported operation as zero. Use a smoke to validate the pipeline, then
   at least three independent fresh-database repetitions for a comparative
   claim; vary arm order across repetitions.

## 1. BEIR NFCorpus: FathomDB FTS, then LanceDB FTS

**Inputs.** Use the locally available BEIR NFCorpus test split: 3,633 corpus
documents, the 323 query IDs named by `qrels/test.tsv`, and those qrels. Pin
the three input hashes, sorted test ID list, document-ID mapping, text-field
construction, and query order. The queries file contains other splits; never
score all its rows. Both arms index the same documents and return document IDs
at the same top-10 boundary. Record each engine's tokenization, stemming,
stopwords, scoring, and actual index-readiness state.

**Run.** First validate and run FathomDB 0.8.27 FTS through the product runner.
Then add and run an in-process LanceDB indexed FTS adapter using the identical
frozen inputs, top-10 projection, host, and query protocol. Time the public
query invocation through fully materialized ordered IDs; separate indexing
and first-query costs. Check that every ID belongs to the shared corpus and
that both arms processed all 323 test queries. Compute nDCG@10 and recall@10
against the same qrels; report MRR@10 only with an explicit relevant-document
rule. Keep latency p50/p95 and per-query times separate from quality. Different
analyzers are declared treatment differences, not silently normalized away.

**Done when.** Two config-bound, validated local receipts and their external
ordered-hit artifacts exist; one paired report identifies eligible metrics,
method differences, uncertainty, failures, and the exact 323-query denominator.
An old IR-C or vendor result is regression/context evidence only.

## 2a. crud-bench: ingest-to-queryable time and bounded scale

**Feasibility first.** Pin an upstream crud-bench commit and inspect its actual
implemented workloads and datastore interface. Its README distinguishes
implemented work from planned items, so a checklist entry alone is not an
executable test. Use its runner directly where it can preserve the declared
timers, result projection, and embedded deployment. If an adapter or small
upstream extension is required, version and test that code and wrap its output
in the normal experiment record. If its pinned revision cannot support a
semantically matched leg, record the limitation and use the existing FathomDB
scale runner for a descriptive FathomDB cell; do not label it a crud-bench
product comparison.

**Workload and clocks.** Start with the qualified 10,000 and 17,272 document
tiers from [SCALE-02](../tracks/scale-02-local-first-envelope.md); retain its
source/derived-row labels. Do not inflate NFCorpus to create a larger lexical
dataset. For each fresh database record: ingest start, last write acknowledged,
index-build call return, first successful query that proves the declared index
serves the new documents, reopen and first successful query, and steady-query
time. A returned build call is never called query-ready by itself. Define the
readiness probe and timeout before running. Record inserted/visible counts,
failures, peak RSS, on-disk bytes, and query p50/p95; keep embedding generation
or downloads outside these database timers. Add a larger tier only after the
two bounded tiers are correct and resource limits are declared.

**Done when.** Each tier has a reproducible time-to-queryable curve with
readiness evidence and resource measurements. A local SurrealDB embedded row
is paired only if the same rows, operation, durability rule, and timing
boundary were exercised. Otherwise the rows remain descriptive.

## 2b. crud-bench: filtered retrieval at measured selectivities

Reuse the same pinned harness revision and a single frozen dataset with a
categorical equality predicate supported by the chosen arms. Predeclare three
predicate cohorts targeting about 1%, 10%, and 33%, then report their **actual**
matching-row counts and selectivities. Freeze query vectors or terms, predicate
values, top-10, metric/distance, exact-oracle code and hashes, and whether the
engine filters before or after candidate selection. The oracle computes top-10
from *only* predicate-matching rows; unfiltered neighbors are invalid gold.

Start with a shared, supported filtered search mode. Qualify vector-filtered
KNN separately: verify a public 0.8.27 FathomDB method, the same vector
distance and predicate semantics, and precomputed pinned vectors first. No
vector-only-to-hybrid substitution. For each eligible cell report predicate
correctness, recall@10 against its predicate-specific exact neighbors,
returned count, p50/p95 latency, and index/resource settings. If 0.8.27 cannot
express the same filter/search operation, emit a typed unsupported cell and a
capability finding, not a false latency or recall comparison.

**Done when.** All three cohorts have verified observed selectivity and exact
gold, with validated receipts for every attempted arm and explicit pairing
eligibility per search mode.

## 3. Hermes-style answer quality, fully local

Freeze a LongMemEval-S cohort before observing product results. Use the
Hermes-style stratified 60-question design only if the locally available
question taxonomy supports ten cases in each of its six intended classes;
otherwise publish the actual class counts and a deterministic, fixed sample
without claiming to reproduce Hermes's cohort. Keep each question's memory
store isolated. Pin question IDs, history-to-record mapping, gold answers,
evidence unit, top-5 boundary, prompt, context-token budget, answerer, judge,
model weights/runtime, decoding, abstention rule, and scoring code.

Feed each arm's retrieved top-5 evidence to the **same local answerer and
judge**. Precompute or locally generate any embeddings with pinned models;
capture that preparation separately. Disable remote model/API calls in
retrieval, generation, and judging. Retain the ordered retrieved IDs, evidence
digest, answer, and judge trace externally so an answer result is bound to its
retrieval result. Score retrieval (R@5/MRR@5 where gold supports it) and answer
correctness, abstention, and supported question-class slices separately.
Measure retrieval, answer generation, and judge time as distinct stages. Start
with the FTS arms from section 1; add vector/hybrid arms only with an explicit
matched method contract. Vendor-published Hermes scores are context only.

**Done when.** The same frozen cohort, evidence budget, answerer, and judge
produce validated per-arm receipts and a paired answer report. If the local
models or gold are unavailable, record a blocked prerequisite rather than
changing the answerer or invoking a network service.

## Sequence and interpretation

Register the tracks and review the config/adapter contract; validate all
inputs; execute section 1; then 2a, 2b, and 3. A smoke precedes each full
run. Retrieval results must be accepted before their answer evidence is used.
For any apparent FathomDB deficit, inspect input/metric mismatch, method
configuration, and actual mechanism; enumerate adjustment options and their
cost before a product decision. Publish the three scoreboards with paired,
descriptive, and unsupported rows clearly distinguished.

The [quality testing roadmap](../../notes/fathomdb-quality-testing-roadmap.md)
supports reusing real-database workloads and independent oracles here. Broad
fault injection, mutation coverage, and new release gates are deferred from
this performance campaign; its evidence can identify a later targeted test.
