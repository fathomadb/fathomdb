# 0.8.24 retrieval-performance evidence specification

## Purpose

0.8.24 makes one declared workload capable of producing both retrieval-quality
evidence and performance evidence. It does not turn EARP into a generic
benchmark, nor does it require an operator to recreate every EARP campaign in
a second, unrelated command.

The release's scale-envelope claim remains separately earned. This
specification defines the evidence integration needed to evaluate the cost of a
quality improvement honestly: a change that improves evidence recall, such as
a reranker or hybrid setting, must also report what that configured workload
costs.

## Terms and boundaries

| Term | Meaning |
| --- | --- |
| EARP | The offline, developer-side retrieval-evaluation platform. It owns pinned gold, retrieval-quality metric eligibility, per-query outcomes, and comparison/sweep inference. |
| Performance protocol | The repeatable timing and resource-measurement protocol. It owns sampling, process-cold/warm separation, percentiles, throughput, storage, and load claims. |
| Resolved workload | The immutable configuration after defaults/inheritance resolve: candidate SHA, corpus and gold identity, store/projection shape, query call and knobs, embedder, selected device, and sampling plan. |
| Evidence family | The linked collection of quality, observed-cost, and (when requested) repeated-performance artifacts for one resolved workload. |
| Quality provenance | The immutable candidate and environment that produced the EARP quality result. |
| Execution provenance | The candidate and environment that actually produced a performance sample. It is captured for every sample run and is never inferred from its quality parent. |

- EARP remains EVAL-ONLY and remains authoritative for retrieval-quality
  semantics. It does not become a production query path, an SDK feature, or a
  CI gate.
- The existing `experiments/` record/index convention remains the durable
  shared summary. A new metric family must not overwrite EARP's locked result
  sidecar or reinterpret retrieval metrics as latency metrics.
- The existing performance-runner and scale-characterization provenance
  conventions remain the starting point for performance claims. This work does
  not authorize an ANN/index replacement, a schema change, a new retrieval
  default, a CUDA requirement, a tag, or publication.

## Product contract

Every completed or blocked EARP campaign records lightweight, observational
cost evidence for the actual resolved workload. The resulting evidence answers:

> Did this configuration improve retrieval quality, and what did it cost in
> this run?

When a campaign requests a performance claim, the system uses that same
resolved workload to execute the declared repetition matrix. The resulting
evidence answers:

> What latency, throughput, storage, and reliability distribution does this
> configuration demonstrate under the declared conditions?

These questions have different statistical requirements. A single quality run
may report observed durations, but it cannot establish p95/p99, QPS,
process-cold behavior, or a support envelope. Those claims require controlled
repetitions; the runner schedules them from the same resolved workload rather
than asking a person to translate the scenario into a second tool.

## Evidence planes

### Retrieval quality — EARP owns

EARP preserves its existing responsibilities:

- corpus/gold pin validation and metric eligibility;
- evidence Recall@K, found/Success@K, precision, MRR, nDCG/MAP only where the
  gold supports them, all-bridges-present, abstention/negative outcomes, and
  answer metrics only under the identical-answerer protocol;
- per-query result, blocker, and comparison/sweep evidence; and
- strict public SDK call-path and knob validation.

### Observed cost — every eligible EARP run records

The EARP execution captures the following without claiming a distribution:

| Phase | Required observations |
| --- | --- |
| Open and setup | engine-open duration; open report; embedder/model events; projection configuration result; dense readiness and drain outcome. |
| Ingest | item/byte counts; accepted, rejected, and failed writes; canonical commit time; synchronous FTS/filter projection time; asynchronous embedding/vector time; accepted-to-ready time. |
| Storage | database, WAL, FTS, and vector/index byte sizes at declared checkpoints; checkpoint result; vector-row and projection-coverage witnesses. |
| Query | per-query wall-clock sample, result count, error/timeout/blocker outcome, selected query call and effective knobs; where available, engine trace phase timings and candidate counts. |
| Environment | candidate SHA and clean status; lock/schema/toolchain; CPU/RAM/disk; SQLite/sqlite-vec; embedder identity/dimension/cache event; explicit CUDA/device state; full command. |

Observed cost is labelled `observed`, never `benchmark`, `p95`, `QPS`, or
support evidence. A missing internal trace is recorded as unavailable; the
collector must not derive an invented phase breakdown from wall-clock time.

### Repeated performance — the performance protocol owns

A declared performance campaign consumes the same resolved workload and adds a
sampling plan. It records raw samples or a lossless reproducible histogram and
reports p50/p95/p99/min/max/mean, sample count, errors, and invalidity reasons
for every valid cell.

The initial matrix covers:

| Workload family | Required treatments and dimensions |
| --- | --- |
| Canonical, FTS, vector, graph, and full-stack ingest | batch size; body/edge/degree distribution; feature profile; embedder/device/cache state; accept, commit, projection, drain, and ready times; byte amplification. |
| ID/collection, FTS, vector, graph, hybrid, reranked, and explained reads | process-cold and warm separately; corpus size; query class/length; limit/filter/view; graph depth/fan-out; candidate/rerank pool; result correctness witness. |
| Mixed load and recovery | declared reader/writer mix, concurrency, WAL/checkpoint policy, open/close lifecycle, tail amplification, lock/busy/error rate. |
| SDK crossing | the same supported operation through Rust, Python, and TypeScript, with binding/call overhead reported separately from engine timing. |

The performance protocol must preserve treatment isolation. It may not pool
first-query process-cold samples with warmed-suite samples, pool different
feature profiles, or treat a failed drain, dirty candidate, missing provenance,
or incomparable environment as a zero or passing result.

## One declaration, linked artifacts

The architecture must implement this relationship:

```text
reviewed campaign config
          |
          v
resolved workload + stable configuration hash
          |
          +--> EARP quality result and per-query sidecar
          |
          +--> observed-cost sidecar for that execution
          |
          +--> optional repeated-performance artifact(s)
                    from the identical resolved workload
          |
          v
experiments/ record + append-only index row, linked by evidence-family ID
```

Required linkage fields are: evidence-family ID; resolved configuration hash;
candidate SHA; corpus/snapshot and gold identities; query-call and effective
knobs; store/projection/feature profile; embedder/device identity; artifact
paths and SHA-256 digests; and the parent quality run when a performance
campaign is scheduled after it.

The shared `record.json` remains compact and typed. Versioned sidecars carry
domain-specific detail, and a blocked performance arm must not change a valid
quality result into a retrieval miss. Conversely, a valid performance artifact
does not make incomplete or ineligible gold a quality result.

## Immutable workload and provenance contract

The performance runner must consume a versioned workload manifest, not an
unvalidated subset read from a parent's `record.json`. The manifest has
canonical JSON bytes and a SHA-256 digest. It contains, at minimum:

- quality parent run ID, evidence-family ID, result-sidecar path and SHA-256;
- resolved-config canonical bytes and SHA-256; quality candidate SHA, clean
  assertion, branch/baseline identity, lock/build/toolchain and device
  provenance;
- corpus snapshot and gold paths/identities/digests, query call, effective
  knobs, store/projection/feature profile, embedder identity/dimension and
  selected device; and
- the predeclared performance plan: treatments, repetitions, ordering/warm-up
  rule, aggregation rule, invalid-result policy, and command.

The quality writer stages this manifest as a quality artifact before any
performance execution, lists its relative path and digest in the quality
record, and binds it to the quality evidence-family ID. The runner verifies the
manifest, parent artifact digest, and resolved-config digest before execution.
It captures separate execution provenance for each cell: execution candidate
SHA and clean state, lock/build/toolchain/device/environment, command, and
relevant fixture digests. It records both identities durably.

If quality and execution provenance differ, the artifact remains useful as a
cross-candidate observation only when it has a distinct execution-workload
digest and an explicit `cross_candidate_reexecution` relation to the quality
parent. It does not join the parent's evidence family as the same resolved
workload, is invalid for a same-candidate cost/quality comparison, and must not
inherit the quality candidate's SHA or clean assertion. Missing or unverifiable
provenance is an invalid performance cell, never an assumed match.

## Campaign behavior

1. Validate and resolve one reviewed campaign configuration before any work.
2. Run EARP through real public SDK calls on a fresh scenario database and
   write its existing quality artifacts.
3. Capture the observed-cost sidecar for that same execution.
4. If no performance claim is requested, close the evidence family with the
   honest scope: quality plus one-run observed cost.
5. If a performance claim is requested, derive repeat cells from the immutable
   resolved workload and execute them through the performance protocol. The
   operator supplies no duplicate configuration.
6. Link all sidecars, stage/validate them, materialize the shared record, then
   append the experiment index last.

Comparison and sweep arms remain individually resolved. A quality comparison
may claim a causal difference only under EARP's one-knob rule; its performance
comparison must preserve the same arm pairing, hardware class, corpus, and
sampling policy. A quality improvement does not excuse an undisclosed cost
regression.

## Performance cell validity and reporting

A performance artifact is a complete matrix of typed cell records. Each cell
records its treatment, raw phase samples, counts, storage checkpoints,
execution provenance, errors/timeouts, and either `complete` or a typed
invalidity reason. A failed cell does not erase earlier raw samples or prevent
the artifact from recording the planned matrix; it makes any affected aggregate
ineligible under the plan's invalid-result rule.

The runner may write a successful one-sample smoke artifact, but it reports raw
values only. Percentiles require a predeclared, completed sample count:

- fewer than 20 valid samples: raw samples, min/max, and mean only;
- 20–99 valid samples: p50 and p95 may be reported as **descriptive empirical
  order statistics**, never as tail or support claims; and
- 100 or more valid samples: p50/p95/p99 may be reported as descriptive
  empirical order statistics, still scoped to the declared fixture and
  environment.

The plan fixes warm-up, treatment order/randomization, repetition count, and
aggregation before the first measured cell. No artifact establishes a QPS,
reliability, p95/p99 support threshold, or portability statement merely by
containing a percentile field; those claims require the separately reviewed
support protocol and equivalent-environment evidence.

Treatment names state exactly what they warm. The initial same-process executor
has `fresh_store` and `fresh_store_warm_query`: both create and ingest a fresh
database; only the latter performs an unmeasured query before timed query
phases. Open/write timings from those treatments remain fresh-store timings and
must not be compared as warmed ingest results. `process_cold` is reserved for a
future subprocess executor with an explicit process and OS-cache witness.

## Result interpretation

| Result | Permitted statement | Prohibited statement |
| --- | --- | --- |
| Quality plus observed cost | “This exact EARP run improved/changed the eligible metric and observed these phase durations.” | “This configuration meets a p99, QPS, or support target.” |
| Repeated performance characterization | “This declared workload produced these fixture- and environment-scoped distributions.” | “The result applies to a different corpus, hardware class, SDK, or configuration.” |
| Support-envelope candidate | “This evidence is eligible for the separately reviewed 0.8.24 support decision.” | “A single synthetic/host result establishes product-wide support.” |
| Blocked/invalid performance arm | “Quality result is valid; performance evidence is unavailable for the named reason.” | Treating unavailable cost as zero or silently dropping it. |

## Acceptance criteria

- One reviewed configuration resolves to a stable workload identity that EARP
  and performance execution consume without hand-transcription.
- An EARP run produces a validated observed-cost sidecar or a typed explicit
  reason why a field is unavailable; it does not silently omit a requested
  phase.
- An optional repeated-performance run is linked to the exact quality
  configuration and emits raw/reproducible samples, provenance, treatment, and
  invalidity information required by the performance-and-hardening initiative.
- A reranker/hybrid/graph/vector configuration can report eligible quality and
  its observed cost from one campaign execution.
- A p95/p99/QPS/storage/support claim is rejected unless the repeated protocol
  supplied the required samples and environment/fixture equivalence.
- Rust, Python, and TypeScript measurements distinguish binding cost from
  engine cost and use real databases and public calls.
- Existing EARP retrieval schemas, result semantics, and experiment-index
  append-only behavior remain compatible; incompatible changes require a new
  versioned sidecar/schema and migration-free adoption.

## Architecture ruling

The evidence contract above is fixed. HITL selected the implementation home in
`steward` ledger seq-250:

| Option | Shape | Benefit | Cost / risk |
| --- | --- | --- | --- |
| A. EARP performance sidecar | EARP owns collection of both observed cost and repeated-performance execution, writing a new performance sidecar. | One obvious user command and direct control of quality/performance linkage. | Broadens an intentionally retrieval-only EARP runner; risks mixing metric and sampling responsibilities. |
| B. Independent performance runner with an EARP adapter | The performance runner owns collection and repeated execution; EARP exports/accepts the immutable resolved workload and links the resulting sidecars. | Preserves EARP's retrieval-only boundary and reuses the existing performance/scale protocol. | Requires a narrow adapter and a clear family/index linkage contract. |

**Ruled: Option B.** EARP emits the lightweight observed-cost sidecar needed
to explain its own quality result. The independent performance runner owns
repeated sampling and performance claims while consuming the exact
EARP-resolved workload. This avoids a second operator configuration without
turning EARP into a general benchmark framework.

The choice does not alter the requirement for one declaration, linked
artifacts, and no manual duplicate run.

## Initial implementation boundary

The current implementation prototypes the no-duplicate-workload seam without
claiming that either collector fully conforms to this contract:

- Every diagnostic, characterization, comparison, sweep, and answer-arm
  quality result currently writes a versioned one-run observed-cost sidecar.
  It records the phase timings, aggregate counts, and SQLite-file sizes
  currently available to that execution, plus resolved query knobs in the
  quality sidecar. This collector is a partial local prototype: until it gains
  typed unavailable-field reasons, per-query observations, and complete
  environment/provenance capture, it cannot satisfy the full observed-cost
  acceptance criterion or make a cost-completeness claim.
- The independent runner can repeat a saved diagnostic or corpus-scale
  characterization workload and writes a local prototype
  `performance.earp.v1.json` artifact. Its local developer CLI accepts only a
  prior quality-run ID, never a duplicate corpus/query/knob configuration.
- The present bridge is a local prototype, not yet a conforming repeated-
  performance publication path: it must gain the immutable manifest, separate
  execution provenance, typed incomplete-cell artifact, schema validation,
  digest verification, and staged/idempotent writer described above before it
  may make a repeated-performance claim.
- The available fresh execution treatment is named `fresh_store`: a new
  temporary database in the current Python process. The runner rejects the
  label `process_cold`; a future subprocess executor with an explicit
  OS-cache/process witness is required before that treatment can be offered.
- Arms campaigns retain separately named one-run cost observations, so no
  control/treatment duration is pooled. Repeated paired arm performance and
  a true process-cold executor remain the next performance-protocol slice;
  neither is implied by the initial artifact.

This boundary is intentionally narrow. It makes the no-duplicate-workload
architecture explicit while preserving a clean distinction between an observed
run and a support-quality benchmark.

## Artifact durability rules

`performance.earp.v1.json` has its own versioned JSON schema. The writer
serializes and validates the sidecar and its manifest before it creates a run
directory. It then stages all sidecars atomically, materializes the shared
record with their relative paths and SHA-256 digests, and appends the index
last. Its collision and idempotence behavior matches the EARP writer: equal
durable evidence is idempotent; different evidence at the same identity is a
typed collision; a record/index failure cannot leave a complete-looking
artifact. The performance writer never bypasses these guarantees with a direct
unvalidated `record.json` write.

## Non-goals

- Setting numerical performance thresholds before a current baseline exists.
- Making any campaign a mandatory CI or release gate without a separate HITL
  ruling.
- Replacing the existing scale protocol, inventing a competing benchmark
  authority, or declaring ANN/HNSW work.
- Treating CUDA embedding as a general retrieval accelerator or changing the
  CPU-default, driverless runtime contract.
