# FathomDB 0.8.25 prework — Slices 0–7

## Purpose and boundary

Slices 0–6 prepare decisions. Except for Slice 0's isolated release setup, they
inspect and write durable proposals without changing product code, tests,
dependencies, public documentation, or accepted contracts. Slice 7 implements
only the repository-preparation work explicitly approved in Slice 6.

Slices 10+ remain separate feature slices. Each writes its own requirements,
acceptance criteria, reviewed design, TDD RED/GREEN implementation, code review,
verification, and status record. Slice 7 may update a Slice 10+ plan with work
identified during prework, but it must not implement that feature work.

## Slice 0 — environment and project-infrastructure preflight

**Goal:** establish an isolated, reproducible release workspace and identify
environment or repository-infrastructure decisions before changing the product.

Work:

1. Verify the 0.8.24-containing `main` baseline, create `release/0.8.25`, create
   a dedicated release worktree, and perform all 0.8.25 work there. Do not switch
   or pollute the primary `main` checkout.
2. Create or update the overall 0.8.25 plan before later prework starts.
3. Inventory environment setup and record current versus needed state:
   - Python version, development/test dependencies, `.venv` ownership, and the
     worktree-safe launcher/shim decision;
   - Rust toolchain, targets, native build prerequisites, Cargo caches, and
     cross-compilation constraints;
   - Node/npm and TypeScript tooling required for binding parity;
   - CUDA, CPU, ptrace, SQLite, and native-library availability;
   - Tegra/L4T packages, Python/Rust/native artifact requirements, and packaging
     compatibility inherited from 0.8.24;
   - Windows build, CUDA, Python SDK, WAL, and runner needs, including work
     already allocated to 0.8.26; and
   - local data, ignored credentials, Airlock/evaluation support, disk, and
     worktree dependencies.
4. Inventory project infrastructure: release-state/board needs, CI/release
   workflow, native artifact matrix, registry rehearsal, documentation indexes,
   branch/worktree hygiene, and verification entry points.
5. Establish `release-state-0.8.25.json` and `STATUS-0.8.25.md` through the
   repository's single-writer/generated-view contract before changing the
   release plan from proposed to active.
6. Treat the current shared `.venv/bin` shim as planning-only. Select and prove
   an isolated release-bound native build/test arrangement before feature work;
   it must test the release sources, honor the no-editable-install-from-worktree
   rule, and avoid rebuilding or installing into the primary `main` checkout.

Durable output records facts, decisions required, recommendation, owner, and
whether a setup action is already complete. Slice 0 may perform only the
isolated branch/worktree and non-product local setup needed to conduct planning.

## Slice 1 — dependency and library sweep

**Goal:** identify dependency work without upgrading anything.

Work:

1. Inspect Dependabot state and every tracked Rust, Python, JavaScript, GitHub
   Actions, documentation, and release-tool dependency source.
2. Enumerate every library or action with an available or required upgrade,
   including current version/source, candidate version, direct/transitive role,
   affected artifacts, and security/reliability motivation.
3. For every exact pin, Git source, patch/replace, prerelease, or upper bound,
   trace why it exists from ADRs, design records, lockfiles, tests, upstream
   compatibility, platform packaging, or prior incidents. Never infer that a
   pin is accidental.
4. Classify each item: update in 0.8.25, retain with verified reason, investigate,
   or postpone. Record compatibility, migration, platform, and rollback risks.
5. Propose an ordered implementation and verification plan for candidates
   proposed for inclusion, including coupled upgrades such as
   `rusqlite`/SQLite extensions or binding/native-package stacks.

Write the sweep and proposal durably. Do not edit manifests, lockfiles,
workflows, sources, or generated artifacts in Slice 1.

## Slice 2 — repository cruft review

**Goal:** identify stale, duplicate, misleading, or misplaced material without
performing cleanup.

Review the full repository by category:

- program/release plans, boards, handoffs, ledgers, and experiment records;
- `dev/` requirements, acceptance criteria, architecture, interfaces, designs,
  test plans, traceability, and source-adjacent engineering records;
- product source, tests, fixtures, scripts, migrations, generated artifacts,
  feature flags, and dead compatibility paths;
- developer notes, intermediate findings, draft documents, and worktree/run
  artifacts; and
- public documentation, examples, release notes, API references, and package
  metadata.

For every finding record exact path/symbol, evidence, inbound references,
historical or current authority, risk, and one proposed action:

- **keep** — current and correctly placed;
- **deprecate in place** — retained for history with a clear authority pointer;
- **archive in place** — immutable historical evidence, excluded from active
  navigation;
- **delete** — no authority, consumer, evidence value, or required reference.

Write the proposal durably. Do not rename, move, deprecate, archive, or delete
anything in Slice 2.

## Slice 3 — product-contract and architecture drafts

**Goal:** translate accepted needs and discovered drift into reviewable draft
contract changes, without adopting them.

Work:

1. Review product/user needs and draft CRUD changes: create, rename, update,
   deprecate, or delete.
2. Review existing requirements and acceptance criteria and draft the same CRUD
   actions for each: create, rename, update, deprecate, or delete. Derive new
   falsifiable criteria for retained needs, preserve traceability, and do not
   mint global acceptance IDs without explicit authorization.
3. Review architecture, public interfaces, wire contracts, and existing ADRs;
   draft required CRUD changes or successor decisions rather than contradicting
   accepted authority.
4. Allocate every draft requirement, acceptance criterion, architecture change,
   interface change, migration, test obligation, and documentation change to
   exactly one implementation slice.
5. Add work assigned to Slice 10+ directly to that feature slice's plan. Do not
   leave feature obligations in the prework implementation backlog.

Write drafts and the allocation matrix durably. Do not change accepted product
contracts, architecture, source, tests, or public documentation in Slice 3.

## Slice 4 — architecture and code-alignment review

**Goal:** challenge the proposed architecture against prior prework and the
as-built product.

Work:

1. Review Slices 0–3 and propose necessary architecture corrections, including
   product-boundary, identity, provenance, lifecycle, query, platform, and
   operational consequences.
2. Perform a high-level code survey across schema, Engine, query/retrieval,
   projections, lifecycle/erasure, bindings, CLI, and packaging.
3. For each mismatch, identify whether code should change, architecture should
   change, or both require a successor decision. Cite concrete code and current
   authority.
4. Allocate candidate changes proposed for inclusion to Slice 7 only when they
   are repository preparation. Add every product/feature change directly to its
   owning Slice 10+ plan during Slice 4; do not leave it only in the alignment
   report. Slice 6 decides whether each candidate is included.

Write the architecture proposal and code-alignment findings durably. Do not
change architecture authority, code, schema, interfaces, or tests in Slice 4.

## Slice 5 — verification-adequacy review

**Goal:** determine whether the repository can prove its requirements, critical
paths, and release claims.

Work:

1. Build a requirement-to-acceptance-criterion matrix and identify requirements
   with no falsifiable criterion.
2. Build an acceptance-criterion-to-test matrix and identify missing, indirect,
   skipped, vacuous, masked, non-hermetic, or implementation-authored oracles.
3. Assess testing against the product's overall goals: identity, provenance,
   atomicity, lifecycle, erasure, retrieval, projections, concurrency,
   cross-SDK parity, packaging, installation, and recovery boundaries.
4. Identify critical paths and confirm each has positive, negative, failure,
   restart, concurrency, and lifecycle coverage proportional to its risk.
5. Assess unit, property, integration, stress, performance, platform, artifact,
   and registry-installed verification, including actual execution in CI.
6. Allocate repository-test-infrastructure repairs to Slice 7. Add every
   feature-specific test obligation directly to its owning Slice 10+ plan during
   Slice 5; do not leave it only in the adequacy report.

Write the adequacy report and proposed verification changes durably. Do not
alter acceptance criteria, tests, CI, or source in Slice 5.

## Slice 6 — proposal register, HITL decisions, and Slice 7 design

**Goal:** turn Slices 0–5 into a concise, reviewable decision package.

Work:

1. Enumerate every proposal with source slice, exact target, dependencies, and
   proposed owning implementation slice.
2. Score each proposal on four explicit axes:
   - **understood:** high/medium/low, with unresolved questions;
   - **risk:** critical/high/medium/low, covering change and non-change risk;
   - **effort:** XS/S/M/L/XL with the main cost driver; and
   - **release disposition:** include in 0.8.25 or postpone, with rationale.
3. Present the register interactively and concisely to the HITL. Collect an
   explicit include/postpone/reject/needs-more-information decision for every
   item and record it durably with the human as decider.
4. Write the Slice 7 implementation plan for approved prework only. Confirm
   every Slice 10+ obligation is already in its owning feature plan.
5. Have a read-only subagent independently review the Slice 7 plan against the
   Slice 0–6 evidence, HITL decisions, scope boundary, dependency order, TDD,
   verification, and cleanup requirements. Allow at most two documented FIX-n
   cycles.
6. Present the reviewed Slice 7 plan and resulting 0.8.25 plan interactively to
   the HITL. Capture approval or corrections and update the durable plan.

Slice 6 changes planning records only. It does not implement a proposal.

## Slice 7 — approved prework implementation

**Goal:** prepare the repository for feature work by implementing only the
Slice 0–6 items explicitly approved for Slice 7.

The Slice 7 plan must enumerate each approved change, requirement, acceptance
criterion, design reference, file/symbol target, dependency, test, review, and
verification command. Work assigned to Slice 10+ is prohibited here even if it
was discovered during prework.

Execution:

1. Reconfirm branch/worktree isolation and the approved Slice 7 scope.
2. For each behavioral change, write and preserve the failing RED test before
   implementation, make it GREEN, and refactor without changing the oracle.
   Pure documentation changes use their applicable lint/contract check.
3. Run an independent code review and resolve findings under the repository
   FIX-n limits.
4. Use a read-only subagent to independently run or inspect the planned test and
   verification evidence; do not let the implementation author self-certify the
   result.
5. Run focused checks and the repository verification gate, recording exact
   commands, exits, commit, residual skips, and environmental limitations.
6. Write a Slice 7 status record mapping every approved item to implemented,
   postponed, rejected, or blocked evidence.
7. If Slice 7 used a child branch/worktree, merge through the reviewed release
   path, verify the landed commit, and remove only worktrees/branches proven
   clean, merged, and free of unique artifacts.
8. Advance the release plan to Slice 10. Do not begin Slice 10 implementation
   as part of Slice 7 closure.

## Prework completion condition

Prework is complete only when Slice 7 has landed or the HITL explicitly decides
that no Slice 7 implementation is required, every Slice 10+ obligation is in its
own plan, the status record is durable, and the immediate-next pointer names
Slice 10.
