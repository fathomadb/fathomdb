# FathomDB 0.8.27 refactor test approach

## Purpose and authority

This document defines the test-writing approach for the 0.8.27 feature and
refactoring ladder. It supplements the eventual release plan and slice plans;
it does not authorize implementation, release-state changes, or publication.
Accepted ADRs, interface contracts, the approved release plan, and the release
state remain authoritative if they conflict with this document.

The central rule is:

> Tests must remain more stable than the code being reorganized. Test observable
> contracts and invariants, not the new file layout, private helper names, or
> internal call graph.

Slice 20 is a behavior correction and therefore uses strict fix-to-spec TDD.
Slices 40-140 are primarily behavior-preserving refactors and therefore use
locked characterization, conformance, and equivalence tests around mechanical
moves. Slice 150 qualifies the integrated candidate rather than inventing new
behavior.

## Test classes and ownership

Each important invariant has one deep owning suite and, where necessary, thin
binding or artifact parity checks. The same semantic matrix should not be
copied into every language.

| Invariant | Deep owner | Thin parity or qualification checks |
| --- | --- | --- |
| Erasure completeness and truthful failure | Rust engine integration | Python, TypeScript, exact Memex consumer |
| Public surface stability | Surface comparison harness | Installed wheel and npm-package consumers |
| Transaction atomicity and ordering | Rust engine fault-injection integration | Binding error and blocking/async mapping |
| Wire parsing and validation precedence | Shared fixture corpus | Rust, Python, Node, TypeScript consumers |
| Projection generation and recovery | Rust engine integration and property tests | Applicable CPU, CUDA, and package routes |
| Read eligibility and snapshot authority | Rust engine integration | Binding-level public-path smokes |
| Documentation and taxonomy | Documentation checks and human review | Installed examples where public |

Tests should be named for the behavior they protect, for example
`erase_source_original_first_removes_closed_replacement`, rather than for a
slice number or implementation module.

## Broad practices

### Separate behavior changes from structural moves

- Slice 20 must commit or otherwise retain a visible failing test before the
  product fix. Test files are read-only while fixing that failure.
- Later slices move code verbatim, regain green, and only then simplify within
  the new boundary.
- A refactor-discovered behavior defect becomes a separate RED/GREEN correction.
  It must not be hidden inside a move or excused as cleanup.
- Assertion changes and mechanical import/path changes must be reviewed
  separately. A move is not permission to refresh expected behavior.

### Apply TDD according to the work type

- A defect or semantic addition requires a genuine failing product test first.
- A characterization test for already-correct behavior may initially pass. Its
  sensitivity must be demonstrated by temporarily injecting a plausible defect,
  observing the expected failure, and reverting the defect before commit.
- New logic introduced during extraction requires a genuine RED test before the
  new logic is written.
- Do not manufacture RED by asserting a filename, private helper, or module
  topology. If a supposedly mechanical move requires a semantic change, split
  the work.

### Test invariants, not module topology

- Exercise public APIs or narrow, deliberately designed test seams.
- Do not widen private fields to `pub(crate)` only to make split modules or tests
  compile.
- Do not assert that a function lives in a particular file or that one private
  helper calls another.
- Add a test hook only for otherwise unobservable ordering, fault injection, or
  persisted state. Keep it feature-gated and subject to normal Engine connection
  and lifecycle invariants.

### Keep behavioral oracles stable

- Existing behavioral tests remain unchanged across a move whenever possible.
- When test imports must follow a move, isolate that mechanical change and leave
  setup, action, and assertions unchanged.
- Snapshot and golden outputs are human-owned oracles. Never regenerate them
  merely because the refactor changed output.
- A historical versioned fixture remains immutable. Add a new fixture for a new
  version instead of rewriting history.

### Make every important test non-vacuous

For every conformance, parity, or surface test, identify a plausible violation
that the test would reject.

- Surface tests inspect the real exported surface rather than a hand-written
  subset.
- Parity tests consume one shared contract or fixture rather than duplicated
  same-file or same-language literals.
- Surface harness self-tests introduce a synthetic extra, missing, or changed
  export and prove the comparison fails.
- Count tests derive their expected values from the seeded physical inventory;
  they do not settle for `count > 0` or a final zero alone.
- Controls prove both the changed and unchanged cases. A destructive-operation
  test names the exact rows that must survive.

### Use real databases and prove physical state when required

- Database integration tests use a real database, not a mock.
- Functional query invisibility is not erasure proof. Erasure tests inspect raw
  canonical, provenance, projection, vector, telemetry, and WAL-backed state.
- When the contract concerns at-rest state, close the Engine and inspect through
  a fresh independent connection or process.
- Projection publication tests inspect the physical vector row. A terminal or
  readiness record alone does not prove publication.
- Unique secret sentinels make persistence residue attributable and prevent an
  unrelated row from satisfying an absence assertion.

### Test failure behavior and all side-effect planes

For multi-stage operations, inject failures before and after important side
effects and snapshot every affected plane:

- canonical rows;
- provenance links and closure records;
- registry and readiness state;
- projection terminal, queue, sidecar, and physical rows;
- telemetry and diagnostic files; and
- WAL-visible durable state.

A rejected or rolled-back operation must leave the complete snapshot unchanged,
not merely preserve the primary canonical count.

### Use property tests where required

Codec, projection, recovery, and round-trip layers receive property-based tests
with human-defined invariants. Useful properties include decode-after-encode,
stable validation precedence, closure idempotence, exact rollback, and
generation monotonicity. Generated snapshots are not acceptable test oracles.

### Make concurrency deterministic

- Prefer barriers, explicit rendezvous hooks, and observed state transitions to
  sleeps.
- Use process isolation for runtime globals, native loading, memory, environment
  configuration, and sub-millisecond measurements.
- A timing threshold is used only where timing is itself contractual and the
  fixture supplies adequate slack.

### Test applicable feature combinations explicitly

- Run default, operator, and test-hooks configurations independently.
- Run mutually exclusive native backends through separate routes rather than a
  misleading `--all-features` invocation.
- Native-platform, driverless CPU, and CUDA evidence is required only when the
  moved path warrants it.
- A CUDA-linked process running a CPU embedder proves build compatibility, not
  CUDA computation. Selection, allocation, and actual execution need separate
  witnesses.

### Distinguish source tests from artifact tests

- A worktree-linked native extension is not release evidence.
- Binding slices build the relevant artifact and exercise it in a clean consumer
  environment when package shape or native registration is at risk.
- Qualification uses fresh wheels and independently packed npm artifacts built
  from the candidate commit.
- Evidence records the candidate SHA, feature set, platform, artifact hashes,
  command, actual exit status, and observed test counts.
- Piped, wrapped, or background commands must preserve the tested command's real
  exit status.

## Cross-slice working cadence

For each mechanical extraction in Slices 40-130:

1. Run the focused owning tests at the exact pre-move commit.
2. Make one bounded, mechanical move without cleanup or semantic edits.
3. Run the focused tests, applicable feature checks, and public-surface
   comparison.
4. Refactor inside the new boundary, adding RED tests first for any new logic.
5. Run `./scripts/agent-verify.sh` after the meaningful edit.
6. Before slice close, run full-workspace clippy and check in addition to the
   focused suites.
7. Preserve the commands, exits, candidate commit, and any platform-specific
   evidence in the slice record.

If the same failure mode recurs twice, stop and re-read the owning test, relevant
ADR, and prior correction record before attempting a third fix.

## Slice-specific approach

### Slice 20 — F27-01 correction-safe source erasure

Slice 20 owns the true RED/GREEN behavior correction. Its deep Rust integration
suite must cover:

- a same-bucket correction and replacement;
- a cross-bucket replacement with the original bucket erased first;
- a cross-bucket replacement with the replacement bucket erased first;
- a closure that is already complete before erasure;
- an unaffected source and unrelated records as positive survivor controls; and
- a real incomplete blocker that preserves the truthful fail-loud result.

Every content-bearing seeded row or store should carry a unique sentinel.
Content-free metadata uses keyed identity and exact-count oracles instead. For
each successful case, tests must:

1. Inventory the exact pre-erasure canonical and projection rows.
2. Invoke the supported `erase_source` path.
3. Assert that the requested source bucket and closed physical dependents needed
   for truthful completion lose all erased content and live authority.
4. Assert that unrelated source buckets and records survive unchanged.
5. Compare `ExciseReport` counts with the requested bucket's exact pre-call
   canonical and row-owned projection inventory. The published report does not
   count dependent rows removed by closure; changing that meaning requires a
   separate interface and ADR decision.
6. Close the Engine and independently prove absence of erased payload,
   logical/artifact/source-revision identities, and live authority from
   canonical rows, both provenance directions, content-bearing projections,
   vector sidecars and physical rows, telemetry, and WAL-visible durable state.
   The raw non-PII `source_id` may occur only in one new committed-deletion
   `excise_source_audit` row (`record_key` and `payload_json.source_id`, with
   exact report counts) and, when the fixture has affected physical dependents,
   one `source_bucket` closure `root_value` (otherwise zero). Assert exact row
   and field counts, no additional audit row on scrub-only retry, the exact
   non-content proof, and rejection of every other raw identity occurrence.

Blocker coverage must distinguish two accepted phases. A pre-commit dependency
or persistence refusal rolls back the protected source bucket exactly. A
post-commit telemetry or WAL scrub failure returns the established
`ErasureIncomplete` error after canonical row deletion has committed, preserves
the durable pending-scrub obligation, and completes it on an idempotent retry.
Neither phase may falsely report successful closure.

The exact Memex characterization scenario and setup remain unchanged. Replace
its old `pytest.raises(storage_failed)` oracle with exact success receipt/count,
restart/visibility, physical-absence, and survivor assertions; a success-only
assertion is vacuous. Freeze the revised consumer test through Slice 150.
Python and TypeScript add thin public-API parity smokes: one corrected
successful path and one correctly mapped incomplete failure. They do not copy
the full engine matrix.

### Slice 30 — release rebaseline and surface comparator

Slice 30 treats the baseline as a reusable comparison instrument, not a prose
inventory. Bind it to the exact release SHA and capture:

- Rust default, operator, and test-hooks public surfaces;
- facade re-exports and public paths;
- Python native registrations and stub surface;
- Node native declarations and generated exports; and
- package-root and supported subpath exports.

The comparison harness needs self-tests proving that it rejects a synthetic
added export, removed export, changed re-export, missing Python registration or
stub entry, changed Node declaration, and changed package export. Surface data
must come from real compiler, module, declaration, or package introspection. Two
duplicated literals are not a parity test.

The approved baseline is human-reviewed and immutable until Slice 150. Boundary
maps and the exception register are reviewed artifacts, not product tests. The
size scanner may report findings but never determines test or CI success.

### Slice 40 — engine foundation

Run the focused suite and surface comparison after each 300-1,200-line move.
Test shared errors, identity, temporal primitives, and subsystem hooks through
their semantic contracts:

- exact error variants, sources, and public conversions;
- identity normalization, equality, and invalid inputs;
- temporal boundaries, open/closed intervals, and overflow cases; and
- test-hook presence under `test-hooks` and absence from default builds.

Keep `Engine` at crate root and rely on the surface comparator to protect its
path. Do not add filename tests or expose private fields for test access.

### Slice 50 — erasure, lifecycle, dependency closure, and provenance

Move the corrected Slice 20 implementation verbatim before refactoring it. Keep
the Slice 20 regression suite locked. Add focused tests only where the extracted
boundary introduces independently meaningful logic:

- dependency discovery from both provenance axes;
- already-complete closure and idempotent retry;
- exact physical deletion accounting;
- rollback on a closure or persistence blocker; and
- drain -> freeze -> mutate -> at-rest ordering.

A bounded property or state-machine test over supported dependency shapes is
valuable, provided it does not invent deferred multi-source semantics. Preserve
the published `lifecycle` path through the Slice 30 comparator.

### Slice 60 — write, ingest, consolidation, and actuation

Concentrate on transaction and ordering boundaries. Inject failures at
validation, translation, execution, auxiliary enrollment, and commit, then
compare all state planes with the pre-call snapshot. Cover:

- structural and database-dependent validation before mutation;
- same-batch operation ordering;
- caller-owned source identity and provenance;
- replay and idempotency behavior;
- rejected writes with zero canonical, registry, terminal, or queue mutation;
  and
- atomic rollback after a late refusal.

New wire or translation codecs receive round-trip and validation-precedence
properties. Separate validation, translation, execution, and commit only where
the tests identify a real transaction or invariant boundary.

### Slice 70 — projections, vectors, embedding, and reranking

Treat projection generation, registry, and maintenance as state machines. Test:

- canonical commit before projection publication;
- exact serving-generation changes;
- interruption and restart recovery;
- rollback without false readiness;
- terminal, sidecar, and physical vector-row agreement in one snapshot; and
- lifecycle eligibility independently from physical completeness.

Codec, recovery, and projection round trips receive property tests. Use
deterministic vectors for fixed CPU behavior. CPU/CUDA numerical equivalence uses
an explicit justified tolerance rather than byte identity. Run each relevant
feature route separately and retain native evidence only for paths actually
moved.

### Slice 80 — reads, search, graph, and evidence

Organize tests around the intended boundaries:

- codec round-trip and corruption properties;
- table-driven validation and error precedence;
- real-database execution behavior; and
- public result and ordering contracts.

Exercise snapshot authority while concurrent mutations occur, eligibility
before every bounded candidate cap, deterministic tie ordering, and transaction
lifetime. Result-only assertions are insufficient where an ineligible row could
consume a candidate window; use controlled fixtures and, where necessary, SQL
or plan-structure assertions.

For `graph_expand.rs`, types and validation, codec, and execution each need an
appropriate test layer. Split ranked and graph evidence tests only if the
dependency map and fixtures demonstrate genuinely independent seams.

### Slice 90 — open, configuration, WAL, and diagnostics

Use fresh-process tests for global runtime configuration and probes. Cover:

- default and overridden configuration;
- malformed or conflicting configuration;
- open, close, and independent reopen;
- WAL ownership and checkpoint behavior;
- busy and locking behavior without read-to-write promotion surprises;
- probe and diagnostic side effects; and
- operator error precedence and envelopes.

Fault-inject open and shutdown paths and assert that they leave no orphaned
runtime or WAL state. Re-run root re-export and operator-feature comparisons
after every extraction.

### Slice 100 — PyO3 binding decomposition

Build and import an actual PyO3 artifact. Compare it with the Slice 30 baseline
for:

- one `_fathomdb` module and its registrations;
- exported names and callable signatures;
- exception class identity and error mapping;
- ABI and import behavior;
- blocking and GIL behavior; and
- native registrations versus `_fathomdb.pyi`.

Use deterministic threads and barriers for blocking behavior rather than narrow
timing thresholds. Test only supported public imports; no test should care which
internal Rust module contains an implementation. Update and validate stub
citations in the same slice.

### Slice 110 — napi-rs binding decomposition

Build and install or pack the Node artifact in a clean consumer. Compare:

- generated native exports and declarations;
- package-root and supported subpath exports;
- error envelopes and panic containment;
- sync throw versus Promise rejection behavior;
- string validation, including NUL and lone-surrogate cases; and
- async or blocking semantics with deterministic rendezvous tests.

Use the shared validation fixture corpus so Node behavior cannot drift from the
Python or Rust boundary while all source-level tests remain green.

### Slice 120 — TypeScript SDK decomposition

Add consumer compile fixtures that import from the package root and every
supported subpath. Compare declarations and runtime exports with the baseline.
Protect:

- exact public names and signatures;
- overload and generic behavior where public;
- wire shapes and error precedence;
- validation through the shared fixture corpus; and
- thin `Engine` wiring to the native binding.

Tests must not import newly private modules to prove their existence. The
package behavior and declarations are the contract, not the source tree.

### Slice 130 — Python SDK facade decomposition

Test root and documented module imports, contractual `__all__` values, callable
signatures, exception identities, and runtime/stub agreement. Run public examples
or doctests where documentation is executable. Preserve the same shared error
and wire fixtures used by the native and TypeScript layers.

Keep deep database semantics in the engine suite and use thin Python parity
checks. No test should depend on whether implementation now lives in `read.py`,
`graph.py`, `admin.py`, or a narrow helper.

### Slice 140 — architecture and documentation convergence

This slice is primarily documentation and structural conformance. Validate that:

- source citations and referenced paths resolve;
- documented public paths import or compile;
- executable examples run;
- every remaining file over 3,500 lines has an approved exception or follow-up
  disposition; and
- every 2,000-3,500-line subsystem has a recorded human review.

Test exception-register coverage, not the size threshold. The scanner remains
advisory and must not become a CI gate. Do not add product tests merely to encode
the final filenames or taxonomy.

### Slice 150 — integrated release qualification

Slice 150 should write little or no new product test code. It executes and
records the already-defined qualification set:

- exact public-surface comparison against the Slice 30 baseline;
- full `agent-verify`;
- full-workspace clippy and check;
- applicable feature combinations;
- clean package builds;
- isolated installed-artifact smokes;
- applicable native-platform, driverless CPU, and CUDA routes; and
- the unchanged exact Memex consumer test against the candidate artifact.

The candidate manifest binds all evidence to the reviewed commit and artifact
hashes and distinguishes source, native binary, package, platform, and closeout
identities. An unavailable platform is recorded honestly rather than converted
to a pass.

If qualification reveals a product defect, return it to an owning repair slice
with a new RED test. Never weaken a qualification test or refresh the baseline
to make the candidate pass. Publication remains a separate explicit
authorization.

## Slice close checklist

Before closing any slice, confirm:

- the owning invariant tests fail under a named plausible defect;
- behavioral assertions were not changed to accommodate the refactor;
- the focused suite passed at the final commit;
- `./scripts/agent-verify.sh` passed after the meaningful edit;
- full-workspace clippy and check passed before the green claim;
- applicable feature routes were exercised separately;
- artifact claims came from fresh artifacts rather than linked worktree builds;
- commands, exits, test counts, SHAs, and hashes were retained;
- unavailable evidence was recorded as unavailable, not passed; and
- no unrelated cleanup or deferred behavior entered the slice.

## Forbidden test patterns

- Tests that assert implementation filenames, line counts, or private call
  structure.
- Surface tests built from hard-coded inclusion lists without real
  introspection.
- Cross-binding comparisons against duplicated local literals.
- Query-only erasure proof for content that can remain physically stored.
- Terminal/readiness-only proof of physical vector publication.
- Success-only transaction tests that ignore auxiliary state.
- Sleeps used as the primary concurrency oracle.
- Blind snapshot regeneration or agent-generated expected outputs.
- Worktree-linked native extensions presented as package evidence.
- `--all-features` used as a substitute for valid mutually exclusive feature
  routes.
- Piped or wrapped test commands whose real exit status is not preserved.
- Size thresholds promoted from advisory signals into correctness gates.
