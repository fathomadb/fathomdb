## Findings

- **N1 not implemented; owner decision needed.** At the default release
  threshold 0 the pool is empty after the embedder drops without any
  caller synchronize, so design § 8's premise ("nothing synchronizes after
  an engine closes") does not hold on this tree. Only the opt-in
  `FATHOMDB_POOL_RELEASE_THRESHOLD=max` keeps its 288 MiB after close,
  which is that setting's documented meaning ("the pool keeps everything
  it has reserved"). The conditional of test-plan R14 has one test passing
  and one failing, so neither branch applies as written. Both tests are
  unchanged.
- **R16 does not reach the private pool.** The engine test never runs the
  module-load early `cuInit` (`run_module_load_early_init`), which only the
  N-API and PyO3 load hooks call. The decision therefore falls back with
  reason `cuinit_not_at_load` (`cuda_pool_policy.rs` `init_gate`), and a
  plain Rust engine process is on the 0.8.27 path. The close-and-exit part
  is clean. This is a test-design finding for R-VERIFY; the test is not
  edited.
