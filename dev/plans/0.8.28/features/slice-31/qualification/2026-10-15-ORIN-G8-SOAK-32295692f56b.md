# Orin G8 soak: 60-minute characterization and the memory-growth justification

G8 (test-plan § 4.2 window B) failed its RSS drift bound for Node in window
B (+12.1 % against < 10 %). The owner asked for the growth to be
characterized. Two 60-minute soaks were run: pool on (the product default)
and pool off (the control). The owner accepted G8 as measured on
2026-10-15 (steward ledger seq 345, Q39). This record gives the justification. The
per-minute series, the gate summaries and the guard lines are in
`2026-10-15-ORIN-G8-SOAK-32295692f56b.log`.

## Host, artifacts and runs

- Jetson AGX Orin 64 GB, `10.83.10.13`, power mode MAXN, kernel
  `5.15.199-tegra`. The guard line was identical before and after each
  soak: `# R36 (release), REVISION: 5.2, GCID: 46426093, …` and
  `/usr/local/cuda-12.6` (5 lines per soak, all in the log). Nothing was
  installed.
- Artifacts: `venv-tip/` and `node-tip/` built from `32295692f` (window P
  record, [2026-10-15-ORIN-PA-32295692f56b.md](2026-10-15-ORIN-PA-32295692f56b.md)).
  Later slice commits do not change pool behaviour at run time.
- Runner: the Slice 31 harness `window-b.sh` with `GATES=g8` or `g8s`,
  `SOAK_SECONDS=3600` and `FATHOMDB_REQUIRE_LIVE=1`. One Node and one Python
  process ran at the same time under the GPU lock, each with the no-swap
  condition. Each minute every process ran an embed, a 32-item batch embed
  and a rerank in a loop, then took one sample. Pool off is
  `FATHOMDB_POOL_MODE=off`. Node then takes the synchronous allocator path
  and Python takes the default pool.
- Pool on: 17:12 to 18:12 UTC. Pool off: 19:43 to 20:43 UTC.

## Results

The G8 drift compares the median RSS of the last five minutes with the
median of the first five minutes. The bound is < 10 %.

| Run | Node RSS (MiB) | Node drift | Python RSS (MiB) | Python drift |
| --- | --- | --- | --- | --- |
| Window B, 20 min, pool on | 812 → 932 | +12.1 % FAIL | 741 → 788 | +3.5 % PASS |
| Window B, 20 min, pool off | 792 → 811 | +0.1 % PASS | 743 → 760 | +2.0 % PASS |
| 60 min, pool on | 809 → 931 | +12.4 % FAIL | 741 → 821 | +10.5 % FAIL |
| 60 min, pool off | 787 → 894 | +8.2 % PASS | 739 → 819 | +10.6 % FAIL |

Every run had 0 errors, 0 output mismatches, no swap, and no abort. System
MemAvailable stayed between 48,970 and 49,211 MiB. Embed latency did not
degrade in any run:

- 60 min, pool on: Node 19.1 → 18.6 ms over 44,953 iterations; Python
  18.3 → 17.7 ms over 70,396.
- 60 min, pool off: Node 98.5 → 100.0 ms over 11,242; Python
  18.2 → 17.7 ms over 77,516.

## Justification

**Python: the climb is the test harness, not the product or the pool.**

- In both 60-minute runs, Python RSS rose exactly 1.0 MiB per one-minute
  sample, then stopped:
  - pool on: 741 → 821 MiB, flat from minute 52;
  - pool off: 739 → 819 MiB, flat from minute 51.
- The two curves agree to within 2 MiB, so the pool does not cause the
  growth.
- The step follows wall-clock time, not work done. It is 1.0 MiB whether a
  minute ran 1,155 iterations or 1,329, so it is not a per-embed retention.
- The cause is the harness's per-minute sampler. Before each sample,
  `pool_smoke.py` builds and discards 200,000 Python dicts as deliberate
  host-allocator churn (`keep.extend(...)`; `keep.clear()`). Python's
  object allocator keeps arenas it has touched, and the retained set grows
  per churn event until reuse reaches a steady state, which here took about
  50 minutes. The control proves the attribution. The exact arena mechanism
  is inferred and was not instrumented.
- The 20-minute window B runs fit the same curve: +3.5 % and +2.0 %, the
  first 20 minutes of the same ramp.

**Node: bounded growth to a working set, with or without the pool.**

- The JS heap stayed flat at 5.4-5.5 MiB in every Node run, so the growth
  is native memory.
- Pool on: RSS rose in steps from 809 to 928 MiB over the first 21 minutes.
  It then held at 928-931 MiB for the remaining 39 minutes, about 30,000
  more iterations. The last 30 minutes added 1.1 MiB. The ceiling matches
  window B's 20-minute run (932 MiB) at three times the iterations, so the
  growth does not scale with the number of embeds.
- Pool off: RSS also rose, from 787 to 888 MiB in the first 11 minutes, and
  held at 888-894 MiB afterwards. Window B's 20-minute pool-off run stayed
  flat near 811 MiB, so the size of the early rise varies between runs, but
  it is bounded in both.
- The pool's added footprint is the plateau difference, about 40 MiB
  (931 against 888-894). This is expected:
  - On Tegra the GPU shares DRAM with the CPU, so memory the private CUDA
    pool reserves is counted in the process's RSS.
  - A pool keeps the memory it has reserved for reuse until an engine
    closes or a release point is reached (design § 14.1; cudarc fork D-5).
  - The steady mix of single embeds, 32-item batches and reranks therefore
    reserves its peak working set once and reuses it.
- The pool on is about 5 times faster than the pool-off path: 18.6 against
  100.0 ms per embed. Window C's G9 measured 2.0-4.75 times. A fixed 40 MiB
  for that speed-up is the intended trade.
- The G8 bound measures drift from the first five minutes, which is still
  inside the warm-up ramp. A curve that rises and then stays flat fails it
  even when nothing leaks.

**System level.** No run reduced system MemAvailable beyond normal noise,
no run swapped, and every run held its output identity (0 mismatches). No
evidence of a leak was found.

## Disposition

The owner accepted G8 as measured on 2026-10-15 (Q39), as for Slice 30's
Node drift (Slice 30 plan revision 3.3).

The 0.8.29 todo `TC-84f7f62d-2284-4b86-b925-3dbb1e77c4c8` (todos ledger seq 307) covers two follow-ups:

- replace the drift bound with a plateau criterion, for example a growth
  slope over the last 30 minutes of a 60-minute soak, judged against the
  pool-off control;
- remove the per-minute host-allocator churn from the Python sampler, or
  measure it separately.

Not measured: the pool's own reserved bytes. No binding exposes pool
counters (Slice 30 deviation D-1); the SDK-level close proof is todo
TC-8278f17d.
