**Deviation (harness defect).** All 41 processes, in both arms, exited with
`failedStep=rerank` (`ceScore: null`). This happened after every embed and
batch timing had been recorded. The cause is in the harness, not in either
arm:

- `pool-consumer.mjs` always runs a rerank step.
- The x86 release contract's `CUDA_NAPI_FEATURES` is `embed-cuda` and does not
  include `rerank-cuda`.
- The reranker weights (`cross-encoder/ms-marco-TinyBERT-L2-v2`) are not in
  the local HF cache, so a rerank build would need a non-registry download.

Stock `analyze.py <series-root> g9x` therefore counts n = 0 and prints FAIL.
The table above comes from `g9x_embed_only.py` (shown in full in the log). It
uses analyze.py's own `runs`, `per_process`, `boot` and `med`, and it accepts
a run whose only failure is the rerank step. Rerank was not measured.

**Contention.** No `cargo`, `rustc`, `nvcc` or `cc1plus` process was running
when the series started. A process from another session (python3 and a
Playwright ffmpeg) kept load1 near 2.1–2.7. The harness's load1 < 2.0 gate
therefore made the runs wait: 71 wait lines for newP and 7 for baseP. Every
run started on a quiet sample, and no run was refused.
