## D release sequence and proposed settling rule

Use fresh children for each SDK/threshold/lifetime mode because allocator
configuration and model singletons are process-global. No module-level CLS or
reranker calls in the ordinary last-model case; disable default reranker so its
static cannot pin the pool. Two real engines default-embed through SDK APIs,
drain accepted work, then await first and last close, observing the decided
private pool after each. For the max first-close comparison, finish both
engines' work and obtain a passive before-close sample. Admit no allocations,
forwards or new models between that sample and the passive after-first-close
sample. Require positive before-close RESERVED and exact equality of the two
RESERVED readings, with the same pool/context and a remaining live model. This
matches the existing two-model Orin oracle: positivity alone would allow an
incorrect partial trim to pass. Only AFTER that comparison, run the surviving
engine's same-input forward and require unchanged output; then close it.

Read test-only counters without synchronization: initial decided-pool baseline,
both models alive after natural completed SDK work, first close, then last
close/drop. Each snapshot includes PID/UUID/ordinal/context/pool/live-model count
and checked USED/RESERVED. At max first-close RESERVED equals its positive
pre-close reading with no intervening allocation, before the survivor forward;
final
live-model count0 and USED/RESERVED0 must be observed within5s of last close
return or scope drop. Poll at50ms using a monotonic clock; retain every read and
first success time. Reject wrong identity/read error/missing private decision,
lost context,5s timeout or nonzero final counters. No manual synchronize/trim,
forced GC, counter reset, later GPU work, memory pressure or longer replacement
window. Production last-model cleanup may synchronize/trim as already contracted.

Rationale: Q34 permits a briefly held scheduler reference; a finite5s window
fits existing bounded-exit intent and exposes both reference retention and
cleanup failures. It is a proposal, not an existing guaranteed scheduler SLI.
If independent design review finds it unsupported, revise with reasoning before
results, not after a timeout. Record close-return versus actual model-count0
separately; do not substitute live-count observation for physical counters.

Separate controls: threshold0 first/last close, deterministic Rust scope/drop,
selected Python ownership release, unclosed-process exit, one module-level CLS
singleton plus engine close, and engine
reranker singleton plus engine close. The latter two intentionally retain live
models/USED/RESERVED until exit under max. They must still exit normally within
the existing bound; pre-exit zero is not their oracle. No expectation of equal
reservation byte counts across SDKs; compare exact before/after reservation only
within the same max first-close case, and require actual last release.
Non-private/driverless/CPU observation returns named unavailable status.
Node's awaited close is the pre-exit reservation-release oracle. JS scope exit
does not imply deterministic native object collection; the unclosed Node child
tests bounded process exit only, without forced GC or a pre-exit zero claim.
