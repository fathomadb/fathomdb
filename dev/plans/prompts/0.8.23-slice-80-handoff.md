### 80.7 — extend `doctor gpu` for Tegra/SBSA (depends on 80.6)

Design doc § 7 80.7 already has the full two-tier detection algorithm,
directly adapted from an independently-researched sibling-project design
note (`~/projects/memex/dev/notes/2026-08-18-tegra-sbsa-platform-detection-design.md`
— read it, it has reference implementations and a named Jetson-Thor
detection bug you must not repeat). Key facts already verified on this
host, don't re-derive:

- `fathomdb doctor gpu [--json]` **already exists** (Slice 70, landed on
  this branch). Exit codes `0`/`65`/`70`, documented at
  `dev/interfaces/cli.md:65`. You are extending this, not building a new
  CLI verb.
- The classifier that decides CPU-fallback-vs-error already exists and is
  architecture-agnostic:
  `src/rust/crates/fathomdb-embedder/src/candle_bge.rs::classify_cuda_driver_error`
  maps `CUDA_ERROR_NO_BINARY_FOR_GPU` / `CUDA_ERROR_UNSUPPORTED_PTX_VERSION`
  to `CudaProbeError::Incompatible`, which `doctor gpu` reports as
  `cuda_incompatible` with typed CPU fallback, exit `0`. This is **already
  the mechanism** that fires when a Tegra-linked binary hits the wrong
  hardware, or a generic AArch64 binary hits Tegra — your job in 80.7 is
  the *detection* layer (which tells the user what's wrong and what to do),
  not a new refusal path.
- Detection: **do not use `uname` as the Tegra signal.** Use
  `/proc/device-tree/compatible` containing `nvidia,tegra` OR
  `/etc/nv_tegra_release` existing (Tier 1, filesystem-only, no subprocess)
  to detect Tegra-family; only fall back to `nvidia-smi --query-gpu=name`
  checking for the `nvgpu` substring (Tier 2) to resolve the one genuine
  ambiguity — Jetson Thor, which is Tegra-family but SBSA-capable, and
  which broke exactly this check in `jetson-containers` upstream
  (`https://github.com/dusty-nv/jetson-containers/issues/1286`). Check
  subprocess exit status before reading `nvidia-smi`'s stdout — a caught
  bug in the memex design note's own draft was exactly this (a failed
  `nvidia-smi` call with empty stdout misread as an affirmative signal).
- Ruled behavior, don't relitigate: SBSA → refuse-and-continue-on-CPU
  (never refuse-and-fail), guided install command printed (never a silent
  network fetch/build during install).

## 4. Traps already hit once — don't repeat these

- **Never `pip install -e src/python/` or `maturin develop` in this
  worktree.** `AGENTS.md:135` documents this and this session violated it
  once anyway — it corrupted `src/python/pyproject.toml`'s `version` field
  (maturin wrote back a nonsense dev-version stamp) while running `pip
  install -e 'src/python[dev]'` to build a test venv. Caught and reverted
  before it touched any commit, but it's a real, reproduced failure mode,
  not theoretical. If you need a Python dev environment in this worktree,
  the `.venv` created during 80.3 already has `pytest`/`hypothesis`/`ruff`/
  `pyright` installed and a working `fathomdb` 0.8.22 build — use what's
  there; don't re-run the install command.
- **This host has no bare `python3.11`/`3.12`/`3.13` on PATH.** Modern
  Python exists only via `uv` (`uv python list --only-installed` currently
  shows 3.12, 3.13, 3.14 installed; `uv python find 3.13` resolves them).
  `scripts/lib/agent-python-env.sh::select_python_for_venv` (landed in
  80.3) already handles this correctly — if you write any NEW script that
  needs a modern interpreter, source that function rather than assuming
  bare `python3.11` will resolve.
- **The shell sandbox's worktree-isolation guard rejects some command
  shapes** as "too complex to verify... stays inside worktree" —
  specifically `PATH=... cmd | pipe` combos, `env VAR=x cmd --flag`, and
  multi-statement `export X; cmd` sequences. When you hit this, either use
  a single `VAR=val cmd` prefix with no pipe, or `uv run --python X.Y --
  cmd` (which the sandbox accepts), or split into separate Bash calls.
- **`cd` persists across Bash tool calls in this harness.** A `cd src/ts &&
  npm ci` in one call leaves you in `src/ts` for the *next* call too. This
  session got bitten by exactly that. Prefer `(cd dir && cmd)` in a
  subshell, or absolute paths, or explicitly `cd` back.
- **Don't run `npm audit fix`.** Root `npm ci` currently reports 2
  vulnerabilities (1 moderate, 1 high) in transitive deps. This repo has an
  explicit offline pin-rot governance gate (`package.json:15`,
  `scripts/pinned-override-rot.json`) specifically to prevent an
  undocumented dependency override from becoming an untracked security
  exception — `npm audit fix` would silently rewrite the lockfile outside
  that process. Leave it; it's not your problem to fix here.
- **The shared `.git/config`'s `core.hooksPath` is set to an absolute path
  (`/home/coreyt/projects/fathomdb/.git/hooks`), not the repo-relative
  `scripts/hooks` `scripts/install-hooks.sh` is supposed to set.** This is
  pre-existing, affects the main checkout and all worktrees (shared
  config), and is unrelated to Slice 80. Don't run `scripts/bootstrap.sh`'s
  full sequence carelessly assuming it's a no-op here — `install-hooks.sh`
  would rewrite that shared config as a side effect. If you need bootstrap
  steps, run the specific pieces you need (gitleaks/shellcheck/actionlint
  install, `.venv` creation) directly rather than the whole script, or flag
  the hooksPath question explicitly before running it.
- **Full `scripts/agent-test.sh --tier=fast` takes several minutes** (83
  suites; the candle-cpu regression alone is ~60s real compile+run). Always
  `run_in_background: true` and poll/wait, never block synchronously.
