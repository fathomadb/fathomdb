## 3. Design doc § 7 80.5, quoted in full

> The PID-in-`nvidia-smi` witness is unavailable on Tegra (§ 2.5) and must
> be replaced by something device-truthful on both discrete and integrated
> GPUs. Proposed primary witness, in the process under test:
>
> 1. Assert the resolved device is `Device::Cuda(N)` — not a silent CPU
>    fallback. `resolve_device()` already warns loudly on fallback; the
>    witness must turn that warning into a hard signal.
> 2. Assert a **nonzero GPU allocation delta** across model load, measured
>    through the CUDA API in-process, so the proof does not depend on an
>    external reporting tool.
>
> `tegrastats` GR3D utilization sampling is admitted as corroboration only,
> never as the sole witness. The existing x86_64 PID witness is **retained**
> for discrete GPUs — this sub-slice adds a second mechanism, it does not
> remove the first, and the x86_64 lane's evidence strength must not drop.

R80-6 (§ 4): "The CUDA GPU witness must prove device engagement on a Tegra
integrated GPU, where `nvidia-smi` reports no compute processes."

use it) is natively compiled, and even that's gated by a soft

does not need to work around a fork-level build failure on `sm_87`. Verify
by actually running it on this Jetson (you have real CUDA 12.6 + driver
540.5.0 here), don't pre-emptively add fork-change complexity.

### Pointers into the actual codebase (read, not guessed)

- **The x86_64 witness this augments** — `scripts/release/cuda-preflight.sh`,
  function `seal_gpu_observation` (around line 463). It's an external,
  post-hoc, **black-box** shell/Python witness: it launches the built
  artifact (wheel or npm package) in a Docker container, polls
  `nvidia-smi --id=0 --query-compute-apps=pid,process_name` for the
  container's host PID, and once found, stamps a JSON file
  (`gpu-$consumer-cuda-witness.json`) with `nvidia_smi_uuid`, `process_id`,
  `process_name`. This is NOT in-process — it observes the artifact from
  outside. Your new witness is explicitly the opposite shape ("in the
  process under test," per the design doc) — don't try to make this
  function work on Tegra; it structurally can't (no compute-apps PID to
  poll), which is the whole reason 80.5 exists. Leave this function alone.
- **Slice 72's Rust-side telemetry precedent** —
  `src/rust/crates/fathomdb-engine/tests/support/slice72_gpu_telemetry.rs`.
  This is integration-test support code (not shipped), also built around
  shelling out to `nvidia-smi` (see its `Command::new("nvidia-smi")` call
  sites, e.g. around lines 1077 and 1093) for UUID/driver-version queries
  and a `TelemetrySnapshot` struct. Useful as a precedent for the *shape* of
  evidence (UUID-bound, structured, retained) but not as code to reuse
  directly — it depends on `nvidia-smi` reporting things Tegra doesn't.
- **Device resolution / CPU-fallback classification** —
  `src/rust/crates/fathomdb-embedder/src/device_policy.rs`
  (`resolve_embed_device_policy` / `resolve_embed_device_policy_from_env`,
  around lines 385/488) and
  `src/rust/crates/fathomdb-embedder/src/candle_bge.rs` (device resolution
  around line 377, `classify_cuda_driver_error` around line 276 — this is
  the same classifier 80.7 will extend for `doctor gpu`). No literal
  `log::warn!`/`eprintln!` call was found by a direct grep for "warns
  loudly on fallback" as the design doc phrases it — the "warning" may be
  a typed `CpuFallbackReason`/similar returned value rather than a log
  line. Read this code yourself before assuming a specific call site; the
  design doc's intent is clear regardless of the exact mechanism: the
  *witness* must hard-fail (not just log) if resolution isn't
  `Device::Cuda(N)` when CUDA was requested.
- **The in-process CUDA API primitive for the allocation-delta witness** —
  `candle-core-fathomdb` (the pinned Candle fork,
  `Cargo.lock`: `candle-core-fathomdb 0.10.2`, git rev `5719d90`) depends on
  **`cudarc 0.19.7`** (confirmed via `Cargo.lock`, not the other `cudarc
  0.17.8` also present in the lockfile for an unrelated crate —
  double-check which one you actually link against before using it).
  `cudarc::driver::result::mem_get_info() -> Result<(usize, usize),
  DriverError>` (confirmed present in the vendored source at
  `~/.cargo/registry/src/index.crates.io-*/cudarc-0.19.7/src/driver/result.rs:1114`)

  it before and after model load, assert `free_before - free_after > 0`.

## 4. Traps already hit this session — don't repeat these

- **Bare `python3` on this host is 3.10.12** (no `datetime.UTC`, no
  `tomllib`). Any script you invoke directly with `python3 foo.py` outside
  of `scripts/agent-test.sh` (which prepends `.venv/bin` to `PATH` itself
  via `scripts/lib/agent-python-env.sh`'s `use_checkout_venv_python_path`)
  needs the same treatment: `PATH="$PWD/.venv/bin:$PATH" python3 ...`, or
  just call `.venv/bin/python3` directly. Bit this session running
  `scripts/tests/test_cuda_release_contract.sh` standalone.
- **The shell sandbox rejects some Bash command shapes** as "too complex to
  verify... stays inside worktree" — specifically `PATH=... cmd | pipe`
  combos, `cd dir && cmd` chains combined with further `&&`/`;`, and
  multi-statement `export X; cmd` sequences run inline. When you hit this,
  write the sequence to a script file in the scratchpad directory and
  `bash` that file instead — every multi-step Docker/build invocation this
  session needed went through that workaround.
- **`curl` to arbitrary internet hosts from the Bash tool is denied** by
  the permission layer (confirmed: `curl` to `nodejs.org` and
  `static.rust-lang.org` were both denied outright, no prompt). Use the
  `WebFetch` tool for anything that needs a real external URL (e.g. a
  release tarball's published SHA-256) — this doesn't apply to you unless
  80.5 needs a new pinned download, which it shouldn't (CUDA/cudarc are
  already vendored dependencies).
- **`cd` persists across Bash tool calls in this harness.** A `cd
  some/dir` in one call leaves you there for the next call too. Prefer
  absolute paths or `(cd dir && cmd)` subshells.
- **`docker run` without `--user $(id -u):$(id -g)` leaves root-owned files
  in the mounted worktree** you can't clean up without sudo. If your
  witness work ends up needing a container for any reason (it shouldn't —
  this is in-process Rust code, built and run directly on this host, not
  containerized, unlike x86_64's manylinux CUDA build), always pass
  `--user`.
- **`agent-lint-shell.sh` only scans `git ls-files` output** (tracked +
  staged, not merely present-on-disk). A new file with an early-exiting-
  consumer or SC2312 finding won't be caught until you `git add` it. Stage
  before your final lint pass, not just before commit.
- **A background `agent-test.sh --tier=fast` run reflects whatever the
  files looked like when it started, not when it finishes** — if you edit
  a file after launching a background full-suite run (e.g. applying a
  code-review nit), that edit races the run and its result for suites it
  hasn't reached yet is unreliable. Either wait for edits to fully settle
  before launching the authoritative run, or re-launch a fresh one after
  any late edit. This session hit exactly this once (a stale run showed a
  spurious `test-steward-orient` failure that was purely a race with a
  concurrent edit, not a real bug — confirmed by a clean re-run).
- **Full `scripts/agent-test.sh --tier=fast` takes 5–10 minutes** on this
  host (85 suites; several, like the real npm registry round-trip in
  `test_idempotent_republish.sh` and the CUDA contract fixture sweep in
  `test_cuda_release_contract.sh`, take 10–20s each on their own). Always
  `run_in_background: true` and wait for the notification or poll via
  `Monitor`, never block synchronously.
