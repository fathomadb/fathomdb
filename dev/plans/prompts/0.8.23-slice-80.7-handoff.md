## 3. The one decision that changed under you

**D-80.6-3 was reversed on 2026-08-19.** If you were briefed earlier, or you
read a stale summary, you may believe the Tegra artifact ships as a
`-tegra`-suffixed distribution. **It does not.**

The ruling now: **the distribution name stays `fathomdb`**, and the Tegra build
is distinguished by a **PEP 440 local version** (`+tegra`) served from a
**first-party PEP 503 index**.

Three findings drove it, all in `dev/tegra-platform-reference.md` § 3.2:

1. Two distributions sharing the `fathomdb/` import package corrupts **pip's own
   uninstall bookkeeping** — both `RECORD`s claim the same paths, so removing
   either guts the survivor. That is worse than the failure it would prevent,
   and it happens before any import, so no import-time guard can catch it.
2. PyPI rejects our bare `linux_aarch64` tag with **HTTP 400 under any name**,
   so renaming buys no channel we don't already have.
3. It is what NVIDIA and PyTorch actually do for Jetson.

**Why this lands on your desk:** it changes what your install command says, and
it created **AC80-27**, which is yours.

## 4. Scope — six items, no more

### 4.1 Two-tier detection (R80-8) — core

Both signals are **confirmed on this host**; you do not need to re-derive them:

```text
$ tr '\0' '\n' < /proc/device-tree/compatible
nvidia,p3737-0000+p3701-0005
nvidia,p3701-0005
nvidia,tegra234                 <-- contains "nvidia,tegra"

$ cat /etc/nv_tegra_release
# R36 (release), REVISION: 5.2, GCID: 46426093, BOARD: generic, EABI: aarch64, ...

$ ls /sys/firmware/acpi/tables
ls: cannot access '/sys/firmware/acpi/tables': No such file or directory

$ nvidia-smi --query-gpu=name --format=csv,noheader
Orin (nvgpu)                    <-- contains "nvgpu"
```

- **Tier 1 (Tegra family, filesystem only, no subprocess).** Either signal alone
  suffices: `/proc/device-tree/compatible` contains `nvidia,tegra`, **or**
  `/etc/nv_tegra_release` exists. The latter also supplies the L4T revision.
- **Tier 2 (resolve the Thor ambiguity).** Tier 1 false → `/sys/firmware/acpi/tables`
  present means SBSA-capable non-Tegra. Tier 1 true → `nvidia-smi --query-gpu=name`
  containing `nvgpu` means classic Tegra iGPU; absent (`NVIDIA Thor`) means
  Tegra-family but SBSA-capable.

**Do not use `uname` as the sole Tegra signal.** `jetson-containers` shipped
exactly that and broke when Jetson Thor began reporting `tegra` in `uname -a`
despite being SBSA-capable. **AC80-11 encodes the Thor case as a named negative
test specifically so this cannot recur.**

Two implementation constraints, both from real bugs:

1. **Check the subprocess exit status before reading stdout.** An early Rust
   sketch didn't, so a failing `nvidia-smi` with empty stdout read as
   SBSA-affirmative instead of failing closed.
2. **`nvgpu` is unofficial and empirically observed** — no documented NVIDIA API
   confirms it, and it may change across JetPack versions without notice. Tier 1
   must be tried first precisely because it is filesystem-only. Tier 2 must
   degrade to a named `probe_failed`-shaped outcome — **never a silent default** —
   if `nvidia-smi` is missing, times out, or exits non-zero. Invoke it by
   **absolute path with a bounded timeout**.

Reference implementations for all three language surfaces exist in
`~/projects/memex/dev/notes/2026-08-18-tegra-sbsa-platform-detection-design.md`.
**You only need the Rust one** — `doctor gpu` is Rust-CLI-only, and neither SDK
exposes an independent GPU-**diagnostic** surface today.

Be precise about what the SDKs now do carry: 80.6 part B added
`GpuAllocationWitness` / `embedderGpuAllocationWitness` to the Python and
TypeScript surfaces (`src/ts/src/index.ts:766,781`). That is a **witness record
hanging off `OpenReport`**, not a diagnostic entry point — it reports what one
engine open observed, and it only populates when
`FATHOMDB_GPU_ALLOCATION_WITNESS` is set. Do **not** mistake it for an existing
SDK `doctor gpu`, and do not route your detection through it.

### 4.2 SBSA refusal (R80-9) — core

On detected SBSA hardware, `doctor gpu` reports `cuda_incompatible` naming
`arm64-sbsa` explicitly as unsupported, **exits 0**, and the process continues on
the typed CPU path. Never attempt to load a Tegra-linked binary there, and never
fail the process outright — an unsupported *accelerator* is not a reason to make
the *database* unusable.

### 4.3 Guided install (R80-10) — core, **content changed by D-80.6-3**

Print the exact install command for the detected host. Do not fetch or build
anything. Three hard constraints:

- **Name the first-party index.**
- **Pin exactly** — `==<version>+tegra`, never floating.
- **Print only after affirmative Tegra detection.** This is not cosmetic: a bare
  `linux_aarch64` wheel is **tag-compatible on Graviton**, so the same command
  pasted on generic aarch64 installs an unloadable build. Detection-gating is
  what makes the command safe to print at all.

`--extra-index-url` is the honest flag here (pip documents **no priority**
between indexes, and we do not mirror our dependency closure the way PyTorch
does, so `--index-url` would be a lie). Prefer also documenting the `uv` form,
which is structurally safe: `[[tool.uv.index]] explicit = true` plus a
`[tool.uv.sources]` pin restricts the index to `fathomdb` alone.

This was a deliberate rejection of `node-llama-cpp`'s silent postinstall
download-and-build ("can take up to an hour", fails opaquely without build
tools). Do not reintroduce it.

### 4.4 Displaced-build detection (AC80-27 / D-80.7-1) — core, **new**

Detect a host that Tier-1/Tier-2 identifies as **Tegra**, carrying an installed
`fathomdb` that is **not** the Tegra build. Report a named, typed outcome
**distinct from both** `cuda_incompatible` and the healthy Tegra case, plus the
pinned, index-qualified command that repairs it.

**Why this is load-bearing, not polish.** D-80.6-3 accepts a real cost — a later
`pip install -U fathomdb` from PyPI silently replaces the Tegra build with the
generic one — **explicitly conditioned on the case being detected**. Ship the
naming decision without this and its own justification is unmet. Observed in the
wild on Jetson: facebookresearch/xformers#1193.

Criteria:

- Read the installed distribution's **build identity — the `+tegra` local version
  segment**. **Not** the presence of CUDA symbols; a generic build on a Tegra
  host may expose those and still be wrong.
- A fixture proves the Tegra-host/generic-build combination is reported, not
  passed.
- A fixture proves a **non-Tegra host with a generic build is not flagged**.
- The install command is emitted only on the affirmative-detection path.

**Distinct from AC80-25.** The co-installation guard
(`src/python/fathomdb/_coinstall.py`) detects a *corrupted* environment that the
revised naming should no longer produce; AC80-27 detects a *wrong-but-intact*
one that is expected in normal use. **Neither may be implemented and claimed as
covering the other** — AC80-27 says so explicitly.
