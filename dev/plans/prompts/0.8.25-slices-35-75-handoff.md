## Per-slice engineering loop

For each slice, use one main writer in the release worktree. Review agents are
read-only and may inspect that worktree. Do not allow concurrent writers.

1. **Orient and reconcile.** Verify the predecessor's closure from Git and the
   release-state writer. Compare the slice plan/design with current code,
   requirements, acceptance criteria, architecture v2, public interfaces, and
   all predecessor changes. Update the plan or design only where the evidence
   requires it.
2. **Design gate.** Obtain an independent design review before implementation.
   Record findings and each correction cycle durably in the slice directory.
   A design is READY only when no unresolved implementation-shaping P1/P2
   finding remains.
3. **TDD RED.** Add real-database tests that fail for the intended reason.
   Commit the preserved RED witness separately. No generated oracle and no
   database mock.
4. **GREEN and refactor.** Implement the smallest contract-complete behavior.
   Preserve Rust/Python/TypeScript and wire parity when the public surface
   changes. Do not edit a valid RED test merely to make it pass.
5. **Implementation review.** Have an independent read-only code reviewer
   inspect the exact Git commit. Correct concrete findings. Up to eight FIX-n
   cycles are authorized when genuinely needed; do not manufacture cycles or
   stop with a known correctness issue merely to save a cycle. Record every
   cycle and exact reviewed SHA.
6. **Independent verification.** Use a different read-only verification agent
   to reproduce focused acceptance tests, applicable cross-SDK/package routes,
   and repository gates from the exact candidate commit. If verification finds
   a defect, restore RED/GREEN discipline, obtain review of the correction, and
   re-run the affected and enclosing gates.
7. **Close durably.** Write `status.md` and the supporting review/verification
   records. Update `dev/plans/release-state-0.8.25.json`, then regenerate its
   declared views with `./scripts/check-release-state-views.sh --write`. Never
   hand-edit text inside generated blocks. Run the state checker,
   documentation lint, and applicable final gates. Commit and push the explicit
   `release/0.8.25` branch ref.
8. **Checkpoint and compact.** Capture reusable engineering lessons outside the
   repository, update the memory index, confirm a clean pushed branch, then
   compact context before opening the next slice.

Use additive commits. Never skip hooks, rewrite release-branch history, merge
to `main`, tag, publish, or delete artifacts without explicit owner authority.
All historical performance runs and data remain retained.
