# 0.8.23 Slice 60 — Windows WAL checkpoint diagnosis

## Review and disposition

Reviewed the release plan, work since its planning baseline, the Slice 3
allocation, Slice 5 verification gap, Slice 6 preparation/workplan, both
assigned design inputs, existing CI, and the live erasure implementation and
tests. The engine already has a bounded five-attempt WAL-truncate retry and a
typed fail-closed `ErasureIncomplete` result. The same-process test covers
that invariant but cannot supply the Windows cross-process evidence.

- Approved N23-WINDOWS-WAL / R23-WINDOWS-WAL-DIAGNOSIS /
  AC23-WINDOWS-WAL-DIAGNOSIS as bounded diagnostic evidence labels. They were
  not promoted into locked authoritative requirement/acceptance documents.
- Approved a real SQLite, separate-process, Windows-x64 source test and a
  dedicated GitHub-hosted Windows job with retained diagnostic output.
- Rejected speculative retry tuning, binding-finalizer/GC diagnosis,
  reader-pool changes, and public error-field expansion. No measured data yet
  supports any of them.

The design review is
`dev/design/0.8.23-windows-wal-checkpoint-reader-conflict.md`.

## TDD

RED was staged first: the Windows parent test waited on the required ready
sentinel before an ignored child test existed to write it. On a Windows runner
that state times out, proving the test cannot accidentally run without a
pinned cross-process reader. The current Linux host has no
`x86_64-pc-windows-msvc` target, so the platform-selected RED command could
not execute here.

GREEN supplies the child test. It opens a separate real `rusqlite` connection,
begins and pins a read snapshot, writes a ready sentinel, waits for parent
release, commits, and exits. The parent records elapsed time and the typed
`wal_checkpoint` diagnostic, signals release, and reaps the child before
asserting the outcome. Production erasure code and retry constants are
unchanged.

## Fix-N — retained protocol evidence

Independent review found that the first artifact would have emitted only the
post-reap typed error, not proof of the ready/release/reap protocol. RED added
eight required immutable source markers to the Linux-runnable workflow
contract test; `bash scripts/tests/test_windows_wal_diagnosis_ci_job.sh` then
failed 8 assertions at `6bfe592a`, each naming a missing marker. GREEN emits
non-secret lifecycle records in the real parent/child test for child PID/start,
ready, parent-ready observation, checkpoint start/result plus elapsed time,
release signaled, child release observation, and successful child reaping.
The same test now passes 23 assertions, including a committed mutation arm
that removes the child-start marker from a temporary source copy and requires
the contract to fail. Those `--nocapture` lines are written to the
always-uploaded Windows CI artifact.

## Fix-N 2 — child artifact visibility

GitHub Actions job `95235671915` passed its parent test, but its retained log
did not include `child_ready` or `child_release_observed`. The parent had
`--nocapture`; its self-invoked ignored child did not, so Rust captured the
child's successful `eprintln!` lines. This is insufficient lifecycle evidence,
not a completed acceptance witness.

RED extended the Linux-runnable contract with a targeted
`.arg("--nocapture")` requirement and failed one assertion. GREEN adds that
argument to the child invocation. The contract now includes a mutation arm
that removes the argument from a temporary source copy and requires the
targeted assertion to fail. A fresh Windows job must retain the complete parent
and child sequence before this Slice can close.

## First-party Windows evidence and completion

The first GitHub-hosted `windows-latest` source-test job,
[`95235671915`](https://github.com/fathomadb/fathomdb/actions/runs/31976063970/job/95235671915),
completed successfully at its parent assertion but is deliberately **not** the
completion witness. Its retained artifact lacked `child_ready` and
`child_release_observed`: the self-invoked child had captured its successful
diagnostics. That gap triggered Fix-N 2; `423baf6a` adds child `--nocapture`.

The repaired GitHub-hosted `windows-latest` job,
[`95236592394`](https://github.com/fathomadb/fathomdb/actions/runs/31976435962/job/95236592394),
completed successfully and passed the source test (1 passed). Its retained
artifact records the full protocol in order: `child_started`, `child_ready`,
`parent_ready_observed`, `checkpoint_start`, `checkpoint_result` (116 ms), the
typed `ErasureIncomplete` at `wal_checkpoint` with `SQLITE_BUSY` on all five
attempts and 212 frames, `release_signaled`, `child_release_observed`, and a
successful `child_reaped`. This is the required first-party Windows x64
diagnostic witness.

The reviewed supporting note
`dev/notes/0.8.23-memex-windows-x64-wal-evidence-20260816.md` is consistent
with the measured timing/lifetime sensitivity and the fail-closed contract. It
does not establish a surviving-reader root cause and does not justify retry
tuning, so the approved no-tuning diagnostic boundary remains unchanged.

Slice 60 is complete on `origin/release/0.8.23` at `423baf6a`; integration to
`origin/main` remains pending. The state/board closure records the two Windows
job URLs and the rejected-first-run history rather than treating the first
