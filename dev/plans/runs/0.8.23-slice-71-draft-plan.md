# Slice 71 — draft cross-encoder reranker dual-runtime plan

## Purpose and boundary

Slice 71 is a proposed follow-on to Slice 70. It makes cross-encoder semantic
reranking capable of using either CPU or a compatible GPU from one supported
artifact, without an end-user rebuild. It must not broaden Slice 70's embedding
scope or claim that SQLite retrieval, FTS, graph, indexing, or storage become
GPU workloads.

When a user selects a GPU-bound reranker, the cross-encoder inference path must
use that selected GPU or fail typed. Candidate retrieval and exact database
scoring may remain CPU work and must be attested separately rather than
misreported as GPU reranking.

## Required discovery before design approval

The Slice 71 agent first audits and records:

1. Every current reranker implementation and feature tuple, including its
   provider/device-selection path, CPU/GPU fallback behavior, local-model
   loading, and which paths are compiled into each supported artifact.
2. The Rust, Python, and TypeScript configuration and OpenReport/error seams;
   current `FATHOMDB_RERANK_DEVICE` behavior; and whether an SDK option is
   necessary or environment configuration remains the one cross-SDK transport.
3. The existing `doctor` and configuration surfaces. The repository currently
   has no `init` root; introducing a configuration-writing `init` command is a
   separate public-interface/ADR decision, not an assumed implementation step.
4. Slice 20's artifact/rehearsal inputs and the additional cross-encoder model
   cache, checksum, driverless, GPU-engagement, and forced-failure evidence
   needed for reranking.

The agent then updates this draft with audited requirements, acceptance
criteria, and a reviewed design before implementation begins.

## Draft requirements and acceptance criteria

**R71-1 — no-rebuild, strict reranker policy.** On each supported CUDA-capable
artifact, the reranker accepts exactly `auto`, `cpu`, or `cuda:N`; `cpu` never
initializes CUDA, `auto` selects CPU only with a typed reason, and forced
`cuda:N` performs no CPU retry or fallback.

**AC71-1.** RED→GREEN policy/provider tests cover CPU, CPU-only artifact, no
visible device, incompatible device, successful GPU, session/inference
initialization failure, malformed/retired values, and forced CUDA. A forced
GPU request never produces a CPU cross-encoder result.

**R71-2 — explicit, cross-SDK observability.** Rust, Python, and TypeScript
surface the reranker requested policy, compiled capability, effective device,
safe device identity facts, and classified reason in stable result/open-report
shapes. The GPU device state is distinct from the embedding-device report.

**AC71-2.** Binding tests assert both a present GPU selection and a recorded
`auto` CPU fallback. Error tests assert forced GPU failure is typed and is not
rewritten as a successful CPU outcome.

**R71-3 — diagnostics and configuration parity.** `doctor gpu [--json]`
reports embedding and reranker capability/selection independently, without
database mutation, model download, or inference. Configuration behavior is
documented consistently across SDKs. A proposed `init` command, if still
needed after audit, requires its own approved public-interface design.

**AC71-3.** CLI tests pin text/JSON fields and exit behavior, distinguish the
two subsystems, and prove the diagnostic has no DB/loader/download side effect.

**R71-4 — artifact and smoke truth.** A supported CUDA-capable artifact carries
both CPU and GPU reranker capability. Its rehearsed installed bytes prove
driverless CPU/default behavior, compatible-GPU inference engagement, and
forced-GPU failure; GPU attestation does not label CPU retrieval as GPU work.

**AC71-4.** Slice 20 contract mutations reject reranker feature omission,
driverless/GPU/forced-failure smoke omission, package digest substitution, and
any claim of CUDA support on an unqualified platform. Real hardware evidence
remains `PENDING_EXTERNAL` until valid trusted-route artifacts exist.

## Proposed TDD and review sequence

1. Audit the actual reranker implementation and package seams, then approve or
   revise these draft requirements.
2. Write and independently review the Slice 71 design and public-interface
   changes.
3. Commit behavioral RED tests for strict policy and report propagation.
4. Implement Green provider/runtime/binding behavior; independently code-review
   it.
5. Commit RED artifact/doctor tests, implement Green, and independently verify
   the full local scope.
6. Record Slice 71 status. It remains `PENDING_EXTERNAL` for trusted CUDA
   artifact/hardware evidence and never publishes a registry.
