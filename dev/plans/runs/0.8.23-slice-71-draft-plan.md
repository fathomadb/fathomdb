# Slice 71 — cross-encoder reranker dual-runtime plan

## Purpose and boundary

Slice 71 is a continuation of Slice 70's product-runtime work. Slice
70 establishes the no-recompile dual CPU/GPU contract for embedding; Slice 71
extends that same contract to cross-encoder semantic reranking so FathomDB's
supported runtime is GPU-enabled when a compatible GPU is present while the
same compiled artifact continues to support CPU execution. Switching between
CPU and GPU must be a runtime configuration decision, never an end-user rebuild.
This does not claim that SQLite retrieval, FTS, graph, indexing, or storage
become GPU workloads.

When a user selects a GPU-bound reranker, the cross-encoder inference path must
use that selected GPU or fail typed. Candidate retrieval and exact database
scoring may remain CPU work and must be attested separately rather than
misreported as GPU reranking.

## Completed discovery and approved design

The Slice 71 audit found that the existing Candle TinyBERT reranker had an
independent legacy parser and loud CPU fallback. The approved implementation
design is `dev/design/0.8.23-slice-71-reranker-dual-runtime.md`. It narrows the
plan to the strict Candle CPU/CUDA provider path and its artifact feature
routes; it does not claim an ONNX cross-encoder or GPU database retrieval.

1. Every current reranker implementation and feature tuple, including its
   provider/device-selection path, CPU/GPU fallback behavior, local-model
   loading, and which paths are compiled into each supported artifact.
2. The Rust, Python, and TypeScript configuration and OpenReport/error seams;
   current `FATHOMDB_RERANK_DEVICE` behavior; and whether an SDK option is
   necessary or environment configuration remains the one cross-SDK transport.
3. The existing `doctor` and configuration surfaces. The repository currently
   has no `init` root; introducing a configuration-writing `init` command is a
   separate public-interface/ADR decision, not an assumed implementation step.
4. Slice 20's artifact/rehearsal inputs and the additional cross-encoder model
   cache, checksum, driverless, GPU-engagement, and forced-failure evidence
   needed for reranking.

The implementation starts with provider-injected policy tests. Actual compatible
GPU execution and installed-artifact receipts remain `PENDING_EXTERNAL`.

## Requirements and acceptance criteria

**R71-1 — no-rebuild, strict reranker policy.** On each supported CUDA-capable
artifact, the reranker accepts exactly `auto`, `cpu`, or `cuda:N`; `cpu` never
initializes CUDA, `auto` uses a present compatible GPU and selects CPU only with
a typed reason when no usable GPU is available, and forced `cuda:N` performs no
CPU retry or fallback. CPU and GPU execution paths coexist in the same runtime
artifact.

**AC71-1.** RED→GREEN policy/provider tests cover CPU, CPU-only artifact, no
visible device, incompatible device, successful GPU, session/inference
initialization failure, malformed/retired values, and forced CUDA. A forced
GPU request never produces a CPU cross-encoder result, while `auto` proves that
a present compatible GPU is selected without rebuilding or replacing the
runtime artifact.

**R71-2 — explicit, cross-SDK observability.** Rust, Python, and TypeScript
surface the reranker requested policy, compiled capability, effective device,
safe device identity facts, and classified reason in stable result/open-report
shapes. The GPU device state is distinct from the embedding-device report.

**AC71-2.** Binding tests assert both a present GPU selection and a recorded
`auto` CPU fallback. Error tests assert forced GPU failure is typed and is not
rewritten as a successful CPU outcome.

**R71-3 — diagnostics and configuration parity.** `doctor reranker-gpu [--json]`
reports reranker capability/selection without database mutation, model download,
or inference; it is distinct from Slice 70's embedding `doctor gpu` command.
Configuration behavior is documented consistently across SDKs. No `init`
command is part of this slice.

**AC71-3.** CLI tests pin text/JSON fields and exit behavior, distinguish the
two subsystems, and prove the diagnostic has no DB/loader/download side effect.

**R71-4 — artifact and smoke truth.** A supported CUDA-capable artifact carries
both CPU and GPU reranker capability. The candidate-only v3 route retains
driverless CPU/default and forced-GPU installed-artifact evidence; compatible
GPU engagement and visible-incompatible classifier receipts remain external.
GPU attestation does not label CPU retrieval as GPU work.

**AC71-4.** The v3 contract mutations reject reranker feature omission,
required local smoke or forced-failure omission, package digest substitution,
and any claim of CUDA support on an unqualified platform. Compatible-GPU and
visible-incompatible hardware evidence remains `PENDING_EXTERNAL` until valid
trusted-route artifacts exist.
