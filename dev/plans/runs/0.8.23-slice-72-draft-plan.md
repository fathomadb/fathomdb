# Slice 72 — concurrent embedding and cross-encoder GPU coexistence

## Purpose and boundary

Slice 72 characterizes one CUDA-capable runtime using its selected GPU for both
embedding and optional cross-encoder (CE) reranking in the same process. It
must prove the product behavior, record bounded CPU/GPU utilization and memory
observations, and state the limits of that evidence without turning device
selection into a scheduler, reservation system, or performance promise.

The scope is the production embedding and CE paths, not SQLite retrieval.
Bit-KNN candidate retrieval, exact-f32 database reranking, FTS, fusion, graph,
and storage remain CPU work. A CE result is not evidence that those stages ran
on a GPU.

The three real-runtime tests below require a CUDA-capable build, both pinned
local model caches, and an authorized NVIDIA runner. Their absence is an
explicit `PENDING_EXTERNAL` condition; deterministic provider tests cannot be
substituted for real residency or utilization evidence. The tests freeze
`CUDA_VISIBLE_DEVICES` before resolving `cuda:0`; that ordinal is process
visible, never a claim about the host ordinal.

## Requirements and acceptance criteria

**R72-1 — one process, independently selected shared CUDA device.** A
CUDA-capable artifact with both `embed-cuda` and `rerank-cuda` compiles must be
able to open the default embedder and load/use the TinyBERT reranker in one
process. The test explicitly selects the same visible CUDA ordinal for
`FATHOMDB_EMBED_DEVICE` and `FATHOMDB_RERANK_DEVICE`, then proves both
resolutions are CUDA, identify the same UUID, and produce a valid embedding and
a real CE rerank. There is no exclusive claim, reservation, or implicit
different-device behavior.

**AC72-1.** The basic real-runtime test fails on a CPU fallback, different or
missing UUID, model-load substitution, no CE scoring, invalid embedding, or
incorrect rerank fixture result. It records the exact build features, driver,
logical ordinal, and UUID. It is eligible only on the designated CUDA runner;
otherwise it reports a clear external prerequisite and makes no success claim.

Before `Engine::open`, the harness must verify the exact immutable BGE and
TinyBERT cache files and hashes. It must use an isolated XDG cache root for
BGE and the **parent** cache root required by `FATHOMDB_RERANKER_CACHE` for
TinyBERT, then mount or make both read-only. A cache miss, sensor absence, or
unauthorized runner must stop before model loading; `FATHOMDB_SKIP_NETWORK_TESTS`
is not a loader-level network block and is insufficient.

**R72-2 — bounded low/moderate co-residency characterization.** A second
real-runtime test warms both models and runs bounded, overlapping embedding and
CE work in the same process. Projection embedding is deliberately serialized
inside an engine, so this means overlapping BGE and CE requests, not concurrent
embedding workers. The approved design must pin a small pair count, maximum
token length, embedding shape, operation count, timeout, and a barrier/latch
which proves overlap. It asserts functional completion and captures
before-warm, warmed, and overlap samples.

**AC72-2.** The retained record distinguishes process CPU time/RSS from
device-wide GPU compute utilization, GPU-memory utilization, and
total/used/free VRAM. It binds each GPU sample to the selected UUID and records
the FathomDB process PID separately as a compute-app observation; GPU-wide
metrics are not represented as per-process values. It records other observed
compute PIDs as confounders. The test does not use an unverified free-memory
value as an admission guarantee and does not impose a portable utilization,
throughput, or VRAM threshold. An OOM, hang, device error, wrong-device
observation, absent PID correlation, or missing required telemetry is a failed
characterization, never a CPU retry or a fabricated sample.

**R72-3 — explicit stress only.** The third test is a controlled concurrent
stress characterization. It is marked `#[ignore]` and additionally requires a
dedicated opt-in environment sentinel; neither ordinary test runs nor a broad
`AGENT_LONG` setting may start it accidentally. Its duration, concurrency,
request count, model-cache identities, host identity, samples, and outcome are
recorded with the run.

**AC72-3.** The stress run asserts correctness and bounded termination, not a
machine-independent speed target. It records peak/summary process CPU and RSS,
device-wide GPU compute/memory utilization, VRAM use, UUID/PID correlation, and all typed
failures. It does not run while the selected GPU is allocated to an unrelated
workload without recording that workload as a confounder. A failed or partial
stress run is retained as failure evidence and does not modify product fallback
policy.

**R72-4 — measurement method is test-only and honest.** The approved design
must select a Linux telemetry source that can bind process and GPU observations
without adding production polling or a public telemetry API. Sampling cadence,
window-averaging limits, warm-up boundary, summary calculation, retention
format, and behavior when NVML/`nvidia-smi` is unavailable must be specified.
CPU RSS/time and GPU system-wide utilization must not be represented as the
same metric or as a per-request allocation guarantee.

**AC72-4.** A versioned retained JSON receipt schema records monotonic
timestamps; pre-warm, warm, and overlap phases; selected UUID; test PID;
device-wide metrics; process presence; other compute PIDs/confounder flag; and
sensor source/version plus explicit unavailable/null fields. Unit tests cover
parser/normalizer and UUID/PID binding with captured fixtures; the real tests
use the selected sensor and reject malformed, wrong-UUID, wrong-PID, absent, or
out-of-order samples. No test invokes `nvidia-smi` or NVML on the
embedding/reranking hot path.

**R72-5 — TC-5 GPU-path decision.** The slice audits the current private
`fathomdb-tc5-benchmark` crate's `tc5-benchmark-cuda` feature and the CPU-only external TC-5 execution
contract. It records whether a GPU TC-5 characterization is needed for the
Slice 72 question, with evidence rather than assumption.

**AC72-5.** The design records the decision and its rationale. The expected
outcome is **no new TC-5 execution path in Slice 72**: TC-5 measures pre-fusion
vector work and intentionally excludes CE, while Slice 72 measures concurrent
embedder-plus-CE co-residency. If an audit identifies a separate need for
GPU-query-embedding TC-5 results, it must propose a new execution-contract
amendment covering hardware/UUID, CPU and GPU controls, cache/build identity,
and result comparability before any run or claim. It must not relabel CPU
sqlite-vec retrieval as GPU work.

## Required design, tests, and documentation

1. Audit the exact embedding and reranker model-loading/concurrency seams,
   current CUDA UUID evidence, existing PR-9 serialized embedding guard, and
   the current TC-5 executor/contract. Write and independently review a Slice
   72 design before tests or production changes.
2. Commit a RED test contract before Green. The three named real-runtime tests
   are: basic functional coexistence; bounded low/moderate shared-residency;
   and explicitly invoked stress. Basic/moderate require a named runner
   sentinel and serialized test process; stress requires both `#[ignore]` and
   `FATHOMDB_SLICE72_STRESS=1`, never `AGENT_LONG`. Preserve and restore all
   policy/cache/XDG/CUDA environment on every path. Keep deterministic
   telemetry/parser tests separate from the three hardware tests.
3. Do not use mock databases. The functional and low/moderate tests use a real
   engine, real cached BGE and TinyBERT assets, and a CE fixture that proves a
   rerank rather than merely loading a model.
4. Update project documentation, including `README.md` where it describes GPU
   capability; public `docs/` guidance/reference material; `dev/design/`,
   `dev/interfaces/`, the Slice 70/71/72 planning/status records, and
   `dev/DOC-INDEX.md`. Correct the stale public claim that reranker selection
   has a legacy grammar or CPU fallback. State plainly that both models may use
   one GPU, that there is no resource manager or hard Candle memory cap, and
   that observed GPU utilization is sampled/system-wide rather than a
   per-request guarantee.
5. Treat documentation as a review gate: an independent reviewer must compare
   every changed public, project, and developer document with the final code,
   test results, and retained characterization evidence. The reviewer must
   return PASS before closure; `agent-lint-md`, `agent-lint-docs`, strict MkDocs
   build, link checks, and release-state view checks are necessary but not a
   substitute for that semantic review.

## Readiness assessment and approved implementation boundary

The 2026-08-18 code-grounded review confirms that the product already supports
independent CUDA policy resolution for embedding and reranking, and does not
reserve a GPU for either. It also confirms that BGE projection calls are
serialized while the CE singleton does not share that lock; Slice 72 therefore
tests product-path overlap between BGE and CE, rather than an impossible claim
of parallel engine embedding workers. The implementation may add a test-only
telemetry helper and a feature-gated real-engine integration target, but must
not add a product scheduler, public telemetry API, or TC-5 execution change.

This plan is **READY**. Design review must validate the exact harness, cache,
receipt, and test activation choices before implementation begins.

## Exclusions and stop conditions

- No automatic GPU placement, device reservation, memory quota, allocator cap,
  or continuous production NVML polling.
- No public benchmark controls, no general SDK telemetry API, and no change to
  normal CPU fallback/error semantics.
- No GPU TC-5 run, external performance claim, registry action, tag, push, or
  publication without a separately approved execution-contract amendment.
- Do not weaken a test or synthesize GPU residency/utilization evidence when
  a CUDA runner, driver, sensor, or cache is unavailable.
