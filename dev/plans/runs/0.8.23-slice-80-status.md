# Slice 80 — AArch64 correctness and Jetson Orin CUDA

Slice 80 has **eight** internal sub-slices (design doc:
`dev/design/0.8.23-aarch64-tegra.md` § 6–7) — 80.6.5 was split out of 80.6 by
HITL ruling while 80.5 was landing, on a hardware boundary: it is the only
sub-slice that cannot be proven on this Jetson (§ 7 80.6.5). This record tracks
landed progress; it is not a closure record. Seven sub-slices (80.1–80.7,
excluding the separately scoped 80.6.5) are landed and verified. Only 80.6.5
remains; it is the x86_64-lane, HITL-gated work described below.

## Plan review and design review (complete)

The drafted slice plan was reviewed and approved without change to its
requirements or acceptance criteria. An independent design review (a
general-purpose agent, not this session's own analysis) checked the design
doc's factual claims against the tree and a real Jetson Orin AGX host
directly, and found two things needing correction before implementation:

- 80.1's glibc-floor fix was originally scoped against the wrong build path
  for the x64 Linux npm artifact (`build-napi-cuda.sh` on the CUDA runner).
  Verified directly: `build-napi`'s matrix has no Linux x64 row at all, and
  `publish-npm-platform-linux-x64-gnu`'s artifact dependency is unsatisfiable
  today because `canonical-cuda-package-route-required`
  (`release.yml:728-738`) unconditionally blocks any non-dry-run release
  pending Slice 20's canonical CUDA route. 80.1 is rescoped to what
  `build-napi` actually builds (`linux-arm64-gnu`, plus both Python wheel
  architectures).
- R-3 (Candle `sm_87` buildability risk) was overstated. Direct inspection of
  the pinned Candle fork checkout confirmed `candle-kernels/build.rs` compiles
  every kernel the BGE embedder path touches via PTX (forward-compatible
  JIT), not native SASS; only MoE kernels (unused by BGE) are natively gated.
  Softened accordingly.

Both findings, plus three citation-line-number drifts, were folded into the
design doc (`dev/design/0.8.23-aarch64-tegra.md`, commit `f56d39f5`). The doc
moved from `PROPOSED`/draft to `ACTIVE`/commissioned; its own § 9

## 80.5 landed (Tegra-portable GPU witness + loader publish fixes)

Landed at `55c152fe`, real-hardware verified on this Jetson Orin AGX.

**Design revised before implementation, reviewed twice.** § 7 80.5's original
four paragraphs stated the intent correctly but were not implementable: no
measurement primitive, no failure semantics, no home for the code, no consumer.
The commissioning pass added § 2.7 (measured host facts), R80-12/R80-13,
AC80-15..AC80-21, and decisions D-80.5-1..6. An independent design review
returned NEEDS_FIXES on three findings, all resolved before any code was
written:

- **CRITICAL — `auto` semantics.** R80-11/AC80-7 and § 7 80.6 grouped `auto`
  with `cpu` as "never touches CUDA". False against the landed code:
  `resolve_embed_device_policy`'s `Auto` arm selects CUDA when a device probes,
  and ADR-0.8.23-dual-runtime-device-policy states "`auto` is default on
  CUDA-capable artifacts". As written, AC80-7 was unsatisfiable on the very
  Tegra artifact 80.6 builds, and an implementer honoring it literally would
  have regressed `auto` to CPU — the opposite of the slice's goal. R80-11 now
  enumerates the three cases; AC80-7 targets `cpu`; new **AC80-21** asserts the
  unset/`auto` → `cuda:0` behavior positively so it cannot be "fixed" away.
- **MAJOR — the x86_64 strengthening could not happen in 80.5.** AC80-19
  originally required the shared witness record to gain allocation fields, but
  that record is produced inside the installed wheel/npm process, which can
  only call the public SDK, and D-80.5-4 rules 80.5 adds no SDK surface.
  Sourcing it from a sibling process would be the not-the-artifact weakness the
  slice forbids for Tegra. The `/v2` schema bump was **withdrawn**; 80.5 lands a
  separate `fathomdb.tegra-gpu-allocation-witness/v1` record, and the merge plus
  x86_64 strengthening became **AC80-22 in the new sub-slice 80.6.5**.
- **MAJOR — hidden schema consumers.** Four, all enumerated in the design and
  left byte-untouched: `verify-cuda-preflight-witness.py`,
  `cuda_preflight_v2_fixture.py` plus its two committed fixtures, the Slice 10
  design doc's 11-key statement (whose PID sentence is *mutation-tested* by
  `test_slice70_cli_artifact_design.sh:74,134`), and
  `check-cuda-release-contract.py:685`'s pinned failure fragment.

**The measured correction that reshaped the witness.** § 2.7 first recorded a
256 MiB allocation moving `cuMemGetInfo`'s free by 274,161,664 bytes. That was
a single observation on a never-used GPU and **does not reproduce**. Re-measured
by two independent probes: on any host that has run a GPU workload since boot,
the first 256 MiB allocation moves free by 1,032,192 bytes, the second by
512,000, the third and fourth by **0**, and a 133,466,304-byte allocation — the
exact model size — moves it by **0**. Tegra's nvgpu/nvmap page pool retains
freed pages and satisfies allocations from them. Implemented as originally
specified, the witness would have failed closed on every run on every realistic
host (the model load charged 6,189,056 bytes for a 133 MB model). D-80.5-3 was
revised: the control allocation is a **precondition**, not corroboration — it
holds 1 GiB blocks until one is charged in full, draining the pool, and only
then is the model loaded. The original figure is retained in § 2.7 as corrected
rather than quietly overwritten.

**Delivered.** `fathomdb-embedder/src/gpu_witness.rs`, compiled unconditionally
with only the cudarc-backed samplers behind `embed-cuda` — mirroring how
`device_policy.rs` splits pure policy from the `CudaProvider` boundary, so the
verdict logic, floor, UUID normalization and serialization are testable on
GPU-less CI. Plus `scripts/release/verify-tegra-gpu-witness.py` (fail-closed,
41 distinct rejections), a registered fast-tier suite, a committed real-Jetson
fixture, and an env-gated hardware arm that SKIPs by name.

**Loader defects folded in by HITL direction (R80-14, R80-15 / AC80-23,
AC80-24).** Found while producing this sub-slice's own evidence, and
load-bearing for it:

- `materialize_from_hf_hub` hard-linked the HF hub's *relative* symlink instead
  of its target — Linux `link(2)` does not dereference — so the cache entry
  resolved to a nonexistent `blobs/` under the FathomDB cache root. Dangling,
  recreated on every retry, permanent failure. It fires only when the two caches
  share a filesystem, which is why the containerized CUDA preflight never saw
  it: there `hard_link` fails cross-device and the `fs::copy` fallback
  dereferences correctly.
- Adding read-verification then converted a previously harmless torn read into a
  **destructive delete**. This path runs outside the loader lock, so a racer's
  `fs::copy` (`O_TRUNC`) truncated an entry another racer was hashing, which
  then removed an entry it did not own. Reproduced deterministically: 7 of 8
  concurrent cold starts failed, hashing
  `e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855` — the
  SHA-256 of zero bytes.
- Closed by publishing through a temporary and `fs::rename`, the pattern
  `fetch_under_lock` already uses. Temp names come from **atomic exclusive
  creation** (`link(2)`/`O_CREAT|O_EXCL`, bounded retry), not from being
  improbable: a PID-derived name collides across PID namespaces, and the RED
  test reproduced exactly that with two pid-1 processes — the topology
  `scripts/release/cuda-preflight.sh` creates by bind-mounting caches into
  containers. `sync_all()` was added to the copy fallback only; the hard-link
  path writes no file data, so the post-rename parent-directory fsync suffices.

**Independent web research against normative sources** (The Open Group POSIX,
man7, Rust std, Microsoft Learn) settled three load-bearing claims before
acceptance: `rename()` replaces a destination symlink — including a dangling one
— rather than following it, so the explicit unlink is unnecessary and was
removed; a same-inode rename is a documented no-op, which is the *common* case
here (every racer links the same hub blob) and is why temp cleanup must run
unconditionally; and temp-then-rename is the consensus pattern, independently
arrived at by `huggingface_hub` itself, whose own lock is documented as
best-effort precisely because correctness rests on the atomic rename.

**Verification** (independent subagent, not the implementers' own claims):

- `scripts/agent-test.sh --tier=fast`: `registered=86 ran=86 passed=76
  failed=10` — the same 10 pre-existing failure names as the pre-80.5 baseline
  of `85/85/75/10`, none new, +1 registered suite as expected.
- Real-hardware witness reproduced **twice from scratch**: `delta_bytes`
  143,290,368 and 143,876,096 against a `delta_floor_bytes` of 67,108,864
  (2.13x), within 1.9% of the committed fixture's 141,246,464 — a 0.4% spread,
  so the measurement is stable rather than lucky. Both records verified by
  `verify-tegra-gpu-witness.py --nvidia-smi`, which genuinely exercises the
  § 2.7 normalization: this host's `nvidia-smi` reports
  `bbbe9f37-7028-556a-930b-54e5f3b67a82` with **no `GPU-` prefix** while the
  record carries it. The slice's premise re-confirmed:
  `nvidia-smi --query-compute-apps=pid,used_memory` returns `[N/A], [N/A]`.
- **A false claim was caught and corrected.** The implementer reported
  `cargo clippy -p fathomdb-embedder --features embed-cuda --all-targets --
  -D warnings` clean. It is **not** — it fails with 7 errors. Verification
  proved this pre-existing by running the identical command against a scratch
  export of `2dbe7c63`, where it fails with **9**. 80.5 takes it 9 → 7. This
  gate must not be described as green anywhere until the remaining 7
  (`tc5-benchmark`-only items dead in an `embed-cuda`-without-`tc5-benchmark`

- `--features loader-test-hooks,tc5-benchmark --all-targets -D warnings` clean;
  `cargo fmt --check` clean; `ruff` clean on both new Python files;

**Known limitations, recorded rather than smoothed over.** The witness holds up
to 16 GiB of control blocks on a 61 GB unified-memory box; it is an opt-in,
`embed-cuda`-gated evidence lane that never runs in a shipped path, and the
sole-GPU-consumer precondition is *stated, not enforced* — a concurrent GPU
tenant could push the delta over the floor or mask it, so an unattributable
delta is a named failure (R80-12). The pool-drain technique depends on
undocumented nvmap behavior that a future JetPack could change; it would surface
as failing closed, never as a false pass. And libtest has no runtime "skipped"
status, so the SKIP arm prints its named reason but the harness line still reads
`ok` — not a false pass in substance, since nothing asserts GPU engagement.

## 80.6 landed (Jetson Orin CUDA build + binding plumbing + first-party evidence)

**Commits.** `c836854a` (design — naming decision revised), `27758156` (part A —
Tegra CUDA build, per-family glibc floor), `eafd14a1` (part B — GPU allocation

(`dev/tegra-platform-reference.md`), `f1ca18c2` (80.6.5 git prerequisite),

**The naming decision was reversed, and it is the most consequential thing in
this sub-slice.** D-80.6-3 previously ruled a `-tegra`-suffixed distribution
sharing the `fathomdb` import package. Ecosystem research reversed it: the
distribution name **stays `fathomdb`**, distinguished by a PEP 440 local version
