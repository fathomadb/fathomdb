# Slice 80 — AArch64 correctness and Jetson Orin CUDA

Slice 80 has seven internal sub-slices (design doc: `dev/design/0.8.23-aarch64-tegra.md`
§ 6–7). This record tracks landed progress; it is not a closure record. Two
sub-slices (80.1, 80.3) are landed and verified. Five remain: 80.2, 80.4,
80.5, 80.6, 80.7.

## Plan review and design review (complete)

The drafted slice plan was reviewed and approved without change to its
requirements or acceptance criteria. An independent design review (a
general-purpose agent, not this session's own analysis) checked the design
doc's factual claims against the tree and a real Jetson Orin AGX host
directly, and found two things needing correction before implementation:

- 80.1's glibc-floor fix was originally scoped against the wrong build path
  for the x64 Linux npm artifact (`build-napi-cuda.sh` on the CUDA runner).
  Verified directly: `build-napi`'s matrix has no Linux x64 row at all, and
  `publish-npm-platform-linux-x64-gnu`'s artifact dependency is unsatisfiable
  today because `canonical-cuda-package-route-required`
  (`release.yml:728-738`) unconditionally blocks any non-dry-run release
  pending Slice 20's canonical CUDA route. 80.1 is rescoped to what
  `build-napi` actually builds (`linux-arm64-gnu`, plus both Python wheel
  architectures).
- R-3 (Candle `sm_87` buildability risk) was overstated. Direct inspection of
  the pinned Candle fork checkout confirmed `candle-kernels/build.rs` compiles
  every kernel the BGE embedder path touches via PTX (forward-compatible
  JIT), not native SASS; only MoE kernels (unused by BGE) are natively gated.
  Softened accordingly.

Both findings, plus three citation-line-number drifts, were folded into the
design doc (`dev/design/0.8.23-aarch64-tegra.md`, commit `f56d39f5`). The doc
moved from `PROPOSED`/draft to `ACTIVE`/commissioned; its own § 9
commissioning edits (already applied at `89e4b8c2`) were corrected from
"not applied" to a provenance record. All eight HITL decisions the slice
needed are ruled; none are open.

## 80.3 — AArch64 developer environment (landed, `60f62f14`)

Ubuntu 22.04 and every Jetson (L4T R36) ship Python 3.10, which lacks stdlib
`tomllib` (needed by several release/CI gates) and whose ensurepip-bundled
pip (22.0.2) predates `--dry-run` (needs ≥22.2). Fixed and verified against
real Python 3.10+tomli and real `uv`-managed Python 3.13 environments on this
host, not inferred:

- `select_python_for_venv()` / `create_venv_with_selected_python()`
  (`scripts/lib/agent-python-env.sh`) pick the newest available ≥3.11
  interpreter — bare `python3.13`/`3.12`/`3.11` on PATH, or `uv python find`
  for hosts (this one included) where a modern interpreter exists only via
  `uv python install`, never as a bare PATH command. Wired into
  `scripts/bootstrap.sh`, replacing a bare `python3 -m venv`. Fails closed
  with no partial state on either a missing interpreter or a failed
  `-m venv` itself.
- `tomli` fallback added to `scripts/check-license-consistency.sh`,
  `scripts/check-pinned-override-rot.py` (one shared `_import_tomllib()`
  helper), and `scripts/security/check-gitleaks-current-config.py` — the
  third site was found only after installing gitleaks surfaced it; the
  design doc's original two-file list missed it. `tomli` added to
  `src/python/pyproject.toml`'s `[dev]` extra, gated
  `python_version < '3.11'`.
- `dev/release/tests/pip_skew.sh`: the wheel-BUILD step deliberately keeps
  the OLD system pip (inherits `--system-site-packages` setuptools/wheel,
  offline); the final `--dry-run` RESOLVE step now uses a separately-selected
  modern interpreter's pip instead, since `--dry-run` never installs and
  needs no setuptools.
- New `scripts/tests/test_dev_environment_tools.sh`: one gate naming every
  pinned dev tool (shellcheck, gitleaks, actionlint, ruff, pyright, js-yaml)
  missing or at the wrong version.
- `AGENTS.md` documents the AArch64/Jetson prerequisite.

Independent code review (code-reviewer agent): `PASS_WITH_NOTES`, no critical
issues. Three nits resolved before commit: partial-venv cleanup covered the
"no interpreter found" case but not a failed `-m venv` itself (fixed, with a
new negative-test arm); `_import_tomllib` had narrowed from `ImportError` to
`ModuleNotFoundError` relative to the three call sites it replaced (broadened
back to match exactly); `pip_skew.sh`'s resolve step didn't verify the
selected interpreter has an importable `pip` module before use (fixed,
degrades to a clean skip rather than a misleading resolver-conflict failure).

**Verification.** `scripts/agent-test.sh --tier=fast` run three times on this
Jetson Orin AGX across the sub-slice (initial baseline, after the venv+tomli
fix, final after all pinned tooling installed). All three of 80.3's targeted
failures (`test-check-license-consistency`, `test-check-pinned-override-rot`,
`test-pip-skew`) are green. Final run: `registered=83 ran=83 passed=71
failed=12`. All twelve remaining failures are outside 80.3's scope and none
are attributable to a missing or too-old tool:

- **80.2's own targets (2):** `test-install-shellcheck`,
  `test-idempotent-republish` — both are x86_64-hardcoded test fixtures
  (§ 2.2 of the design doc), not yet fixed.
- **Explicitly out of scope per design doc § 2.3 (2):**
  `test-check-release-state-views` (network-transport failure in a shallow-
  clone probe), `test-shell-pipefail-guards` (cascades from the same arm).
- **Pre-existing branch content drift, unrelated to environment (8):**
  `test-public-doc-truth`, `test-slice70-embedding-docs-contract`,
  `test-runtime-release-alignment`, `test-release-workflow-scope`,
  `test-gitleaks-guards`, `test-linux-first-platform-scope`,
  `test-pypi-publish-roundtrip`, `test-actionlint-fixture`. These surfaced

  `test-actionlint-fixture`'s failure ("release.yml missing shipped napi

AC80-5 ("zero failures attributable to environment") is satisfied.

## 80.1 landed (glibc floor)

Landed at `52ac698f`, real-hardware verified on this Jetson Orin AGX.

- `build-napi`'s `linux-arm64-gnu` matrix row now builds inside a
  digest-pinned `manylinux_2_28_aarch64` container
  (`scripts/release/Dockerfile.napi-manylinux`, `scripts/release/
  napi-artifact-contract.sh`) instead of on the bare `ubuntu-24.04-arm`
  runner, mirroring the Python wheel build and the CUDA manylinux
  precedent (`Dockerfile.cuda-manylinux`, `cuda-artifact-contract.sh`).
  The other three `build-napi` rows (darwin-x64, darwin-arm64,
  win32-x64-msvc) are untouched — no glibc floor applies to them.
- New gates: `scripts/check-glibc-floor.sh` (AC80-1/AC80-2 — `objdump -T`,
  falling back to `readelf -V`, fails closed when neither tool is
  present) and `scripts/check-glibc-floor-doc-truth.sh` (AC80-9 —
  `docs/compatibility/index.md`'s stated floor must match
  `scripts/release/glibc-floor-contract.sh`'s `GLIBC_FLOOR` constant).
  Both TDD'd (RED confirmed before the checker existed) and registered
  in `agent-test.sh` fast tier.
- `scripts/release/smoke/smoke-npm-package.sh` and `smoke-pypi-wheel.sh`
  (AC80-3/R80-2) now run the floor gate against the artifact actually
  installed from the registry, gated to Linux hosts only (`.node`/`.so`
  also exist on macOS, which carries no glibc floor).
- Real-hardware proof, not just local unit tests: ran
  `scripts/release/provision-napi-manylinux.sh` on this host, which
  built the real Docker image and validated Node 25.9.0 / Rust 1.95.0
  inside it; then ran the actual containerized `napi build` against
  this repo's real `fathomdb-napi` crate (same invocation shape as the
  new release.yml step), producing a real `fathomdb.linux-arm64-gnu.node`
  binary owned by the host user (`--user $(id -u):$(id -g)`, not root).
  That real binary passed `check-glibc-floor.sh --floor 2.28` (exit 0).
- Independent code review (`code-reviewer` subagent) returned
  NEEDS_FIXES on first pass: a real, reproducible bug in
  `smoke-npm-package.sh` (`REPO_ROOT` resolved via a relative
  `BASH_SOURCE[0]` path *after* `cd`'ing into the scratch workdir, which
  would crash every real post-publish npm smoke run before it reached
  either the new glibc check or the pre-existing open/write/search/close
  assertions). Fixed and reproduced-fixed (traced with `bash -x` against
  a real invocation shape). Also addressed on review: the containerized
  build step now self-asserts Node/Rust versions and the pinned
  `RUSTUP_TOOLCHAIN` before building (matching `cuda-preflight.sh`'s
  verification style), and both smoke scripts fail closed (rather than
  silently skip) when no native binary is found on a Linux host.
- `scripts/agent-test.sh --tier=fast`: `registered=85 ran=85 passed=73
  failed=12` — identical 12-failure set to the pre-80.1 baseline (§
  "Verification" above), both new suites green, no regressions.
  `scripts/agent-lint-shell.sh` (shellcheck default ruleset + the
  repo's pipefail/masked-return legs) is clean for every file this
  sub-slice touches. `actionlint` on `release.yml` is clean.
